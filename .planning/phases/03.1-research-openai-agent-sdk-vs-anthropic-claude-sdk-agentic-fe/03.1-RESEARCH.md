# Phase 03.1: Research OpenAI Agent SDK vs Anthropic Claude SDK Agentic Features

**Researched:** 2026-06-12
**Domain:** LLM Agent Frameworks — OpenAI Agents SDK vs Anthropic Claude SDK agentic capabilities, with DeepSeek API compatibility verification
**Confidence:** HIGH

## Summary

This research compares the full agentic stack of OpenAI (Python SDK + Agents SDK) vs Anthropic (Claude SDK + Managed Agents + Claude Code), with every feature verified for DeepSeek API compatibility — the actual provider used by Rob Box (NOT OpenAI/Anthropic directly).

**Primary finding:** OpenAI Agents SDK (v0.17.5) is the correct and proven choice for Rob Box. It already powers `dialogue_node.py` via `OpenAIChatCompletionsModel` with DeepSeek's OpenAI-compatible API. The Anthropic ecosystem offers Managed Agents (a cloud-hosted orchestration service) and Claude Code (a CLI tool), neither of which is a drop-in library replacement. DeepSeek's Anthropic-compatible API has significant gaps (no MCP, no images, no code execution), making Anthropic SDK features largely unusable through DeepSeek.

**Primary recommendation:** Stay with OpenAI Agents SDK for agent orchestration. Upgrade `openai` from v1.101.0 (currently installed) to >=2.37.0 as planned in PR #837. Pin versions in all `requirements.txt` files. Anthropic SDK offers no advantages for Rob Box given DeepSeek API limitations.

## 2. OpenAI Agents SDK — Deep Dive

### 2.1 Agent Loop Architecture

The OpenAI Agents SDK loop is:
```
Runner.run(agent, input)
  → Agent generates response via Model
  → Model returns text OR tool_call OR handoff
  → If tool_call: Runner executes tool → feeds result back to Model → loop continues
  → If handoff: Runner switches to target Agent → loop continues
  → If text: Runner returns RunResult with final_output
  → Loop ends when: max_turns reached, agent produces final output, or error
```

**History management:**
- The SDK maintains `input_items` list internally
- `RunResult.to_input_list()` returns the full conversation for next turn
- Rob Box manages its own `_conversation` list and feeds truncated history via `previous_response_id`-less mode
- Session objects (SQLite, Redis, MongoDB) provide persistent memory across runs

**Error handling:**
- `MaxTurnsExceeded` — raised when agent exceeds `max_turns` (Rob Box catches this)
- `ToolTimeoutError` — per-tool timeouts with configurable behavior (`error_as_result` or `raise_exception`)
- `ModelBehaviorError` — invalid JSON from model
- Runner-managed retries with composable policies (network_error, http_status, provider_suggested)

**Parallel tool calls:**
- Controlled via `ModelSettings(parallel_tool_calls=False)` 
- Rob Box sets this to `False` because DeepSeek sometimes ignores it — enforced via `_output_lock` asyncio.Lock

**Interrupt/Barge-in:**
- No built-in barge-in support in the SDK
- Rob Box implements custom cancellation: `_run_task.cancel()` on new STT input, `_run_cancelled` flag, forced TTS event flush
- Anthropic's approach is similar — no built-in barge-in, application-level control

### 2.2 Tools & MCP Integration

**Function tools:**
```python
@function_tool
async def fetch_weather(location: Location) -> str:
    """Fetch the weather for a given location."""
    return "sunny"
```
- Automatic schema generation from type hints + docstrings (griffe)
- Pydantic Field for constraints
- Per-tool timeouts
- Custom error handlers (`failure_error_function`)
- Tool output images/files support

**MCP integration:**
```python
from agents.mcp import MCPServerStreamableHttp, MCPServerSse

async with MCPServerSse(
    name="my_mcp_server",
    params={"url": "http://localhost:8000/sse"},
) as server:
    agent = Agent(
        name="Assistant",
        tools=[server],
    )
```
- Streamable HTTP and SSE transports
- `MCPToolManager` for multi-server setups
- Rob Box uses custom `LLMToolCallAdapter` instead (ROS 2 services, not stdio MCP)

**Hosted tools** (OpenAI-only, NOT DeepSeek compatible):
- WebSearchTool, FileSearchTool, CodeInterpreterTool, HostedMCPTool, ImageGenerationTool, ToolSearchTool
- These call OpenAI's hosted infrastructure — completely unavailable via DeepSeek

[CITED: openai.github.io/openai-agents-python/tools/, openai.github.io/openai-agents-python/mcp/]

### 2.3 Sandbox Agents

OpenAI's Sandbox Agents provide:
- Isolated filesystem workspace
- Shell execution
- Memory/caching
- Skills (reusable capability bundles)
- Compaction (context window management)
- Snapshot/restore
- Docker sandbox backend (in addition to hosted)
- Manifest-defined file entries

**DeepSeek compatibility:** NOT COMPATIBLE. Sandbox agents require the OpenAI Responses API and OpenAI-hosted infrastructure. The Docker sandbox (local) could theoretically work with any model, but the sandbox agent orchestration still depends on OpenAI's API for agent loop management.

**Rob Box applicability:** LOW. Rob Box runs on Raspberry Pi 5 with limited resources. Sandbox isolation adds overhead with no clear benefit. The Codex tool (workspace-scoped shell+edits) is more relevant but also experimental.

### 2.4 Voice Pipeline & Realtime Agents

**Realtime Agents** (gpt-realtime-2):
- WebSocket-based voice agents
- Automatic interruption detection
- Guardrails integration
- Context management
- **DeepSeek compatibility:** NOT COMPATIBLE — requires OpenAI's realtime models

**Voice Pipeline** (STT → Agent → TTS):
```python
from agents.voice import VoicePipeline, VoicePipelineConfig
from agents.voice.models import OpenAIProvider

pipeline = VoicePipeline(
    config=VoicePipelineConfig(
        stt_model=OpenAIProvider(...),
        tts_model=OpenAIProvider(...),
    )
)
```
- Designed as a modular pipeline
- STT and TTS can be swapped
- The agent in the middle uses the standard Agent/Runner
- **DeepSeek compatibility:** PARTIAL — the Agent portion works with DeepSeek, but STT/TTS default implementations use OpenAI models. Rob Box already has custom STT (Vosk) and TTS (Silero/Yandex) nodes.

**Rob Box applicability:** The VoicePipeline abstraction is useful for reference architecture but Rob Box already has a working custom pipeline (STT node → dialogue_node → TTS node). Adopting the VoicePipeline would require rewriting working infrastructure.

[CITED: openai.github.io/openai-agents-python/realtime/, openai.github.io/openai-agents-python/voice/]

### 2.5 Guardrails & Human-in-the-Loop

**Guardrails:**
- Input guardrails: validate before agent runs
- Output guardrails: validate agent response
- Tool guardrails: validate tool arguments
- Run in parallel with agent execution
- **DeepSeek compatibility:** YES — guardrails run locally in your code, not on OpenAI servers

**Human-in-the-Loop:**
- Approval gates on tools: `@function_tool(needs_approval=True)`
- `result.interruptions` contains pending approvals
- `result.to_state()` / `state.approve()` / `state.reject()` for pause/resume
- **DeepSeek compatibility:** YES — this is SDK-level logic, model-agnostic

[CITED: openai.github.io/openai-agents-python/guardrails/, openai.github.io/openai-agents-python/human_in_the_loop/]

## 3. Anthropic Claude SDK — Deep Dive

### 3.1 Messages API & Tool Use

The core of Anthropic's agentic offering is the Messages API with `tool_use`:

```python
import anthropic

client = anthropic.Anthropic()
response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    tools=[{
        "name": "get_weather",
        "description": "Get the current weather for a city",
        "input_schema": {
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"],
        },
    }],
    messages=[{"role": "user", "content": "What's the weather in Paris?"}],
)
```

**Agent loop (manual):**
```
User sends message → Claude returns text OR tool_use (stop_reason: "tool_use")
→ Application executes tool → Application sends tool_result
→ Claude returns text OR another tool_use → loop continues
→ Loop ends when stop_reason: "end_turn"
```

Unlike OpenAI Agents SDK, Anthropic does NOT provide a built-in agent runner. The application must:
1. Manage the conversation history (messages list)
2. Detect `stop_reason == "tool_use"` 
3. Execute tools
4. Format `tool_result` messages
5. Loop until `stop_reason == "end_turn"`

**Streaming:** Supported via `client.messages.stream()`, with `text`, `input_json`, `content_block_start/stop`, `message_start/delta/stop` events.

**Prompt caching:** Anthropic supports caching system prompts and tool definitions for reduced latency/cost. DeepSeek Anthropic API: `cache_control` is **ignored**.

**Parallel tool calls:** Claude can emit multiple `tool_use` blocks in one response. DeepSeek Anthropic API: `disable_parallel_tool_use` is **ignored**.

[CITED: platform.claude.com/docs/en/agents-and-tools, GitHub anthropics/anthropic-sdk-python examples]

### 3.2 Managed Agents (NEW in v0.109.0)

Anthropic Managed Agents is a **cloud-hosted orchestration service**, not a local Python library. Key concepts:

- **Environments:** isolated execution contexts
- **Agents:** versioned configurations (model, system prompt, tools, skills, MCP servers)
- **Vaults:** secret storage for MCP credentials
- **Sessions:** stateful conversation with an agent version
- **Toolsets:** built-in (`agent_toolset_20260401`), MCP (`mcp_toolset`), custom
- **Skills:** reusable capability bundles (Anthropic-provided like `xlsx`, or custom)
- **Sandbox workers:** self-hosted or Anthropic-hosted code execution
- **Deployments:** managed rollout of agent versions
- **Outcomes:** evaluation results

Example from SDK:
```python
# Create environment
environment = anthropic.beta.environments.create(name="my-env")

# Create agent with tools
agent = anthropic.beta.agents.create(
    name="my-agent",
    model="claude-sonnet-4-6",
    system="You are a helpful assistant.",
    tools=[
        {"type": "agent_toolset_20260401"},
        {"type": "custom", "name": "get_weather", ...},
    ],
    mcp_servers=[{"type": "url", "name": "github", "url": "..."}],
)

# Create session
session = anthropic.beta.sessions.create(
    environment_id=environment.id,
    agent={"type": "agent", "id": agent.id, "version": agent.version},
)

# Stream events
with anthropic.beta.sessions.events.stream(session.id) as stream:
    for event in stream:
        if event.type == "agent.custom_tool_use":
            # Handle custom tool
            anthropic.beta.sessions.events.send(
                session.id,
                events=[{"type": "user.custom_tool_result", ...}],
            )
```

**DeepSeek compatibility:** NOT COMPATIBLE. Managed Agents require:
1. Anthropic's cloud infrastructure (environments, vaults, sessions are server-side)
2. Anthropic models (Claude Sonnet/Opus)
3. Anthropic API authentication

Even if you point `base_url` to DeepSeek, the `anthropic.beta.agents`, `anthropic.beta.environments`, `anthropic.beta.vaults`, and `anthropic.beta.sessions` APIs do not exist on DeepSeek's servers.

**Rob Box applicability:** NONE. This is a cloud service for deploying production AI agents. Rob Box is an autonomous robot running on-premises Raspberry Pi 5.

[CITED: GitHub anthropics/anthropic-sdk-python examples/agents_comprehensive.py, release notes v0.109.0]

### 3.3 Claude Code

Claude Code is an **agentic CLI coding tool** (132k GitHub stars), written primarily in Python (79.7%) with some Shell and TypeScript. It:
- Lives in the terminal
- Understands your codebase
- Executes routine tasks, explains code, handles git workflows
- Supports plugins and custom commands
- Uses the Anthropic API (Messages + tool_use) for its agent loop

**Architecture patterns worth adopting:**
1. **Subagent model:** Claude Code spawns subagents for parallel independent tasks (similar to `gsd-dispatching-parallel-agents`)
2. **Tool-based architecture:** Everything is a tool — file reads, writes, git operations, shell commands
3. **Permission system:** `allow/deny/ask` for tool execution
4. **Context management:** Automatic codebase mapping, relevant file discovery
5. **Streaming feedback:** Real-time streaming of agent thoughts and actions

**DeepSeek compatibility:** YES — DeepSeek officially supports Claude Code with DeepSeek API:
```bash
export ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic
export ANTHROPIC_AUTH_TOKEN=<deepseek-api-key>
export ANTHROPIC_MODEL=deepseek-v4-pro
```
[VERIFIED: api-docs.deepseek.com/quick_start/agent_integrations/claude_code]

**Rob Box applicability:** INDIRECT. Claude Code is a development tool, not a library. Its architectural patterns (subagents, tool-based design, permission system, streaming feedback) can inspire Rob Box's agent architecture, but Claude Code itself cannot be embedded in the robot.

[CITED: github.com/anthropics/claude-code, api-docs.deepseek.com]

## 6. Thematic Comparison

### 6.1 Agent Loops (D-07, D-12)

| Aspect | OpenAI Agents SDK | Anthropic (Messages API) | Winner for Rob Box |
|--------|-------------------|--------------------------|-------------------|
| **Loop management** | Built-in Runner handles turns, tool dispatch, handoffs | Manual: app must detect stop_reason, execute tools, loop | **OpenAI** — less code |
| **History management** | `to_input_list()`, Session objects, auto-truncation | Manual: app manages messages list | **OpenAI** — session backends |
| **Error handling** | MaxTurnsExceeded, ToolTimeoutError, retry policies | App-level try/except | **OpenAI** — structured errors |
| **Interrupt/Barge-in** | No built-in; `asyncio.Task.cancel()` in Rob Box | No built-in; app-level | **Tie** — both need custom |
| **Parallel tools** | `ModelSettings(parallel_tool_calls=False)` | `disable_parallel_tool_use` (ignored by DeepSeek) | **OpenAI** — explicit control |
| **Streaming** | `Runner.run_streamed()` with events | `client.messages.stream()` with events | **Tie** — both good |
| **Turn limits** | `max_turns` on Runner | App-level counter | **OpenAI** — built-in |

**Architecture diagram — OpenAI Agents SDK loop (as used in Rob Box):**
```
User speech → STT Node → /voice/stt/result (ROS 2 topic)
                              ↓
                       dialogue_node._on_stt()
                              ↓
                       asyncio.run_coroutine_threadsafe(
                           _process_speech(text), loop
                       )
                              ↓
                       _build_agent() → Agent with:
                         - system prompt
                         - function_tool decorators
                         - MCP adapter tools
                         - OpenAIChatCompletionsModel
                              ↓
                       Runner.run(agent, text, max_turns=N)
                              ↓
                       ┌─── Agent Loop (SDK-managed) ───┐
                       │ Model returns text/tool/handoff │
                       │ → If tool: SDK executes tool    │
                       │ → Tool result → Model           │
                       │ → Repeat until done             │
                       └─────────────────────────────────┘
                              ↓
                       result.final_output → speak_text tool
                              ↓
                       /voice/dialogue/response (ROS 2 topic)
                              ↓
                       TTS Node → Speaker output
```

**Architecture diagram — Anthropic approach (hypothetical for Rob Box):**
```
User speech → STT Node → /voice/stt/result
                              ↓
                       dialogue_node._on_stt()
                              ↓
                       Build messages: [system, ...history, user]
                              ↓
                       ┌─── Manual Loop ───────────────┐
                       │ client.messages.create(...)    │
                       │ → If stop_reason="tool_use":  │
                       │   execute tool locally         │
                       │   append tool_result to msgs   │
                       │   loop again                   │
                       │ → If stop_reason="end_turn":   │
                       │   break                        │
                       └────────────────────────────────┘
                              ↓
                       Extract text → speak_text
                              ↓
                       /voice/dialogue/response
```

**Conclusion:** OpenAI Agents SDK's built-in Runner eliminates ~100 lines of manual loop management. The Anthropic approach requires reimplementing what the SDK already provides.

### 6.2 Voice + Realtime (D-05)

**OpenAI Realtime Agents:** Only work with OpenAI's `gpt-realtime-2` model via WebSocket. DeepSeek has no equivalent. → NOT APPLICABLE.

**OpenAI Voice Pipeline:** Modular STT→Agent→TTS design. The Agent portion works with DeepSeek, but default STT/TTS use OpenAI models. Rob Box already has a working custom pipeline. → REFERENCE ONLY.

**Anthropic:** No voice/realtime API. → NOT APPLICABLE.

**Recommendation:** Rob Box's current architecture (Vosk STT → dialogue_node Agent → Silero/Yandex TTS) with custom barge-in via VAD + asyncio cancellation is the right approach. Neither SDK offers a better alternative compatible with DeepSeek.

### 6.3 Multi-Agent Orchestration

**OpenAI Agents SDK:**
- **Handoffs:** `agent1.handoff(agent2)` — transfers conversation to another agent
- **Agents as tools:** `agent.as_tool()` — orchestrator calls sub-agents as tools
- **Conditional tools:** `is_enabled` callback for dynamic tool availability
- **Structured input:** Pydantic models for typed agent-to-agent communication

**Anthropic:**
- **Managed Agents:** Cloud-hosted multi-agent orchestration with environments, deployments, outcomes — NOT usable via DeepSeek
- **Manual orchestration:** App-level agent dispatch using Messages API

**Rob Box recommendation:** If multi-agent is needed (e.g., separate agents for music, navigation, conversation), use OpenAI Agents SDK handoffs or agents-as-tools. Both patterns already work with DeepSeek.

### 6.4 Sandbox + Workspace (D-06)

**OpenAI Sandbox Agents:** Docker-based local sandbox with filesystem, shell, memory, skills. Theoretically model-agnostic for local Docker sandbox, but the agent orchestration layer uses OpenAI Responses API.

**Anthropic Self-Hosted Sandbox Workers:** Part of Managed Agents. Workers execute code in isolated environments. Cloud-orchestrated — NOT usable via DeepSeek.

**Claude Code workspace model:** Runs directly in the project directory with filesystem access, git integration, shell commands. This is the most practical pattern for Rob Box.

**Rob Box recommendation:** Sandbox isolation is not needed for Rob Box. The robot already runs in Docker containers with limited filesystem access. Claude Code's "work directly in the project" pattern is more relevant. If isolated code execution is needed, use a simple subprocess with timeout — don't adopt full sandbox infrastructure.

## 10. Common Pitfalls

### Pitfall 1: DeepSeek Ignores `parallel_tool_calls=False`
**What goes wrong:** DeepSeek occasionally emits multiple tool calls in one response even when `parallel_tool_calls=False` is set. This causes race conditions in output (speak_text, play_sound).
**Why it happens:** DeepSeek doesn't fully respect this OpenAI parameter.
**How to avoid:** Rob Box already handles this with `_output_lock = asyncio.Lock()` in dialogue_node.py — each output tool acquires the lock before executing.
**Warning signs:** Multiple TTS utterances playing simultaneously, sound effects overlapping speech.

### Pitfall 2: v1.x → v2.x `openai` Migration Breaking Changes
**What goes wrong:** Code written for `openai` v1.x fails with v2.x because the client API changed significantly.
**Why it happens:** `openai` v2.0.0 was a major rewrite (Stainless SDK). Client initialization, response types, and error handling all changed.
**How to avoid:** Test thoroughly after upgrading. Check imports: `from openai import AsyncOpenAI` (v2) vs `import openai` (v1).
**Warning signs:** `AttributeError`, `ImportError`, type mismatches on response objects.

### Pitfall 3: Tracing Fails Without OpenAI API Key
**What goes wrong:** `openai-agents` tries to upload traces to OpenAI by default, gets 401 errors.
**Why it happens:** Tracing uses OpenAI's dashboard, requires `OPENAI_API_KEY`.
**How to avoid:** `set_tracing_disabled(True)` — already done in Rob Box setup.
**Warning signs:** 401 errors in logs about tracing.

### Pitfall 4: Responses API Default
**What goes wrong:** `openai-agents` defaults to OpenAI Responses API, which DeepSeek doesn't support. Returns 404.
**Why it happens:** The SDK uses Responses API by default for OpenAI models.
**How to avoid:** Use `OpenAIChatCompletionsModel` explicitly (already done) or `set_default_openai_api("chat_completions")`.
**Warning signs:** 404 errors, "not found" on API calls.

### Pitfall 5: `deepseek-chat` / `deepseek-reasoner` Deprecation
**What goes wrong:** After 2026-07-24, these model names stop working.
**Why it happens:** DeepSeek is standardizing on `deepseek-v4-flash` and `deepseek-v4-pro`.
**How to avoid:** Rob Box already uses v4 model names. Verify no hardcoded `deepseek-chat` or `deepseek-reasoner` strings remain.
**Warning signs:** API errors about unknown model after July 24, 2026.

# Source: Derived from anthropic-sdk-python examples/tools.py
import anthropic

client = anthropic.Anthropic(
    base_url="https://api.deepseek.com/anthropic",

        model="deepseek-v4-pro",
        max_tokens=500,
        system=system_prompt,
        tools=tools,
        messages=messages,
    )
    
    if response.stop_reason == "end_turn":
        final_text = response.content[0].text
        break
    
    if response.stop_reason == "tool_use":
        for block in response.content:

                # Execute tool
                result = execute_tool(block.name, block.input)
                # Append to messages
                messages.append({
                    "role": "assistant",
                    "content": [block],
                })
                messages.append({
                    "role": "user",
                    "content": [{
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": result,
                    }],
                })
