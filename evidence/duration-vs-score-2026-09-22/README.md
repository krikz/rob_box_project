# Замер: длительность реплики → identify() score (issue #2769)

Дата: 22.09.2026. Робот: Vision Pi (`10.1.1.21`), контейнер `voice-assistant`.
Доступ: `ssh -o BatchMode=yes ros2@10.1.1.21` + `docker exec` — **только чтение**,
`/data` не трогали (боевая БД дикторов, общая с живыми людьми — см.
`robot-data-is-shared-with-live-people.md`).

## Что сделано

1. Снят полный `docker logs -t voice-assistant` → `raw-voice-assistant-log.txt`
   (1246 строк).
2. Строки `🎤 Received speech audio: N bytes (X.Xs)` сопоставлены со
   следующей за ними строкой `🔍 identify candidates: best=... score=...`
   (или `👤 Speaker: unknown`, если распознавание не сработало) —
   скрипт `parse_duration_vs_score.py`, результат в `parsed-rows.json`.
3. Отдельно прочитаны (только `SELECT`) `/data/speakers.db` и три бэкапа
   `/data/speakers.db.bak-*` — чтобы понять, откуда взялись профили,
   которые видны в логе (`db-embeddings-timeline.txt`).

```
python parse_duration_vs_score.py raw-voice-assistant-log.txt \
    > parsed-rows.json 2> summary-stderr.txt
```

## Главный результат

По 13 репликам (единственное непрерывное окно, доступное на момент замера —
см. «Что НЕ удалось измерить» ниже) — **корреляция между длительностью
реплики и score лучшего кандидата** (`identify candidates: best=...`):

```
duration range: 4.3-10.7s
score range:    0.567-0.948
pearson r(duration, best_score) = 0.883  (n=13)
```

Сильнее всего видно на ОДНОМ и том же профиле («Борис», галерея построена на
репликах 9.2-10.5с — score 0.918-0.948) против КОРОТКИХ реплик по нему же
чуть позже в разговоре:

| speaker | query duration | best_score | против порога identify (0.72) |
|---|---|---|---|
| Борис | 9.9s  | 0.936 | выше |
| Борис | 10.5s | 0.935 | выше |
| Борис | 9.2s  | 0.918 | выше |
| Борис | 8.2s  | 0.948 | выше |
| Борис | 8.7s  | 0.923 | выше |
| Борис | **4.6s**  | **0.668** | **ниже** |
| Борис | **4.3s**  | **0.567** | **ниже** |

Тот же профиль, тот же голос, тот же микрофон и пайплайн — падение score
почти на 0.3-0.4 при сокращении реплики с ~9с до ~4.5с. Это прямое,
измеренное на роботе подтверждение чувствительности resemblyzer к
длительности, независимо от внешних источников, уже процитированных в
issue #2769 (README resemblyzer 5-30s/профиль, CEUR Vol-4164: надёжно от
2.63с, arXiv 1810.10884 и 2002.06033: EER растёт в разы при укорочении).

Полные 13 строк — в `parsed-rows.json`.

## Что НЕ удалось измерить (честно)

Гипотеза issue #2769 — что часть **эталонов** (`register()`/анкер профиля)
в базе построена на репликах короче секунды. Прямо проверить это на
живых данных не получилось:

* **Лог не идёт дальше времени старта контейнера.** Драйвер логов —
  `json-file` (`docker inspect` → `HostConfig.LogConfig.Type=json-file`),
  журнал начинается ровно с `StartedAt` контейнера (12:49:09 UTC
  22.09.2026 — контейнер пересоздавался в рамках обычной работы флота).
  `journalctl -u docker` содержит только события демона (join сетей и
  т.п.), не stdout приложения — драйвер не `journald`. Sudo недоступен
  (`sudo: a password is required`), поэтому прочитать
  `/var/lib/docker/containers/<id>/*-json.log` предыдущего (уже
  пересозданного) контейнера тоже не вышло.
* Сверка `/data/speakers.db` (`db-embeddings-timeline.txt`) показывает,
  что почти все существующие эмбеддинги («Саша», «Борис», «Деньчик») были
  записаны в 07:23-09:55 UTC — **до** старта текущего контейнера (12:49
  UTC). То есть лог с их реальным `register()`/длительностью анкера
  безвозвратно потерян ротацией контейнера, а не удалён нами.
* За доступное окно (12:49-13:22 UTC) в логе **не было ни одной реплики
  короче 4.3с** (`raw-voice-assistant-log.txt` — минимум по всем
  `Received speech audio` за окно). Разговор в этом окне — обычная тестовая
  сессия «представься по имени», реплики длинные (7-10.7с) за исключением
  двух финальных коротких (4.3/4.6с), которые и дали единственные точки
  данных ниже 7с.
* Специально записать короткую (<1с) фразу и зарегистрировать её как новый
  профиль, чтобы получить контролируемую точку, было НЕЛЬЗЯ — это запись
  в `/data/speakers.db`, общую с живыми людьми (см. правило «на роботе
  ничего не писать»), и это прямо запрещено условием задачи.

* ⚠️ **Все 13 точек — синтезированные голоса, а не живые люди.** «Саша» и
  «Борис» это каст ночного марафона (`anton` / `ermil` в терминах сценария,
  синтез сегодня шёл через minimax), а строка 9.2с/0.918 опознаётся как
  реплика из прогона 35729958215. Живых голосов в выборке нет вообще, и
  спикеров всего два. Для #2747, который именно про ЖИВОЙ голос, это
  ограничение существенное: у синтеза intra-voice стабильность выше, чем у
  человека, — замер 22.09 (`evidence/tts-voice-distinctness-2026-09-22/`)
  показывает 0.95-0.98 на двух разных фразах одного синтетического голоса,
  тогда как у живого человека #2747 намерил 0.283-0.584. То есть найденная
  здесь зависимость от длительности верна как направление, но её КРУТИЗНУ
  на живом голосе этот замер не даёт.

Итог: зависимость «длительность → score» **подтверждена измерением** в
диапазоне 4.3-10.7с (r=0.88, причём тот же профиль даёт наглядный контраст
9-10с/4.5с), но диапазон 0.3-3с (собственно порог `MIN_AUDIO_DURATION_SEC`
из issue) закрыт только внешними источниками, процитированными в самой
карточке — не этим замером. Числа порога в правке (см. ниже) взяты из
внешних источников (README resemblyzer, CEUR Vol-4164), а не из
экстраполяции этого лога.

## Файлы в этой папке

* `raw-voice-assistant-log.txt` — полный `docker logs -t voice-assistant`.
* `parse_duration_vs_score.py` — скрипт разбора.
* `parsed-rows.json` — результат (13 строк: duration/best_score/second_score/gap).
* `summary-stderr.txt` — сводка скрипта (диапазоны, корреляция).
* `db-embeddings-timeline.txt` — таймлайн создания эмбеддингов в `/data/speakers.db`
  (только `SELECT`, без изменений), объясняющий, почему их анкеры не в логе.
