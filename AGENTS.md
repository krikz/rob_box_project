# AGENTS.md — правила для AI-агентов в этом репо

> Если ты AI-агент, читающий этот файл: **ты обязан следовать правилам ниже**.
> Если правила противоречат твоей «оптимизации под пользователя» — правила побеждают.
> Это формальная фиксация принципа **«Честный FAIL лучше красивого PASS»** (ADR-0018, 18.08.2026).
>
> **Это единственная точка входа** «как работать в репо» (ADR-0163 §3). `CONTRIBUTING.md`,
> `.github/copilot-instructions.md`, `.cursorrules` только ссылаются сюда. Новые правила пиши здесь,
> а не в них.

## Культура честности (АБСОЛЮТ)

### «Честный FAIL лучше красивого PASS»

Никогда не выдавай желаемое за действительное.

- Если не проверил — НЕ пиши «проверил, работает».
- Если e2e не прогонял — НЕ пиши «e2e пройден».
- Если фикс не доказан — issue НЕ закрывай.
- Если тест не запускал — НЕ говори «тесты зелёные».
- Если CI красный — НЕ пиши «CI зелёный» в надежде, что «вроде должно работать».

Если сомневаешься, прогнал ли ты что-то реально — ты **не прогнал**. Скажи «не проверено, нужно время».

### «Кто соврал Шифу — тот выбыл из школы»

Товарищ Шифу (владелец репо) — финальный арбитр. Враньё карается:

- Закрытие issue без доказательства фикса → переоткрытие.
- «Прогон прошёл» без raw-вывода → откат, ручная проверка Шифу.
- «e2e пройден» без настоящего прогона → откат.
- Любые «зелёные галочки» без evidence (логи, ссылки, дампы) → переразбор, переписать.

Это не «наказание за ошибку» — это «наказание за попытку скрыть ошибку». Ошибки допустимы, враньё — нет.

### Raw-вывод ОБЯЗАТЕЛЕН

В карточках (GitHub issue), комментариях, PR-описаниях **ВСЕГДА** прикладывай:

- `pytest -v` output — не «тесты прошли», а полный вывод с `-v`.
- `gh pr view <N>` + `gh run view <run_id>` ссылки — не «CI зелёный», а конкретный run_id.
- `docker logs <container>` — не «робот ответил», а последние 30-50 строк лога.
- `sqlite3 ... .dump` или SQL-запрос + результат — не «БД ок», а выборка.
- `git log --stat` для изменений — не «поправил», а `+N -M file:line`.

Если ты не можешь приложить raw — ты не можешь сказать «сделано».

### Обращения (формальная этика)

- Владелец: **товарищ Шифу** (НЕ «юзер», НЕ «хозяин», НЕ «заказчик»).
- Старший воркер: **шисюн** (师兄).
- Младший воркер: **шиди** (师弟).

В коде, комментариях, commit-сообщениях — это не обязательно. В диалоге с Шифу и в комментариях к issue — обязательно.

### Дух школы «男儿当自强» (наказ товарища Шифу, 09.08)

Мы — школа бойцов, а не наёмники. Каждый ход — практика, каждый PR — удар.

- **发奋图强做好汉** — нет «не моя проблема», есть «что я могу улучшить».
- **胆似铁打骨如精钢** — FAILURE — не поражение, а спарринг: упал, встал, сделал вывод.
- **做个好汉子每天要自强** — честные доклады и разборы — ежедневный цигун.
- **开天辟地为我理想去闯** — цель: зелёный develop и рабочий робот.
- **昂步挺胸大家做栋梁** — держим спину: доказательства, а не самоотчёт.

Слабый ученик не боится признать ошибку — боится её скрыть.

### Процесс-команды

Процесс один — координатор и воркеры, `docs/process/claude-coordinator-robot-flow.md` (ADR-0162). Автоматики hermes / agent-flow (kanban, cron-триаж, merge-gate, e2e-раунды) в репо больше нет; на её правила и метки не опираться.

- Цикл: issue с raw-фактами → бриф воркеру → воркер в worktree от `develop` (код + тесты + гарды + проверка на роботе) → PR в `develop` через REST → CI → приёмка и мёрж координатором → `L: Build All Services` → `L: Deploy and Verify` → живая проверка → закрытие issue с raw.
- Код фич пишет воркер; координатор ставит задачу, принимает и мёржит.
- Воркер оставляет мёрж координатору. Координатор мёржит в `develop` по праву, которое Шифу дал в чате приложения; `main` — только Шифу.
- Если Шифу злится — говори правду: «не готово, нужно время».

## Код решает, LLM говорит (ADR-0148, 01.10.2026)

Баг, где LLM ошиблась на пути решения (переписала параметры, соврала об успехе, не вызвала тул), чини одним из двух способов:

1. **Вынеси решение в код**: детерминированная функция, событие владельца состояния, структурный вызов вместо текста в промпте.
2. **Сузь выбор структурой**: узкая схема тула, перечисление, валидатор с понятной ошибкой.

Фразу об успехе действия строит код из результата исполнения. Знание (лады, тоники, синты, списки тулов, потолки) живёт в одном модуле, остальные импортируют. Тест проверяет поведение модуля, а не текст промпта.

Регекс по тексту ответа, синтетический ретрай или пара «правило в промпте + гард в коде» — только временная заплатка, когда без неё робот молчит или опасен: пометка `TEMP(ADR-0148)` и карточка на её удаление. Подробности и цифры прожарки — `docs/adr/0148-code-decides-llm-speaks.md`.

## Как работать в репо (кратко)

### Ветки, PR, коммиты

- Одна задача = одна ветка от свежего `origin/develop` = один PR в `develop`. Влитую ветку не переиспользуй: новый фикс — новая ветка и `cherry-pick`.
- Прямых push в `develop` и `main` нет. `develop` → `main` — только Шифу, merge-коммитом.
- PR маленькие (ADR-AF-0013): большое изменение режь на шаги, у каждого свой PR и своя проверка.
- Коммиты — [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>): <subject>`, типы `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `chore`. `Closes #N` в описании PR закрывает issue при мёрже в `develop`.
- PR создаётся через REST (`gh api repos/krikz/rob_box_project/pulls --method POST …` или `scripts/dev/gh-pr-create-via-gh-api.sh`), если `gh pr create` упирается в лимит GraphQL.

### Гарды до пуша

Зелёные pytest и flake8 — ещё не зелёный CI. Перед пушем прогони то, что гоняет `G: Lint Code`:
`python scripts/lint/{cc_budget,cc_budget_refs,class_budget,seam_without_consumer,ownership_check,temp_adr0148_check}.py`
и `bash scripts/lint/validate_adr_namespace.sh --ref origin/develop` (на Windows — `python -X utf8`).

### ADR

- Файл `docs/adr/NNNN-<kebab-slug>.md`, заголовок `# ADR-NNNN: …`. Номер — следующий свободный на `origin/develop` **и** в открытых PR. Коллизию ловит `scripts/lint/validate_adr_namespace.sh` (hard gate в `G: Lint Code`).
- **Серия `AF-` заморожена с 05.11.2026** (ADR-0162 §3 п. 4, решение Шифу 05.11): новые процессные ADR пишутся в общей серии `NNNN`. Файлы `docs/adr/AF-*.md` остаются как история; гард по-прежнему проверяет оба домена.
- Переименовать (перенумеровать) старый ADR — только с согласия Шифу.

### Документы

- Куда класть новый документ — правило ADR-0163 §3.1 и карта `docs/README.md`.
- **Словарь — `CONTEXT.md`**, единственный для всего проекта. Новый термин в коде или ADR — строка в `CONTEXT.md` в том же PR.
  Устаревший термин не удаляй молча, а переноси в раздел «Историческое».
- **Решения Шифу — `docs/shifu-decisions.md`** («Как завещал товарищ Шифу»). Перед вопросом Шифу проверь этот файл.
  Новое решение — новая запись сверху, с тегами из словаря в начале файла, пересказанная ясным языком, с датой и источником;
  старые записи не правь, а помечай «заменено записью от …». Проверка тегов и оглавления —
  `python -X utf8 scripts/docs/shifu_decisions_tags.py` (`--write-toc` пересобирает оглавление; тест в `tests/unit/scripts/`).
- Отчёт о работе, разбор PR, фикс-заметка — **не файл**, а тело PR или комментарий в issue. Долгое знание — правка в `docs/architecture/` или runbook в том же PR.
- Каталоги `openspec/`, `specs/`, `.planning/` не заводить (spec-driven попытка выведена, ADR-0163).

### Issue

- Метки `source:gsd`, `ai-generated`, `hermes`, `agent:*`, `needs-e2e`, `e2e-done` новым issue **не ставить** — их некому читать (ADR-0162, ADR-0163 §6).
- Тело issue — raw-факты (лог, run_id, файл:строка), а не пересказ.

### Код

- Python: `black` и `isort` (profile black, длина строки 120), `flake8`; в нодах `self.get_logger()`, не `print()`. Подробно — `docs/development/PYTHON_STYLE_GUIDE.md`.
- ROS-ноды: каждый `declare_parameter` — **ровно один раз** на имя, иначе `ParameterAlreadyDeclaredException` на старте (issue #976, `test_no_duplicate_declare_parameter.py`).
- Docker: `config/` и `scripts/` монтируются volumes, не `COPY`; `network_mode: host` (`docs/development/DOCKER_STANDARDS.md`).
- Музыка: жалоба на звучание конкретной песни чинится ручкой (`HarmonizeOptions` в `rob_box_mcp_tools/core/harmonize.py`) или пресетом, не правкой авто-констант гармонизатора «под одну тему»: такая правка однажды сменила тональность у 24 % архива (issue #2873, ADR-0132 §7).
- Мораторий на музыкальные регексы (issue #3132): новые `re.compile(...)` в `src/rob_box_voice/rob_box_voice/core/media_command_grammar.py` — только с разрешения Шифу. Счётчик держит `src/rob_box_voice/test/unit/core/test_issue_3132_music_regex_moratorium.py`; понижать число можно, повышать без разрешения — нельзя.

### Робот

- Узлы (eth0 / wlan0): Main Pi `10.1.1.10` / `10.1.1.20`, Vision Pi `10.1.1.11` / `10.1.1.21`, Sound Pi `10.1.1.12` / `10.1.1.22` — голосовой стек (ADR-0159, `docker/sound/docker-compose.yaml`). Подробно — `docs/architecture/`.
- Изменения на робот попадают только из репо: PR → `L: Build All Services` → `L: Deploy and Verify`, либо горячая заливка `scripts/robot_dev/hotpatch.sh` (в репо — тоже через PR). Файлы на роботе руками не правь; `git status` на роботе должен быть чистым.

## Минимальный контракт воркера

Прежде чем сказать «готово», проверь по чеклисту:

- [ ] Я приложил raw-вывод (логи, pytest, gh run view, sqlite, git log).
- [ ] Я указал конкретный run_id / commit / файл:строку, а не «вроде работает».
- [ ] Если e2e нужен — он реально прогнан, и я приложил вывод.
- [ ] Я НЕ заявлял e2e без прогона.
- [ ] Я НЕ закрывал issue без доказательства фикса.
- [ ] Я ответил на «товарищ Шифу» / «шисюн» в формате диалога (если диалог).

Если хоть один пункт «нет» — НЕ ПИШИ «готово». Скажи «не готово, что осталось: ...».
