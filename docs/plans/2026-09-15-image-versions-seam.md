# План: «Версии образов: git как канал доставки» — ревью кандидата против ADR-0094

**Дата:** 2026-09-15
**Статус кандидата:** Speculative
**Автор:** architect-review (эта сессия)
**Связанные документы:** ADR-0094 (`docs/adr/0094-image-versions-push-as-part-of-build.md`, принят 2026-09-14), ADR-0111 (`docs/adr/0111-voice-resources-image-sourcing.md`), ADR-0018 (честность), `docs/plans/2026-09-15-service-manifest.md` (параллельная задача — манифест сервисов; здесь не дублируется, см. §8)

---

## TL;DR

**Вердикт: НЕ переоткрывать ADR-0094.** Механизм «SHA-тег в файле под git» не дублирует знание реестра — он хранит знание, которого в реестре нет и не может быть (историческую привязку «ветка/дата → набор образов»). Все зафиксированные инциденты (#1139, #1244, #1482, #1388, t_dd49849b) — это баги *реализации* push-скрипта, и все они уже почищены точечными патчами, а не архитектурной переделкой. Два независимых прошлых захода на «убрать git из этого пути» (ADR-0031 вариант A — отдельный workflow; ADR-0031 вариант B / issue #1139 — per-service ветки) провалились или были отменены по итогам эксплуатации, оба зафиксированы в самом ADR-0094 §1.3, §2. Ниже — точечные улучшения вместо переоткрытия.

## 1. Факты (измеримые свидетельства)

### 1.1 Частота изменений

Команда:
```
git log --oneline -400 --name-only --pretty=format:"" -- docker .github | grep -v '^$' | sort | uniq -c | sort -rn | head
```

Результат (проверено в этой сессии):

| Файл | Изменений за последние 400 коммитов, трогающих `docker/` и `.github/` |
|---|---|
| `docker/vision/.image-versions.dev` | **134** |
| `docker/main/.image-versions.dev` | **134** |
| `docker/vision/docker-compose.yaml` | 17 |
| `.github/workflows/L-Build Vision Pi Services.yml` | 10 |
| `docker/vision/scripts/vision-hailo/start_vision_hailo.sh` | 9 |

Это подтверждает исходную формулировку кандидата (в задаче заявлено «135» — фактическое число на момент проверки 134; расхождение на один коммит несущественно, вероятно, из-за момента снятия среза).

Диапазон этих 400 коммитов по датам: `2026-08-29 … 2026-09-15` (17 дней) — команда `git log -400 --pretty=format:"%ad %h" --date=short -- docker .github`. Т.е. **134 коммита за 17 дней ≈ 7.9 коммитов/день** только по одному файлу. Полная история файла (`git log --follow`) — **285 коммитов** с 2026-03-04 по 2026-09-15 (полный жизненный цикл репозитория, ~6.5 месяцев).

Вывод из этого факта отдельно: высокая частота изменений сама по себе — не свидетельство поломки. Это файл, который меняется программой (`sed -i`) на каждом успешном build, а не человеком руками. Частота — ожидаемое следствие того, что build-job — самый частый источник коммитов в `docker/`+`.github/` за весь этот период. Здесь и далее частота используется только как контекст, не как самостоятельный аргумент «за переезд».

### 1.2 Механизм job `update-image-versions`

`.github/workflows/L-Build Vision Pi Services.yml:539` (аналогично — `L-Build Main Pi Services.yml:326`, упомянуто в ADR-0094 §1.3):

1. `:561` — шаг «Tag with SHA and update .image-versions».
2. `:578-591` — функция `tag_and_push()`: `docker tag` мутабельного тега (`dev`/`test`/`latest`) в неизменяемый `<bucket>-<sha>` и `docker push` в **локальный** registry (`LOCAL_PREFIX=localhost:5000/...`). GHCR здесь не участвует (см. комментарий в файле про «GHCR push убран»).
3. `:598-624` — функция `verify_in_registry()`: HTTP `HEAD`/`GET /v2/.../manifests/<tag>` к локальному registry для **каждого** только что запушенного тега, ДО записи в файл. Если хотя бы один тег не подтверждён — job падает, файл не трогается (bugfix issue #1482, `:562-566`, `:594-597`).
4. `:637+` — `sed -i` по `docker/vision/.image-versions.${DOCKER_TAG}`, подставляет **один и тот же** `NEW_TAG=${DOCKER_TAG}-${SHORT_SHA}` во все 7-8 переменных сервисов компонента (важное наблюдение — см. §2.3).
5. `git commit -m "ci: vision SHA tags → ${NEW_TAG} [skip ci]"` + `bash scripts/ci/push-image-versions.sh "$CURRENT_BRANCH" vision`.

`scripts/ci/push-image-versions.sh` — retry-цикл (`IMAGE_VERSIONS_PUSH_ATTEMPTS`, по умолчанию 5) с `git pull --rebase` перед каждым `git push`, таймаутом `GIT_TERMINAL_TIMEOUT=60` на сетевые git-операции (issue #t_dd49849b) и явным `git rebase --abort` при неудачном rebase.

Job `update-image-versions:546` — `timeout-minutes: 10` с комментарием:
> «Issue #t_dd49849b: 2.7h+ hang observed on concurrent runs (round-224+225+develop) when git pull --rebase / git push blocked indefinitely under ref contention. Hard 10-min cap surfaces the failure visibly.»

### 1.3 Как деплой читает файл

`.github/workflows/L-Deploy and Verify.yml`:
- `:307-317` (Vision), `:567` (Main) — «[Vision/Main Pi] Update Code»: `git fetch origin && git checkout <ref> && git reset --hard origin/<ref>`. Робот получает файл целиком через hard reset, не выборочным pull-ом.
- `:380-381` (Vision), `:595-596` (Main) — «Pull Docker Images»: `if [ registry_source != 'local' ] && [ -f .image-versions.${IMAGE_TAG} ]; then set -a && . .image-versions.${IMAGE_TAG} && set +a; fi && docker compose pull --ignore-pull-failures`.
- `:449`, `:528` (Vision), `:646` (Main) — тот же паттерн условного source-инга файла перед `docker compose up -d --force-recreate --pull never` (`:536`, `:651`).
- `:25-30` — `registry_source` (`skip|github|local`, default `github`); `:92-97` — маппинг `environment → IMAGE_TAG` (`production→latest`, `staging→dev`, `test→test`).

Ключевое условие: `registry_source != 'local'`. Файл **сорсится только когда образы идут не из локального registry** (т.е. в дефолтном/боевом пути `registry_source=github`). При явном `registry_source=local` (staging-прогоны на self-hosted раннере) файл **игнорируется**, и compose берёт голые мутабельные теги (`${IMAGE_TAG}` — просто `dev`/`test`/`latest`) — то, что физически лежит в локальном registry на момент pull. Это отдельный, самостоятельный путь «файл не участвует» — уже сегодня существующий, не гипотетический.

`--ignore-pull-failures` (:381, :596) и `--pull never` (:536, :651) на `up`, `pull_policy: if_not_present`/`missing` (упомянуто в `docs/architecture/diagnostics/2026-09-15-robbox-vision-pull-failure.md` и зафиксировано в недавних коммитах `3223a5a7`, `9bfc56c9` из текущей истории репозитория) — это уже существующий defense-in-depth: если pull по любой причине не удался (в т.ч. registry недоступен), деплой не падает целиком, а `docker compose up` работает с тем, что уже есть в локальном кэше Pi.

`git log --all --oneline --grep="#1139"` / `--grep="#1244"` / `--grep="#1482"` (проверено в этой сессии):

| Коммит | Что сделал |
|---|---|
| `51e041a14` | fix(ci #1139 revert): `.image-versions` снова коммитятся прямо в текущую ветку, а не в `ci/image-versions` |
| `d417b7228` | fix(ci #1139 revert): retry+rebase push в текущую ветку — гонка main/vision (оба коммитят в develop, non-fast-forward rejected) |
| `85db3f5ce` | fix(ci #1139 v2): `.image-versions` → per-service ветки `ci/image-versions-{main,vision}` — develop не засоряется SHA-tag коммитами |
| `4b09947a1` | Merge PR #1244 (per-service ветки, попытка №2) |
| `98de836a6` | **revert**(ci #1244): SHA-теги снова в develop — `ci/image-versions-*` ветки не работают (деплой тянет голые dev-теги, роботы получают старый код). Decision #1316 |
| `3faa93b43` | fix(ci #1388): race-safe `push-image-versions` helper + 9 regression-тестов (текущий скрипт) |
| PR #1483 / `d53fed3c7` | fix(ci #1482): `GITHUB_SHA` вместо `git rev-parse HEAD` + registry-verify перед записью |

Что это означает по существу: **дважды** (issue #1139 «шум в develop» и issue #1244 «SHA-теги коммитятся отдельно») команда пыталась убрать git-коммиты из основной ветки, перенеся их в per-service ветки `ci/image-versions-{main,vision}`. Оба раза откатывали, потому что **деплой при `registry_source=local` не читает эти ветки** — робот получал старые образы. Т.е. предыдущая попытка «файл, но не в develop, а в отдельной ветке без основной истории» (= альтернатива (в) из задания этого документа) уже опробована на практике и провалена дважды, с зафиксированной причиной провала.

Остальные issue из задания:
- **#1482** — bugfix: `git rev-parse --short HEAD` (локальный HEAD после `git pull --rebase` мог сместиться) заменён на `${GITHUB_SHA::7}` (SHA коммита, который триггернул run) + registry-verify перед записью в файл. До фикса — робот на round-163 не обновлялся, потому что `.image-versions.test` указывал на образ, которого не существовало.
- **#1388** — race main↔vision: оба build-job коммитят в одну ветку; решение — вынести push-логику в переиспользуемый скрипт с pull-rebase-retry (`scripts/ci/push-image-versions.sh`).
- **#1560** — «spam-trigger» защита от 30+ ручных запусков `L-Build-All-Services.yml` в день на develop; **не про сам image-versions механизм**, а про то, что вызывало build слишком часто. Связан лишь косвенно (упомянут в шапке ADR-0094 как «связанный issue»).
- **t_dd49849b** — 2.7h+ зависание `git pull --rebase`/`git push` при трёх параллельных ранах (develop + 2 round-ветки e2e) под ref contention; закрыт через `GIT_TERMINAL_TIMEOUT=60` + `timeout-minutes: 10` на job.

Ни один из этих инцидентов не является аргументом «файл в git — плохая идея архитектурно». Все — про конкретные баги реализации push-скрипта (HEAD race, отсутствие таймаута, отсутствие pre-write verify), и все закрыты точечными патчами, без изменения самого решения «файл живёт в develop».

## 2. Что является источником правды сегодня

Задание явно требует разобрать это честно: одно знание или два.

### 2.1 Что знает реестр (registry)

Локальный registry (`localhost:5000`, он же `10.1.1.249:5000` = katana) после `update-image-versions` содержит для каждого сервиса **два** тега на один и тот же digest:
- мутабельный `oak-d-humble-dev` (создан обычным build-шагом, `L-Build Vision Pi Services.yml`, через `l-build-service` action, тег = `docker_tag` без SHA);
- неизменяемый `oak-d-humble-dev-f54b6ad` (создан в `tag_and_push()`, `:578-591`).

Реестр отвечает на вопрос: **«какие образы физически существуют и по каким тегам их можно скачать прямо сейчас»**. Это факт о текущем состоянии хранилища. У реестра нет понятия «какая версия — правильная для деплоя на этой неделе»: мутабельный тег `dev` в любой момент может быть переписан следующим build, и реестр не хранит, что было раньше (если только не запрашивать по digest, для которого тоже нужно знать, какой именно digest искать).

### 2.2 Что знает файл в git

`docker/vision/.image-versions.dev` (и аналоги `.test`/`.latest`, `docker/main/...`) содержит: **«для деплоя из этой ветки должен быть использован именно этот неизменяемый SHA-тег»** — то есть акт **выбора**, зафиксированный в момент последнего успешного build+verify. Это не факт о хранилище, а факт о namespace **«текущее решение»**, дополнительно снабжённый историей через git log (см. §4).

### 2.3 Это одно знание или два?

Формально — **одно логическое знание** («какой build — актуальный кандидат на деплой»), но оно **не дублируется**, а **преобразуется**: registry знает существование конкретного digest под конкретным неизменяемым тегом; файл знает, какой из существующих неизменяемых тегов — **выбранный**. Убрать файл и спросить у registry «какой тег актуальный» — нельзя: у registry нет понятия «актуальный», только «существующий». Мутабельный тег `dev` в registry — это ближайший аналог «выбранного», но он:
- переписывается на каждый build без истории (`docker push` того же тега — предыдущий digest теряет имя, остаётся только в `docker image prune`-мусоре);
- один общий для всех потребителей одновременно, то есть не даёт зафиксировать «для деплоя валиден именно этот build», если build ещё идёт или частично упал (отсюда и exists `verify_in_registry` — именно чтобы не выбрать build, который начался, но не завершился).

Отдельное наблюдение при чтении кода (не было в задании, но всплыло по факту): **внутри одного файла есть настоящее дублирование другого рода.** `NEW_TAG="${DOCKER_TAG}-${SHORT_SHA}"` (`:566-567`) — единое значение, подставляемое `sed`-ом в 7-8 разных переменных (`OAK_D_TAG`, `LED_MATRIX_TAG`, ...) за один запуск job'а. Т.е. текущий формат файла моделирует «версия на сервис», а фактически используется как «версия на компонент» (все сервисы Vision Pi одного запуска всегда получают один и тот же SHA-суффикс). Это не довод за переезд в другое место — это довод, что при точечной доработке (§7) можно упростить формат, не трогая семантику «где живёт».

**Вывод по этому разделу:** знание не дублируется 1:1 между registry и файлом — это два разных вопроса («что существует» vs «что выбрано»), и переезд не оправдан аргументом «одно и то же хранится в двух местах». Дублирование, которое реально есть, — внутри самого файла (per-service гранулярность без per-service вариативности), и это лечится точечно.

## 3. Зачем ADR-0094 выбрал текущий вариант

ADR-0094 (`docs/adr/0094-image-versions-push-as-part-of-build.md`) — не новое проектное решение, а **фиксация фактического положения** (§3.1) после того, как обнаружилось, что предыдущий ADR (ADR-0031, «вынести push в отдельный workflow») был утерян при renumber 25.08 (PR #1662) и его acceptance criteria никогда не выполнялись (§1.3: «Ни один из пунктов 1.1–1.5 не реализован»).

Ключевые аргументы ADR-0094 своими словами, с цитатами:

1. **«Это не идеал, но это то, что работает сейчас»** (§3.1, дословно: «Это **не идеал**... но это **то, что работает сейчас** и для чего есть bash-скрипты с retry+rebase+timeout»). Аргумент не «текущий механизм лучший из возможных», а «альтернатива не готова и не доказана, а baseline работает и покрыт инструментами». Это не аргумент «за git навсегда», а аргумент «сейчас — не время трогать, потому что нет готовой замены».

2. **Явный отказ от per-service веток** (§2, второй пункт): «было отклонено в самом ADR-0031 (вариант B) из-за deploy-проблем (#1244 ретро: deploy не подтягивает `.image-versions` оттуда). Ветки в текущем deploy contract не читаются». Этот аргумент **остаётся в силе** — deploy-контракт (`registry_source != 'local'` читает файл из текущей ветки через `git reset --hard`, см. §1.3) сегодня по-прежнему не умеет читать отдельную ветку без явной доработки самого деплоя.

3. **Отдельный workflow отложен не из-за принципиального отказа, а из-за отсутствия e2e smoke-теста** (§2, третий пункт и §6 п.3): «требует отдельной карточки + e2e-смок-теста на deploy» и «сейчас ветки не существует → smoke невозможен → задача заморожена». Это **не** «отдельный workflow — плохая идея», а «нет ресурса проверить её, пока сама ветка/механизм не существует». Это открытый, не закрытый вопрос внутри самого ADR-0094 (см. §6 этого документа, п.3 списка "Связанные задачи").

4. **HOTFIX.md и code разошлись** (§1.3): документация утверждала «SHA-теги идут в ci/image-versions», а код делал прямой коммит в develop — независимо от того, какой вариант правильный, расхождение документации с кодом само по себе было проблемой, и ADR-0094 её устраняет синхронизацией, а не выбором нового механизма.

5. **Явный набор «что НЕ предлагается»** (§2) — architect осознанно исключил три альтернативы (реюз номера 0031, per-service ветки, немедленный вынос в отдельный workflow) с обоснованием по каждой, а не просто промолчал о них.

Все пять аргументов, кроме частично четвёртого (который решён — HOTFIX.md синхронизирован), остаются в силе на дату этого документа (2026-09-15, на следующий день после принятия ADR-0094). За сутки не появилось новых фактов, которые бы их опровергли — наоборот, дополнительное расследование (§1.4 этого документа) только подтверждает, что per-service ветки дважды проваливались на практике.

## 4. Воспроизводимость — отдельно, как требует задание

Главный содержательный аргумент **за** файл в git: история `develop`/`main` отвечает на вопрос «что было раскатано 10 сентября» без обращения к внешним системам, просто `git log`.

Проверка воспроизводимости этого свойства:
```
git log --follow --pretty=format:"%ad" --date=short -- docker/vision/.image-versions.dev
```
— выдаёт полную последовательность дат изменений с 2026-03-04 по 2026-09-15. Для любой даты внутри этого диапазона `git log --before="2026-09-10" -1 -- docker/vision/.image-versions.dev` детерминированно называет коммит, а `git show <commit>:docker/vision/.image-versions.dev` — точное содержимое файла (какие SHA-теги были прописаны) на тот момент. Это не гипотетическое свойство — оно проверяемо прямо сейчас в этом репозитории.

**Что теряется при переезде на резолвинг digest из registry (альтернатива (б), см. §5):**
- Registry (и локальный `localhost:5000`, и GHCR) не хранит историю смены мутабельного тега. `docker pull image:dev` сегодня и `docker pull image:dev`, случись он 10 сентября, — физически разные digest'ы, но узнать, каким он был 10 сентября, из самого registry нельзя (только если retention/garbage collection ещё не подчистил старый layer, и то — нет способа спросить «какой digest был у тега `dev` 10 сентября», потому что registry API не версионирует теги).
- GHCR audit log / registry access log существуют, но: (a) не проверялись в рамках этого расследования (в задании нет прямого указания искать их отдельно — сделаю оговорку в §6 открытых вопросов, т.к. не подтверждено ни существование, ни доступность такого лога для локального registry на katana); (b) даже если бы существовали, это добавляет внешнюю систему как источник правды вместо репозитория, что для вопроса «что раскатано в этот robot-проект в такую-то дату» менее локально, чем `git log` в том же репозитории, где живёт весь остальной код.

**Что могло бы заменить эту функцию, если решение всё же переезжать:**
- Deployment-запись (отдельный artifact/issue-comment/release note на каждый успешный `L-Deploy and Verify.yml` run с зафиксированными digest'ами) — не существует сегодня в репозитории (проверено: `ls .github/workflows/ | grep -i "release\|tag"` — пусто; выделенного deployment-log механизма не найдено).
- Docker image labels (`org.opencontainers.image.revision` = git SHA, зашитый в сам образ при build) технически отвечают на вопрос «из какого коммита собран этот конкретный образ», но не отвечают на обратный вопрос «какой образ был задеплоен на робота в дату X» — для этого всё равно нужен внешний журнал деплоев, которого нет.

**Вывод: замены сегодня не существует.** Это самостоятельный и достаточный довод не отказываться от файла-в-git без предварительного проектирования такой замены — именно то, что просит задание («если замены нет — это сильный довод оставить как есть»).

## 5. Альтернативы

| | (а) Как есть (ADR-0094) | (б) Deploy резолвит digest из registry по плавающему тегу, файл удаляется | (в) Файл остаётся, но пишется не в develop, а в артефакт/release/ветку-хранилище без истории | (г) Файл остаётся в develop, но упрощается (см. §7) |
|---|---|---|---|---|
| **Атомарность** (нельзя задеплоить несуществующий образ) | Да — `verify_in_registry` (`:598-624`) проверяет каждый тег ДО записи в файл; после — deploy читает уже проверенный набор | Частично — деплой должен сам резолвить + верифицировать digest на каждый запуск, дублируя ту же проверку, но уже без "заморозки" выбора между build и deploy (окно гонки шире: build может обновить `dev` между verify и pull) | Да, если пишущая сторона делает verify так же, как сейчас (переносимо) | Не меняется относительно (а) |
| **Поведение при недоступном registry** | Deploy не зависит от registry для получения *списка* версий (git reset достаточно); сам pull всё равно нужен, но `--ignore-pull-failures` + `--pull never` (уже реализовано, `:381,536,596,651`) — робот стартует на закэшированных образах | Деплой **не может** даже определить, какой тег деплоить, без обращения к registry (нет ни файла, ни пина) — то есть теряется единственный независимый от registry источник "что деплоить"; ухудшение относительно (а) | Не хуже (а), если хранилище (release/branch) читается независимо от registry | Не меняется относительно (а) |
| **Воспроизводимость "что было раскатано X числа"** | Да, `git log` (см. §4) | **Нет**, если не строить отдельный deployment-log (не существует сегодня, см. §4) | Частично — release/artifact retention обычно ограничен по времени (GitHub Releases хранятся дольше, artifact — 90 дней по умолчанию); ветка-хранилище без merge-истории теряет удобство `git log -p` по датам, если это force-push поверх одной головы | Да, не хуже (а) |
| **Число гонок** | 1 известная точка гонки (develop, main+vision оба пишут) — уже покрыта retry+rebase (`push-image-versions.sh`) и таймаутом | Гонка переносится в момент deploy (два параллельных deploy-рана могут резолвить разный digest, если build случился между ними) — не устранена, а перемещена | Такая же гонка на уровне ветки-хранилища, если туда пишут main+vision одновременно (то же самое, что пытались в #1139/#1244) | Гонка та же, что в (а) — не меняется |
| **Число сущностей** | Файл в git + registry (2 сущности, разные роли — см. §2) | Registry + логика резолвинга в deploy-workflow (файл исчезает, но логика "какой тег правильный" переезжает в deploy, становится сложнее: нужен эквивалент verify_in_registry на стороне deploy) | Файл + registry + третья сущность (артефакт/ветка-хранилище) — **больше** сущностей, чем (а) | Файл (упрощённого формата) + registry — не меняется относительно (а) |
| **Уже пробовалось?** | — (это baseline) | Не пробовалось в этом репозитории в явном виде | **Да, дважды**, issue #1139 и #1244, оба раза отменено на практике (§1.4) | Не пробовалось, но это не архитектурный переезд, а рефакторинг внутри (а) |

**(г)** добавлена мной как более реалистичная альтернатива «своего варианта», раз в задании явно разрешено добавить лучший вариант при обнаружении. Она не про «переоткрыть ADR-0094», а про точечные улучшения внутри принятого решения — раскрыта в §7.

## 6. Вердикт

**Не переоткрывать ADR-0094.**

Обоснование, коротко:
1. Заявленное свидетельство («135 [134] изменений файла») — реальное, но само по себе не показывает архитектурную проблему: это ожидаемая частота CI-бота, а не признак нестабильности решения.
2. Источник правды сегодня — **не дублирование одного знания**, а два разных факта (registry: что существует; файл: что выбрано), см. §2. Аргумент «один и тот же факт в двух местах» не подтвердился.
3. Все перечисленные в задании инциденты (#1482, #1388, t_dd49849b, #1139, #1244) — баги реализации push-скрипта, все закрыты точечными патчами (registry-verify, GITHUB_SHA вместо HEAD, GIT_TERMINAL_TIMEOUT, retry+rebase helper), ни один не требовал архитектурного переезда для устранения.
4. Главная альтернатива, прямо предложенная кандидатом (файл вне develop — веткой/артефактом), **уже опробована дважды** и дважды отменена по факту эксплуатации (issue #1139, #1244) — с задокументированной причиной провала (deploy не читает отдельную ветку). Переоткрытие означало бы третью попытку того же самого без новых вводных, устраняющих прежнюю причину провала.
5. Главный довод за текущее решение — воспроизводимость «что было раскатано в дату X» — не имеет сегодня готовой замены (§4). Отказ от файла без предварительно спроектированной замены — чистая потеря функциональности.

**Если бы вердикт был "да"** (не тот случай здесь, но фиксирую по требованию задания) — переоткрытие оправдано только при появлении **одновременно**: (а) готовой конструкции deployment-log, закрывающей §4, и (б) объяснения, почему повторная попытка per-service/отдельной ветки не наткнётся на ту же причину провала, что #1139/#1244 (то есть деплой должен научиться читать этот источник в `registry_source=local`-пути, а не только в `github`-пути).

## 7. Что тогда стоит починить точечно

Мелкие улучшения, не ломающие ADR-0094 (не переезд, а рефакторинг внутри принятого решения):

1. **Устранить внутреннее дублирование в файле** (см. §2.3). Сегодня 7-8 переменных на компонент получают один и тот же `${DOCKER_TAG}-${SHORT_SHA}` за один build — гранулярность «версия на сервис» существует только на бумаге. Можно либо (а) оставить формат как есть, но задокументировать явно, что per-service поля сейчас всегда синхронны (снижает риск, что кто-то станет полагаться на независимость полей), либо (б) в будущем, если появится реальный use-case независимого обновления одного сервиса — тогда и только тогда усложнять. Не менять сейчас без явного триггера — это не баг, а неиспользуемая на практике возможность.

2. **Удалить phantom-теги**, уже зафиксированные в ADR-0094 §1.4 п.1 и §6 п.1 (`MICRO_ROS_AGENT_TAG` — issue #2425, `SUPERVISOR_TAG`/`QUEST_TAG` — issue #2377). Follow-up карточка уже описана в самом ADR-0094, отдельно создавать не требуется — достаточно напомнить, что она не закрыта.

3. **Подключить `scripts/ci/check_image_versions_usage.sh` в CI** (ADR-0094 §3.2 — скрипт добавлен, но не подключён, там же явно написано «не подключён в этом PR»). Блокируется пунктом 2 (сейчас даст exit 1 из-за phantom-тегов). Порядок: сначала §7.2, потом подключение.

4. **Дедупликация `verify_in_registry`.** Функция определена идентично в `L-Build Vision Pi Services.yml:598-624` и (по аналогии, не проверено построчно в рамках этого документа — см. открытый вопрос ниже) в `L-Build Main Pi Services.yml`. Вынести в общий `scripts/ci/verify-image-in-registry.sh` по аналогии с уже вынесенным `push-image-versions.sh` — снижает число мест, которые нужно чинить синхронно при следующем баге вроде #1482.

5. **`[skip ci]`-гигиена.** Коммиты `ci: vision/main SHA tags → ... [skip ci]` (`L-Build Vision Pi Services.yml:678`, `L-Build Main Pi Services.yml:469`, `L-Build Single Service.yml:616`) полагаются на нативную поддержку GitHub Actions `[skip ci]` в сообщении коммита. Один workflow с `push: branches: [develop]` **без** `paths:`-фильтра — `G-Auto-merge to Main.yml:6-8` — триггерится на любой push в develop, включая эти бот-коммиты; нативный `[skip ci]` должен его глушить, но это не было явно перепроверено в рамках этого документа (см. открытый вопрос). Точечная проверка: убедиться, что `G-Auto-merge to Main.yml` не создаёт лишних PR/раннов на каждый image-versions коммит.

Ни один из пунктов 1-5 не требует нового ADR — это рабочие карточки уровня devops, часть уже описана в самом ADR-0094 §6.

## 8. Открытые вопросы

1. **GHCR/registry audit log** — не проверялось в рамках этого расследования, существует ли у GHCR или у локального registry на katana механизм, который бы восстановил «каким был digest тега `dev` в дату X» без git-файла. Если такой механизм есть и доступен программно — это меняет расчёт в §4 (появляется потенциальная замена), но не меняет вердикт §6 (нет второго аргумента для переоткрытия, кроме воспроизводимости).
2. **`verify_in_registry` в `L-Build Main Pi Services.yml`** — не сверено построчно с версией в Vision-workflow; предполагается идентичность по аналогии структуры (`update-image-versions:326`, тот же паттерн), но для точного дедуп-плана (§7.4) нужна отдельная сверка diff'а обеих версий функции.
3. **`G-Auto-merge to Main.yml` на бот-коммитах** — не подтверждено эмпирически (например, по логам прошлых ранов), что `[skip ci]` там действительно гасит запуск, а не просто гасит его в UI/списке коммитов при иной семантике. Пункт §7.5 — это гипотеза для проверки, не подтверждённый факт.
4. **Статус кандидата «Speculative»** — не найден отдельный документ-реестр, где кандидат был бы явно заведён со статусом (проверено: `grep -rln "Speculative" docs/` не даёт релевантного файла-реестра именно для этого кандидата). Статус принят на веру из формулировки задачи; если у кандидата есть карточка/issue-номер вне этого документа — стоит связать этот план с ней явно постфактум.
5. **Связь с манифестом сервисов** (`docs/plans/2026-09-15-service-manifest.md`) — на момент написания этого документа файл манифеста ещё не существовал в репозитории (проверено `ls docs/plans/`). Если манифест сервисов в итоге станет местом, где перечисляются `*_TAG` переменные декларативно (а не через `grep` по compose/scripts, как сейчас в `check_image_versions_usage.sh`), это может упростить §7.1-7.3, но это вопрос к параллельной задаче, не к этому документу.

## 9. Неподтвердившиеся/скорректированные факты из формулировки задачи

- «135 раз» → фактически **134** для каждого из двух файлов (расхождение на 1, не меняет вывода).
- «следующий — 16» → фактически следующий по частоте файл (`docker/vision/docker-compose.yaml`) — **17**, не 16 (близко, не меняет вывода).
- Прочие количественные и текстовые утверждения задания (номера строк job'а, `timeout-minutes: 10`, номера issue в комментариях, наличие `--ignore-pull-failures`/`--pull never`, содержание ADR-0094 и утерянного ADR-0031) — подтверждены точным чтением файлов, расхождений не найдено.
