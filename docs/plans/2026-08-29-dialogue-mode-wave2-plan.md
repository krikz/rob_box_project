# 1. Супервизор ↔ диалоговая нода: как это устроено сегодня

Это ключевой узел для §1/§3.3/§3.5 спека, и он **асимметричен**: телеметрия
ходит, управление — почти нет.

## 1.1 Что реально ходит

**Телеметрия (работает):**

```
dialogue_node:460  →  /voice/dialogue/state  →  supervisor._on_voice_state_msg:211
                                              →  StateAggregator
                                              →  /avatar/state (latched, transient_local,
                                                 msgpack, 1 Гц, supervisor_node.py:186)
                                              →  quest streams/registry.py:78, telegram SupervisorClient
```

**Управление (единственная живая нитка):**

```
webxr voice_mode cmd → quest_node.set_voice_mode:300
   → /avatar/set_voice_mode (std_msgs/String)
   → supervisor._on_set_voice_mode:224 → _apply_voice_mode:232
       ├─ mode ∉ VOICE_INPUT_MODES → отказ
       ├─ self._mode != "active"   → отказ (но в проде AVATAR_SUPERVISOR_MODE=active,
       │                             docker-compose.yaml:330 → ветка проходит)
       └─ SetParameters на /dialogue_node/set_parameters (supervisor_node.py:257)
   → dialogue_node.parameters_callback:838  ← ⛔ ТОЛЬКО ЛОГИРУЕТ
   → единственный реальный потребитель: _on_quest_stt:1656 (quest_ttts | quest_stt)
```

То есть архитектурно правило «супервизор — единственный, кто меняет
`voice_input_mode`» (ADR-0028 S5) соблюдено, транспорт есть, и в проде он даже
включён в `active`. Но за параметром нет поведения, кроме маршрутизации
Quest-STT.
