# Карта покрытия диалоговой ноды e2e-сценариями

> **Дата:** 2026-08-29 · **База:** `develop` @ `2da2b122`
> **Что это:** инвентаризация «52 тула харнеса против существующих сьют» + описание
> трёх новых сценариев и того, что означает падение каждого зонда.

## ⚠️ Честность (ADR-0018)

Ни одна из трёх новых сьют **не прогонялась**. Ниже — разбор по коду и по текстам
существующих сценариев. Статус новых сьют до первого живого прогона — неизвестен.

---

## 1. Что было до этой работы

Всего зарегистрированных MCP-тулов: **52** (по `def name(self) -> str` в
`src/rob_box_mcp_tools/rob_box_mcp_tools/tools/*.py`).

Существующие сьюты (`.github/e2e/scenarios/*.json` + `docker/vision/test/scenario_runner/scenarios/*.yaml`)
касались **30** из них. Непокрытыми оставались **22**:

| Область | Непокрытые тулы |
|---|---|
| Навигация | `move_direction`, `navigate_to_waypoint`, `navigate_to_coordinates`, `list_waypoints`, `delete_waypoint`, `clear_waypoints` |
| Картография | `start_mapping`, `continue_mapping`, `finish_mapping`, `optimize_map`, `load_map` |
| Музыка | `get_music_state`, `list_tracks`, `save_track`, `load_track`, `delete_track`, `search_samples` |
| Память / знания | `memory_search`, `faq_search` |
| Прочее | `get_perception_context`, `get_sound_info`, `estimate_tts_duration` |

Перекос очевиден: существующие сьюты плотно покрывают музыку-генерацию, голоса и
barge-in — то есть всё, вокруг чего в последние недели были инциденты. Навигация,
картография и работа с треками не покрыты **вообще**, хотя тулы существуют и
доступны LLM.

## 2. Три новые сьюты и почему их три, а не одна

Разделение не косметическое — у файлов разный режим запуска и разный смысл красного.

| Сьюта | Должна быть зелёной? | Где запускать |
|---|---|---|
| `dialogue_tools_coverage_v1` | **Да.** Красный = регрессия | Можно в CI |
| `dialogue_gap_probe_v1` | **Нет.** Красный = подтверждённая находка | Вручную, читать лог |
| `dialogue_motion_coverage_v1` | Да, но | 🚨 Только вручную: двигает робота, перезаписывает карту |

Смешать их в один файл нельзя: тогда известные дыры красили бы пайплайн вечно, а
безопасные шаги нельзя было бы гонять без человека у кнопки останова.

## 3. `dialogue_tools_coverage_v1` — добор непокрытого

16 шагов, замкнутые жизненные циклы вместо разрозненных вызовов:
`save_track → list_tracks → load_track → stop_music → delete_track` и
`save_waypoint → list_waypoints → delete_waypoint`. Прогон не оставляет мусора.

Три тула вынесены из жёсткого gate намеренно — их отсутствие в логе является
**результатом**, а не провалом:

- `faq_search` — срабатывает только при загруженном FAQ-профиле (`faq_mode_enabled`);
- `estimate_tts_duration` — служебный, его зовёт планировщик, а не LLM по своей воле;
- `get_perception_context` — зависит от живой камеры на стенде.

Если за прогон ни один из них не вызвался ни разу — значит тул недостижим на
практике, и это надо заводить отдельной карточкой.

Два инварианта безопасности вшиты в `must_not_call`: вопрос о списке точек не
должен приводить к движению, а удаление одной точки — к `clear_waypoints`.
Сам `clear_waypoints` не проверяется нигде: он уничтожает пользовательские данные.

## 4. `dialogue_gap_probe_v1` — что означает падение каждого зонда

| Зонд | Гипотеза | Что означает падение |
|---|---|---|
| `gp01` план DJ-сета | §4.1 спека обещает «сет заканчивается финальным треком и прощанием». Тула `save_dj_set_plan` в коде **нет**, сет глохнет по счётчику `DJ_AUTO_MAX_TRANSITIONS = 24` | Подтверждена карточка W7-1 |
| `gp04` wake-word под музыкой | ADR-0024 в статусе **proposed**, не accepted | ADR закрыт не полностью, §4.1/§5 спека завышают факт |
| `gp06` смена TTS-провайдера | §4.4 обещает «явный инструмент смены провайдера». Тула нет | Подтверждена карточка W5-6. Отдельно смотреть: не выдумает ли LLM вызов несуществующего тула — это другой сорт бага |
| `gp07` язык вывода | §3.2 обещает ответ на выбранном языке. `tts_text_guard` режет чанк с >10 % «чужой» письменности (issue #1709) | §3.2 физически заблокирован, нужна W6-4/W6-5 |
| `gp09` повторное представление | Баг «один голос = два профиля» (W5-4, фикс в `942f6d20`) | Фикс не сработал; смотреть новые строки `identify candidates` / `merged into existing profile` |
| `gp10` смена говорящего | §2.3 обещает «робот понимает, что это другой человек». Детектора нет ни в коде, ни в промпте | Подтверждена карточка W5-3 |
| `gp12` MERGE вне песни | §2.5. Issue #968 проверялся только на песне | См. ниже — тут возможен «полузелёный» исход |
| `gp14` честная память | §2.4 «старые тёрны не протекают в новый вопрос» | Утечка контекста после сброса сессии |

**Про `gp12` отдельно.** Четыре хука планировщика — `set_group_boundary`,
`set_frozen_touch_hook`, `set_llm_continue_hook`, `set_eta_provider` — на момент
написания сьюты **ни к чему не подключены** в `dialogue_node`. Поэтому наиболее
вероятный исход: робот **не обрывается** (это чинит W2-8, issue #1734), но добавка
приходит обычным ответом LLM, а не правкой сегментов через `task_delta`. Такой
результат ценен: он разделяет «STOP больше не глушит» и «MERGE реально едет».

**Требование к прогону gap-сьюты:** `barge_in_policy=classify`. В прод-конфиге
до сих пор `replace`, поэтому перед прогоном:

```bash
ros2 param set /dialogue_node barge_in_policy classify
```

## 5. Чего эти сьюты принципиально не проверяют

Честный список, чтобы зелёный прогон не создавал ложного спокойствия.

**Требуют перезапуска робота — автоматике недоступны:**

- персистентность выбранного голоса и TTS-провайдера по пользователю (§4.4):
  `VoiceStateStore` — обычный `dict` в памяти, после рестарта всё теряется;
- «тёрны в БД не храним» (§2.4): сегодня история переживает перезапуск, что прямо
  противоречит спеку.

Проверяются только руками: выставить голос → перезапустить `voice-assistant` →
спросить тем же голосом.

**Требуют долгого ожидания:**

- idle-сводка при ~3 минутах тишины (§2.4) — её в коде нет вообще; сценарий с
  трёхминутной паузой в общем прогоне нерентабелен.

**Требуют железа оператора:**

- всё, что про Quest: рация, робот-голос, приглушение вывода при PTT (W2-7),
  обратный аудио-канал в шлем (W4-5/W4-6).

**Структурно недостижимо для мок-раннера:**

- всё, что происходит **внутри** `stt_node` до публикации в `/voice/stt/result`.
  Мок-сценарии инжектят текст в этот топик, то есть в выход ноды. Именно поэтому
  баг issue #1734 не ловился моками и был найден только живым голосовым прогоном.

## 6. Как запускать

```bash
gh workflow run "L: E2E Voice Test" -f scenario=dialogue_tools_coverage_v1
```

Gap-сьюта — тем же способом, но **не ставить в блокирующий gate CI**, пока зонды
не превратятся в закрытые карточки. Motion-сьюта — только вручную, при человеке
рядом с роботом.
