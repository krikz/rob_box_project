## Проблема 1: Ложные сообщения об ошибках

### Описание проблемы
**Симптомы:**
- Робот успешно выполняет команды (воспроизводит звуки 5 раз, показывает анимации)
- Но потом говорит пользователю: "Извините, у меня возникли проблемы..."
- В логах видно успешное выполнение, но таймаут при получении результата

**Отчет пользователя:**
> "Робот прекрасно произвел пять раз милый звук и показал анимацию пожарной машины но на оба запроса он потом сказал что он не смог этого сделать!!!"

### Анализ логов
```
[mcp_server-9] ✅ Инструмент play_sound выполнен успешно
[mcp_server-9] 📤 Публикую результат для play_sound (request_id: 291c90b0)
[mcp_server-9] ✅ Результат опубликован на /mcp/result
[sound_node-7] ✅ Завершено: cute

[dialogue_node-4] ⏱️ Timeout ожидания результата для play_sound (request_id: 291c90b0)
[dialogue_node-4] ⚠️ play_sound вернул ошибку: Timeout ожидания результата инструмента
```

**Временной анализ:**
- Результат опубликован: `[1769698313.828010016]`
- Таймаут произошел: `[1769698315.818339024]`
- **2 секунды** между публикацией и таймаутом!

### Корневая причина

**QoS (Quality of Service) несоответствие** в ROS 2:

| Компонент | Топик | QoS Профиль | Статус |
|-----------|-------|-------------|--------|
| `mcp_server.py` | `/mcp/result` (pub) | **BEST_EFFORT** | ✅ |
| `llm_adapter.py` | `/mcp/result` (sub) | **BEST_EFFORT** | ✅ |
| `deepseek_adapter.py` | `/mcp/result` (sub) | **RELIABLE** (по умолчанию) | ❌ |

**Почему это ломает связь:**

В ROS 2 подписчик с `RELIABLE` QoS **НЕ МОЖЕТ** получать сообщения от издателя с `BEST_EFFORT` QoS. Это по дизайну - RELIABLE гарантирует доставку, BEST_EFFORT - нет.

**Последствия:**
1. MCP сервер публикует результат с BEST_EFFORT
2. Подписчик DeepSeek адаптера с RELIABLE отклоняет сообщение
3. Коллбэк `on_result()` никогда не вызывается
4. `execute_tool_call_sync()` истекает по таймауту
5. Возвращается ошибка в LLM
6. LLM сообщает пользователю о неудаче

### Решение

**Файл:** `src/rob_box_mcp_tools/rob_box_mcp_tools/deepseek_adapter.py`

**До:**
```python
import rclpy
from rclpy.node import Node
from std_msgs.msg import String

class DeepSeekToolCallAdapter:
    def __init__(self, node: Node):
        self.node = node
        
        # По умолчанию QoS = RELIABLE
        self.execute_pub = node.create_publisher(String, "/mcp/execute", 10)
        self.result_sub = node.create_subscription(String, "/mcp/result", self.on_result, 10)
```

**После:**
```python
import rclpy
from rclpy.node import Node
from rclpy.qos import QoSProfile, ReliabilityPolicy, HistoryPolicy
from std_msgs.msg import String

class DeepSeekToolCallAdapter:
    def __init__(self, node: Node):
        self.node = node
        
        # QoS для минимизации задержек в Zenoh (совпадает с MCP server)
        qos_profile = QoSProfile(
            reliability=ReliabilityPolicy.BEST_EFFORT,
            history=HistoryPolicy.KEEP_LAST,
            depth=10
        )
        
        self.execute_pub = node.create_publisher(String, "/mcp/execute", qos_profile)
        self.result_sub = node.create_subscription(String, "/mcp/result", self.on_result, qos_profile)
```

**Изменения:**
1. Добавлен импорт `QoSProfile, ReliabilityPolicy, HistoryPolicy`
2. Создан `qos_profile` с `BEST_EFFORT` (соответствует MCP серверу)
3. Применен `qos_profile` к обоим топикам (`/mcp/execute` и `/mcp/result`)
4. Добавлен комментарий объясняющий цель

### Почему BEST_EFFORT правильный выбор

Система использует **Zenoh DDS** мост, который лучше работает с BEST_EFFORT:
- Меньшая задержка (нет накладных расходов на ретрансляцию)
- Лучше для управления роботом в реальном времени
- Приемлемо для голосовых команд (идемпотентные операции)
- Согласуется со всей остальной MCP коммуникацией

## Проблема 2: Отказ воспроизводить звуки более 5 раз

### Описание проблемы

**Симптомы:**
- Пользователь: "Робокс проиграй звук ошибка 10 раз"
- Робот отказывается: "Извините, я не могу выполнить ваш запрос..."
- НО: Звук "милый" робот воспроизвел 5 раз без проблем

**Отчет пользователя:**
> "Почему робот отказывается воспроизводить звук ошибки пять раз после того как я его попросил сделать это десять раз хотя звук милый он пять раз воспроизвел!!"

### Анализ логов

```
[stt_node-6] ✅ Yandex STT: "Робокс проиграй звук ошибка 10 раз"
[dialogue_node-4] 💬 Один запрос: проиграй звук ошибка 10 раз
[dialogue_node-4] 🏁 Stream завершён: stop (обработано 0 chunks)
[tts_node-5] 🔊 TTS: Извините, я не могу выполнить ваш запрос на воспро...
```

LLM **отказался** использовать инструменты и вернул `stop` с извинением.

### Корневая причина

**Файл:** `src/rob_box_voice/prompts/master_prompt_compact.txt`  
**Строка 21 (старая версия):**

```
6. **ЧРЕЗМЕРНЫЕ ПОВТОРЕНИЯ:** Если просят повторить что-то >5 раз 
   (например "скажи мяу 100 раз"), ОТКАЖИСЬ вежливо и объясни, 
   что можешь сделать это 3-5 раз максимум для комфортного взаимодействия.
```

LLM **следовал инструкциям** и отказывался от запросов >5 повторений!

**Почему это слишком ограничительно:**
- 10 повторений - разумный запрос для тестирования или демонстрации
- 5 повторений - слишком мало для практических применений
- Ограничение должно предотвращать только абсурдные запросы (>50-100)

### Решение

**Файл:** `src/rob_box_voice/prompts/master_prompt_compact.txt`

**До:**
```
6. **ЧРЕЗМЕРНЫЕ ПОВТОРЕНИЯ:** Если просят повторить что-то >5 раз 
   (например "скажи мяу 100 раз"), ОТКАЖИСЬ вежливо и объясни, 
   что можешь сделать это 3-5 раз максимум для комфортного взаимодействия.
```

**После:**
```
6. **ПОВТОРЕНИЯ:** Можешь повторять звуки/действия до 15 раз 
   (например "проиграй звук 10 раз" - ОК!). Если просят >20 раз, 
   предложи меньше (10-15 раз) для комфортного взаимодействия.
```

**Изменения:**
- Увеличен лимит: 5 → 15 повторений
- Добавлен явный пример: "проиграй звук 10 раз" - ОК!
- Порог отказа: >5 → >20 раз
- Более позитивная формулировка (не "ОТКАЖИСЬ", а "предложи меньше")

### Обоснование нового лимита

| Повторений | Ситуация | Действие |
|-----------|----------|----------|
| 1-15 | Нормальный запрос | ✅ Выполнить |
| 16-20 | Граничная зона | ✅ Выполнить |
| 21+ | Чрезмерный запрос | ⚠️ Предложить 10-15 |
| 50+ | Абсурдный запрос | ❌ Вежливо отказать |

## Предотвращение в будущем

### QoS проблемы

1. **Всегда проверяйте QoS** при создании publishers/subscribers для MCP топиков
2. **Используйте BEST_EFFORT** для всей MCP коммуникации (документировано в mcp_server.py)
3. **Проверяйте логи** на таймауты после успешного выполнения
4. **Используйте `ros2 topic info -v <topic>`** для инспекции QoS настроек

### Промпт ограничения

1. **Документируйте лимиты** в комментариях промпта с обоснованием
2. **Тестируйте граничные случаи** (ровно на лимите, чуть выше лимита)
3. **Анализируйте отказы** - если LLM отказывается, проверьте промпт
4. **Итеративно настраивайте** лимиты на основе реального использования
