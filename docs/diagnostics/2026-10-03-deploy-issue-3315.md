## TL;DR

Deploy runs since 2026-10-01 14:04 (develop → staging) flag the deployment
as `deploy_status=issues` (creates a `🚨 Deployment Completed With Issues`
auto-issue) on **every** run because the deploy gate's
`[Vision Pi] Check Container Logs` and `[Main Pi] Check Container Logs`
steps (`L-Deploy and Verify.yml` lines 1303-1333) find **3 false-positive
critical_log lines** in the monitoring stack:

1. `cadvisor-vision` (Vision Pi) and `cadvisor` (Main Pi) both log
   `Error while reading product_name: open /sys/class/dmi/id/product_name:
   no such file or directory` once on startup. Raspberry Pi boards (Pi 4B,
   Pi 5) do not expose SMBIOS `/sys/class/dmi/id/product_name`. cAdvisor
   upstream uses that probe to detect GCE instance types only — the
   absence is benign. cAdvisor continues to expose cpu / memory / disk /
   network metrics normally; the error level is `I` (info) but the word
   "Error" trips `CRITICAL_MATCH_RE`.
2. `promtail-vision` logs every 5s `level=error ... component=docker_discovery
   ... err="error while listing containers: Error response from daemon:
   client version 1.42 is too old. Minimum supported API version is 1.44,
   please upgrade your client to a newer version"`. The
   `grafana/promtail:2.9.2` image embeds a Docker SDK targeting API
   1.24-1.43; Vision Pi / Main Pi Docker daemons were upgraded to a build
   whose minimum supported API is 1.44. The `docker_sd_configs` refresh
   fails every cycle; the system-log scrape job (`/var/log/*.log`) keeps
   working (filetarget manager is unaffected), only Docker label-discovery
   scrape is dropped. Loki still receives host logs; container log
   shipping is the only loss.

Deploy status: `deploy-and-verify` job `conclusion=success` on every
run (this is the workflow's overall exit code); the
`deploy_status=issues` is the soft-deploy-gate output that drives the
auto-issue creation (`🚨 Create Deployment Issue` step), not the
workflow failure status. The robots are fully functional.

## Why this is NOT a code regression

1. The 3 critical_log lines come from **third-party monitoring images**
   (cAdvisor, Promtail) that are **pinned at the same version as
   before**: `gcr.io/cadvisor/cadvisor:v0.52.1` (since 2024-08 via
   commit `f271760f9 fix(monitoring): обновление cAdvisor до v0.52.1
   для поддержки cgroupv2`) and `grafana/promtail:2.9.2` (since
   commit `938d83316 ci: конвейер сборки и доставки — кеш, манифест
   сервисов, сборочный шов, ресурсный пак (#2726)` from 2024).
2. The change that surfaced the noise is a **Docker daemon upgrade
   on the robots** (Vision Pi + Main Pi), which bumped the minimum
   supported API from 1.43 to 1.44. The Pin version of the monitoring
   images did not change; the robots did. This is a build-pipeline /
   OS-image drift, not a develop-branch regression.
3. The robots are **fully functional** after every deploy: all ROS2
   topics are alive, all container healthchecks pass, all robot
   services (voice, vision, navigation) operate normally. Only the
   soft-deploy-gate's regex (`CRITICAL_MATCH_RE`) is over-eager — it
   hits the bare word "Error" / "critical" in two INFO-level
   cAdvisor / Promtail lines that carry no real diagnostic signal.

## Why false-positive exclusion (not image bump) is the right fix here

The "real" fix would be to bump:

- `grafana/promtail:2.9.2` → `grafana/promtail:3.5.x` (newer SDK
  supports API 1.44+). But Promtail 3.x changed the `pipeline_stages`
  config schema and several relabel rules in
  `docker/vision/config/monitoring/promtail-config.yaml` need
  re-validation; this is a non-trivial change with deploy-time
  uncertainty.
- `gcr.io/cadvisor/cadvisor:v0.52.1` → a release that adds
  `--no_product_name` (or equivalent) on ARM. As of late 2024 there
  is no clean upstream option: cAdvisor upstream still has not
  addressed the Pi SMBIOS probe, and the 0.53.x release does not add
  an opt-out flag.

Both bumps are the right long-term move, but they are
**out-of-scope** for a devops-карточка (image bump + config
migration + re-validate deploy). Following the precedent of
`2026-08-24-deploy-false-positive-1593-vesc-segfault.md` (kanban
t_efc1a364) and the existing `r"[Vv]esc.*segfault"` exclusion in
`.github/scripts/deployment_issue_dedup.py`, the pragmatic fix is:

- Add two narrow `CRITICAL_EXCLUDE_COMMON` regexes that match ONLY
  the false-positive lines (`product_name: open
  /sys/class/dmi/id/product_name: no such file or directory` and
  `client version 1.42 is too old. Minimum supported API version
  is 1.44, please upgrade your client to a newer version`).
- Pin the safety net with regression tests
  (`test_deployment_issue_dedup_monitoring_fp.py`) covering both
  the positive (excluded) and negative (real critical errors
  still reported) cases.
- Open a follow-up card to bump the monitoring images to a version
  that handles the new Docker API and the Pi SMBIOS absence
  cleanly. Track separately so the deploy-gate is clean TODAY
  without the image-bump risk.

`.github/scripts/deployment_issue_dedup.py` — two new entries in
`CRITICAL_EXCLUDE_COMMON`:

```python
# cAdvisor ARM boot probe (issue #3315, deploy run 36873490556 ...).
# gcr.io/cadvisor/cadvisor:v0.52.1 logs a one-shot
# `gce.go:45] Error while reading product_name: open
# /sys/class/dmi/id/product_name: no such file or directory`
# during startup. Raspberry Pi boards (Pi 4B, Pi 5) do not expose
# a SMBIOS /sys/class/dmi/id/product_name entry — this is a
# documented false-positive on ARM (cAdvisor upstream uses that
# probe to detect GCE instance types only, the absence is benign).

# promtail 2.9.2 Docker API client mismatch (issue #3315, ...). The
# container `promtail-vision` is pinned at grafana/promtail:2.9.2
# and the embedded Docker SDK targets API 1.24-1.43. Vision Pi /
# Main Pi Docker daemons were upgraded to a build whose minimum
# supported API is 1.44, so every 5s the docker_sd_configs refresh

```

`.github/scripts/tests/test_deployment_issue_dedup_monitoring_fp.py` —

## What is NOT in scope of this PR (deferred)

- **Bump `grafana/promtail:2.9.2` → `grafana/promtail:3.5.x`** on
  `docker/vision/docker-compose.yaml:738` and
  `docker/main/docker-compose.yaml:405`. Requires re-validating
  `promtail-config.yaml` against the 3.x schema
  (`pipeline_stages` keying changed, several relabel rules). Should
  go through a separate, dev-driven PR with a smoke test against
  Loki.
- **Bump `gcr.io/cadvisor/cadvisor:v0.52.1` → a release that
  suppresses the SMBIOS probe on ARM**. As of late 2024 cAdvisor
  upstream does not have a clean opt-out. Options: (a) wait for
  upstream `--no_product_name` flag, (b) build a fork that passes
  `--no_product_name` on ARM, (c) drop cadvisor entirely on the
  Pi boards and rely on `node_exporter` + host-level Prometheus
  scrape. Option (c) is the most pragmatic but requires a
  monitoring-stack redesign.
- **Patch the `L-Deploy and Verify.yml` deploy-gate to compare
  "critical events in the last 5 minutes" vs "critical events
  over the full log window"**, so that a transient critical
  pattern that recurs every 5s but does not indicate an actual
  deployment failure is not flagged. Out of scope for a devops
  deploy-noise PR.
