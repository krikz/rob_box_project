# Спецификация LLM-формализатора для `voice_input_mode=quest_llm_formalize`

> index 1, AV-28 #1920). Зафиксированные в нём числа и инварианты —
> контракт: менять без согласования с шисюном / карточкой нельзя.

> **Контекст.** ADR-0027 §3.4 определяет 4 голосовых режима
> `dialogue_node`. Один из них — `quest_llm_formalize` (Phase 3): оператор

> 6 системных промптов) уже заложен в PR #1931 (`wip(voice AV-28 #1920):

## 1. Зачем это нужно

Оператор в очках Meta Quest нажимает PTT, наговаривает черновик речи
(«ну короче батарейка садится, может проц десять осталось, надо бы
на базу»), отпускает — и через секунду-две слышит из динамика робота
ту же мысль, переписанную в стиле «Технический» (или «Ленин», или
«Деловой» — что выбрано в HUD/супервизоре). Вокруг стоят люди, им
слышно: речь звучит как готовое объявление, не как черновик с
«короче/ну/может».

Это превращает очки из персонального микрофона в **микрофон для
публичных выступлений** через аватара — ADR-0027 §1.1 («робот как
аватар оператора»).

## 2. Контракт LLM-вызова формализатора

### 2.1. Где живёт вызов

**Отдельная точка** в `dialogue_node`, не идущая через
`_dispatch_turn` / `_call_llm_dialog` с `speak_text`. Логика:

```
_on_quest_stt(msg) при voice_input_mode == "quest_llm_formalize":
    text = msg.data.strip()
    if not text: return
    preset = self._resolve_preset()              # читает voice_preset (YAML default = technical)
    language = self._resolve_output_language()    # читает voice_output_language (default = ru)
    sys_prompt = load_preset_prompt(preset, language)  # src/rob_box_voice/config/presets/<key>.txt
    user_msg = format_formalize_user_message(text)      # см. §2.3
    out = self._call_formalize_llm(sys_prompt, user_msg)  # см. §2.2, §2.4
    self._speak_direct(out)                                   # plain text → TTS, без ANTI-DUP, без §2 цикла
```

Причина отдельного пути — `master_prompt_compact.txt` это диалоговый
промпт с ANTI-DUP, RULE #0 («NO METALANGUAGE»), инструментами, системой
правил. Для формализатора весь этот груз мёртв и даже вредит
(формализатор обязан НЕ говорить «Погнали!» / «Хочешь ещё?», а
`master_prompt_compact.txt` только просит этого не делать).

### 2.2. Параметры LLM-вызова

| Параметр        | Значение                              | Обоснование |
|-----------------|---------------------------------------|-------------|
| `temperature`   | **0.4** (≤ 0.4 для предсказуемости стиля) | Выше 0.4 — модель начинает «творчески» добавлять уточнения и менять смысл; ниже 0.2 — теряется гладкость перефразирования. 0.4 — эмпирический баланс. |
| `top_p`         | 0.9 (дефолт провайдера, не зажимать)  | Не трогаем — `temperature` уже достаточно дисциплинирует. |
| `max_tokens`    | `min(2 × len(input) + 80, 600)`       | Жёсткий потолок длины (см. §2.5). 600 — запас для TTS-чанка ≤ 200 символов × 3 чанка, что больше, чем нужно, но не даёт модели уйти в «длинный пересказ». |
| `tools`         | **пусто** (нет function calling)       | Формализатор НИЧЕГО не вызывает — `speak_text`, `set_voice`, `search_web` ему недоступны. Если увидит `tool_calls` — это регрессия, в тесте должен падать `assert tool_calls == []`. |
| `stream`        | `False`                               | Формат-атом: один вызов, один абзац; стриминг не нужен и мешает проверить «не было ли маркера "done" в середине». |
| `stop`          | **не задаём**                         | Внутренний §-маркер «done» формализатор не использует (он не диалоговый LLM), обрывать вывод не нужно. |
| `model`         | тот же, что у диалогового LLM (`llm_providers[0]`) | Отдельная модель не нужна — задача редактирования текста проще диалога. |

### 2.3. Формат user-message

Ровно одна строка plain text. Шаблон:

```
Исходная фраза оператора (дословно, без wake-word):

"""
<text>
"""

Перепиши её в стиле пресета «<preset_name>» на языке «<language>». Сохрани смысл, длину (±×2) и все факты дословно. Не добавляй ничего от себя.
```

`<text>` подставляется **как есть**, экранирование не нужно (мы
специально используем тройные кавычки `"""` как визуальный fence —
LLM не интерпретирует его как tool-call).

`<preset_name>` — человекочитаемое имя из `voice_presets.yaml`
(«Технический», «Ленин», ...), а не id. Это даёт LLM явный контекст.

`<language>` — `ru` или `en` (значение enum из yaml), в user-message
кладём строкой «русский» / «английский» для естественности (LLM
надёжнее отвечает на естественном языке enum-значений).

**Что НЕ должно попасть в user-message** (анти-инвариант для
разработчика):

- ❌ `system_context` (TTS-провайдер, спикер, время) — формализатор
  не зависит от контекста робота, ему нужна только исходная фраза.
- ❌ история диалога — формализатор stateless, истории не видит.
- ❌ маркеры источника `[TG:...]`, `[Spkr:...]` — текст идёт уже
  очищенный от них (STT-результат на `/voice/stt/quest` сырой, но
  если STT подмешает — формализатор увидит мусор; ответственность
  на `stt_node`, не на формализаторе).
- ❌ инструменты (`speak_text`, ...).

### 2.4. Формат ответа LLM

Ровно **один короткий абзац** plain text. Никакого JSON, никакого
SSML, никакого markdown, никакого префикса («Вот переписанная
версия:»). См. требование 4 в каждом пресет-файле.

Если в ответе пришёл хотя бы один из маркеров:

- ``speak_text`` / ``set_voice`` / ``search_web`` / ``load_skill`` /
  любой tool-call → **отбрасываем весь ответ**, логируем как
  `❌ [quest_llm_formalize] LLM produced tool-call: <first 60 chars>`,
  ничего не озвучиваем. Это регрессия — тест `test_*_no_tool_calls`
  страхует.
- символы CJK / Devanagari / Greek (>10% не-кириллицы/не-латиницы в
  режиме `ru`) → отбрасываем (RULE #UNICODE-SPEECH из
  `master_prompt_compact.txt` применим и здесь — мы не должны
  допускать нечитаемый TTS).

### 2.5. Ограничение длины выхода

Жёсткий лимит: **длина ответа ≤ 2 × длины входа + 50 символов** (на
SSML-паузы). Считаем по Unicode-символам (не по токенам — для
тестируемости).

- Источник: 1 предложение «батарейка садится, может проц десять
  осталось» = ~50 символов. Допустимый ответ: ≤ 150 символов.
- Источник: 4 предложения (100–200 символов). Допустимый ответ:
  ≤ 450 символов.
- Лимит свыше — обрезаем по последней точке/вопросительному/восклицательному
  в пределах лимита. Если точки нет — обрезаем по границе слова
  (`.rsplit(' ', 1)`).
- Если после обрезки длина > 2× входа + 50 — это **не наша проблема**,
  это детект регрессии пресета: логируем и валим тест
  `test_response_length_cap_<preset>`.

## 3. Инварианты «не добавляй / не задавай / не здоровайся»

Эти 5 пунктов — **must-pass** для каждого пресет-теста. Если любой из
них нарушен хотя бы в одной каверзной фразе (см. §4) — пресет не
принимается.

| #   | Инвариант | Тест-как-ловить |
|-----|-----------|------------------|
| I-1 | **Не здороваться.** В ответе нет «привет», «здравствуйте», «добрый день», «hello», «hi», «доброго времени суток» (в любой падежной форме) | regex `r"\b(привет\|здравствуй\|добр(ый\|рого)\|hello\|hi\b)"` — `assert not re.search(...)` |
| I-2 | **Не прощаться.** Нет «пока», «до свидания», «до встречи», «bye», «goodbye» | regex `r"\b(пока\|до свидания\|до встречи\|bye\|goodbye)"` — `assert not re.search(...)` |
| I-3 | **Не задавать вопросов.** Нет «?» в ответе (формализатор переписывает утверждение, а не спрашивает) | `assert "?" not in output` (для `ru`; для `en` тоже, см. §4) |
| I-4 | **Не добавлять факты.** Все числа / имена / марки / идентификаторы из источника присутствуют в ответе **в неизменном виде**. Никаких новых чисел, имён, оценок, рекомендаций. | Извлечь все числа (`re.findall(r"\b\d[\d.,]*\b")`) и имена собственные (capitalize-токены) из источника, проверить, что они в ответе. Дополнительно: длины ответов **не должны прибавлять** оценок «рекомендую», «советую», «необходимо», «следует», «давайте», «может стоит» — `assert not re.search(r"\b(рекомендую\|советую\|необходимо\|следует\|давайте\|может стоит)\b", output, re.I)` |
| I-5 | **Не обращаться к оператору.** Нет местоимений «вы», «ты», «вас», «тебя», «your», «you» в 2-м лице; нет обращений «товарищ», «коллега», «друг» | regex `r"\b(вы\|вас\|вам\|вами\|ваш\|товарищ\|коллега\|your\|you)\b"` — `assert not re.search(...)`. Исключение: «Ленин»-пресет может использовать «товарищи» **в третьем лице множественного числа как стилистический приём**, но не как обращение к оператору — см. §4, тест 4. |

Существующий код (`master_prompt_compact.txt`, RULE #0 «NO
METALANGUAGE») уже запрещает «Погнали!», «Могу...», «Хочешь ещё?» в
диалоговом LLM; эти 5 инвариантов — **усиленная версия того же
контракта** для формализатора, с проверяемыми regex-паттернами.

## 4. Negative tests (каверзные фразы оператора)

Эти 4 кейса — обязательный минимум регрессии. Backend-разработчик
кладёт каждый как параметризованный тест в
`src/rob_box_voice/test/unit/node/test_quest_llm_formalize.py`.

### Test 1: «приветствие»

**Источник (оператор):** «привет всем, сегодня расскажу про лидар»

**Ожидаемое поведение:**
- В ответе нет «привет», «здравствуйте», «добрый день», «hello», «hi».
- Все значимые слова источника присутствуют: «лидар» (или допустимый
  синоним «LiDAR» — для `ru` режима «лидар» в неизменной форме).
- Ответ начинается с существительного/глагола, а не с обращения.
- ✅ Пример ожидаемого ответа (RU, «Технический»): «Доклад посвящён
  лидару.»
- ❌ Запрещено: «Привет всем! Сегодня я расскажу про лидар.» (I-1:
  поздоровался), «Здравствуйте, коллеги, тема — лидар.» (I-1 + I-5).

### Test 2: «вопрос»

**Источник (оператор):** «а кто-нибудь знает почему у нас два лидара
на роботе?»

**Ожидаемое поведение:**
- В ответе нет «?» (I-3).
- Вопрос переформулирован как утверждение, факт «два лидара»
  сохранён.
- ✅ Пример ожидаемого ответа (RU, «Технический»): «На роботе
  установлены два лидара, назначение которых требует пояснения.»
- ❌ Запрещено: «На роботе два лидара — почему?» (I-3: остался знак
  «?»), «Может быть, стоит уточнить у разработчиков?» (I-4: добавил
  рекомендацию, которой не было).

### Test 3: «команда»

**Источник (оператор):** «едь вперёд и остановись через три метра»

**Ожидаемое поведение:**
- Формализатор не должен ни звать `speak_text` / `move_forward` /
  `stop`, ни комментировать команду — он только переписывает текст.
  (Всё исполнение делает **отдельный** путь в supervisor /
  command_node, не формализатор; этот тест страхует, что LLM
  формализатора не пытается взять на себя функции диалогового
  режима.)
- Все числа/единицы измерения источника сохранены: «три метра» →
  «три метра» (или «3 м» для «Технический», но не «300 сантиметров»).
- В ответе нет «окей», «хорошо», «сделано», «выполнено», «done» —
  формализатор не выдаёт подтверждений, что команда принята.
- ✅ Пример ожидаемого ответа (RU, «Технический»): «Движение
  вперёд на 3 м с последующей остановкой.»
- ❌ Запрещено: «Окей, еду вперёд 3 м.» (I-5: «окей» + добавил
  подтверждение), «Сделано.» (I-4: придумал результат).

### Test 4: «Ленин с товарищами» (специфический для пресета «Ленин»)

**Источник (оператор):** «товарищи, батарейка садится»

**Ожидаемое поведение:**
- Если пресет «Ленин», разрешено использовать слово «товарищи» **как
  стилистический элемент речи** (раннесоветская публицистика),
  но **не как прямое обращение к оператору** — ответ должен быть
  пересказом от третьего лица, а не «обращением к аудитории» от
  лица робота.
- Конкретно: ответ про «батарею» или «заряд», а не «Товарищи!
  Следите за батареей!».
- В ответе нет прямого обращения к оператору на «ты»/«вы» (I-5).
- ✅ Пример ожидаемого ответа (RU, «Ленин»): «Заряд батареи
  расходуется быстрее обычного; положение требует внимания.»
- ❌ Запрещено: «Товарищи! Заряд на исходе!» (I-5: прямое обращение
  + восклицание как манифест), «Товарищ оператор, следи за
  батареей.» (I-5: «товарищ» + «ты»-форма).

### Тестовая матрица

Каждый из 4 тестов прогоняется на матрице:

- Пресеты: `technical`, `lenin` (минимум 2; по требованию заказчика
  можно расширить до всех 6).
- Языки: `ru`, `en`.
- Всего: 4 × 2 × 2 = **16 параметризованных кейсов**.

Для каждого кейса проверяются:

1. Длина ответа ≤ 2 × длина источника + 50.
2. Инварианты I-1..I-5 (см. §3).
3. Отсутствие tool-calls (см. §2.4).
4. Сохранение чисел из источника.
5. Начало ответа — с существительного/глагола, не с обращения.

## 5. Совместимость с существующими prompt-секциями

`src/rob_box_core/rob_box_core/prompt_sections.py` — парсер маркеров
`<<<SKILL-MOVE …>>>` для **диалогового** `master_prompt_compact.txt`.
Он не имеет отношения к формализатору: ни пресеты (`presets/*.txt`),
ни user-message формализатора не должны содержать `<<<`-маркеры.
Если backend-разработчик вставит такой маркер в пресет — это
регрессия, не фича; проверка:

```python
from rob_box_core.prompt_sections import MARKER_PREFIX
for path in presets_dir.glob("*.txt"):
    text = path.read_text(encoding="utf-8")
    assert MARKER_PREFIX not in text, f"{path} содержит <<<...>>> — это маркер диалогового промпта, не пресета"
```

Конфликтов с `master_prompt_compact.txt` (диалоговый промпт) нет:
формализатор идёт через отдельный вызов (§2.1) и грузит ТОЛЬКО
`presets/<key>.txt`. RULE #LANG («говорить по-русски»), RULE #0
(«no metalanguage»), RULE #SEARCH («no hallucinated results»)
диалогового промпта НЕ применяются к формализатору напрямую — но
**содержательно дублируются** в пресетах (правило 1 «Preserve the
operator's meaning», правило 2 «No answering the operator», правило 3
«No invented facts», правило 6 «Language: Russian/English»).

Что **намеренно отличается** от диалогового промпта и не должно
«утечь» в формализатор:

| Фича диалогового LLM | В формализаторе |
|----------------------|-----------------|
| `speak_text(text, animation=...)` tool | **нет tools** вообще |
| `set_voice`, `set_tts_provider` tools | нет |
| `search_web`, `load_skill` tools | нет |
| `speak_text` chunking по 200 символов | один абзац plain text (TTS-чанкование делает существующий пайплайн после формализатора, не LLM) |
| SSML `<break>` / `<prosody>` | нет (пресеты прямо запрещают SSML в ответе) |
| JSON streaming `{"chunk": N, "ssml": ...}` | нет (один `speak_direct(out)` после LLM) |
| `done` terminator | нет (нет цикла) |
| Системный контекст (`<system_context>`, `[TTS]`, `[SEGMENT PLAN]`) | нет (формализатор stateless) |
| История диалога (`history_max_turns=20`) | нет |
| Skills (`<<<SKILL-MOVE>>>`, `load_skill`) | нет |

## 6. Acceptance criteria для PR от backend-разработчика

| #   | Критерий | Проверка |
|-----|----------|----------|
| A1  | `_on_quest_stt` при `voice_input_mode=quest_llm_formalize` вызывает **отдельный** LLM-вызов (§2.1), не `_dispatch_turn` | unit-тест `test_quest_llm_formalize_does_not_call_dispatch_turn` |
| A2  | `temperature=0.4` явно передаётся в LLM-вызов формализатора (не провайдерский default, не YAML-глобальный `temperature` для диалога) | unit-тест `test_formalize_temperature_is_capped_at_0_4` (мокаем LLM и проверяем kwargs) |

## 8. Тестовые ресурсы и e2e-контракт

### 8.1. Unit-тесты

Все 16 кейсов из §4 плюс 8 acceptance из §6 — кладутся в
`src/rob_box_voice/test/unit/node/test_quest_llm_formalize.py`.
Запускается через `pytest -v`.

Тесты используют замоканный LLM (как в `test_quest_stt_source.py`):
backend-разработчик сохраняет в
`src/rob_box_voice/test/unit/node/fixtures/formalize_responses/`
golden-ответы для каждой из 16 пар (preset × language × phrase), чтобы
тест был детерминированным. Без golden-ответов LLM может дать
разные формулировки день ото дня, и тест превратится в лотерею.

### 8.2. e2e (после мержа)

`e2e` блок для карточки backend-разработчика:

```yaml
## e2e
voice_text: "Робот, батарейка садится, может проц десять осталось"
voice_file: .github/e2e/voice_commands/rabot_batareika_saditsya.ogg
volume: 150
record_seconds: 30
llm: minimax-m3
tts: minimax-male-qn-qingse
stt: yandex
```

Супервизор должен быть в режиме `voice_input_mode=quest_llm_formalize`,
пресет `technical`, язык `ru`. Ожидаемо: через ~2-3 секунды после
фразы робот говорит «Батарея разряжается ускоренно, остаточный заряд
около десяти процентов.» (или эквивалент по смыслу).
