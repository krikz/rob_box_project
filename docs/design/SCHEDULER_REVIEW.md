## Summary

**Цель планировщика (по #968 и §1 SCHEDULER_DESIGN):** устранить race между `speak_text` и `stop_music` (регрессы v28–v38, где музыка обрывалась на середине рэпа) и дать роботу возможность **осознанно исполнять** длинные творческие задачи — петь куплет за куплетом, вплетать системные события («батарея садится») в PENDING-сегменты и обрабатывать правки пользователя («и ещё про енота!») без перезапуска и паузы. Целевой сценарий — «комар + енот»: пользователь добавляет тему во время куплета, и второй куплет уже про енота, без секунды тишины.

**Ключевые компоненты (по §2–§10 SCHEDULER_DESIGN):** (1) **Сегментная модель** — задача = набор атомарных сегментов со статусами `PENDING_LIVE/FROZEN → (AWAITING_CONFIRMATION?) → ACTIVE → COMPLETED/CANCELLED/REJECTED/SKIPPED`; инвариант `update()` модифицирует только PENDING/AWAITING, ACTIVE доигрывает. (2) **Каналы** (`voice`, `music`, `anim`, `led/expression`) — каждый = FIFO-очередь + state-машина; каналы независимы, деструктивные операции (`stop_music`, REPLACE) ждут естественной границы voice-канала, конструктивные (`speak_text`, `play_animation`) встают в FIFO без блокировки LLM-цикла. (3) **Быстрый слой `quick_decide`** — в rev. v5 сокращён до правил на шум (IGNORE) + одна основная LLM на всё остальное (отказ от двухуровневой схемы зафиксирован в §4.7 и закрывает #14 Q2). (4) **`SchedulerEventBus`** — единый канал входящих системных событий (`battery_critical`, `obstacle_ahead`, `reflex`, user_input), явно разведён с ADR-0001 `SideEffectBus` (см. §5.5). (5) **Эстиматоры + speculative pre-gen** (`SegmentEstimator`, `LLMEstimator`, runtime-расчёт FROZEN/LIVE через §6.5). (6) **Reflex-слой** (§8.10) — формализация существующего в develop пути `STT → command_parser (regex) → command_node → Nav2` как приоритетного источника в EventBus. (7) **Acceptance tool-calling** (§8) — сегменты с `kind ∈ {nav, mapping, mutate}` проходят через `AWAITING_CONFIRMATION` перед ACTIVE, чтобы пользователь успел подтвердить физическое/деструктивное действие.

**Внешние зависимости:** `dialog_core.py` (точка входа tool-loop, PR #907), `dialogue_node.py` (текущий блокирующий `speak_text` через `_output_lock` + ожидание `tts/finished`), `tts_node.py` (TTS-очередь и публикация `tts/finished`), `command_node.py` + `command_parser.py` (reflex-путь в develop), `mcp_server.py:312–375` (регистр тулов для классификации «требует подтверждения»), `async_executor.py` (`AsyncToolExecutor`, `InterruptibleTask` — переиспользуется для speculative pre-gen), `dialog_harness_node`/`dialog.py:264` (подписка на `/reflex/events`), ADR-0001 §5 (`AgentSession` + `SideEffectBus`, фаза 5 — НЕ пересекается с scheduler'ом). LLM — MiniMax API; в плане latency единственное реальное ограничение — rate limit тарифа MiniMax на concurrent requests (планировщик учитывает).

**Риски (по §10/§13/комментариям):** (R1) **Фактическая ошибка в коде-ссылках документа** (комментарий 17): §3.3, §3.4, §8.2, §9.2, §12 ссылаются на `dialogue_node.py:672–702` и `_output_lock` как на «уже существующий» блокирующий `speak_text`, но файл `dialogue_node.py` сейчас ~578 строк, `_output_lock` в `src/` нигде нет. Реальный код ожидания `tts/finished` — в `core/speak_helpers.py:110–142` (`_tts_events` dict + `register_tts`). Если не поправить — исполнитель не найдёт «уже решённую половину проблемы». (R2) **Рассинхрон документа и e2e v38:** §8.2/§12 утверждают «теперь один speech_id = один finished event» (фикс `f3b58ef1`), но e2e v38 (2026-08-01, ПОСЛЕ фикса) показал **три** `tts/finished` на один `speech_id=6ef1b018` — значит, либо фикс покрыл не все пути публикации (минимум 4 в `tts_node.py`: ошибка, barge-in skip, нормальный, fallback через `current_speech_id`), либо v38 был на промежуточном коммите. Без перепроверки планировщик, построенный на «один finished на заказ», снова поймает debounce-проблему. (R3) **Скрытый риск фазы 1:** §3.3 утверждает, что блокировка «переезжает внутрь voice-канала», но текущая реализация сериализует весь LLM-цикл (см. INSIGHT #10: `speak_text` на T+21.34 → `memory_save` на T+23.72 → LLM продолжила, пока рэп ещё не начал звучать). Перенос lock'а в voice-канал — это пересечение с PR #907 (`dialog_core.py`); дифф больше, чем кажется на первый взгляд. (R4) **Сценарий «комар + енот» зависит от цепочки:** quick_decide (правила+LLM) → EventBus → MERGE в scheduler → trigger «нужен LLM-ход» (§4.5) → continuation-hook. Каждое звено по отдельности валидируется, но цепочка end-to-end нигде не прогонялась на реальных таймингах. Самый дешёвый experiment из INSIGHT #8 — вручную подсунуть `[STATE] voice: speaking, music: playing` в system prompt на финальном ходе рэпа — до сих пор не сделан; его результат валидирует (или опровергает) всю схему feedback events без единой строки кода scheduler'а.

## Open Questions

Ниже — открытые вопросы / противоречия / неоднозначности между issue #968 и `SCHEDULER_DESIGN.md` rev. v5. Большая часть «классических» вопросов из §14 уже закрыта в v5 (Q2 light-LLM, G4 prefetch-budget, Q5 reflex-direction, Q6 reflex-feedback, Q7 reflex+AWAITING); оставшиеся ниже — либо явно адресованы архитектору в §14, либо это новые противоречия, выявленные при сверке документа с issue/комментариями.

### Вопросы, требующие решения архитектора (явно адресованы в §14 SCHEDULER_DESIGN)

1. **Q5.1 (§14 #7, NEW в rev. v5) — как отрендерить вопрос AWAITING_CONFIRMATION во время ACTIVE voice-задачи.** Owner предложил: «робот может вплести вопрос в песню, продолжить петь, а если пользователь скажет „робот подтверждаю" — продолжит петь и поедет». Это шире текущего §8.3. В §14 уже предложены три подварианта для архитектора:
   - **A'1. Inline-merge в TTS** — маркер `kind=awaiting_question` вплетается прямо в SSML, TTS-движок рендерит вопрос частью текущего сегмента. Сложность M (~400 LOC, новая фича TTS-движка), нужен streaming TTS с маркерами.
   - **A'2. Прервать на границе** — на ближайшей границе voice-сегмента вставляется короткий вопрос-плана, потом песня продолжается с того же места. Сложность S–M (~150 LOC, расширение voice-канала).
   - **A'3. Пост-amble «на фоне»** — песня не прерывается; LLM через второй voice-output или ducking-эффект говорит вопрос тише/параллельно. Сложность M (~300 LOC, ducking в `tts_node`/`audio_node`).
   **Блокер:** до решения фаза 1.5 не стартует по сценарию §8.7 #3 («кухня во время песни → MERGE с подтверждением»). Архитектурное решение фиксируется в новом разделе §8.11 (отдельная задача).

2. **Q3 (§14 #3) — владелец ROS-топика `/harness/task_events`.** Отдельный нод или достаточно publisher'а из `dialogue_node`? Явно адресован архитектору (kanban t_8f5bb012 / t_f0ddd678 и др.). Затрагивает наблюдаемость scheduler'а и развязку с `dialogue_node`; влияет на дизайн карточек #1, #3 из `CHILD_TASKS_PROPOSAL.md`.

3. **Q10 (§14 #10) — канал передачи reflex-events в SchedulerEventBus.** ROS-топик `/reflex/events` (стандартный путь, observability, +2–5мс DDS round-trip) или прямой вызов Python (≈ +0.1мс, но требует гарантии общего процесса)? Явно адресован аналитику после старта прототипа фазы 1.5, чтобы измерить фактический latency-бюджет reflex-cancel (< 500мс по §8.10.6). Блокер для карточки #5 из `CHILD_TASKS_PROPOSAL.md`.

### Противоречия и фактические ошибки, найденные при ревью

4. **🔴 Код-ссылки §3.3/§3.4/§8.2/§9.2/§12 на `dialogue_node.py:672–702` не существуют** (комментарий 17, не исправлено в v5). Файл `dialogue_node.py` сейчас ~578 строк, `_output_lock` в `src/` нигде нет. Реальный код — `src/rob_box_voice/rob_box_voice/core/speak_helpers.py:110–142` (`_tts_events` dict + `register_tts` + ожидание finished). Пока ссылки не поправлены, вывод «половина проблемы #968 уже решена» строится на коде, который разработчик не сможет найти. **Рекомендация:** добавить карточку #0 в `CHILD_TASKS_PROPOSAL.md` (30 мин, developer) — поправить ссылки и перепроверить инвариант «один finished на speech_id» на текущем HEAD (см. п.5).

5. **🔴 «Один finished на speech_id» (фикс `f3b58ef1`) не подтверждён на e2e v38** (§8.2/§12 vs INSIGHT #10/комментарий 17). v38 (2026-08-01, ПОСЛЕ фикса) показал три `tts/finished` на один `speech_id=6ef1b018` с разными `duration` (10.72с / 13.92с / 13.32с). Либо фикс не покрыл все пути публикации (минимум 4 в `tts_node.py`), либо v38 был на промежуточном коммите. **Рекомендация:** блокировать старт фазы 1 до перепроверки (быстрый e2e или grep по логам на текущем HEAD). Без этого планировщик, построенный на «один finished на заказ», снова упрётся в ту же debounce-проблему.

6. **🟡 Противоречие «прервать ACTIVE на границе» (issue #968, строка 80) vs «ACTIVE доигрывает до границы» (#968, строка 45).** В аудите #15 уже зафиксировано как П2 и помечено «не блокер, но запутает исполнителя». В v5 SCHEDULER_DESIGN.md формулировка не унифицирована (см. §2.1, §4.3 — оба термина сосуществуют). **Рекомендация:** ввести один термин — `critical` = сокращение ACTIVE-сегмента до ближайшей границы (≤4с) и пропуск остатка — и применить по всему документу.

7. **� Противоречие «speak_text блокируется до tts/finished» (§3.3) vs e2e-тайминг v38 (комментарий 10).** §3.3 говорит «LLM-цикл не двигается, пока TTS не договорит», но лог v38 показывает `speak_text` на T+21.34 и `memory_save` на T+23.72 — LLM продолжила через 2.4с, пока рэп ещё не начал звучать. INSIGHT #12 (научная база) и итоговая модель комментария 13 прямо фиксируют: «тулы работают как прежде — мгновенно, планировщик — буфер между LLM и железом». Сейчас в §3.3 и §4.4 одновременно живут обе формулировки, причём §3.3 — про «блокировку переезжает внутрь voice-канала», а итоговая модель — про «голос = FIFO-очередь, не блокировка». Это **семантически одно и то же** (lock в канале ≈ FIFO), но читается по-разному. **Рекомендация:** в §3.3 явно снять противоречие («блокировка остаётся одна, но живёт ниже по стеку, в канале; LLM-цикл не ждёт её»).

8. **🟡 Пробел: владелец `fade-out` (G1 из аудита #15).** §14 #1 помечает как «закрыт rev. v5: fade-out не нужен, гильотина — ок; `MusicManager.stop_all()` в `src/rob_box_mcp_tools/rob_box_mcp_tools/tools/music.py:621` делает 3-этапную остановку». **Но:** §3.2 и §8 (таблица классификации тулов) для REPLACE-флоу всё ещё описывают «fade-out (300мс)» как ожидаемое поведение (см. сценарий §8.7 #3, edge case «сетевой таймаут» в #968). Решение owner'а противоречит тексту ниже по документу. **Рекомендация:** либо убрать упоминания fade-out из §3.2/§8/§11.2/edge cases, либо явно сказать «fade-out НЕ делается; вместо него — мгновенная гильотина через `MusicManager.stop_all()`, см. §13 G1».

9. **🟡 Неоднозначность «мгновенно» в формулировках (N1/N2 из аудита #15).** Issue #968, строка 3: «LLM вызывает инструменты как пулемёт — всё улетает мгновенно» — это про плохое поведение. Итоговая модель комментария 13: «тулы работают как прежде — мгновенно» — это про целевое поведение. Внешне противоречие, по сути — разные точки в цепочке (от LLM vs на железо). В §0 TL;DR rev. v5 это уже разведено («тулы от LLM идут в scheduler мгновенно, scheduler задерживает деструктивные»), но в §1.1 и §11.1 acceptance по-прежнему используется двусмысленная формулировка «`stop_music` не может исполниться раньше». **Рекомендация:** в §1.1 и §11.1 заменить на «`stop_music` не может ДОЙТИ ДО ЖЕЛЕЗА раньше конца TTS-чанка» — формулировка из N2 аудита, явно точнее.

10. **🟢 Пробел: `estimate_tts_duration` (G5 из аудита #15).** §6.2 говорит «планировщик использует тот же механизм, что и существующий тул `estimate_tts_duration`. LLM НЕ обязана вызывать его руками — планировщик сам считает при создании сегмента». Но в коде v38 LLM **вызывала** `estimate_tts_duration` — а планировщик ещё не существует. После появления scheduler'а тул должен быть либо удалён из публичного registry (LLM больше не должна его звать), либо переведён в «internal» и помечен deprecated. **Рекомендация:** явно зафиксировать в §6.2: тул `estimate_tts_duration` после старта фазы 3 переводится в `internal_only` и убирается из system-prompt'а LLM.

11. **🟢 Edge case: «MERGE во время пред-генерации N+1» (G3 из аудита #15) описан в §6.5 текстом, но нет acceptance-критерия в §11.4.** «MERGE во время пред-генерации → незавершённый синтез отменяется, перезапуск по новому плану. Покрыть unit-тестом» — но в §11.4 acceptance указан только общий «Пред-генерация N+1 отменяется при правке без артефактов». **Рекомендация:** в §11.4 явно добавить: «unit-тест: MERGE во время пред-генерации → отмена в течение < 100мс, новый синтез стартует с нуля».

### Решение блокера П1 (barge-in vs MERGE)

Зафиксировано в §4.4: классификация `MERGE/QUEUE/CLARIFY` НЕ отменяет LLM-цикл, классификация `REPLACE` — отменяет, классификация `IGNORE` — ничего. Это **главный сценарий-разблокировщик** для «комар + енот»; его корректность подтверждена в §13 (аудит П1). Не требует дополнительного решения.
