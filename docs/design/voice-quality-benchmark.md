# Бенчмарк качества голосового диалога

**Статус:** черновик 03.09.2026, к обсуждению с товарищем Шифу.
**Зачем:** сравнивать конфигурации робота (скиллы вкл/выкл, провайдер,
модель, промпт) по ПОВЕДЕНИЮ — цифрой, а не ощущением «вроде получше».

## Проблема, из-за которой это пишется

02.09 попытка сравнить два режима по живому логу провалилась по трём
причинам, и каждая системная:

1. **Лог ротируется.** Прогон со скиллами выключенными выпал из
   `docker logs` через несколько часов. Данных для сравнения больше нет.
2. **Нагрузка несопоставима.** В одном режиме крутился восьмиминутный
   DJ-сет с глубокой историей, в другом — пара реплик. Средний размер
   промпта, число итераций, доля ретраев зависят от того, что человек
   говорил, а не от конфигурации.
3. **Заражение историей.** Один битый ответ модели попал в окно истории и
   размножился на тридцать ходов. Метрика, снятая после этого, меряет
   последствия одного сбоя, а не режим.

Значит: фиксированный набор реплик, чистая память, оба режима, оценка по
заранее написанным правилам.

## Как это делают в серьёзных бенчмарках

Три вещи взяты оттуда, а не выдуманы:

* **Оценка по траектории, а не по словам.** BFCL сверяет фактические
  вызовы функций детерминированным AST-матчером — без LLM-судьи, потому
  что судья дорог и шумен. τ-bench идёт дальше и смотрит на состояние
  системы после разговора: важно, что агент СДЕЛАЛ, а не что сказал.
  У нас та же логика: главный критерий — какие инструменты реально
  вызваны, а красота фразы вторична.
* **Надёжность вместо одного прогона.** τ-bench ввёл `pass^k` — доля
  задач, где успешны ВСЕ k попыток. Агент с 70% успеха на одной попытке
  даёт всего ~34% на трёх подряд. Робот, который «иногда играет бит», —
  сломанный робот, и метрика обязана это показывать.
* **Рубрика с обоснованием для качественной части.** Там, где машиной не
  проверить (уместность, характер), оценка ставится по критериям с
  явными описаниями уровней, и каждая сопровождается ссылкой на
  наблюдаемое в траектории, а не на догадку о намерении модели.

Чего мы НЕ копируем: бинарность BFCL. У них тысячи задач, и градиент
получается агрегацией. У нас два десятка кейсов, и «провалено 3 из 19» не
отличает ход, где робот промолчал, от хода, где он вызвал правильный
инструмент, но заболтал пользователя на три абзаца.

## Шкала: градиент, а не pass/fail

Балл кейса — **0.000 … 1.000**, взвешенная сумма пяти критериев. Веса
живут в `scripts/voice_bench/score.py` и пришпилены тестом
(`test_voice_bench_scoring.py`), поэтому любое изменение шкалы видно
диффом, а не сдвигом всех исторических цифр.

| критерий | вес | 1.0 | частично | 0.0 |
|----------|-----|-----|----------|-----|
| `tool_choice` | 0.45 | вызван ожидаемый инструмент | 0.35 — вызваны только чужие (домен нащупан, действие не то) | ни одного вызова, ответ словами |
| `prohibitions` | 0.15 | запрещённых вызовов нет | −0.5 за каждый запрещённый | два и более |
| `speech_form` | 0.15 | форма в норме | −0.3 длинная речь, −0.6 код в речи, −0.6 вырожденный текст | всё сразу |
| `efficiency` | 0.10 | ≤2 обращения к LLM | 0.7 — три, 0.4 — до пяти | больше пяти |
| `stability` | 0.15 | без ретраев и падений | −0.34 за каждое событие | три и более |

**Почему `tool_choice` весит почти половину.** Именно «просьба о музыке,
отвеченная словами без единого вызова» — дефект, ради которого написан
весь change (`dialog_core.py:681`). Ход без вызова получает 0.55 и не
пройдёт порог, как бы складно робот ни говорил.

**Почему промах в инструменте (0.35) дороже нуля.** Вызвать
`get_music_state` вместо `execute_music_code` — это модель, которая
поняла домен, но выбрала не то действие. Это чинится формулировкой в
скилле; молчание чинится куда сложнее.

**Отдельно от балла — надёжность.** `pass^k` = доля кейсов, где **все**
повторы набрали ≥ 0.8. Средний балл и `pass^k` печатаются рядом: первый
показывает, насколько хорошо, второй — насколько стабильно. Один
удачный прогон из трёх — это не «33% качества», это ненадёжный робот.

**Качественный слой (опционально).** Рубрика 0/1/2 на уместность:
2 — ответ такой, какого ждёшь; 1 — приемлемо, но криво; 0 — неуместно
или выдумано. Ставится человеком или LLM-судьёй, хранится рядом с сырьём.
Уровни 1-2 работают без судьи и уже ловят регрессии; судья нужен, когда
две конфигурации одинаково «зелёные».

## Что НЕ является метрикой качества

- **Размер промпта.** Экономия токенов — побочный эффект. Ход, где робот
  промолчал, дешевле любого правильного.
- **Число вызовов.** Пять вместо одного — это потерянные итерации.
- **Длина сета.** Восемь плохих переходов хуже четырёх хороших.

## Протокол прогона

1. **Чистая память.** Перед прогоном — рестарт ноды: ходы живут в окне
   `DialogCore` (`b5cf5daf`), рестарт их обнуляет.
2. **Один прогон = одна конфигурация.** Меняется ровно один параметр
   (`skills_enabled`, провайдер, модель), остальное заморожено.
3. **k повторов** каждого кейса (по умолчанию 3) — иначе `pass^k`
   бессмыслен.
4. **Сырьё сохраняется целиком:** реплика, `spoken`, вызванные
   инструменты, число обращений к LLM, ретраи, хвост лога хода.
5. Отчёт целиком идёт в карточку (ADR-0018).

## Как запускать

Реплика отправляется в `/voice/stt/result` — тот же топик, куда пишет
`stt_node`, поэтому робот обрабатывает её как обычную речь (wake-word в
тексте обязателен, иначе сработает gate). Ответ и траектория читаются из
лог-файла ноды.

```bash
# 1. чистая память + нужная конфигурация
ssh -J ros2@ros2-katana-gf66-11ud ros2@10.1.1.21
sed -i 's/^    skills_enabled: .*/    skills_enabled: false/' \
    ~/rob_box_project/docker/vision/config/voice_assistant/dialogue_node.yaml
cd ~/rob_box_project/docker/vision && docker compose restart voice-assistant

# 2. прогон (скрипты лежат в смонтированном /config)
docker exec voice-assistant bash -lc \
  "source /ws/install/setup.bash && python3 /config/voice_bench/run_bench.py \
   --cases /config/voice_bench/cases.yaml --out /tmp/bench_off.json \
   --repeat 3 --label 'skills=off'"

# 3. то же со skills_enabled=true -> /tmp/bench_on.json

# 4. сравнение (локально, сырьё забрать через scp)
python scripts/voice_bench/score.py --cases scripts/voice_bench/cases.yaml \
    --run bench_off.json --compare bench_on.json
```

Скрипт прогона НИЧЕГО не оценивает — он собирает сырьё. Баллы ставит
`score.py`, чтобы правила можно было менять и перепроверять задним
числом, не гоняя робота заново.

## Состав набора реплик

`scripts/voice_bench/cases.yaml`, покрывает домены целиком — скиллы делят
каталог по доменам, и регрессия может вылезти в любом:

| домен | кейсов | что проверяется |
|-------|--------|-----------------|
| composer | 3 | просьба сыграть → вызов, а не описание словами |
| player | 2 | «включи трек» → библиотека, а не Renardo |
| dj | 2 | режим включается с планом; `load_track` запрещён |
| navigation | 2 | точка сохраняется/используется, `memory_save` запрещён |
| memory | 2 | факт о человеке → память, а не точка |
| voice-tts | 2 | смена голоса → `set_voice`, а не «хорошо, сменил» |
| knowledge | 2 | вопрос о мире → `search_web` перед ответом |
| core | 2 | время и статус — без выдумывания |
| промах роутера | 2 | формулировка не в лоб → домен всё равно найден |

Последняя строка — самая важная для этого change'а: при промахе
пред-роутера модель обязана дотянуться до домена через `load_skill`, а не
ответить «нет такой функции» (регрессия #1403).

## Связь с задачами change'а

Бенчмарк закрывает 8.3 (e2e сценарии) и 8.5 (регрессия #1403) и делает
осмысленной 5.5 (до/после раскола промпта). Без него «стало лучше»
недоказуемо: живой трафик несопоставим сам с собой.

## Источники

- [BFCL: From Tool Use to Agentic Evaluation of LLMs](https://openreview.net/forum?id=2GmDdhBdDk) — AST-матчинг вызовов вместо судьи.
- [Berkeley Function Calling Leaderboard V4](https://gorilla.cs.berkeley.edu/leaderboard.html) — категории и строгая проверка набора вызовов.
- [τ-bench: A Benchmark for Tool-Agent-User Interaction](https://arxiv.org/abs/2406.12045) — оценка по состоянию после разговора.
- [Tau-Bench Explained: pass^k, Simulated Users, State Grading](https://futureagi.com/blog/tau-bench-explained/) — почему `pass^k`, а не `pass@k`.
- [AI Agent Evaluation (2026): Metrics, Frameworks, and Production Failures](https://www.morphllm.com/ai-agent-evaluation) — рубрики с обоснованием, привязка к наблюдаемой траектории.
