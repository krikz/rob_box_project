# Spec: captain-bridge-supervisor-api

## Purpose

Оператор Meta Quest управляет режимом аватара (off / avatar_present /
teleop_only / voice_only / mixed) и правами (teleop / voice floor) из
3D-панели на слое указателя, не голосовыми командами. Это убирает race
между «поговорить с роботом» и «управлять роботом» — наименьший шаг с
наибольшей отдачей в голосовой ветке (аудит 30.08 §4-bis).

Источник правды — `SupervisorState`, который супервизор публикует в
`/avatar/state` (msgpack: `mode`, `teleop_floor`, `voice_floor`,
`last_event`, `last_event_ts_ms`). До первого `STATE_UPDATE` панель
показывает «неизвестно» и БЛОКИРУЕТ кнопки взятия floor — оператор не
должен слать вслепую.

## ADDED Requirements

### Requirement: 3D-панель управления режимом супервизора

Система MUST отображать в сцене 3D-панель с кнопками режима аватара,
кнопками взятия/отдачи floor и честным тумблером «Диалог робота».

#### Scenario: сцена только что загрузилась, STATE_UPDATE ещё не приходил
- **WHEN** панель супервизора только что создана и подписки ещё не дошли до супервизора
- **THEN** строка состояния показывает «статус: неизвестно»
- **AND** все кнопки взятия floor визуально заблокированы (серый фон)
- **AND** клик по заблокированной кнопке возвращает серверу toast «статус неизвестен, повторите позже»

#### Scenario: смена режима аватара принята сервером
- **WHEN** оператор нажимает «Я оператор» на панели
- **AND** текущий режим `off` (валидный переход off → avatar_present, ADR-0028 §4.2)
- **THEN** клиент отправляет `avatar_set_mode{mode: "avatar_present"}`
- **AND** UI остаётся неизменным до `STATE_UPDATE` от супервизора (подсветка по серверному state, не оптимистически)

#### Scenario: смена режима отклонена локальной FSM
- **WHEN** оператор нажимает «Смешанный» при текущем режиме `off`
- **THEN** UI показывает красный toast «переход off → mixed запрещён FSM супервизора (ADR-0028 §4.2)»
- **AND** серверу НЕ отправляется никакая команда

#### Scenario: сервер отклонил команду (avatar_state_nack)
- **WHEN** приходит `JSON_EVENT{type:"avatar_state_nack", reason:"..."}`
- **THEN** UI показывает красный toast с этим reason (без вранья — текст ошибки пробрасывается as-is)

#### Scenario: отображение фактического состояния (STATE_UPDATE)
- **WHEN** приходит `STATE_UPDATE{mode:..., teleop_floor:..., voice_floor:...}`
- **THEN** панель перерисовывается: активный режим подсвечен зелёным
- **AND** индикаторы floor показывают, кто держит (короткое имя клиента, «у вас» если свой)
- **AND** кнопка «Отдать» активна только если floor удерживается этим клиентом

### Requirement: Тумблер «Диалог робота» честен о зоне действия

Система MUST подсвечивать тумблер «Диалог робота» так, чтобы оператор
понимал: «off» глушит только ReSpeaker (люди рядом), а не Quest-микрофон
(ADR-0028 S5, dialogue_node применяет `voice_input_mode=off` только на
физический канал, не на Quest-канал рации).

#### Scenario: тумблер показывает ВЫКЛ
- **WHEN** state.voice_input_mode == "off" (по последнему voice_mode_ack)
- **THEN** лейбл «Диалог робота: ВЫКЛ», подсказка «Глушит людей рядом (ReSpeaker). Микрофон очков продолжает работать.»

#### Scenario: тумблер показывает ВКЛ
- **WHEN** state.voice_input_mode != "off"
- **THEN** лейбл «Диалог робота: ВКЛ», подсказка «Голос рядом слышим, микрофон очков тоже.»

### Requirement: Кнопки floor шлюют ACQUIRE/RELEASE

Система MUST отправлять `avatar_acquire_floor{kind:teleop|voice}` по клику
на «Взять руль»/«Взять голос» и `avatar_release_floor{kind:teleop|voice}`
по клику на «Отдать руль»/«Отдать голос». Подписи кнопок переключаются по
`STATE_UPDATE` (фактический владелец), не по локальному оптимистичному
state.

#### Scenario: кнопка «Отдать» не активна для чужого floor
- **WHEN** STATE_UPDATE говорит, что teleop_floor.held_by = "tg:42" (Telegram)
- **THEN** кнопка «Отдать руль» визуально неактивна; клик по ней — no-op + игнорируется
- **AND** кнопка «Взять руль» помечена как «у tg:42, занят»

### Requirement: Геометрия панели на −105°, не перекрывает camera_oak_depth

Система MUST располагать 3D-панель на радиусе 2.4 м от оператора, под
углом `−105°` от направления «прямо», чтобы не перекрывать экран-стену
(`camera_rear` на z=-3.9) и не налезать на левую боковую видео-панель
(`camera_oak_depth` на `−75°`). Панель имеет свой отдельный PlaneGeometry,
НЕ участвует в PanelManager (это не видео-панель с потоком).

#### Scenario: панель размещена
- **WHEN** сцена инициализирована
- **THEN** позиция панели `(radius·sin(−105°), 1.45, −radius·cos(−105°))` ≈ `(−2.32, 1.45, 0.62)`
- **AND** радиус горизонтальной проекции = 2.4 ± 1e-6
- **AND** нормаль направлена к началу координат (к оператору)

### Requirement: hitTest — чистая функция, тестируется без Three.js

Система MUST реализовать определение попадания в кнопки через чистую
функцию `hitTest(xNorm, yNorm, layout, canvasW, canvasH) → buttonId | null`
(без зависимости от three.js), чтобы логика покрывалась unit-тестами.
Каждая кнопка панели — отдельный меш, зарегистрированный в PointerSystem
под id с префиксом `sup:`, и raycaster из pointer.ts их ловит «как есть».

#### Scenario: клик внутри кнопки
- **WHEN** `hitTest(0.5, 0.5, layout, 512, 640)` и (0.5, 0.5) попадает в rect кнопки «mode:avatar_present»
- **THEN** возвращает строку `"mode:avatar_present"`

#### Scenario: клик в промежутке
- **WHEN** (xNorm, yNorm) попадает в промежуток между двумя кнопками или вне панели
- **THEN** возвращает `null`

#### Scenario: NaN/Infinity/отрицательные координаты
- **WHEN** `hitTest(NaN, 0.5, ...)` или `hitTest(0.5, Infinity, ...)`, или `hitTest(-0.1, 0.5, ...)`
- **THEN** возвращает `null`, без выброса

### Requirement: Хоткей M на desktop переключает видимость панели

Система MUST по нажатию `M` (или русской `Ь`) на desktop переключать
видимость панели (открыть/закрыть), только когда PIN-overlay уже скрыт и
фокус не в input/textarea. По умолчанию панель НЕ видна — оператор
открывает её сознательно (после `H` для подсказки горячих клавиш).

#### Scenario: M после PIN, фокус на document.body
- **WHEN** оператор нажал M, PIN-overlay скрыт, фокус на document.body
- **THEN** если панель видна → скрылась; иначе — появилась

#### Scenario: M во время ввода PIN
- **WHEN** PIN-overlay ещё видим, оператор вводит PIN
- **THEN** клавиша M обрабатывается в input (не должна была ничего поймать, и не ловит)

## Why

**Панель слева на `−105°` (а не «симметрично боковой видео-панели на
`−75°`»):** авторы карточки выбрали именно отрицательный угол больше 90°,
чтобы панель ушла назад по z (sin(−105°) = sin(−75°) ≈ −2.32 м по x,
но z = +0.62 м против −0.52 у camera_oak_depth — Δz = 1.13 м). Это
by-design: горизонтальная проекция совпадает с x=-2.32, но панель
оказывается позади оператора, вне прямого обзора, и не «светит» в зону
экрана-стены. Проверка корректности — по z-расстоянию (Δz ≥ 1 м), а не
по x.

**Подсветка по серверному state, не оптимистически:** иначе оператор видит
«режим применён», а на самом деле FSM супервизора отказала в переходе
(Phase 1 — `applied=false`); клиент не должен врать. ADR-0018 §1.

**«Диалог ВЫКЛ» не глушит Quest-микрофон:** `voice_input_mode=off` на
`dialogue_node` — параметр ReSpeaker-канала, а не всего голосового
ввода. Без честной подписи оператор думает «робот молчит» и удивляется,
когда grip контроллера продолжает слышаться. ADR-0028 S5.

**Floor-кнопки заблокированы до STATE_UPDATE:** в фазе гонки сервер ещё
не прислал ни одного state, но оператор уже видит панель. Клик
«Взять руль» в этом случае — отправка вслепую, и клиент репортит ack
по факту локальной очереди. ADR-0018 §1: «прогнал — не прогнал» →
«не прогнал», и Шифу это уже откатывал (t_3b9fadc5 — провайдер
re-spawn).

**HitTest — чистая функция, а не часть Three.js:** ADR-0018 и общий
стиль пакета (status_hud.ts, panel_manager.ts, stream_menu.ts): формат
без Three.js, рендер — отдельно. Тогда логика покрывается vitest в
jsdom, без WebGL.
