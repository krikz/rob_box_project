**Ограничения, влияющие на подход:**

1. Диалоговый цикл — самописный (`DialogCore._run_with_tools`), не
   `openai-agents` SDK. Внутри него живут поведения, аналогов которым в SDK
   нет: анти-дубликат речи, гуард галлюцинированных текстов песен (#1708),
   silent-retry на пустой ответ (#1217), переупорядочивание батча
   (`stop_music` последним, W7a).
2. Каталог инструментов уже является SSoT (`rob_box_core.tool_catalog`,
   генерится из классов `MCPTool`, дрейф ловится тестом). Второе объявление
   контракта — то, на чём умер Compositor (`e96b912d`).
3. Голосовой цикл латентно-чувствительный, лимит итераций тул-цикла — 8.
4. Метрик по размеру промпта нет вообще; `LLMResponse.usage` заполняет
   только deepseek, а primary-провайдер — minimax.

## Goals / Non-Goals

**Goals (design-level):**

- Расположение текста скилла определяется одним правилом, общим со снимком
  рантайм-состояния: волатильное — в хвост, к текущему ходу.
- Move A и Move B физически разделены и включаются независимо. Move A не
  трогает `tools=`, поэтому кэшируемый префикс провайдера остаётся целым.
- Скилл — данные, не код: объявление живёт рядом с каталогом, текст — в
  файле, исполняемого кода у скилла нет.

**Non-Goals (design-level):**

- Не вводим иерархию скиллов и наследование фрагментов. Плоский список.
- Не делаем автоматическую нарезку мастер-промпта — раскол §5/§6 по
  скиллам делается руками и ревьюится.
- Не трогаем `command_node` и reflex-путь: они и так работают до LLM.

## Decisions

### 1. Скилл = данные поверх каталога, а не класс с обёртками

Объявление скилла — поле `skill` в записи каталога плюс текстовый файл
фрагмента. Никаких `@function_tool`-обёрток.

*Почему не обёртки:* ровно они убили Compositor. Из commit-сообщения
`e96b912d`: `navigate_to_waypoint` рекламировал `name` вместо `waypoint`,
`move_direction` — `duration` вместо `distance`, 13 тулов не доехали до LLM
вообще, 29 из 38 описаний деградировали до заглушек. Причина — второе
объявление контракта параллельно `execute()`.

### 2. Move A вперёд, Move B за флагом

Разделение не косметическое: Move A аддитивен и обратим, Move B ломает
prefix-cache провайдера и добавляет класс отказа «роутер промахнулся →
LLM не видит нужный инструмент» (регрессия класса #1403).

*Альтернатива — делать сразу оба:* отвергнута. Тогда при регрессии
непонятно, что виновато — расположение текста или урезанный каталог.

### 3. Активация: гибрид детерминированного роутера и модельного вызова

Детерминированный путь переиспользует существующий `CommandParser` (тот же,
что в `command_intent_gate`), модельный — инструмент загрузки скилла.

*Почему модельный путь не «запасной»:* результат вызова приходит
tool-сообщением в самый хвост `messages` — это позиция максимальной
свежести, лучше которой не бывает, и модель действует в том же ходу.
Ранняя версия этого разбора рекомендовала только детерминированный роутер
ради экономии round-trip; под цель «свежесть инструкции» это неверно, и
рекомендация изменена.

*Цена:* один вызов расходует одну из 8 итераций тул-цикла. Для музыкальных
ходов, которые и так многоитерационные, это приемлемо; для однотуловых
ходов детерминированный роутер снимает вопрос.

### 4. `openai-agents` SDK не возвращается на диалоговый путь

В SDK есть ровно те два примитива, к которым пришёл этот дизайн:

```
agents/agent.py:232   instructions: str | Callable[[ctx, agent], MaybeAwaitable[str]]
agents/tool.py:243    is_enabled: bool | Callable[[ctx, agent], MaybeAwaitable[bool]]
```

Это подтверждает развилку A/B — авторы фреймворка разделяют её так же.
Но брать сам SDK означает вернуть `Agent`/`Runner` на диалоговый путь,
то есть откатить `e96b912d` и заново завести обёртки (решение 1), потеряв
поведения из §Context.1. Оба примитива воспроизводятся в `DialogCore`
десятком строк.

*Проверка API из обсуждения:* `SkillRegistry`, `skills.add_public(...)`,
`Agent(skills=..., skill_directory=...)` в SDK **отсутствуют** —
`grep -rl "SkillRegistry" .venv/Lib/site-packages/agents/` пусто, среди
полей `Agent` нет ни `skills`, ни `skill_directory`. Реальная skill-фича
SDK — `ShellToolLocalSkill` / `ShellToolInlineSkill` /
`ShellToolSkillReference` (`agents/tool.py:630-663`): скиллы как **папки со
скриптами**, привязанные к окружению shell-инструмента
(`ShellToolLocalEnvironment(skills=[...])`), то есть модель читает и
запускает их через песочницу. Публичные `docx`/`pdf`/`xlsx` — оттуда.
Нашему кейсу это не подходит: нужен код-сэндбокс, а наши скиллы — это
инструкции плюс подмножество инструментов поверх ROS2-топиков.

*Оговорка о доказательности:* проверялось на `openai-agents 0.9.3` из
локального `.venv`; образ робота ставит `>=0.19.4,<1.0.0`
(`docker/vision/voice_assistant/requirements.txt:92`), то есть **новее**
проверенной копии. Сверить surface 0.19.4 в момент написания не удалось —
нет сети. Перед реализацией задачи 6.1 сверку повторить на версии из
образа; вывод «не возвращаем SDK» от этого не зависит (он держится на
решении 1 и §Context.1), но формулировку про отсутствие `SkillRegistry`
нужно перепроверить.

### 5. `MAPPING_WHITELIST` становится обычным скиллом

Режимное сужение инструментов уже существует (`mapping_state.py:32`,
18 разрешённых из 54), но enforcement стоит на стороне исполнения
(`mcp_server.py:1076`): LLM всё равно видит все 54 и тратит ходы на
заблокированные, получая отказ. При включённом Move B whitelist переезжает
на сторону предъявления, и запрещённое просто перестаёт быть видимым.

*Порядок:* переезд делается только после включения Move B; до этого
whitelist остаётся как есть. Дублировать его в двух местах нельзя.

### 6. Инварианты защищены проверкой, а не соглашением

§1 CORE INVARIANTS и §2 ANTI-DUP (вместе 5 136 токенов) остаются в
системном промпте всегда. Проверка на дублирование правила во фрагменте
скилла — блокер сборки, потому что §2 в мастер-промпте прямо помечен как
единственный канонический контракт («NEVER re-read §2 ANTI-DUP from any
other section»), и его копия в скилле создала бы второй источник правды.

## Risks / Trade-offs

- **Скилл активирован не тот / не активирован вовсе** → при выключенном
  Move B цена ограничена: LLM видит весь каталог и может сработать без
  фрагмента, как сегодня. Это и есть причина, по которой Move B выключен
  по умолчанию.
- **Move B ломает prefix-cache провайдера** → смягчается тем, что скилл
  держится на сессию, а не на ход. Величина эффекта **не измерена**;
  задача 0.x существует именно чтобы измерить до включения.
- **Новая поверхность дрейфа «текст скилла ↔ набор инструментов»** →
  drift-guard блокером в CI (требование в спеке). Сегодняшняя проверка
  покрывает только музыку и только warning'ом.
- **Раскол мастер-промпта — ручная операция** → §5/§6 переносятся отдельным
  коммитом с прогоном e2e голосовых сценариев музыки и навигации до/после.
- **Один инструмент в нескольких скиллах** (`stop_music` в трёх) → описание
  берётся из каталога, поэтому расхождения быть не может по построению.
- **Оценка токенов на клиенте, когда провайдер не отдаёт usage** →
  помечается как оценочная; для сравнения «до/после» этого достаточно,
  для биллинга — нет.

## Migration Plan

1. Задачи фазы 0 (метрики) выкатываются первыми и живут неделю без
   остальных изменений — собираем baseline распределения размера промпта.
2. Move A выкатывается за `skills_enabled` (по умолчанию `false`),
   включается на vision-pi, сравнивается с baseline.
3. Move B выкатывается за `skill_tool_narrowing` (по умолчанию `false`) и
   включается только при подтверждённом выигрыше.
4. Откат любой фазы — снять флаг, рестарт ноды. Схема каталога аддитивна
   (новое необязательное поле), откат кода не требует миграции данных.

## Open Questions

- Гранулярность музыкальных скиллов: `composer` / `dj` / `player` тремя
  отдельными или одним `music` с тремя фрагментами. Решается по данным
  фазы 0 (как часто ходы смешивают домены) и не меняет ни спеку, ни
  разбиение задач.
- Держать ли активный скилл в памяти сессии между ходами или
  переактивировать каждый ход. Обе схемы удовлетворяют спеке; выбор
  влияет на prefix-cache и потому откладывается до фазы 0.
