## 0. Коротко

- **Реалистично.** Навигация HIL (лидар, odom, TF, IMU из Gazebo) почти готова: стартовые скрипты Main Pi
  уже понимают `USE_SIM_TIME`, а Gazebo уже отдаёт `/scan`, `/camera/camera/imu`, `/clock`, odom и TF
  под теми же именами, что на роботе. Не хватает переключателя «робот ↔ HIL» и защиты от двойных издателей.
- **Камеры в Gazebo на роботе нет.** В URDF есть только лидар и IMU. Камеры, которые добавил PR #4333, —
  это обзорные камеры в мире для видео, а не камера робота. RGB-D OAK-D в Gazebo нужно добавить.
- **Три ловушки, без которых HIL не заработает или будет опасен** (все [по коду]):
  1. Zenoh-namespace `robots/$ROBOT_ID`: сим сейчас ходит под `ROBOT_ID=sim`, робот — под `RBXU100001`.
     С разными ID топики друг друга не видят.
  2. `gz_ros2_control` берёт URDF у узла `/robot_state_publisher`. В HIL это узел Main Pi с боевым URDF (VESC),
     а не сим-URDF.
  3. Если `ros2-control` на Main Pi не остановлен, в графе окажутся два `/controller_manager` и два
     `diff_drive_controller` на одном топике команд. Тогда команды пойдут и в Gazebo, и на настоящие моторы.
- **Сеть.** Песочница подключена только по Wi-Fi (5 ГГц, линк 866 Мбит/с, RTT до Pi 2.6–3.6 мс, [измерено]).
  Лидар, odom и TF — это десятки КБ/с. Сырая RGB 1280×720 при 5 Гц даёт ~110 Мбит/с. Поэтому картинку
  передавать только сжатой (~0.8 МБ/с) и распаковывать на Vision Pi.

### 1.3 Переключатель «одной командой» (предложение)

Оверлей compose на каждом Pi плюс скрипт-обёртка. Профили compose здесь не подходят: профиль нельзя снять
с уже запущенного сервиса, а нам нужно менять окружение у живых сервисов.

- `docker/main/docker-compose.hil.yaml`. Для пяти сервисов выше — `USE_SIM_TIME=true` и своя БД rtabmap.
  Для `zenoh-router` — дополнительный listen или connect к песочнице, если нужен (см. §3).
- `docker/vision/docker-compose.hil.yaml`. Для `vision-face` — свой `FACE_STORE_ROOT` (см. §5.3).
  Сервис-распаковщик картинки (§4.2) — под профилем `hil`.
- `scripts/hil/hil.sh on|off|status`. Скрипт берёт замок стенда (flock, как у марафона) и ходит по ssh на Main и Vision.
  - `on`: `stop ros2-control lslidar` → `compose -f base -f hil up -d <5 сервисов>` → на Vision `stop oak-d ceiling-camera` →
    `--profile hil up -d`. В конце проверка: в графе нет ни одного `/controller_manager`, кроме гостя из Gazebo (§5).
  - `off`: `docker compose -f docker-compose.yaml up -d` на Main и Vision. Сервисы пересоздаются с боевым
    окружением, остановленные поднимаются. Это одна команда на хост, и она же совпадает с деплоем
    (`docker/main/update_and_restart.sh:53`). Значит, «вернуть как было» = обычный `up -d`.
  - `status`: кто публикует `/scan`, `/clock`, `/controller_manager`; какой `USE_SIM_TIME` стоит у живых контейнеров.

Риск [по коду]: деплой (`update_and_restart.sh`: `down` → `pull` → `up -d`) посреди HIL поднимет `ros2-control`,
то есть моторы и второй контроллер. Поэтому `hil.sh on` обязан держать замок, а деплой обязан его уважать.
Без этого HIL нельзя оставлять без присмотра.

## 2. Время

### 2.1 Кому sim time

| Где | Узлы | Время | Почему |
|---|---|---|---|
| Песочница | Gazebo, bridge, спаунеры | sim | источник `/clock` |
| Main Pi | robot_state_publisher, twist_mux, imu-filter, rtabmap (+icp_odometry), nav2 (все узлы) | **sim** | замкнутый контур «скан → поза → план → команда»: TF и сообщения в нём с метками Gazebo |
| Main Pi | perception (context_aggregator, mcp_server), teleop | настенное | считают по `time.time()` в момент приёма (`context_aggregator_node.py:345-571`). Метки сообщений им не важны |
| Vision Pi | vision-hailo, vision-face, apriltag | настенное (поддержки sim time нет, [по коду]) | метку кадра они передают дальше из `header.stamp` (`gaze.py:479`), поэтому в Observation придёт sim-метка |
| Sound Pi | голос, диалог, ТАРС, Telegram, quest | настенное | живые люди и облака, sim time им не нужен |

### 2.2 Риски смешанных часов

1. **TF с двумя эпохами** [по коду + по документации tf2]. Sim-метки — секунды с запуска Gazebo (~10²–10⁴ с),
   настенные — ~1.76·10⁹ с. Если хоть один настенный издатель `/tf` останется жив (настоящий diff_drive,
   RSP без `USE_SIM_TIME`), буфер tf2 получит метки из двух эпох. Последствия: в Nav2 и rtabmap —
   `extrapolation into the future/past`, rtabmap теряет одометрию. Отсюда правило: в HIL `/tf` публикуют
   только sim-узлы, и `hil.sh status` это проверяет.
2. **Цель навигации с настенной меткой** [по коду]. `_send_nav_goal` ставит `goal.pose.header.stamp = node.get_clock().now()`
   (`src/rob_box_mcp_tools/rob_box_mcp_tools/tools/navigation.py:96`), а mcp_server живёт на настенном времени.
   Для `frame_id="map"` Nav2 трансформ, скорее всего, не нужен. Для относительного движения `frame_id="base_link"`
   (`navigation.py:360`) Nav2 будет искать TF на момент ~1.76·10⁹ в sim-буфере и, вероятно, отклонит цель
   [догадка про поведение Nav2]. Правка в коде: метка `0` («последний трансформ»). Она нужна и роботу,
   отдельная маленькая PR. Та же проверка нужна для `rob_box_quest/nav2_goal.py`.
3. **Таймауты в настенных секундах.** Таймаут навигации 120 с (`navigation.py:224,283`) считается по настенному времени.
   При RTF < 1 поездка в настенном времени дольше, и диалог скажет «не доехал», хотя Nav2 ещё едет.
   RTF песочницы с камерой не мерили. Без камеры сим и Nav2 там уже гонялись (см. план сима §6).
4. **VisionEvent и Observation на разных часах** [по коду]. `VisionEvent.stamp` = настенное `now()`
   (`vision_hailo_node.py:567`), `Observation.header.stamp` = sim-метка кадра (`vision_hailo_node.py:588`).
   Сегодня у Observation на роботе нет подписчиков: трекер этапа 2 ADR-0130 не подключён ([измерено]: у `/perception/observations` только издатели).
   Поэтому вреда нет. Когда трекер появится, ему нужно одно правило: время наблюдения = `header.stamp`. Так он уже и написан (`tracking/observation_adapter.py:32`).
5. **TF-поиск на Vision Pi.** `observation_frames.lookup_transform` ищет TF на метку кадра с таймаутом
   (`observation_frames.py:24,241`). Кэш tf2 стареет относительно самой новой метки в нём, а не часов узла
   [по документации tf2 BufferCore], поэтому sim-метки должны находиться. Таймаут ожидания отмеряется
   по настенным часам узла, это безвредно. [догадка: на живом графе не проверено]
6. **`/clock` по Wi-Fi.** Частоту публикации `/clock` в Gazebo Fortress (шаг 1 мс) не мерили [догадка: до 1 кГц].
   На каждый sim-узел (в Nav2 их около десятка) это 1000 сообщений/с через Zenoh. Перед шагом 1 нужно
   измерить `ros2 topic hz /clock` на песочнице. Если ~1 кГц — бриджить в `/clock` прореженный поток (100 Гц)
   на стороне песочницы.

### 2.3 Рекомендация

Вариант А (рекомендую): sim time только у пяти контейнеров контура навигации на Main Pi. Vision и Sound
остаются на настенном времени и передают метки кадров как есть. Этот механизм уже есть и покрыт тестом
`tests/unit/docker/test_main_scripts_use_sim_time.py`.

Вариант Б (не рекомендую): всё на настенном времени, а на песочнице переписывать метки бриджа на `now()`.
Минусы: при RTF ≠ 1 физика и метки расходятся, одометрия врёт. Это «синтетическая заплатка», которую ADR-0148 запрещает.

## 3. Транспорт: Gazebo → Zenoh → робот

### 3.1 Сеть [измерено]

- Песочница: только `wlo1 10.1.1.250/24`, 5200 МГц, VHT-MCS9 2×2, 866.7 Мбит/с, сигнал −38 дБм.
  Ethernet в той же сети нет.
- Ping с песочницы: до Main eth0 `10.1.1.10` — 2.06/2.66/3.00 мс, 0 % потерь; до Vision eth0 `10.1.1.11` — 2.42/3.65/10.09 мс.
- Pi видят песочницу через eth0 (метрика 100 против 600 у wlan0, `ip -4 addr`), то есть трафик
  идёт так: песочница Wi-Fi → роутер → провод → Pi.
- `NETWORK_TOPOLOGY.md` §1 требует пускать ROS только по Ethernet. HIL от этого правила отходит: сенсоры
  идут по Wi-Fi песочницы. Межузловой трафик робота (Main ↔ Vision ↔ Sound) остаётся на проводе.
- Реальную полосу Wi-Fi (iperf) не мерили: на песочнице нет `iperf3`, а запускать сервер на роботе я не стал.

**Итог.** Навигация HIL — это ~0.2 МБ/с, Wi-Fi её не замечает. Камеру передавать только сжатой. Сырые
110 Мбит/с по Wi-Fi теоретически пролезут, но потеряют кадры и будут мешать остальному трафику (SSH, Foxglove,
Telegram-бот). Глубину пускать через `compressedDepth`; если и это тяжело — 640×360 для обоих потоков
(разрешения RGB и глубины должны совпадать: `gaze.py` — `STATUS_DEPTH_SIZE_MISMATCH`).

### 3.3 Zenoh-роутер на песочнице

- Сейчас роутер не запущен: на песочнице нет контейнеров сима, есть только образ `eclipse/zenoh:1.6.2` [измерено].
- Роутер сима в `docker/sim/compose.yaml` сознательно изолирован: `network_mode: none`, listen `127.0.0.1`,
  connect в никуда (`compose.yaml:66-75`). Для HIL нужен свой оверлей `docker/sim/compose.hil.yaml`:
  - `network_mode: host`, `ZENOH_LISTEN_IP=10.1.1.250`;
  - `ZENOH_CONNECT_ENDPOINTS=tcp/10.1.1.10:7447,tcp/10.1.1.11:7447`. Как у Sound Pi (ADR-0159 §2.2,
    вариант Б): картинка идёт прямо на Vision Pi, а не транзитом через роутер Main Pi;
  - **`ROBOT_ID=RBXU100001`** у всех сим-сервисов [по коду]: `ros_with_namespace.sh:69` подставляет
    `namespace: "robots/$ROBOT_ID"` в сессию. С `ROBOT_ID=sim` (`compose.yaml:48`) ключи не пересекутся с роботом;
  - сим-сервисы robot-state-publisher, twist-mux, rtabmap, imu-filter, nav2 в HIL **не запускать**: они на роботе.
    На песочнице остаются только `zenoh-router` и `gazebo` (и, на шаге 2, конвертер глубины).
- Роутеры робота слушают `tcp/<eth0>:7447` (`zenoh_router_config.json5`, listen) и принимают входящие
  router-to-router. Менять конфиги роутеров робота не нужно, если песочница сама подключается к ним
  [по коду; на живом графе не проверено]. Gossip у роутера включён, `multihop: false`.
- Версии совпадают: rmw_zenoh 0.1.8 и роутер 1.6.2 на роботе и в сим-образе (`docker/sim/Dockerfile:56-58`,
  `docker/base/Dockerfile.depthai:44-68`) [по коду].
- Без HIL песочница к роботу не подключена. После `hil off` роутер песочницы гасится,
  и робот снова работает сам по себе.

### 4.1 Что ждут vision-hailo и vision-face [по коду + измерено]

- Источник `gaze_source: oak_d` (`docker/vision/config/hailo_models.yaml:54,110`) → `OakDSource` (`gaze.py:382-407`):

  - `/camera/camera/depth/image_rect_raw` — 16UC1 или mono16, мм, **того же размера**, что RGB (`gaze.py:346-359`, size mismatch);
  - `/camera/camera/color/camera_info` — нужна K (`gaze.py:362-376`);

- На роботе [измерено]: 1280×720, 5 Гц (`oak_d_config.yaml:28-56`), K выше, frame `camera_color_optical_frame`.
  Вывести TF лица в `base_link`/`map` можно только при TF `base_link → camera_color_optical_frame`.

## 5. Безопасность

### 5.1 Почему моторы не получат команд

Цепочка на роботе [по коду]: `twist_mux` → `/diff_drive_controller/cmd_vel_unstamped` → `diff_drive_controller` в контейнере
`ros2-control` → VESC по CAN (`privileged`, `/dev`, `CAN_INTERFACE=can0`, `docker/main/docker-compose.yaml:236-264`).
Других путей к моторам в compose Main Pi не видно (сервиса `vesc_nexus` в compose нет; скрипт
`docker/main/scripts/vesc_nexus/start_vesc_nexus.sh` лежит, но его никто не вызывает).

Слои защиты:
1. **Остановить `ros2-control`**: нет процесса — нет кадров в CAN. Это основной слой.
2. **Проверка в `hil.sh on`** перед стартом Gazebo: в графе нет `/controller_manager`; `docker ps` не показывает `ros2-control`.
   После старта Gazebo — ровно один `/controller_manager` (гость), и `ros2 topic info /diff_drive_controller/cmd_vel_unstamped`
   показывает одного подписчика. Если их два — `hil.sh` сразу гасит Gazebo и сообщает.
3. **Опционально `ip link set can0 down`** на Main Pi — физически глушит шину. Это изменение конфигурации хоста,
   поэтому только с «да» Шифу в чате.
4. **Кирпичи**: колёса не касаются пола. Даже если всё остальное откажет, робот не поедет. Это не повод
   пропускать слои 1–3: крутящиеся колёса тоже опасны для рук.
5. Деплой во время HIL поднимает `ros2-control`, см. §1.3. Нужен замок.

### 5.2 Ловушка gz_ros2_control

Плагин `gz_ros2_control` в Humble берёт URDF параметром `robot_description` у узла `robot_state_publisher`
(по умолчанию `robot_param`/`robot_param_node`) [по документации gz_ros2_control]. В HIL под этим именем
живёт RSP Main Pi с боевым URDF, где железо — VESC, а не `GazeboSimSystem`. Варианты:
- в сим-ветке xacro задать `<robot_param_node>` другого узла (например `sim_robot_description`), а на песочнице
  запустить RSP под этим именем с `sim:=true`. Его `/tf` и `/robot_description` переназначить в `/sim/...`,
  чтобы они не попали в граф робота;
- spawn тоже брать с `/sim/robot_description` (`sim.launch.py:86` сейчас `-topic robot_description`).

Joint-имена в обоих URDF одни и те же (sim-добавки внутри `xacro:if`, `rob_box.xacro:16-25`, эталонный тест
`test_xacro_sim_arg.py`). Поэтому `/joint_states` из Gazebo годятся для RSP робота [по коду].

### 5.3 Данные робота

- **Лица**: `vision-face` пишет в `FACE_STORE_ROOT=/data/faces` (живой `.env` Vision Pi [измерено]) в режиме `workshop` —
  эмбеддинги и снимки всех. Фото в Gazebo попадут в боевую галерею и, как с «Деньчиком», отравят её.
  На HIL нужен отдельный `FACE_STORE_ROOT` (например `/data/faces-hil`) через оверлей. Это изменение `.env`/compose хоста — решает Шифу.
- **Карта**: rtabmap пишет в `./maps/rtabmap.db` (`docker/main/docker-compose.yaml:129,185`). В HIL нужна своя БД
  (`database_path` из оверлея). Иначе картография в мире Gazebo перезапишет карту мастерской.
- **Именованные места** для «поезжай на кухню» заданы в координатах карты мастерской. В мире Gazebo нужен свой набор.

в режиме `workshop` [измерено, `.env` Vision Pi]. Боевую `/data` не трогать. В HIL нужна отдельная e2e-БД лиц
(оверлей 2c, §5.3) и отдельная голосовая БД (`speakers.db` в e2e-режиме). Голос живого человека
иначе переименует его боевой профиль (правило «узнан голос + другое имя → переименовать», #4054).
Перед каждым прогоном e2e-БД обнуляются, после прогона — листинг `/data/faces` до и после как доказательство, что боевую не трогали.

**Главная ловушка — привязка имени к лицу идёт через голос** [по коду]. `FaceRecognizer.note_voice_identification`
(`src/rob_box_perception/rob_box_perception/face_recognition.py:922-990`) привязывает имя к лицу, только когда голос
уверенно опознан и в кадре ровно одно лицо. Если голос уже привязан к другому лицу — слияние
пропускается (`_voice_merge_skip_conflict`, `:976-984`). В HIL один живой голос озвучивает всех
виртуальных людей: первое лицо получит имя, остальные — нет. Плюс голосовой профиль будет
переименовываться на каждом «знакомстве». Решения (выбирает Шифу):
- (а) отдельный путь «имя названо в ответ на вопрос робота, в кадре одно лицо → имя этому лицу» без голосовой биометрии.
  Решение в коде (ADR-0148), полезно и вживую: знакомство с человеком, чей голос ещё не узнан;
- (б) по одному живому голосу на каждого виртуального человека (несколько людей в мастерской) — дорого и не масштабируется;
- (в) в HIL отключить голосовое опознание и подставлять «голос» по сценарию — это уже не настоящий голос, против идеи Шифу.
Рекомендую (а). Это отдельная карточка с ADR-уточнением к ADR-0123 §6.

**Что нужно для «найти всех»** — ни одного из этих звеньев на роботе сейчас нет:
1. **Исследование карты.** Пакета frontier-исследования в репо нет [по коду: `explore_lite`/`frontier` не найдены в `src/` и `docker/`].
   Варианты: (а) обход заранее заданных точек обзора (сценарий А + разворот 360° на каждой) — дёшево, работает на шаге 1;
   (б) frontier-исследование (`m-explore`/`explore_lite` на Nav2 + rtabmap в mapping, своя БД) — честное «объедь неизвестный офис».
   Рекомендую начать с (а), (б) — следующим этапом.
2. **Детекция людей.** person (YOLOv8n) и face (RetinaFace) на Vision Pi — есть. На рендере не проверены (§4.3, тест шага 2).
3. **Учёт, кого уже видел.** Нужен трекер этапа 2 ADR-0130 / ADR-0161: треки в `map`, лицо без тела рождает трек.
   Статус [по коду]: ADR-0161 `Proposed`, чистое ядро в PR #4326, ноды ещё нет (`docs/adr/0161-camera-tracker-stage2-frame-and-face-birth.md:5`).
   Сегодня у `/perception/observations` нет подписчиков [измерено]. Без трекера «всех» не посчитать: нужен список
   треков в `map` с отметкой «знаком / не знаком» (лицевая запись с именем). Именно поэтому важно, чтобы TF и `map` в HIL были чистыми (§2.2).
4. **Подъезд к человеку.** Цель Nav2 — точка перед треком в `map` на 1–1.5 м, лицом к человеку. Цель ставит код по треку, не LLM.
   Тула «подъехать к треку N» в v2 нет [по коду: в `MOTION_TOOLS`, `knowledge.py:869`, только `move_direction`/`navigate_to_waypoint`/`navigate_to_coordinates`].
5. **Диалог знакомства.** Поздороваться → спросить имя → распознать имя в ответе (`reply_grammar._introduced`,
   `words.introduced_name` — есть) → привязать к лицу по пункту (а) выше → «приятно познакомиться, Вася» строит код по результату привязки.
6. **Критерий «всех».** Список людей в мире известен из SDF (истина стенда). Робот закончил, когда у каждого
   трека в `map` есть имя или когда исчерпаны точки обзора. Итог («познакомился с 4 из 5, Петю не нашёл») строит код.

Мир: `office` с 5 билбордами (разные фото, согласие, §4.4), часть людей за углом и в отдельной комнате.
Один человек повторно на пути, чтобы проверить «уже знаком — не спрашивает снова».

Как проверять:
- Истина: позы людей из SDF. Ground truth робота — `/sim/ground_truth/odom`.
- По каждому человеку: трек в `map` в ≤ 0.5 м от позы из SDF; подъезд (исход Nav2); `SpeechEvent` приветствия и вопроса;
  ответ STT с именем; запись в e2e-галерее с этим именем (листинг `FACE_STORE_ROOT` HIL до/после); повторная встреча не спрашивает имя.
- Негатив: голосовой профиль живого человека в e2e-`speakers.db` не переименовался в имена виртуальных; `/data/faces` не изменилась.
- Raw: `docker logs` vision-face (сводка `voice_merge_skip_*` и attach), нода трекера, dialog_node; листинги БД.

Готово, когда: 3 прогона, ≥ 4 из 5 знакомств в каждом, ноль записей в боевой `/data`. Иначе честный FAIL с разбором, какое звено не сработало.

Объём [догадка]: трекер-нода (этап 2 ADR-0130, уже в работе) + привязка имени без голоса (~1–1.5 дня) + тул «подъехать к треку» (~1 день) +
обход точек обзора и сценарий знакомства (~2 дня) + e2e-раннер (~1 день). Frontier-исследование — ещё ~2–3 дня. Это отдельный эпик поверх шагов 1–3.

### 8.2 Сеть: провод

Схема 04.11 [измерено координатором]: на песочнице `enp2s0` = `10.1.1.30/32`, маршруты `/32` к `10.1.1.10`, `.11`, `.12`
идут через `enp2s0`, интернет и управление (ssh) остаются на Wi-Fi `10.1.1.250`. Пинг 0.2 мс против 2.3 мс по Wi-Fi, линк 100 Мбит/с.
Маршруты на песочнице я видел сам (`ip route`: `10.1.1.10 dev enp2s0 proto static scope link metric 100`, так же `.11`, `.12`).

| Что | Адрес | Где задаётся |
|---|---|---|
| Роутер песочницы слушает, робот обращается к ней | `10.1.1.30:7447` | `HIL_SANDBOX_IP` (по умолчанию `10.1.1.30`) |
| Песочница подключается к роутерам Pi | `tcp/10.1.1.10:7447`, `tcp/10.1.1.11:7447`, `tcp/10.1.1.12:7447` (eth0 Main, Vision, Sound) | `HIL_ROBOT_ROUTERS` |
| Привязка исходящих линков к проводу | `#iface=enp2s0` в каждом endpoint Zenoh | `HIL_SANDBOX_IFACE` (пусто — без привязки) |
| ssh к песочнице | `ros2@10.1.1.250` (Wi-Fi) | `HIL_SANDBOX_HOST` |

Почему так:
- Подсеть та же `10.1.1.0/24`, отдельная не нужна: у Pi на `eth0` уже маршрут `10.1.1.0/24` с метрикой 100 (у Wi-Fi 600), поэтому
  ответы на `10.1.1.30` уходят с Pi по проводу. Конфиги хостов и роутеров робота не меняются.
- `#iface=enp2s0`: если провод пропадёт, линк Zenoh не поднимется, а не уйдёт молча в Wi-Fi. Синтаксис проверен на zenohd 1.6.2
  на песочнице: роутер с `--connect "tcp/127.0.0.1:7449#iface=lo"` открыл сессию ([измерено]: в `@/local/router` есть `sessions` с линком).
- Камера (шаг 2) на 100 Мбит/с идёт **сжатой**: сырая RGB 1280×720 при 5 Гц — это ~110 Мбит/с (§3.2), больше линка.
  Сжатая (~6.5 Мбит/с) остаётся вариантом по умолчанию и на гигабите.
- Запасной путь по Wi-Fi: `HIL_SANDBOX_IP=10.1.1.250 HIL_SANDBOX_IFACE=`, тогда трафик идёт как в §3.1.

### 8.3 Как сим и робот видят друг друга (Zenoh-namespace)

- Каждая нода кладёт ключи под `robots/$ROBOT_ID/...`: `ros_with_namespace.sh` вписывает `namespace` в session config.
  Обычный сим ходит под `ROBOT_ID=sim` с `network_mode: none`, и это не меняется (`docker/sim/compose.yaml`).
- HIL-оверлей `docker/sim/compose.hil.yaml` ставит `ROBOT_ID=$HIL_ROBOT_ID` роутеру и Gazebo (`hil.sh` берёт его из `.env` Main Pi,
  у робота `RBXU100001`), переводит их в сеть хоста и подключает роутер песочницы к роутерам Pi. Ключи сима и робота оказываются
  в одном пространстве. Остальные сервисы сима (RSP, twist-mux, rtabmap, imu-filter, nav2) уводятся в профиль `sim-only`
  и не стартуют: этот стек работает на роботе.
- Проверено на песочнице [измерено 04.11, 15:53–16:01 UTC, без робота: роутер на `127.0.0.1`, connect в пустой `127.0.0.1:7448`]:
  admin space роутера показывает ключи `robots/RBXU100001/0/clock/...` и `robots/RBXU100001/0/diff_drive_controller/cmd_vel_unstamped/...`.
  Фейковый `/controller_manager` под `ROBOT_ID=sim` сторож не видит, под `RBXU100001` — видит (§8.5).
- `gz_ros2_control` берёт URDF у `/sim/robot_state_publisher`. Это свой RSP с сим-URDF в контейнере gazebo (`sim.launch.py hil:=true`,
  xacro-аргумент `sim_robot_param_node`). Его `/tf` и `/tf_static` переназначены в `/sim/tf*`, spawn берёт `/sim/robot_description`.
  Лог плагина: `robot_param_node is /sim/robot_state_publisher`, затем `System Successfully configured!`. У `/tf_static` нет
  ни одного издателя из сима (`Unknown topic '/tf_static'`), у `/sim/tf_static` — один, `/sim/robot_state_publisher`.
- Main Pi на время HIL (`docker/main/compose.hil.yaml`): `USE_SIM_TIME=true` у robot-state-publisher, twist-mux, rtabmap,
  imu-filter, nav2. Каталог `/maps` в rtabmap и nav2 — это `HIL_MAPS_DIR` (по умолчанию `/home/ros2/rob_box_hil/maps` на Main Pi),
  а не боевой `./maps`. rtabmap стартует в `HIL_RTABMAP_MODE=mapping` с пустой HIL-базой, карта мастерской
  (`docker/main/maps/rtabmap.db`) не открывается. `hil.sh` отказывает ещё до первого ssh, если `HIL_MAPS_DIR` указывает
  на `./maps`, `/maps` или `/data`.
- Голос и Sound Pi в HIL не трогаются: голосовая база меняется так же, как в обычной работе робота. Отдельная `speakers.db`
  нужна сценарию Б (§6.4), а не шагу 1.

### 8.4 Сторож «ровно один /controller_manager»

`docker/sim/hil_run.sh` — команда gazebo в HIL, логика в `rob_box_sim.hil`:
1. `precheck`: в графе должен быть виден `/robot_state_publisher` робота (линк поднят, ID совпадает), а `/controller_manager`
   не должно быть ни одного. Иначе выход 2, Gazebo не стартует.
2. `ros2 launch rob_box_sim sim.launch.py hil:=true`.
3. `watch` каждые 5 с: если `/controller_manager` стало больше одного (поднялся `ros2-control` робота после деплоя или перезагрузки
   Main Pi), launch гасится, контейнер выходит с кодом 3 и сам не поднимается (`restart: "no"`).

`hil.sh on` после старта ждёт, пока сторож увидит ровно один `/controller_manager`. При этом контейнер `ros2-control` на Main Pi
не должен работать, значит единственный контроллер — из Gazebo. Иначе сим гасится, а робот остаётся без моторов до `hil.sh off`.

### 8.5 Что проверено на песочнице (без робота) [измерено 04.11]

Образ `shidi-hil-rob-box-sim:hil` из ветки. Настройки: `HIL_SANDBOX_IP=127.0.0.1`, `HIL_ZENOH_CONNECT=tcp/127.0.0.1:7448` (никуда),
`HIL_GUARD_NO_LINK=1` везде, кроме случаев C и D:

| Случай | Результат |
|---|---|
| Обычный старт | `OK: /controller_manager в графе нет` → `joint_state_broadcaster` и `diff_drive_controller` активны → `/controller_manager: 1` |
| A: фейковый `/controller_manager` под `RBXU100001` до старта | `ОТКАЗ: в графе уже 1 × /controller_manager до старта Gazebo`, `Exited (2)` |
| B: фейковый `/controller_manager` под `RBXU100001` после старта | `НАРУШЕНИЕ: в графе 2 × /controller_manager`, `Exited (3)` через ~2 с |
| Фейк под `ROBOT_ID=sim` | сторож его не видит, Gazebo работает (namespace разделяет) |
| C: `HIL_GUARD_NO_LINK=0`, робота нет | `ОТКАЗ: не видно /robot_state_publisher робота`, `Exited (2)` |
| D: `HIL_GUARD_NO_LINK=0`, фейковый `/robot_state_publisher` под `RBXU100001` | precheck OK, `/controller_manager: 1` |
| `/clock` | `ros2 topic hz /clock --window 2000`: **average rate 999.985** |

`/clock` идёт с частотой 1 кГц, это ~1000 сообщений/с на каждую sim-ноду Main Pi (их ~10). Для провода это мелочь,
а нагрузку на CPU Main Pi не мерили. Если Nav2 или rtabmap на Pi не будут успевать, следующий маленький PR —
прореживание `/clock` до 100 Гц на песочнице.
Робот, `hil.sh on` и `hil.sh off` живьём не запускались: первый запуск делает координатор с Шифу.

### 8.6 Запуск

Один раз на песочнице (чекаут и образ; путь и тег задаются в `HIL_SANDBOX_REPO`, `HIL_SIM_IMAGE`):

```bash
ssh ros2@10.1.1.250
git clone -b develop https://github.com/krikz/rob_box_project ~/rob_box_hil   # или git -C ~/rob_box_hil pull
cd ~/rob_box_hil && docker build -f docker/sim/Dockerfile -t rob_box_sim:hil .
```

С машины оператора (нужны ssh-ключи к `10.1.1.10`, `10.1.1.11`, `10.1.1.250`; пароли не используются):

```bash
scripts/hil/hil.sh status          # что сейчас; на Pi меняет только /tmp/hil/remote_pi.sh
scripts/hil/hil.sh on              # только когда робот на кирпичах!
scripts/hil/hil.sh status          # /controller_manager = 1, ros2-control exited, USE_SIM_TIME=true у пяти
docker logs rob-box-hil-gazebo | grep hil-guard        # на песочнице: лог сторожа
scripts/hil/hil.sh off             # сим гаснет первым, затем compose up -d тех же сервисов, замок снимается
```

Настройки лежат в `scripts/hil/hil.conf`. Их можно переопределить переменной (`HIL_SANDBOX_IP=10.1.1.250 HIL_SANDBOX_IFACE= scripts/hil/hil.sh on`)
или своим файлом (`HIL_CONF=~/my-hil.conf`). Мир задаёт `HIL_SIM_WORLD=polygon`.

Что делает `off`: на Main и Vision выполняется `docker compose -f docker-compose.yaml -f /tmp/hil/<pi>.images.yaml up -d --no-deps --pull never`
для тех же сервисов. Образы закреплены по работающим контейнерам, поэтому `off` не тянет новые теги и не зависит от `IMAGE_TAG`
в окружении. Затем проверка: все сервисы `running`, `USE_SIM_TIME` не `true`. Только после неё снимается замок.

Деплой при включённом HIL падает на шаге «[Main Pi] HIL lock (#4371)» до любых остановок на Pi:
`::error::На Main Pi включён HIL (замок /tmp/hil.lock): HIL on since ...`. Перезагрузка Main Pi стирает `/tmp/hil.lock`, а systemd
поднимает `ros2-control`. Тогда сторож гасит Gazebo (случай B), и робот работает как обычно.

Риски (на живом роботе не проверены):
- `/clock` 1 кГц и нагрузка на CPU Main Pi (§8.5);
- Main Pi передаёт ключи робота в облако (`zenoh.robbox.online`), поэтому топики Gazebo в HIL уйдут туда под ID робота [по коду, роутер Main Pi];
- `off` закрепляет образы по `docker ps` на момент вызова. Если контейнер удалили вручную, его сервис не закрепится, и compose возьмёт тег из `.env`;
- icp_odometry на скане Gazebo 360 лучей против 456 у N10 (§6, шаг 1);
- точки `WaypointStore` заданы под карту мастерской, в мире Gazebo их координаты бессмысленны (§6.4).
