# Живые проверки робота и инфраструктуры

## 1. Назначение

Используйте этот runbook после изменения кода, конфигурации или инфраструктуры.
Он показывает, какие проверки нужно выполнить на реальном оборудовании.
Текст следует правилам ASD-STE100 на русском языке.

Основное правило: автоматические тесты проверяют код. Живая проверка проверяет результат на роботе, колонке или сети.

## 2. Когда нужна живая проверка

Выполните живую проверку для этих изменений:

- запуск, остановка или перезапуск контейнеров;
- поведение ROS-нод и топиков;
- микрофон, динамик, камера, LED-матрица, джойстик или моторы;
- сеть, DNS, WireGuard, Zenoh или реестр образов;
- обновление робота или колонки;
- холодный старт после отключения питания;
- время ответа, звук, анимация или движение;
- исправление дефекта, который был обнаружен на оборудовании.

Для изменения только документации живая проверка не нужна.

## 3. Доказательства

Для каждой проверки приложите к issue или PR:

- commit и тег релиза;
- `run_id` сборки и деплоя;
- дату и время в GMT+1;
- имя робота, колонки или площадки;
- точную команду;
- полный вывод команды или ссылку на лог;
- результат `PASS` или `FAIL`;
- непроверенные условия.

Не закрывайте issue только по результатам unit-тестов.
Не заменяйте отсутствующую проверку фразой «должно работать».

## 5. Речь джойстика #4003

### 5.1 Подготовка

1. Влейте исправление в `develop`.
2. Запустите `L: Build All Services` для `develop`.
3. Запустите `L: Deploy and Verify` с `environment=staging` и `registry_source=local`.
4. Поставьте робота на безопасную площадку.
5. Проверьте, что джойстик подключён.

### 5.2 Проверка

1. Включите ARM один раз.
2. Выключите ARM один раз.
3. Воспроизведите дребезг переключателя.
4. Сохраните логи за весь период:

```bash
ssh ros2@10.1.1.10 "docker logs teleop --since 15m 2>&1 | tail -80"
ssh ros2@10.1.1.22 "docker logs voice-assistant --since 15m 2>&1 | grep -E 'TTS:|tts_node|Моторы' | tail -80"
```

### 5.3 Критерий

`PASS`: одна фраза на ARM и одна на DISARM. Дребезг не даёт дополнительных фраз.
`FAIL`: есть повторная или лишняя фраза. Приложите время и обе строки логов.

## 6. Холодный старт Vision Pi

Холодный старт выполняет оператор физически. Удалённое отключение питания запрещено.

### 6.1 Подготовка

1. Проверьте, что нужные образы уже есть на Vision Pi.
2. Убедитесь, что `ExecStart` содержит `docker compose up -d --pull never`.
3. Попросите оператора выключить и включить питание Vision Pi.
4. Дождитесь загрузки и запуска таймера health-check.

### 6.2 Проверка

```bash
ssh ros2@10.1.1.11 "systemctl show robbox-vision.service -p ExecStart; docker ps --format 'table {{.Names}}\t{{.Status}}'; journalctl -u robbox-vision.service -b --no-pager | tail -80"
```

### 6.3 Критерий

`PASS`: контейнеры запущены. В `ExecStart` нет `compose pull`. В журнале нет ожидания registry.
`FAIL`: стек не запустился или попытался скачать образы. Приложите журнал.

## 7. Полный голосовой марафон

### 7.1 Подготовка

1. Используйте чистый worktree от `origin/develop`.
2. Завершите другие e2e-проверки на роботе.
3. Проверьте, что runner с меткой `e2e` доступен.
4. Проверьте, что робот использует тот же `develop`.
5. Выполните preflight:

```bash
REF=develop TTS_PROVIDER=minimax DRY_RUN=1 bash scripts/e2e/run_night_marathon.sh
```

`PASS` preflight: JSON актуальны, все реплики помещаются в окно VAD.

### 7.2 Запуск

```bash
REF=develop TTS_PROVIDER=minimax bash scripts/e2e/run_night_marathon.sh
```

Запускайте только один марафон на роботе.
Не запускайте параллельную e2e-проверку на том же роботе.

### 7.3 Критерий

Приложите `tests/e2e/_artifacts/night_<UTC>/summary.tsv`.
Приложите run_id и результат каждого акта.
Красный акт остаётся `FAIL` до разбора и нового прогона.

## 8. Chuangong

Текущий режим `observe` подтверждает только обнаружение подписанного релиза.
Он не подтверждает обновление и анимацию.

Перед живой проверкой фазы C:

1. Реализуйте stage, activation, health-check и rollback.
2. Получите разрешение Шифу на фактическое обновление.
3. Проверьте свободное место и наличие предыдущего релиза.
4. Проверьте, что HIL-lock снят.
5. Проверьте, что робот стоит в безопасном месте.

Во время проверки сохраните:

- состояние каждого агента;
- журнал `/var/lib/chuangong/`;
- `run_id` команды обновления;
- список контейнеров до и после;
- видео или наблюдение анимации `biguan`;
- результат `chuguan` или rollback.

`PASS`: новый релиз работает на трёх Pi. Анимация видна весь период переключения. Отдельный сломанный релиз возвращается на предыдущий релиз.
`FAIL`: любой узел не обновился, анимации нет или rollback не сработал. Заведите issue с raw-журналом.

## 9. Колонка

Установку выполняет только Шифу. Координатор готовит тег, релиз и команду.

Пример команды для Шифу:

```bash
curl -fsSL https://raw.githubusercontent.com/krikz/rob_box_station/<TAG>/install.sh | TAG=<TAG> sh -s -- <IP>
```

После закрытия установочной SSH-сессии выполните новое подключение:

```bash
ssh -p 2222 root@<IP> 'cat /data/opt/rbx/VERSION; ps | grep station_host | grep -v grep; tail -40 /tmp/station.log'
```

`PASS`: версия совпадает с тегом. Процесс `station_host.py` работает. Лог содержит `слушаю`.
`FAIL`: процесса нет или версия старая. Приложите установочный лог и `/tmp/station.log`.

## 10. rbt_infra

Выполняйте живые проверки по фазам из `rbt_infra/docs/adr/0001-network-architecture.md`.

Для каждой фазы запишите:

- конфигурационный commit;
- имена площадки и робота;
- результат генерации конфигов;
- `wg show` на хабе и спице;
- ответы DNS;
- маршруты и результаты `ping`;
- SSH или HTTP-проверку разрешённого доступа;
- отдельную проверку запрещённого доступа;
- результат отключения основного хаба при проверке резерва.

`PASS`: выполнены критерии соответствующей фазы ADR.
`FAIL`: любой критерий не подтверждён. Не переходите к следующей фазе.
