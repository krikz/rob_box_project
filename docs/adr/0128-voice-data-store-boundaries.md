# ADR-0128 — Границы БД голосового стека: E2E не боевая, шов не теряет живые факты

**Дата:** 2026-09-22
**Статус:** Accepted — реализовано, юнит-тесты зелёные; e2e-подтверждение на роботе НЕ прогонялось (см. §6)
**Автор:** владелец (через агента) + Claude Code
**Связанные:** issue #2750 (боевую speakers.db обнуляет внешний скрипт), issue #2751 (инвентаризация /data — мёртвые БД, миграция #2000, шов не в ту БД), issue #2000 (миграция voice_memory.db → harness_voice.db, закрыта 15.09.2026 — см. §5), issue #2440 (шов идентичности), ADR-0055 (unify voice memory with harness), ADR-0083 §E (operator_memory.db упразднён)

## 1. Контекст

Инвентаризация `/data` на Vision Pi 22.09.2026 (issue #2751) и разбор трёхкратного обнуления `speakers.db` за 12 часов (issue #2750) вскрыли две независимые, но родственные проблемы: у голосового стека нет границы между «боевыми» данными (живые люди в мастерской) и «тестовыми» (E2E-марафон на том же роботе), и у шва идентичности (issue #2440) нет полной картины того, где физически лежат факты профиля.

### 1.1 Боевую speakers.db чистили руками перед каждым прогоном (issue #2750)

За 12 часов трижды: копия `speakers.db.bak-<UTC>Z` + очистка таблицы `speakers`. Профиль живого человека, зарегистрированный в 10:03:26, стёрт в 10:22:00 — за 13 секунд до старта акта 2 ночного марафона («Знакомство и прогрев голосов»), которому по сценарию нужна пустая база (иначе шаг `n211_who_do_you_know` не проходит детерминированно).

Логика бэкапа+очистки **не найдена ни в одном месте репозитория** — проверено `scripts/e2e/run_night_marathon.sh`, `scripts/e2e/gen_night_marathon.py`, `.github/workflows/scripts/e2e_voice_test.sh`, `e2e_voice_lib.sh`, `.github/workflows/L-E2E Voice Test.yml`, `scripts/agent_flow/*`, а также все ветки, где эти файлы отличаются от develop. Формат имени `.bak-%Y%m%dT%H%M%SZ` не встречается в репозитории вообще.

Подтверждено владельцем в комментарии к issue #2750 (22.09, 07:56 UTC): чистка шла вручную по ssh перед каждым прогоном акта 2, готовя чистую базу для проверки фикса ADR-0127 / PR #2743 —

```bash
TS=$(date -u +%Y%m%dT%H%M%SZ)
docker exec voice-assistant sh -c "cp /data/speakers.db /data/speakers.db.bak-$TS"
docker exec voice-assistant python3 -c "import sqlite3; c=sqlite3.connect('/data/speakers.db'); c.execute('DELETE FROM embeddings'); c.execute('DELETE FROM speakers'); c.commit()"
```

— отсюда и формат имени бэкапа, и синхронность с диспетчеризацией запусков (`gh run list` по workflow `L: E2E Voice Test`, ветка `claude/ci-cd-pipeline-analysis-e9b76c`: пять `workflow_dispatch` в ту же ночь, `...072200Z`=07:22:00Z за 15 секунд до старта run в 07:22:15Z). Мотив был не вредительский — акту 2 нужна пустая база, иначе результат нечитаем — но операция шла поверх БОЕВОГО файла руками, вне кода и вне логов ноды, и один раз (третий эпизод, живой человек) задела реального собеседника. §2 — механизм, который делает ручную команду ненужной: чистую базу гарантирует сам узел, а не дисциплина оператора.

### 1.2 Миграция #2000 объявлена «сделана», но данные текут в старое место (issue #2751)

Проверено напрямую (issue #2751 + повторная read-only проверка в рамках этого PR, 22.09.2026 ~08:00 UTC):

```
harness_voice.db: facts=10, turns=6, MAX(created_at)=2026-09-15 14:18:41
voice_memory.db:  voice_turns=5288, voice_facts=102, MAX(created_at) voice_facts=2026-09-22 07:31:50 (сегодня)
```

`harness_voice.db` перестал получать новые записи **ровно в день закрытия issue #2000** (2026-09-15T18:49:20Z, `stateReason: COMPLETED`). Но это совпадение — не следствие: issue #2000 закрыта не мержем финального PR, а автоматическим `auto-sweep pending stale-candidate` (ADR-0022 GATE-2) — последний человеческий/ботовый комментарий перед закрытием (14:32:20) предупреждал именно о таком автозакрытии за неактивность, `commit_id` события `closed` пуст. По коду миграция объявлена в два шага:

- **Phase 1** (ADR-0055, PR #2049, 07.09.2026) — `dialogue_node.yaml: sqlite_db_path` переведён на `harness_voice.db`; это причина, почему там вообще ЕСТЬ 10 фактов и 6 ходов.
- **Phase 2** (PR #2094, коммит `52eb826a7`, тот же день) — перенос MCP-инструментов (`memory_save`/`memory_search`, `WaypointStore`, `FAQStore`) на ту же БД **явно НЕ выполнен**: обнаружен блокер несовместимых схем (`waypoints`: `name` PK у harness vs `id`+`map_id` FK у `WaypointStore`; `faq_items`: `created_at` без FTS5 у harness vs `indexed_at`+FTS5 у легаси `FAQStore`). Переключатель `MCP_USE_HARNESS_VOICE_MEMORY` (`src/rob_box_mcp_tools/rob_box_mcp_tools/mcp_server.py:160-173`) существует в коде, но нигде не установлен в `1` — ни в `docker/vision/docker-compose.yaml` (там задан только `VOICE_MEMORY_DB_PATH=/data/voice_memory.db`, строка 278), ни где-либо ещё. По умолчанию (`"0"`) `mcp_server.py:1252` инстанцирует легаси `VoiceMemory(db_path=.../voice_memory.db)` — тот самый писатель `voice_turns`/`voice_facts`, растущих сегодня.

Definition of Done issue #2000 («`voice_memory.db` больше не пишется») **не выполнен**. Решение здесь — не «доделать Phase 2» (это отдельная, нетривиальная задача — см. блокер схем выше, коммит `52eb826a7` содержит его полный разбор), а зафиксировать факт: миграция не завершена, автозакрытие ввело в заблуждение, и рекомендовать переоткрыть #2000 (см. §5 — не делается этим PR, только фиксируется в issue-комментарии).

### 1.3 Шов идентичности переносит факты не из той БД (issue #2751 п.2)

`VoiceIdentitySeam.merge()` (`src/rob_box_voice/rob_box_voice/utils/identity_seam.py`) до этого ADR переносил факты только через `merge_speaker_facts()` (`rob_box_harness.memory.base`) — она работает с `MemoryStore`, которым конструктор шва получал `SQLiteVoiceMemory(db_path=memory_db_path)`, а `memory_db_path` (`speaker_id_node.yaml:16`) — это `/data/harness_voice.db`. Живые пользовательские факты («не ест лук», «пьёт чай без сахара» — 102 строки, из них у 98 `speaker_id IS NULL` из-за регрессии issue #2747, но 4 строки привязаны к конкретным спикерам) лежат в СОВСЕМ другой таблице другого файла: `voice_facts` в `voice_memory.db` (писатель — MCP-инструмент `memory_save`, §1.2). Склейка двух профилей одного человека (`/voice/speaker/merge`) переносила бы 10 устаревших harness-фактов и молча теряла бы facts из `voice_facts` — именно те 1-4 строки, которые реально привязаны к сливаемому голосу.

## 2. Решение — issue #2750: явный переключатель БД, а не тайная чистка

`speaker_id_node` получает новую тему `/voice/speaker/e2e_mode` (JSON `{"enabled": true|false}` или голый текст `"true"`/`"false"` — тот же приём, что уже принимает `_on_register_request`, чтобы `ros2 topic pub` со стороны ssh не требовал экранирования JSON через три слоя оболочек). Обработчик `_on_e2e_mode_request` (`speaker_id_node.py`) переключает активное соединение `self._db` между двумя ROS-параметрами:

- `db_path` (боевая, дефолт `/data/speakers.db`, без изменений) — используется всегда, пока явно не попросили иначе;
- `e2e_db_path` (новый параметр, дефолт `/data/speakers.e2e.db`) — открывается ТОЛЬКО по явному сообщению в топик.

Переключение — не `ros2 param set`: `db_path` читается один раз в `__init__` (это открытие sqlite-соединения, а не что-то, перечитываемое на лету), так что только код узла умеет менять активную БД. Каждое переключение логируется на уровне **WARNING** (не info) — именно то, чего не хватало в issue #2750: смена БД дикторов теперь физически не может остаться незамеченной в `docker logs voice-assistant`.

**Чистоту E2E-базы гарантирует сам узел, а не вызывающий код.** Ручная ssh-команда (§1.1) существовала именно потому, что акту 2 нужна ГАРАНТИРОВАННО пустая база — простое «открыть другой файл» этого не даёт: если `e2e_db_path` копит профили от марафона к марафону, оператор рано или поздно вернётся к `DELETE FROM` по боевой, потому что «переключатель есть, а чистой базы всё равно нет». Поэтому каждое включение (`enabled: true`) сначала удаляет `e2e_db_path` целиком (и `-wal`/`-shm`/`-journal`) — `_wipe_e2e_db_file()` в `speaker_id_node.py` — и только потом открывает файл заново (пустая схема создаётся автоматически первым же `SpeakerDatabase.__init__`). Путь для удаления — константа узла (`self._e2e_db_path`), не значение из топика: сообщением нельзя попросить стереть что-то ещё.

Владелец топика — `.github/workflows/scripts/e2e_voice_test.sh`: перед сценарием `night_marathon_act2_acquaintance_*` публикует `enabled: true`, в `trap ... EXIT` (гарантированно, что бы ни случилось со сценарием) публикует `enabled: false`. Боевая `speakers.db` при этом физически не открывается на запись ни на секунду.

Почему не «поднять свежий контейнер под E2E» или «монтировать другой volume»: E2E и мастерская делят один физический робот прямо сейчас (issue #2750 писан на живом инциденте во время идущего марафона) — решение обязано работать без перезапуска контейнера (см. общее ограничение задачи — на роботе только чтение, а перезапуск контейнера — тем более не то, что можно сделать втихую посередине рабочего дня оператора).

## 3. Решение — issue #2751 п.2: шов переносит факты из ОБОИХ писателей

`VoiceIdentitySeam.__init__` получает необязательный `legacy_facts_db_path`. Если задан, `merge()` после переноса harness-фактов дополнительно вызывает `merge_legacy_voice_facts()` (новый модуль `utils/legacy_voice_facts.py`) — прямой `UPDATE voice_facts SET speaker_id = <dst> WHERE speaker_id = <src>` по файлу `voice_memory.db`. Это намеренно НЕ переиспользует `merge_speaker_facts()`: та модель (`scope`/`key`, конфликт ключей → выигрывает dst) не соответствует `voice_facts` — там нет понятия «ключ», это плоская последовательность фактов без уникальности, поэтому перенос — простое переприсвоение владельца строки.

`speaker_id_node.py` получает параметр `voice_facts_db_path` (дефолт `/data/voice_memory.db`) и передаёт его в `VoiceIdentitySeam` при склейке (`_merge_identity_async`). `facts_moved` в ack `/voice/speaker/result` теперь — сумма по обоим писателям.

Не сделано (осознанно, вне рамок этого ADR): сама миграция #2000 Phase 2 (объединение схем `waypoints`/`faq_items`) — блокер задокументирован в коммите `52eb826a7` и требует отдельного, более крупного решения (schema-reconciling адаптер, как `WaypointAdapter` для `waypoints`, только для конфликтующих таблиц). Это решение здесь — не обход миграции, а страховка на время, пока обе БД остаются живыми: `voice_facts` и `harness_voice.db` продолжат существовать параллельно до тех пор, пока #2000 не будет доведена (или переоткрыта и закрыта заново честно).

## 4. Уборка мёртвых БД (issue #2751 п.3)

`scripts/maintenance/cleanup_dead_voice_dbs.sh` — dry-run по умолчанию, `--apply` только у человека на роботе (агент этот скрипт не запускал). Шесть файлов:

- `memory.db`, `rob_box_voice.db`, `voice_assistant.db`, `waypoints.db`, `voice.db` — 0 байт, удаляются напрямую после повторной проверки размера (защита от «issue писался неделю назад, могло измениться»).
- `operator_memory.db` (+ `-shm`/`-wal`) — НЕ 0 байт, но код признаёт его упразднённым явным текстом (`supervisor_node.py:173`, ADR-0083 §E: «`/data/operator_memory.db` упразднён», оба агента делят `harness_voice.db` через колонку `agent`) — архивируется в `_archive_2751/`, не удаляется: архивная копия дешевле ошибки.

`speakers.db.bak-*` (issue #2750) в уборку не входит. Уточнение из того же комментария владельца (§1.1): 44 профиля в самом старом бэкапе (`...20260921T224624Z`) — в основном мусор от предыдущих E2E-прогонов (синтетические голоса актов, а не живые люди с февраля), так что восстановление всех 44 не предполагается требованием; какие строки там всё же живые (если есть) и что с ними делать — решение владельца, не блокирует этот PR.

**`voice.db` (пересоздан 22.09 01:32) — причина не найдена.** Проверено: контейнеры `voice-assistant`/`avatar-supervisor` перезапущены 22.09 06:41:33Z — ПОЗЖЕ создания файла, то есть не текущий процесс. Ни одно место в репозитории не конструирует путь `/data/voice.db` буквально (единственный дефолт с похожим именем — `SQLiteVoiceMemory(db_path="~/.rob_box/voice.db")`, `sqlite_voice.py:129` — резолвится в `/root/.rob_box/voice.db` внутри контейнера, другой каталог, не бинд-маунт `/data`). Наиболее вероятная (но НЕ подтверждённая логами) гипотеза — разовая ручная команда с относительным путём и `cwd=/data` (`sqlite3.connect('voice.db')` создаёт файл самим фактом открытия соединения) в духе того же паттерна, что объясняет §1.1. Честно зафиксировано как нерешённое.

## 5. Про issue #2000

Этим ADR/PR #2000 **не переоткрывается** — по инструкции задачи решение остаётся за владельцем. Рекомендация зафиксирована здесь и продублирована комментарием в #2000 и #2751: закрытие было автоматическим (ADR-0022 GATE-2 stale-sweep), а не подтверждением выполнения; Definition of Done не выполнен (`voice_memory.db` продолжает быть основным писателем MCP-инструментов). Реальный объём оставшейся работы — Phase 2 из коммита `52eb826a7`, не тривиальный однострочник.

## 6. Проверка

Юнит-тесты (без ROS/резэмблизера — тот же приём, что в существующих тестах модуля):

- `src/rob_box_voice/test/unit/utils/test_legacy_voice_facts.py` — прямой перенос строк `voice_facts` (перенос, отсутствие таблицы/файла — не ошибка, no-op для равных/пустых id).
- `src/rob_box_voice/test/test_identity_seam.py::test_voice_seam_merge_also_moves_legacy_voice_facts` — `merge()` с обоими писателями сразу (воспроизводит пропорцию замера issue #2751: 1 harness-факт + 2 живых).
- `src/rob_box_voice/test/test_identity_seam.py::test_voice_seam_merge_without_legacy_path_stays_backward_compatible` — старый акцептанс-тест issue #2440 не ломается без `legacy_facts_db_path`.
- `src/rob_box_voice/test/unit/node/test_e2e_db_isolation.py` — `_on_e2e_mode_request`: боевая БД не открывается на запись, пока включён e2e-режим; регистрации во время e2e-режима не попадают в боевую и наоборот; **включение стирает профиль, оставшийся от прошлого марафона** (`test_enable_wipes_leftover_e2e_file_from_previous_marathon` — прямая проверка гарантии из §2); идемпотентность повторного `enabled: true`; plain-text `"true"`/`"false"`.
- `src/rob_box_voice/test/test_yaml_param_consistency.py` — новые ключи YAML (`voice_facts_db_path`, `e2e_db_path`) объявлены в `declare_parameter` (обе конфигурации, src и docker).

**Чего нет:** e2e-подтверждение на роботе (акт 2 марафона с реально включённым `e2e_mode` и не тронутой боевой `speakers.db`) — не прогонялось, репозиторий сейчас read-only для агента, а робот занят идущим марафоном. Метку `e2e-done` не ставить.
