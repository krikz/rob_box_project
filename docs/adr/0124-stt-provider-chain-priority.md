# ADR-0124 — Приоритет и фолбек STT-провайдеров: `minimax → yandex → vosk` (заменяет ADR-0091 §2.2, §2.3, §5)

**Дата:** 2026-09-21
**Статус:** Accepted — реализовано и проверено на роботе 21.09.2026 (PR #2706 wiring, PR #2708 классификация отказов; подтверждение — §4.5)
**Автор:** владелец + Claude Code
**Заменяет:** ADR-0091 §2.2 (порядок `vosk → minimax → yandex`), §2.3 (`stt_chain.yaml` как конфиг цепочки), §5 спеки `stt-provider-contract.md`
**Связанные:** issue [#2365](https://github.com/krikz/rob_box_project/issues/2365) (Phase 2 wiring, карточка `t_99e504d2`), ADR-0091 (контракт MiniMax STT), ADR-0108 (empty-text семантика MiniMax), issue #1083 (цепочка TTS), issue #1082 (`HealthCache` для LLM), issue #1229 (`/voice/tts/provider_state`), issue #1252 / #1734 (дублирование конфига), issue #1004 (`declare_parameter` как SSoT), issue #2702 (общий health-кэш облаков)

## 1. Контекст

ADR-0091 принял MiniMax STT как третьего провайдера и зафиксировал Phase 1 (адаптер `MiniMaxSTTProvider`) и Phase 2 (подключение в цепочку). Phase 1 уехал в develop ещё 14.09 (PR #2369, #2427, #2537), Phase 2 не начинался: `stt_node._recognize_with_fallback` до сегодняшнего дня собирал ровно два провайдера, `yandex → vosk`, а `config/stt_chain.yaml` был документацией, которую не читал никто — включая ноду.

То есть у нас был готовый, оттестированный и полностью выключенный провайдер.

ADR-0091 §2.2 предлагал порядок `vosk → minimax → yandex`: офлайн вперёд ради latency barge-in. Владелец 21.09.2026 решил иначе — `minimax → yandex → vosk`, и это решение фиксирует настоящий ADR. Причины:

- **Качество важнее 0.5 секунды.** Vosk small-ru-0.22 на нашем железе регулярно отдаёт мусор («а», «не»), и `select_recognition` его же отбрасывает как `low_confidence` — то есть «Vosk первым» на практике означало бы «заплатить Vosk-проход, выбросить результат и всё равно пойти в облако». Экономии нет, есть лишний шаг.
- **Однородность с остальным стеком.** TTS ходит `minimax → yandex → silero` (issue #1083), LLM — `deepseek → minimax` с `HealthCache` (issue #1082). Третья доменная модель приоритетов, в которой локальный провайдер первый, а облачные — фолбек, заставляла бы оператора держать в голове два разных правила для одного и того же робота.
- **Vosk — последний рубеж, а не первый эшелон.** Его ценность в том, что он работает без сети и без денег на счету. Это свойство фолбека.

Что при этом выяснилось и чего ADR-0091 не предусматривал:

1. **Бюджет был один на всю цепочку.** `select_recognition(timeout_s=, max_retries=)` давал повторы только `providers[0]`, а таймаут — общий. С тремя провайдерами это неверно: у MiniMax свои 5с, у Yandex — 12с (issue #1477), Vosk офлайновый и таймаут ему не нужен.
2. **Не было кэша «мёртвых».** 21.09 у нас одновременно лежали MiniMax и Yandex — не пополнен баланс. Без кэша нода на **каждой** фразе честно ждёт оба облака по таймауту, прежде чем дойти до Vosk. У TTS (issue #1083) и LLM (issue #1082) такой кэш есть с августа; у STT его не было.
3. **Провайдер отправлял headerless PCM под видом WAV.** Phase 1 клал сырые байты цепочки в поле `file` с именем `audio.wav` и типом `audio/wav`. Пока провайдер стоял вне цепочки, это ничего не стоило; при включении — MiniMax не смог бы узнать sample rate.
4. **`recognize()` глушит ошибки в `None`.** Для кэша «мёртвых» это фатально: «кончились деньги» (лежит 5 минут) и «моргнула сеть» (лежит 30 секунд) выглядят одинаково — как тишина.

## 2. Решение

### 2.1 Порядок цепочки

```
minimax → yandex → vosk
```

Порядок задаётся ROS-параметром `stt_provider_chain` и нормализуется в `STTNode._normalize_provider_chain` по тем же инвариантам, что и цепочка TTS (issue #1083):

| Инвариант | Поведение |
|---|---|
| только известные провайдеры | `minimax`, `yandex`, `vosk`; прочее — warning и выброс |
| без дубликатов | сохраняется позиция первого вхождения |
| **`vosk` всегда последний** | указан в середине — переносится в конец; не указан — дописывается |
| пустая/битая цепочка | дефолт `[minimax, yandex, vosk]` |
| ровно `[vosk]` | легитимный офлайн-режим, не трогаем |

Инвариант «vosk всегда последний» — прямой аналог «silero всегда последний» в `tts_node`. Оператор не должен иметь возможности конфигом сделать робота глухим при мёртвой сети.

### 2.2 Per-provider бюджет

`ProviderPolicy(timeout_s, max_retries, retry_backoff_s)` — по одному на провайдера, передаётся в `select_recognition(policies=...)`:

| Провайдер | timeout | retries | почему |
|---|---|---|---|
| minimax | 5.0с | 1 | стоит первым, не должен съедать бюджет фразы, если облако тупит |
| yandex | 12.0с | 1 | issue #1477 — фразы 4–6с с pre-roll выходят за 5с deadline |
| vosk | ≥10с | 0 | офлайн, холодный прогон на Pi ~2–4с; повтор мусора даст тот же мусор |

Провайдер без явной политики живёт по старому правилу (общий `timeout_s`, повторы только первому) — обратная совместимость для существующих тестов и вызовов.

### 2.3 Кэш «мёртвых» провайдеров

`ProviderDeadCache` в `stt_fallback.py` — тот же паттерн, что `tts_node._provider_dead_until` (issue #1083) и `rob_box_harness.health.HealthCache` (issue #1082):

| Класс отказа | Пример | TTL |
|---|---|---|
| квота / ключ | HTTP 401/403/429, gRPC `UNAUTHENTICATED` / `RESOURCE_EXHAUSTED` | `provider_dead_ttl_s` = 300с |
| транзиентный | сеть, 5xx, таймаут, `DEADLINE_EXCEEDED` | `provider_dead_ttl_transient_s` = 30с |

Правила:

- Провайдер в кэше пропускается, и пропуск виден в логе попыток как `reason="dead"` — оператор читает причину в той же строке `stt_attempt`, а не гадает, куда делся MiniMax.
- Успешное распознавание снимает отметку (баланс пополнили — провайдер вернулся в строй).
- `empty` и `low_confidence` **не** помечают мёртвым: облако ответило, просто нечего сказать. Мёртвым делают только `timeout` и `error`.
- Квота не ретраится внутри попытки: повтор вернёт ровно то же самое.
- **Если мёртвыми оказались все — кэш игнорируется** и цепочка идёт целиком. Глухой робот хуже медленного.

Кэш персистится в `provider_state_file` (`/data/stt_provider_state.json`) в том же формате `{"provider": ..., "dead_providers": {name: epoch_ts}}`, что и у TTS. voice-assistant перезапускается часто (#2676 — OOM и каскадные рестарты), и без персистентности каждый рестарт снова платил бы полный таймаут мёртвому облаку.

### 2.4 Типизация отказов

Новые исключения в `stt_fallback`: `STTAuthError` (ключ), `STTQuotaError` (деньги/квота) — рядом с существующим `STTTimeoutError`. Маппинг:

| Источник | Условие | Исключение | TTL |
|---|---|---|---|
| MiniMax | `MiniMaxSTTAuthError` (401/403) | `STTAuthError` | длинный |
| MiniMax | `MiniMaxSTTRateLimitError` (429) | `STTQuotaError` | длинный |
| MiniMax | `MiniMaxSTTUnavailableError`, текст `timeout:` | `STTTimeoutError` | короткий |
| Yandex | `UNAUTHENTICATED` / `PERMISSION_DENIED` | `STTAuthError` | длинный |
| Yandex | `RESOURCE_EXHAUSTED` | `STTQuotaError` | длинный |
| Yandex | `DEADLINE_EXCEEDED` | `STTTimeoutError` | короткий |

`stt_node._recognize_minimax` ходит в `provider.transcribe()`, а не в `provider.recognize()`, именно ради этого: `recognize()` по контракту Phase 1 глушит всё в `None`, а `None` неотличим от тишины. Сам `recognize()` не меняется — он остаётся публичным контрактом Protocol'а и семантикой ADR-0108.

### 2.5 Видимость фактического провайдера — лог и файл, без нового топика

Фактический провайдер (первый живой в цепочке, а не номинальный из параметра) фиксируется при **смене** — на старте и когда цепочка сползла на другой провайдер, не на каждую фразу:

```
🎧 STT provider → 'vosk' (chain=['minimax', 'yandex', 'vosk'],
   dead={'minimax': 287.4, 'yandex': 291.1}, reason=recognize, last_attempt=vosk)
```

плюс запись в `provider_state_file`, которую можно прочитать снаружи:

```json
{"provider": "vosk", "dead_providers": {"minimax": 1758413100.0, "yandex": 1758413104.0}}
```

**Топика `/voice/stt/provider_state` мы НЕ заводим.** У TTS аналогичный топик оправдан — у него четыре потребителя (mcp_server, dialogue_node, quest_node, supervisor). У STT потребителя нет ни одного, а топик без потребителя — ровно то, что ловит сторож issue #2118 (ADR-0021 policy), и заносить в его baseline свой же свежий шов было бы обходом собственного правила. Появится потребитель (например, оператор через mcp-инструмент «кто тебя сейчас слышит») — топик добавляется одной строкой рядом с логом, формат payload уже описан выше.

### 2.6 Конфиг цепочки — ROS-параметры, а не `stt_chain.yaml`

ADR-0091 §2.3 требовал отдельный файл `src/rob_box_voice/config/stt_chain.yaml` с hot-reload по таймеру. **Отменяем.** Файл удалён, вся конфигурация — через `declare_parameter` + `stt_node.yaml`.

Причина прямая: второй YAML-источник для того же значения уже дважды стоил нам инцидента. `wake_words` жили в семи местах и разошлись на три разных списка (#1252); `barge_in_policy` продублировали — получили #1734. Issue #1004 после этого зафиксировал правило: ключ существует, только если он объявлен через `declare_parameter`, а YAML ноды — его единственное зеркало. `stt_chain.yaml` был ровно заготовкой третьего такого инцидента: он уже врал (говорил `enabled: false` и `vosk → minimax → yandex`), и никто этого не замечал, потому что его никто не читал.

Hot-reload цепочки тоже отменяется: ROS-параметры и так меняются на лету, отдельный таймер перечитывания файла не нужен.

## 3. Рассмотренные альтернативы

### A. Оставить порядок ADR-0091 (`vosk → minimax → yandex`)

Отклонено владельцем. Мотив ADR-0091 — latency barge-in — на нашем качестве Vosk не окупается: его результат в большинстве случаев всё равно отбрасывается как `low_confidence`, и мы платим лишний проход. Плюс расхождение с моделью приоритетов TTS и LLM.

### B. Подключить MiniMax, но без кэша «мёртвых» (минимальный wiring)

Отклонено. Именно этот вариант мы бы и увидели сегодня в бою: на пустом балансе обоих облаков робот отвечал бы через 1–2 минуты (ровно симптом issue #2702 в TTS-домене). Кэш — не «дополнительная фича», а условие, при котором цепочка из трёх провайдеров вообще пригодна к эксплуатации.

### C. Сразу переиспользовать `rob_box_harness.health.HealthCache` (общий кэш для LLM/TTS/STT)

Отложено, это issue #2702. `HealthCache` тянет `rob_box_llm` и `httpx`, а `stt_fallback.py` намеренно stdlib-only — на этом держится его тестируемость без ROS. Формат персистентности (`dead_providers: {name: epoch_ts}`) выбран **идентичным** TTS-овскому, чтобы объединение свелось к смене пути, а не к миграции данных.

### D. Публиковать `/voice/stt/segments` и диаризацию MiniMax в этом же ADR

Отложено. ADR-0091 §2.4 описывает топик, но у него до сих пор нет потребителя, а `speaker_id_node` работает с d-vector, а не с cluster id. Сначала — работающая цепочка и фолбек; диаризация — отдельной карточкой после накопления логов (issue #2348).

### E. Включать MiniMax флагом `minimax_stt_enabled=false` по умолчанию (как предлагал ADR-0091 §2.2 «до parity-прогона»)

Отклонено. Провайдер выключается сам, если нет `MINIMAX_API_KEY` — это уже достаточный предохранитель, и он честнее: цепочка деградирует ровно там, где у неё нет ключа. Дефолт `false` означал бы, что после мержа на роботе не изменится ничего и мы снова получим «готовый выключенный провайдер», как после Phase 1.

## 4. Последствия

### 4.1 Положительные

- MiniMax STT наконец в строю — Phase 2 закрыта.
- При мёртвых облаках робот платит за них **один раз** за TTL, а не на каждой фразе.
- Рестарт ноды не сбрасывает знание о лежащем облаке.
- На вопрос «кто сейчас слушает» отвечает одна строка лога при смене провайдера + `provider_state_file`.
- Одна модель приоритетов на три домена (STT/TTS/LLM) вместо двух разных.
- Побочно: `select_recognition` упала по цикломатике с 18 до 6 (ADR-0021), разложена на `_classify_attempt` / `_policy_for` / `_live_providers` / `_run_provider`; параметры цепочки вынесены из `__init__` в `_init_provider_chain_params`, чтобы `__init__` остался в бюджете 20.
- Побочно: исправлена отправка headerless PCM под видом WAV (§1 п.3).

### 4.2 Отрицательные / риски

| Риск | Mitigation |
|---|---|
| Облачный провайдер первым = платим за каждую фразу | Кэш «мёртвых» + `minimax_stt_enabled`; при пустом балансе цепочка сама сходит на Vosk и держится там |
| +0.5–1с latency в среднем случае по сравнению с Vosk-first | Осознанный размен на качество (§1); если barge-in пострадает — порядок меняется одним параметром, без кода |
| Провайдер «ожил», но ответил мусором | `empty`/`low_confidence` не снимают и не ставят отметку — цепочка просто идёт дальше |
| Квота кончилась в середине TTL-окна «живой» | Реактивный путь: первая же 429 помечает мёртвым, как в TTS |
| Кэш пережил пополнение баланса и держит провайдера мёртвым до 5 минут | Приемлемо; оператор может удалить `provider_state_file` или подождать TTL |
| `stt_chain.yaml` удалён, а на него ссылаются README/CHANGELOG/ADR-0091 | Ссылки обновлены в этом же PR |

### 4.3 Нейтральные

- Контракт `/voice/stt/result` (plain text) **не меняется** — инвариант P0 (ADR-0001).
- `/voice/stt/speaker` не меняется.
- `MiniMaxSTTProvider.recognize()` и семантика ADR-0108 не меняются.
- Старый вызов `select_recognition` без `policies`/`dead_cache` работает ровно как раньше.

## 4.4 Что показал живой прогон 21.09.2026 (Vision Pi)

Цепочка поехала и Vosk отвечает, но первый же прогон вскрыл, что **классификация отказа по HTTP-статусу недостаточна**.

Проба `/v1/speech_to_text` прямо из контейнера при непродлённой подписке:

```
HTTP_STATUS: 500
BODY: {"type":"error","error":{"type":"server_error",
       "message":"your current token plan not support model, asr-1.0 (2061)",
       "http_code":"500"}}
```

То есть MiniMax сообщает про **план** через HTTP 500, а про исчерпанную квоту — через HTTP 200 с `base_resp.status_code=2056` (этот конверт уже разбирает `rob_box_llm.providers.minimax_tts`). Оба случая попадали в `MiniMaxSTTUnavailableError` → транзиентный TTL 30с вместо 300с. В логе это выглядело как `dead={'minimax': 11.3}`, и робот переспрашивал облако каждые полминуты, платя ~1.6с на фразу (две попытки).

**Решение:** `_raise_for_http_status` сначала разбирает **тело** (`_body_error_message`, оба конверта) и сверяет сообщение с `QUOTA_HINTS` (`2056`/`2061`/`1008`/`token plan`/`usage limit`/`insufficient balance`/`not support model`) — зеркало `rob_box_harness.health.QUOTA_EXHAUSTED_HINTS`. Совпало → `MiniMaxSTTRateLimitError` → `STTQuotaError` → длинный TTL и без повтора.

Второе, что вскрылось: у Yandex в метрике стояло голое `reason=error` за 50мс и **ни одной** строки `grpc error`. Причина — `except grpc.RpcError` обёрнут вокруг вызова `RecognizeStreaming()`, который лишь открывает стрим; реальная ошибка прилетает при **итерации** по `responses`, а цикл обёрнут не был (это поведение старше ADR-0124). Код статуса не доходил ни до лога, ни до кэша. Цикл обёрнут, ошибка идёт через `_map_grpc_error`.

Настоящая причина отказа Yandex STT на роботе — **не деньги и не сеть, а закрытая папка Yandex Cloud**:

```
GRPC_CODE: StatusCode.PERMISSION_DENIED
GRPC_DETAILS: Permission to [resource-manager.folder b1gfmjogjodcgff82pjd,
  resource-manager.cloud b1g1s54gba2kdlp4fune,
  organization-manager.organization bpf691j509jibhoolgu1] denied
```

Это та самая папка `b1gfmjogjodcgff82pjd`, которую ADR-0091 §1 уже называл «в архиве». `PERMISSION_DENIED` → `STTAuthError` → длинный TTL: архивная папка не откроется за 30 секунд.

> **Поправка к первой редакции этого раздела.** Первый пробник 21.09 вернул `UNAVAILABLE ... ipv6:[2a0d:d6c1:0:1c::27b]:443: Network is unreachable`, и §4.4 сначала утверждал, что причина — отсутствие IPv6-маршрута. Это было разовое срабатывание gRPC-резолвера: он пробовал IPv6 и не доходил до сервера вообще. После редеплоя тот же пробник соединяется за ~1с и получает чистый `PERMISSION_DENIED`. IPv6 чинить не нужно — нужно восстановить доступ к папке (или завести новую и обновить `YANDEX_API_KEY`).
>
> Мораль для отладки: по одному пробнику нельзя объявлять корневую причину, если ошибка сетевого уровня могла замаскировать прикладную. Отсюда же ценность пункта «третье» ниже — с `error=` в логе этот разбор виден без походов на робота.

Асимметрия, замеченная попутно: `tts_node` на тот же `PERMISSION_DENIED` ставит Yandex мёртвым на **30с** (транзиентная классификация), STT — на 300с (auth). Права на архивную папку за 30с не появятся, так что STT здесь корректнее; выравнивание — в issue #2702 вместе с объединением кэшей.

Третье: `log_attempts` печатал `reason=error`, но **выбрасывал** `STTAttempt.error`, хотя строка уже лежала в объекте. Именно поэтому, чтобы узнать, что ответили облака, пришлось лезть на робота двумя пробниками. Теперь `error=` печатается в метрике попытки.

## 4.5 Подтверждение после редеплоя (Vision Pi, 21.09.2026)

Все три правки из §4.4 проверены на живом роботе, и заодно — главный сценарий ADR: **провайдер вернулся сам, без рестарта ноды**.

TTL стал длинным там, где должен:

```
🎧 STT provider → 'vosk' (chain=['minimax','yandex','vosk'],
   dead={'minimax': 293.5, 'yandex': 294.5}, reason=recognize, last_attempt=vosk)
```

Причина отказа теперь читается прямо из лога, без походов на робота пробниками:

```
[stt_attempt_metric] provider=minimax reason=error latency_ms=1334 attempt=0 text=-
  error='STTQuotaError('minimax STT: minimax API error: your current token plan
  not support model, asr-1.0 (2061)')'
[stt_attempt_metric] provider=yandex reason=error latency_ms=1026 attempt=0 text=-
  error='STTAuthError('Yandex STT auth failure: StatusCode.PERMISSION_DENIED ...')'
```

Повтора у MiniMax на квоте больше нет — одна попытка вместо двух (`attempt=0` и сразу следующий провайдер).

Затем владелец включил подписку MiniMax **в середине сессии**, ничего не перезапуская:

```
17:01  minimax reason=error   STTQuotaError(... asr-1.0 (2061))
17:01  minimax reason=dead    dead 293s more
17:02  minimax reason=dead    dead 279s more
       ... TTL истёк, провайдер переспрошен ...
17:10  minimax reason=ok      latency_ms=3093  'Робокс, расскажи, ник дот?'
17:11  minimax reason=ok      latency_ms=3159  'Робот, расскажи анекдот.'
```

Файл состояния вернулся в `{"provider": "minimax", "dead_providers": {}}` — отметку снял первый же успешный ответ (§2.3, «успешное распознавание снимает отметку»). Цепочка снова останавливается на первом провайдере.

Два наблюдения на будущее:

* **Latency MiniMax ~3.1с** против ~1.5–2.2с у Vosk, при бюджете `minimax_stt_timeout_s=5.0`. Запас ~1.9с; на длинных фразах (в логах были 6–7-секундные) есть риск упереться в таймаут и заплатить 5с прежде чем уйти дальше. Признак — `minimax:timeout` в логе; лечится параметром, без пересборки.
* **MiniMax отдаёт текст с заглавной буквы и пунктуацией** («Робот, расскажи анекдот.»), в отличие от Vosk. Wake-роутер это переживает — проверено: `🎯 Wake word detected: "Робот, расскажи анекдот."`, `strip_wake_word` дал `расскажи анекдот.`.

## 6. Границы решения

**Не входит в ADR-0124:**

- Диаризация MiniMax и `/voice/stt/segments` — остаётся в ADR-0091 §2.4, реализации нет.
- Топик `/voice/stt/provider_state` — до появления первого потребителя (§2.5).
- `STTResult` / `recognize_result()` из ADR-0091 §2.1 — не понадобились для цепочки, откладываются до диаризации.
- Объединение health-кэшей STT/TTS/LLM — issue #2702.
- Ре-калибровка порогов speaker-id — issue #2348.
- Закрытая папка Yandex Cloud `b1gfmjogjodcgff82pjd` (`PERMISSION_DENIED`) — организационная проблема, не код; отдельная карточка (§4.4).
- e2e-сценарий на фолбек STT — отдельная карточка после мержа.
- Изменение формата `/voice/stt/result` — ЗАПРЕЩЕНО (инвариант P0).

## 8. Поправка 23.09.2026 — `yandex → minimax → vosk` (issue #2866)

Товарищ Шифу пополнил счёт Yandex SpeechKit и решил поставить Yandex primary. Порядок §2.1 меняется на:

```
yandex → minimax → vosk
```

Инварианты §2.1 (vosk всегда последний, дедуп, выброс неизвестных) и механика §2.2–§2.5 не меняются — меняется только значение `stt_provider_chain` в обоих `stt_node.yaml` и `DEFAULT_STT_PROVIDER_CHAIN` в `stt_node.py` (пустая/битая цепочка теперь сводится к `[yandex, minimax, vosk]`). Согласованность YAML↔код сверяет `test_yaml_param_consistency.py::test_stt_provider_chain_matches_code_default`.

Мотив из E2E (акт 2, run 35886659057): `minimax:timeout(8328ms)->minimax:ok(3010ms)` — фраза ждала ~12 с. Yandex в том же прогоне отвечал (`empty`, без auth-ошибки), то есть `PERMISSION_DENIED` из §4.4/§6 на тот момент не воспроизводился. Качество Yandex vs MiniMax на ru-RU по накопленным логам **не измерялось** — это решение владельца, а не результат сравнения (§7, последний пункт, остаётся открытым).

**`provider_state_file` старый порядок не «залипает».** Файл хранит только `dead_providers` (wall-clock срок) и информационное поле `provider`; порядок цепочки в нём не пишется и при старте берётся из ROS-параметра. Единственный эффект — если в файле на момент деплоя лежит ещё не истёкшая отметка `yandex` (permanent-лестница #2767 даёт до 1800 с), нода пропустит Yandex до её истечения и будет слушать MiniMax. Счётчик лестницы (`_permanent_streak`) не персистится, поэтому после рестарта первая же новая отметка снова 300 с, а первый успех Yandex снимает её (`mark_alive`).
