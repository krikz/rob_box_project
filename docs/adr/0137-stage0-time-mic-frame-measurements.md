## 2. Решение

### 2.1 Общее время: chrony, Main Pi — сервер (Q14)

**Топология.**

```
  интернет-NTP (ru.pool.ntp.org ×3, pool.ntp.org)
        │  (только абсолютное время)
        ▼
  Main Pi chronyd ── allow 10.1.1.0/24, local stratum 10
        │  eth0 10.1.1.10, провод
        ▼
  Vision Pi chronyd ── server 10.1.1.10 iburst prefer minpoll 2 maxpoll 4   (внешних пулов нет)
```

- **Почему chrony, а не timesyncd.** `systemd-timesyncd` — только SNTP-клиент: не умеет быть сервером для второго Pi и не даёт оценку offset/погрешности к источнику. chrony — полноценный NTP клиент+сервер, `chronyc sources/tracking` дают offset и ошибку в микросекундах — это и есть метрика.
- **Внешний NTP.** Main Pi берёт внешние пулы (те же, что в `sync_time.sh`: из сети 10.1.1.x отвечают). Vision Pi — **только** Main Pi: межпайное расхождение не должно зависеть от интернета. Если интернета нет, Main Pi продолжает раздавать своё время (`local stratum 10`): абсолютное время уплывает, **общее** — нет. Для §2.5/§2.9 важно общее.
- **Адрес сервера — `10.1.1.10` (eth0), не `10.1.1.20`.** `10.1.1.20` — Wi-Fi Main Pi (им пользуется `L-Architecture Audit` для SSH). Время по Wi-Fi дало бы джиттер в единицы–десятки мс и нарушило бы ADR-0130 §2.11 («восприятие не должно зависеть от Wi-Fi»). Провод `10.1.1.10` — тот же путь, по которому идут Наблюдения через Zenoh (F3). Переопределяется `--server`.
- **Хост, не контейнер.** Системные часы — общие для ядра; менять их из контейнера можно только с `CAP_SYS_TIME` (фактически привилегированный контейнер ради одного демона). Сейчас время ведёт хостовый timesyncd — chrony встаёт на его место. `docker-compose`/Dockerfile не трогаются.
- **Два демона — конфликт.** `setup_chrony.sh` ставит chrony и выключает `systemd-timesyncd` (`systemctl disable --now`), если unit остался. В Ubuntu пакет `chrony` объявляет `Conflicts: time-daemon`, а `systemd-timesyncd` — `Provides: time-daemon`, поэтому apt сам удаляет timesyncd (проверено `apt-cache show chrony` в песочнице Ubuntu 24.04; на Pi не проверено). `timedatectl set-ntp true` после этого управляет `chrony.service` (`/usr/lib/systemd/ntp-units.d/50-chrony.list`).
- **Параметры клиента.** `minpoll 2 maxpoll 4` (опрос 4–16 с) — по LAN дёшево и быстро ловит дрейф после прогрева/нагрузки. `makestep 1.0 3` — шаг часов только в первые 3 обновления (дальше — плавная подстройка, без прыжков времени под ROS). После настройки скрипт делает `chronyc waitsync` и `chronyc makestep`.

**Метрика (этап 0).** Снимается `chronyc -n -c sources` (CSV): у выбранного источника (`^*`) берутся адрес, скорректированный offset и оценка ошибки; рядом печатается сырой `chronyc tracking` / `chronyc sources`. Итог — одна строка для grep:

```
chrony_check role=vision source=10.1.1.10 offset_ms=0.012 error_ms=0.200 max_ms=5 verdict=PASS
```

Правило вердикта: **vision** — FAIL (код 2), если нет выбранного источника, источник ≠ Main Pi, или |offset| > 5 мс; **main** — FAIL, только если в конфиге нет `allow` (не раздаёт время); отсутствие внешнего источника у Main Pi — WARN, не FAIL (межпайное время от этого не страдает). chronyd не отвечает — код 3.

**Решение: где читается метрика.** На этапе 0 — **только** `setup_chrony.sh --check` (вручную и из деплоя через `sync_time.sh`, §2.5). ROS-метрики и нового топика нет.

| Вариант | Решение | Почему |
|---|---|---|
| `setup_chrony.sh --check` (raw-строка, код выхода) | **принят** | потребителя метрики ещё нет; проверка нужна человеку и деплою, не ноде |
| Метрика в `/perception/health` | отвергнут **на этапе 0** | новый шов без потребителя (сторож `seam_without_consumer`); появится вместе с потребителем — трекером этапа 2, который отбрасывает поздние улики (`evidence_late_dropped`, ADR-0130 §2.5) |
| Экспортер chrony → Prometheus (`10.1.1.249`) | отвергнут **на этапе 0** | новый контейнер/сервис = правка compose, запрещённая этапу 0 |

> **Отклонение от родителя, требует подтверждения Шифу.** ADR-0130 §2.11 пишет «метрика в Prometheus». Этап 0 её **не даёт** — сознательно, по договорённости с оркестратором (не плодить метрики до появления потребителя). Предложение: Prometheus-метрика расхождения — в дочернем ADR этапа 1 или 2, когда появится её читатель.

### 2.2 Фрейм микрофонного массива в URDF

- Имя: **`mic_array_link`**, `fixed`-joint `mic_array_joint` к **`base_link`** (на чём физически стоит ReSpeaker — не задокументировано, F4; все сенсоры в URDF висят на `base_link`).
- Положение — xacro-свойства `mic_array_xyz` / `mic_array_rpy` в шапке `rob_box.xacro`. Со слов владельца (28.09.2026): «на высоте лидара, чуть левее, почти симметрично потолочной камере» → `xyz = -0.1707 -0.06 0.4765` (z лидара, x лидара и потолочной камеры; потолочная камера стоит на y=+0.065, «левее» трактовано как «слева при взгляде на робота спереди», то есть правый борт, y<0), `rpy = 0 0 0`. Рулеткой не измерено, знак y требует подтверждения — но на азимут DOA он не влияет: `yaw` и знак отсчёта всё равно калибруются замером (§2.3).
- Фрейм без меша и инерции (как `camera_*_frame`): это точка отсчёта азимута, не тело.
- **Договорённость об ориентации:** `Z` — вверх; ось `X` фрейма — направление, в котором прошивка отдаёт `DOAANGLE = 0°`. Тогда азимут в `base_link` = `yaw(mic_array_link) + sign · DOA`, где `sign = +1`, если прошивка считает против часовой (как REP-103), и `−1`, если по часовой. `yaw` и `sign` — результат замера §2.3 (`measure_doa.py summary` печатает `bearing = offset + (sign)·doa`); `offset` записывается в `mic_array_rpy` (yaw), `sign` — в дочерний ADR этапа 5 как параметр потребителя. Переворачивать фрейм (`roll = π`) ради знака не предлагается: неочевидно для читателя URDF.
- Зачем точный `xyz`, а не только `yaw`: смещение массива от `base_link` на 10 см даёт до ~6° ошибки азимута на человека в 1 м — сопоставимо с допуском 15°. Замер DOA (§2.3) от этого не зависит (углы ставятся от центра массива), а этап 5 — зависит. Поэтому `xyz` — открытый вопрос в.1, блокирующий этап 5, но не этап 0.

### 2.3 Методика замера DOA (Q17)

**Предусловие (блокер).** `/audio/direction` должен реально публиковаться: `ros2 topic hz /audio/direction` ≈ 10 Гц. По коду сейчас — 0 Гц (F5). Нужен отдельный малый PR: `audio_node.py:1035` `get_direction()` → `get_doa()` + тест, который не подменяет отсутствующий метод `MagicMock`'ом (например, `MagicMock(spec=ReSpeakerInterface)`). В этот PR фикс **не включён**: этап 0 по ADR-0013 — измерения, а правка голосовой ноды — отдельный баг со своим issue/e2e. Пока фикс не влит, `measure_doa.py measure` честно падает с кодом 3 через 10 с («ни одного `/audio/direction`»).

**Постановка.**

1. Тихая комната; робот молчит (нет TTS/музыки/SuperCollider — иначе `audio_node` гейтит VAD, F6).
2. Вокруг **центра массива** (отвес на пол) — метки на расстоянии 1.5 м через 45°: 0° — вперёд по `X base_link`, против часовой положительно (REP-103). Погрешность разметки ±2–3° — записать.
3. Источник: человек стоя (или колонка на ~1.2 м — записать высоту: у плоского массива точность падает с углом места; человек 1.6 м на 1.5 м от массива на 0.57 м — это ≈ 35° над плоскостью).
4. На каждом из **8 углов — 3 фразы** (≈ 2–3 с каждая, пауза > 1 с между ними) → **24 замера**; минимум для вердикта — 20 замеров по ≥ 4 углам, включая 0/90/180/270.

**Что такое замер.** Одна VAD-фраза. DOA копится **только пока VAD = True** (последний фронт `/audio/vad`), первые 0.3 с после фронта отбрасываются (оценка сходится), фразы короче 3 отсчётов — в брак (с подсчётом). Оценка замера — круговое среднее отсчётов фразы. Ошибка — круговая (`359° vs 1°` = 2°, не 358°).

**Конвенция 0°/знака** неизвестна (F7), поэтому `summary` по умолчанию подбирает `offset ∈ [0,360)` (шаг 1°) и `sign ∈ {+1,−1}` по минимуму суммы квадратов ошибки. Подгонка 2 параметров на тех же ≥ 20 замерах слегка занижает ошибку — это принимается; если конвенция уже известна, `--offset/--sign` её фиксируют.

**Вердикт (Q17):**

| Условие | Вердикт | Что это значит для этапа 5 |
|---|---|---|
| ≥ 20 замеров, ≥ 4 угла, **p95 \|ошибки замера\| ≤ 15°** | «≤15°: DOA годится для выбора говорящего трека (ADR-0130 §2.9)» | DOA выбирает говорящий трек |
| то же, p95 > 15° | «>15°: только повернуться на звук» | говорящий — как сейчас; ADR-0130 §8 п.4 (уточнение поворотом) — решается по этим цифрам |
| данных меньше | «НЕДОСТАТОЧНО ДАННЫХ …», код 2 | вердикта нет |

p95 (а не среднее) выбран как консервативный: на 20–30 замерах это «второй-третий худший». p50, max и p95 по отдельным отсчётам печатаются справочно.

**Инструмент:** `scripts/maintenance/measure_doa.py` (`measure` — rclpy, в контейнере `voice-assistant` на Vision Pi; `summary` — без ROS). Новых топиков/нод не создаёт — только подписывается на существующие.

### 2.4 Методика замера загрузки (Q13, этап 8)

**Инструмент:** `scripts/maintenance/measure_load.sh` на хосте каждого Pi: каждые 5 с (по умолчанию 120 с) — `host_cpu_pct` (`/proc/stat`), `load1`, температура SoC, `docker stats --no-stream` по контейнерам (CPU%: 100 = одно ядро; память), и один снимок NPU. В конце — сводка mean/max.

**Сценарии** (по 10 мин, `--duration 600`, на обоих Pi одновременно): (A) робот стоит, всё запущено, людей нет; (B) диалог голосом + человек в кадре (лицо/Hailo работают); (C) навигация (RTAB-Map + Nav2 на Main Pi). Сверка — cadvisor в Grafana за тот же интервал (F9).

**CPU vs load.** В ADR-0130 §1.3 — `load ≈ 6.5` на Main Pi. load average считает и ожидание I/O, поэтому для бюджета основной — `host_cpu_pct`; `load1` пишется для сопоставимости с §1.3.

**NPU (Hailo-8).** `hailortcli` в контейнерах нет (F8); скрипт ищет его на хосте, затем в `vision-hailo`, и берёт сырой 5-секундный снимок `hailortcli monitor` в файл (не разбирая). Данные в `monitor` появляются, только если процесс инференса запущен с `HAILO_MONITOR=1` — в `docker/vision/docker-compose.yaml` этого нет, а compose этапу 0 трогать нельзя. **Ожидаемый честный результат этапа 0: «NPU metric unavailable»** (или пустой снимок). Прокси-метрики (FPS/латентность инференса в логах `vision-hailo`) — справочно. Для этапа 8 нужен отдельный шаг: `HAILO_MONITOR=1` + общий `/tmp/hmon_files` у `vision-hailo`/`vision-face` (открытый вопрос в.4).

**Бюджет трекера на Main Pi (ADR-0130 §2.11) — предложение на утверждение:**

- трекер (≈ 10 треков × 10 Гц) — **≤ 10 % одного ядра в среднем, ≤ 25 % в пике** (CPU% его контейнера);
- ставить трекер на Main Pi можно, если в сценариях A–C **среднее `host_cpu_pct` Main Pi ≤ 75 %, max ≤ 90 %** до его добавления;
- если хуже — пересмотр §2.11/Q13 (что разгрузить или куда переносить), а не «как-нибудь влезет» (ADR-0130 §6).

### 2.5 `sync_time.sh` и дубли (аудит #3109)

Выбран минимальный честный вариант: **один писатель времени на Pi**.

- `sync_time.sh` получает в шапке пометку «устарел с ADR-0137» и ранний выход: если `chrony` активен — timesyncd **не трогается**, выполняется только `setup_chrony.sh --check` (роль и сервер — из маркера в `/etc/chrony/chrony.conf`). Деплой (F2) продолжает его звать и получает в логе строку `chrony_check …`, ничего не ломая (`|| true`).
- Где chrony ещё не поставлен — `sync_time.sh` работает как раньше (timesyncd): до ручного `setup_chrony.sh` на роботе поведение не меняется.
- Удалять `sync_time.sh` сейчас нельзя: его зовёт деплой-воркфлоу; правка workflow — не этап 0. После того как chrony стоит на обоих Pi — follow-up: деплой зовёт `setup_chrony.sh --check` напрямую, `sync_time.sh` удаляется.
- `setup_node.sh:setup_time_sync` (третий писатель timesyncd, F1) на Pi с chrony безвреден: `timedatectl set-ntp true` включает `chrony.service`, а `timesyncd.conf` пишется в пустоту. Перевод его на `setup_chrony.sh` — тот же follow-up.

## 5. Отвергнутые альтернативы

| Альтернатива | Почему нет |
|---|---|
| Оставить timesyncd, оба Pi на внешний NTP | так сейчас: разные серверы (+5 / +33 мс, ADR-0130 §1.3), межпайное расхождение не измеряется и зависит от интернета |
| Vision Pi: Main Pi + внешние пулы | при сбое Main Pi Vision уйдёт на интернет-источник — межпайное расхождение снова зависит от интернета; лучше честный FAIL в `--check` |
| Сервер времени на `10.1.1.20` (Wi-Fi Main Pi) | джиттер Wi-Fi; противоречит ADR-0130 §2.11 |
| chrony в контейнере | нужен `CAP_SYS_TIME`/privileged ради демона, который на хосте уже есть в виде timesyncd |
| PTP (`ptp4l`) вместо NTP | цель 5 мс, NTP по проводу даёт на порядок лучше; PTP — лишняя сложность без заказчика |
| Два скрипта времени с одинаковой ролью | дубли (#3109); выбран «один писатель» (§2.5) |
| Фрейм микрофона сразу с «правильными» числами на глаз | выдало бы заглушку за измерение (ADR-0018) |
