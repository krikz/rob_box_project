## 1. Проблема

1. **DJ-переход — это таймер, который будит голосовую LLM.** `DJModeController.tick()` (`dj_mode.py:494-562`) раз в 5 с проверяет `next_transition_at`/`form_ends_at` и отдаёт в голосовой ход промпт `build_auto_prompt` (`dj_mode.py:984`) на 1–2 КБ. Модель должна сама вызвать `compose_music`, `speak_text` и `set_dj_mode(next_transition_sec=…)`. Когда она промахивается, срабатывают ретраи Bug B. Бюджет хода на переходе — `DJ_TURN_BUDGET_S = 20 с`: это оценка, которую пришлось закладывать в тайминг, потому что переход ждёт облако.
2. **План сета — ярлыки, а не числа.** `set_plan` — строка «Трек N: …», её разбирает `_PLAN_ENTRY_RE`. Живой план 28.09: пять ярлыков, везде «132 bpm», а сет шёл в 124. Ярлыки ни во что не компилируются: `style="club"` использует только `bpm/root/scale/seed/repeat` (`_CLUB_PARAMS`, `music.py:3741`), и «кислотный bass» превратился в `bass=dub`.
3. **От фразы до звука 12–25 с** — всё это время голосовая LLM думает над вызовом `compose_music`.
4. **Первый трек по запросу юзера разбирается без размышления.** Пример 28.09: «8-битный монстр» → `compose_music(name='8bit monster')` → `rtttl_library.get` всегда возвращает лучшего кандидата по тексту (#2896) → сыграла Raumschmiere «Monstertruck Driver», хотя тема Марио в базе есть. Голосовая модель работает с `thinking` **выключенным** (§8.4), и решение «что имел в виду юзер» принимается за один проход без рассуждения.
5. **#3112 в fade-пути ненаблюдаем.** `wrap_with_fade` (`club_transition.py:98-134`) откладывает `Clock.clear` + `Clock.set_time` в `_rbx_next_track` через `Clock.schedule(..., Clock.next_bar() + 32)`, а `_execute_with_clock_phase` (`music.py:3813`) снимает фазу сразу после `exec`, то есть по старому клоку. На живом сете получились смещения 16/20/32/40/84 из 128. Сработал ли `set_time` через 32 доли — не видно: второго снимка нет. Плюс `/g_freeAll` уходит в начале фейда (`music.py:1627`) и обрывает хвосты.

## 2. Решение — обзор

```
 голос: «сыграй X» / «ты диджей Y»                 (голосовая LLM или роутер Ш2)
        │ request_track(request=<слова юзера>, …) / set_dj_mode(…)
        ▼
 ┌─────────────── процесс владельца плеера (ADR-0141) ───────────────────┐
 │ QuickParse (≤50 мс, без сети) → seeded TrackSpec → render → PREVIEW    │ ≈1 с до звука
 │        │                                                               │
 │        └─► Reasoner (фоновая задача, thinking вкл.) ──► TrackSpec'     │
 │                     дедлайн, 1 попытка на провайдера                   │
 │                                ▼                                       │
 │                     validate_spec → render → sanitize                  │
 │                                ▼                                       │
 │   Queue[Artifact{token, expected_previous_token, program, source}]     │
 │                                ▼                                       │
 │   Player (владелец): исполняет ТОЛЬКО на границе фразы/формы           │
 │     события: started(token) · nearly_finished(token) · finished(token) │
 └────────────────────────────────────────────────────────────────────────┘
        │ latched /voice/music/state (ADR-0141) + /voice/music/event
        ▼
 dialogue_node читает состояние; на DJ-переходах LLM НЕ вызывается
```

Семь решений ниже (Р1–Р7) описывают этот конвейер.

## 3. Р1. Событие движка «скоро конец формы» и молчаливый переход

**Аналог:** Alexa AudioPlayer `PlaybackNearlyFinished` + `expectedPreviousToken`; в ответ на это событие `outputSpeech` запрещён.

### 3.1 События плеера

Владелец плеера (ADR-0141) публикует события в `/voice/music/event` (JSON, `RELIABLE`, `KEEP_LAST 10`, не latched) и одновременно вызывает их внутри процесса:

| Событие | Когда | Поля |
|---|---|---|
| `started` | новый трек **реально** встал на клок: вызов изнутри `_rbx_next_track` (§8) | `token`, `clock_beat`, `phase_offset_beats`, `form_beats`, `bpm`, `source` (`seeded`/`reasoned`/`free_code`) |
| `nearly_finished` | за `lead_beats` до конца текущего прохода формы, который план назначил последним для этого трека | `token`, `form_end_beat`, `form_end_epoch`, `lead_beats` |
| `finished` | конечный трек отыграл (ADR-0141) | `token` |

`token` = `track_id` из ADR-0141: одна строка на исполненную программу, вида `<set_id>:<track_no>:<source>:<sha8 программы>`.

### 3.2 За сколько

`lead_beats = (fade_bars + 1) × 4`. При `fade_bars = FADE_BARS = 8` это 36 долей, 17,4 с при 124 BPM. Лишний такт — запас на `exec` и планирование.

Считаем в долях клока, а не в секундах: владелец знает `form_end_beat`, потому что сам ставил трек с выравниванием (#3112, `clock_align_prelude`). Секунды (`form_end_epoch`) — только для наблюдателей. Для зацикленного DJ-трека «конец» — это конец прохода номер `passes` из спеки трека (§5, поле `passes`, по умолчанию 1).

### 3.3 Что делает владелец по `nearly_finished`

1. Берёт из очереди первый артефакт, у которого `expected_previous_token == token` текущего трека.
2. Если такого нет — берёт **заранее отрендеренный seeded-артефакт** для того же `track_no`. Он готовится в момент `started` текущего трека, стоит микросекунды и существует всегда.
3. Оборачивает программу в переход (новый `wrap_with_fade`, §8.2): фейд стартует на границе такта `form_end_beat − fade_bars·4`, новый трек встаёт **ровно** на `form_end_beat` через `Clock.schedule(_rbx_next_track, <абсолютная доля>)`, а не на `next_bar()+32`.
4. Протухшие артефакты, у которых `expected_previous_token` не совпал (юзер между делом сменил трек), выбрасываются с метрикой `artifact_stale`. Свежий трек они не перебьют.

### 3.4 Голосовая LLM на DJ-переходах не вызывается

- `DJModeController.tick()` больше не вызывает `hook.dispatch(build_auto_prompt(n))` для переходов. `build_auto_prompt` для переходов удаляется, а вместе с ним Bug B-ретраи DJ-перехода и бюджет `DJ_TURN_BUDGET_S`.
- Контроллер в dialogue_node остаётся **читателем**: персона и тема (ADR-0140), отложенное прощание по `finished` финального трека.
- Выкрик на переходе («Разгоняемся!» через `speak_text`, `dj_mode.py:1088-1094`) **по умолчанию выключен**. Вариант под флагом: ризонер кладёт в спеку готовую строку `hype_line` (≤30 символов), и владелец отдаёт её в TTS на `started` без LLM-хода. Решает Шифу (§12, В2).
- **Acceptance по логам:** за сет в ≥5 переходов нет ни одного голосового LLM-запроса с `[DJ_AUTO` и ни одного хода, вызванного из `DJModeController.tick`. Сверка — `grep` по логу dialogue_node + счётчик `voice_llm_requests{origin="dj_tick"} == 0`.

## 4. Р2. Генератор трека — чистая функция

```python
def generate_track(inp: TrackInput) -> TrackSpec          # seeded: детерминированно, без сети
async def reason_track(inp: TrackInput, provider, deadline) -> TrackSpec | None   # ризонер
def validate_spec(raw: dict, inp: TrackInput) -> TrackSpec    # SpecError(path, reason)
def render_spec(spec: TrackSpec, *, entry: Entry) -> str      # Renardo-программа, детерминированно
```

**`TrackInput`** — неизменяемый снимок, без ссылок на живые объекты:

| Поле | Откуда |
|---|---|
| `request` | слова юзера **дословно** (не перефраз голосовой LLM), для DJ — строка плана |
| `persona`, `theme` | `dj` из `/voice/music/state` |
| `state` | снимок ADR-0141: `track_id`, темп и тоника сета, что уже звучало (`played`) |
| `set_slot` | запись плана сета для этого трека (§6) или `None` |
| `anchors` | поля, которые ризонер **не может** менять: для первого трека — якоря превью (§7.3), для DJ — `bpm` сета и форма перехода |
| `palette` | белые списки из кода (§5.3) |
| `limits` | потолки уровней и длины формы (§5.3) |
| `seed` | `DJModeController._track_seed` (как сейчас) |

**`TrackSpec`** — выход, данные без побочных эффектов (§5). Рендер детерминирован: одинаковая спека даёт побайтно одинаковую программу. Рендерят существующие аранжировщики: `club_arranger.render_club` (club) и `arranger.render(CompositionSpec)` (classic, тема из RTTTL). Новых генераторов нот не пишем — расширяем их входы до осей из §5.

**Регресс-якорь:** `render_spec(seeded_spec(seed=s)) == render_club(seed=s)` побайтно для набора сидов. Seeded-путь через спеку звучит ровно как сегодня.

## 5. Структурированная спека трека (`TrackSpec`)

### 5.1 Где живёт

- `src/rob_box_mcp_tools/rob_box_mcp_tools/core/track_spec.py`: dataclass-ы, `validate_spec`, `track_spec_schema()`. Чистый модуль без Renardo/ROS, как `arrangement_matrix.py`.
- **JSON-схема не пишется руками, а генерируется** функцией `track_spec_schema()` из констант кода: `KICK_PATTERNS`, `HATS_PATTERNS`, `ROLE_SYNTHS`, `SECTION_TEMPLATES`, `PROGRESSIONS`, `VALID_ROOTS`, `BPM_RANGE`, `LAYER_LEVELS`. Снимок схемы кладётся в `test/fixtures/track_spec.schema.json`, и тест сверяет его с генерацией. Так фасад не может разъехаться с кодом — это прямой урок `set_pitch(pitch: float)` против настоящего `set_pitch(action: str)` у MusicSkill (§9).
- Валидатор написан на чистом Python, без `jsonschema`: пакета нет в зависимостях `rob_box_mcp_tools`. Ошибка — `SpecError(path="sections[2].energy", reason=…)`, этот путь уходит в лог и метрику.

### 5.2 Поля (v1)

```jsonc
{
  "version": 1,
  "style": "club" | "classic",
  "bpm": 124,                        // = anchors.bpm, иначе SpecError
  "root": "A#", "scale": "minor",    // club v1: только minor (SUPPORTED_SCALES)
  "form": { "template": "long_build_32" | null,     // null → своя матрица ниже
            "block_bars": 2, "blocks": 16 },        // длина формы = blocks·block_bars тактов
  "passes": 1,                       // сколько проходов формы до nearly_finished (1..4)
  "sections": [                      // по границам фраз, покрывают форму без дыр
    { "name": "intro", "blocks": [0, 4], "energy": 3,           // 0..10, целое
      "progression": "i-VI-III-VII",                            // имя из PROGRESSIONS
      "root_shift": 0 }                                         // 0|5|7 полутонов (соседи по квинтовому кругу)
  ],
  "groove": {                        // оси грува: дорожка × секция (план качества §6)
    "kick":  { "intro": "off", "drop": "four_on_floor" },      // off | ключ KICK_PATTERNS
    "hats":  { "intro": "offbeat", "drop": "shuffle" },         // off | ключ HATS_PATTERNS
    "bass":  { "drop": { "rhythm": "sixteenths_pump", "pitches": "root_octave" } },
    "lead":  { "drop": { "density": 2, "syncopation": 1 } }     // 0..3
  },
  "timbre": { "lead": "pluck", "bass": "retrobass", "pad": "warmpad" },   // ⊂ ROLE_SYNTHS
  "matrix": {                        // план качества §7.10: слой × блок, маски 0..15 | "x"
    "kick": "0 0 0 1  x x x x  x x 12 0  x x x 9", "…": "…"
  },
  "levels": { "lead": 0.9 },         // множители 0..1 к LAYER_LEVELS (потолок как ADR-0132)
  "melody": null | { "library_id": "supermar", "why": "…", "confidence": 0.0..1.0 },
  "hype_line": null | "≤30 символов",   // только если включён флаг §3.4
  "notes": "свободный текст ризонера, в рендер не идёт, только в лог"
}
```

Правила валидатора (помимо типов и перечислений):

- `bpm`, а для первого трека ещё `root`/`scale`/`form.blocks`, равны якорям;
- секции покрывают форму без дыр и перекрытий, границы кратны 4 тактам;
- у каждой дорожки матрицы ровно `form.blocks` ячеек;
- сумма пиков одновременно звучащих слоёв ≤ 1,2 — тот же бюджет, что `role_peak_sum` в `arranger.py:170`;
- `melody.library_id` существует в архиве **и** был в списке кандидатов, который код показал ризонеру (§7.5). Выдуманный id — это `SpecError`.

Оси `groove.bass`, `groove.lead` и маски по секциям `render_club` сегодня не умеет — у него один рисунок на трек. Их поддержка — отдельный PR с golden-тестами (§11, PR-3). Пока его нет, валидатор v1 принимает у этих осей только значения, которые рендер уже умеет, а схема честно их сужает. Схема не обещает того, чего не делает рендер — это урок `_club_ignored`.

### 5.3 Палитра и пределы — откуда

| Список | Источник (единственный) |
|---|---|
| синты по ролям | `club_arranger.ROLE_SYNTHS` (все ⊂ `tools/music.py:259 CRITICAL_SYNTHS`) |
| рисунки бочки/хэтов | `KICK_PATTERNS`, `HATS_PATTERNS` |
| прогрессии | `club_arranger.PROGRESSIONS` (по имени) |
| шаблоны формы | `arrangement_matrix.SECTION_TEMPLATES` |
| мелодии | RTTTL-архив, **только** id из выдачи кандидатов (§7.5) |
| уровни | `LAYER_LEVELS` × `levels` (0..1), `MAX_LAYER_AMP = 0.85` |

### 5.4 Детерминированный рендер

`render_spec(spec, entry)`:

- `entry="fresh"` — полная программа: `Clock.clear()` → `clock_align_prelude(F)` → `Clock.bpm` → плееры → `Clock.future` при конечном треке. Это как сейчас, и обязательно с выравниванием #3112.
- `entry="reveal"` — **без** `Clock.clear`, `set_time` и `bpm`: только переприсваивание шести плееров. Нужно для замены превью на ризонер (§7.4).

Гейты секций — `amp=var(...)` из матрицы (`ArrangementMatrix.gate_var`). Результат всегда проходит `sanitize_renando`: санитайзер — последний рубеж, а не единственный.

## 6. Р3. План сета — числа, а не ярлыки

### 6.1 Поля (`SetPlan`, `core/set_plan.py`, чистый модуль)

| Поле | Тип | Обязательно | Примечание |
|---|---|---|---|
| `set_id` | str | да | эпоха старта сета |
| `bpm` | int | да | **единственный** темп сета = `DJState.set_bpm`; в треках его нет |
| `root`, `scale` | str | да | тоника сета (`_set_root`) |
| `tracks[]` | list | да, 2..50 | |
| `tracks[].no` | int | да | |
| `tracks[].energy` | int 0..10 | да | энергетическая дуга числами |
| `tracks[].root_shift` | 0/5/7 | да | движение тональности (`KEY_WALK` — дефолт) |
| `tracks[].template` | ключ `SECTION_TEMPLATES` \| null | нет | null — решает генератор трека |
| `tracks[].passes` | 1..4 | да | сколько проходов формы трек звучит |
| `tracks[].timbre_family` | `warm`/`bright`/`dark` | нет | подсказка, не синт |
| `tracks[].melody_hint` | str \| null | нет | название песни — идёт в `request` генератора, **не** в `name=` |
| `tracks[].label` | str | нет | ярлык для людей; в рендер не идёт |
| `max_minutes` | int | нет | лимит #2856 |

По построению плана «132 vs 124» не бывает: темп в треке задать нельзя, а спека трека с `bpm ≠ plan.bpm` не проходит валидатор.

### 6.2 Кто генерирует

1. **На старте сета — seeded-план мгновенно:** дуга энергии по шаблону (например 4, 6, 8, 9, 7, 5 для 6 треков), `root_shift` по `KEY_WALK`, `passes = 1`. Сет звучит с первой секунды.
2. **Ризонер в фоне** получает тему, персону и seeded-план и возвращает `SetPlan'` с теми же обязательными полями. Валидация: `bpm` и `root` равны seeded, сыгранные треки не трогаются. Прошёл — план заменяется **начиная со следующего не отрендеренного трека**.
3. Юзер меняет темп только через `set_dj_mode(bpm=…)`: план пересчитывается, в очереди остаются только ещё не исполненные артефакты, и они перегенерируются.

### 6.3 Где хранится

- **Авторитетный экземпляр** — у владельца плеера (ADR-0141), в том же процессе, что очередь артефактов. Публикуется в поле `dj.plan` latched-состояния.
- `DJState` в dialogue_node получает поле `plan: Optional[SetPlan]` — **зеркало** из топика, только для чтения (ответить на «что дальше?», персона, прощание). Строка `set_plan` остаётся на один PR как вид для обратной совместимости, потом удаляется.
- Тоника и темп сета сейчас живут в `DJState` (`set_bpm`, `set_root`). После переноса источник у них один — план владельца, а `DJState` только отражает.

## 7. Р4. Ризонер для первого трека: превью сразу, трек «раскрывается»

Ключевое требование Шифу. Ризонинг нужен **и для первого трека** — для самого ответа на «сыграй X», а не только для «трека N+1» в сете.

### 7.1 Сценарий

1. Юзер: «сыграй X».
2. **Превью через ~1 с:** QuickParse без LLM → seeded `TrackSpec` → `render_spec(entry="fresh")` → звук.
3. **Параллельно** ризонер с включённым thinking разбирает **тот же** запрос: какую мелодию из базы выбрать (или никакую), форму, гармонию, грув, тембры; при необходимости — код (§10).
4. Результат проходит валидатор и на ближайшей границе фразы **заменяет превью как продолжение того же трека**. Ризонер не успел или не прошёл валидацию — превью доигрывает само. Это честный fallback, не ошибка: пишется метрика и строка в лог, юзеру ничего не сообщается.

### 7.2 Что превью выбирает дёшево (без LLM), а что только ризонер

| Параметр | Превью (QuickParse, ≤50 мс, без сети) | Только ризонер |
|---|---|---|
| темп | темп сета; или жанровое слово из закрытой таблицы («техно» → 130, «лоу-фай» → 85); иначе 124 | темп «по смыслу» неназванного жанра — нельзя, если якорь уже звучит (§7.3) |
| тоника/лад | тоника сета или `KEY_WALK`; иначе от сида; лад `minor` | — (якорь) |
| форма | шаблон с интро: `long_build_32`, `dj_dave_32` | секции, дуга энергии, свои матрицы |
| грув/тембры | `club_kit(seed)` | оси по секциям, тембры под тему/персону |
| мелодия | **только** точное попадание: `covers_tokens(record, request)` (`rtttl_library.py:240`) = все значимые слова запроса есть в записи | непрямые отсылки («8-битный монстр», «та песня из Тетриса»), выбор из кандидатов, «мелодии нет — играй оригинал» |
| гармония | прогрессия от сида | прогрессия по секциям, `root_shift` |
| код | нет | свободная дорожка (§10) |

**Правило превью:** мелодию из базы превью играет, только если запрос покрыт записью целиком. «8bit monster» против «Monstertruck Driver» — слово «8bit» не найдено, значит превью играет **без темы**: пэд, хэты, бас в тонике. Ложную мелодию превью не ставит никогда. Это не новый регекс-гард: `covers_tokens` уже есть и уже честный.

### 7.3 Якоря: превью — это интро готового трека

Чтобы замена звучала как раскрытие одного трека, а не как два трека подряд:

- **Якоря** (ризонер получает их в `anchors` и не может менять, иначе `SpecError`): `bpm`, `root`, `scale`, `form.blocks` (длина формы F), `timbre.pad`, рисунок хэтов интро.
- **Превью стартует с выравниванием #3112:** `next_bar = k·F`, поэтому позиция в форме = `Clock.beat mod F`.
- Превью всегда начинается с шаблона, где первые 4–8 тактов — интро (пэд + хэты, бочка с затакта). Это и есть «раскрытие одного лупа» из референсов (план качества §7.1 п.6, §7.5, §7.8).

### 7.4 Как звучит замена

- Замена = `render_spec(spec', entry="reveal")`: **переприсваивание** `d1..d3/p1..p3` без `Clock.clear`, запланированное `Clock.schedule` на границу фразы (8 тактов).
- Гейты секций `amp=var(...)` в Renardo считают фазу от доли 0 клока (`TimeVar.get_current_index`, док #3112). Клок выровнен на `k·F`, поэтому новые гейты подхватывают **ту же позицию формы**: замена на такте 16 попадает в блок 8 матрицы ризонера, то есть в build/lift, а не в начало.
- Слои пэда и хэтов продолжаются тем же тембром (якоря). Новое — бочка, бас, лид, мелодия — входит по матрице ризонера. На слух это «вошли слои», а не «сменился трек».
- **Не проверено:** переприсваивание плеера посреди `var`-гейта без щелчка и без двойной ноты на границе. Это проверка на роботе в PR-7.

**Для classic-трека с мелодией** (ризонер выбрал тему из базы) форма classic не совпадает с F превью. Тогда замена — это `entry="fresh"` на границе фразы с коротким фейдом в 1 такт: тот же темп и та же тоника. Тема транспонируется в тонику превью через `root=`. **Не проверено**, что classic-путь с `name=` сейчас честно уважает `root=`: ADR-0132 п.6 фиксировал, что при `name=` `root/scale` игнорировались, — сверить в PR-7.

### 7.5 Как ризонер ловит «8-битного монстра»

По ADR-0132 и памяти проекта («учить LLM правилам, а не хакать под запрос») никакой таблицы алиасов «монстр → Марио» в коде нет. Вместо неё:

1. Ризонеру доступен **только один read-only тул** — `search_melody(query) → [{id, title, artist, match_info}]` (уже есть, `SearchMelodyTool`), не более 3 вызовов. Исполнительных тулов у ризонера нет вообще (§9).
2. В промпте — правило: запрос может быть непрямой отсылкой («8-битный» = чиптюн, игровая музыка). Нужно сформулировать 2–3 гипотезы, искать каждую, выбрать запись, у которой **смысл** совпадает с запросом, или честно выбрать `melody: null` и сыграть оригинальный трек в жанре.
3. Валидатор принимает `melody.library_id` только из выдачи `search_melody` в этом же ходе.
4. **Честная оговорка:** «8-битный монстр» неоднозначен, и Марио — ожидание Шифу из #3113, а не единственный верный ответ. Acceptance поэтому — не «всегда Марио», а «не сыграл запись, в которой нет смысла запроса». Набор таких запросов для регресса ризонера (с ожиданием Шифу на каждый) — вопрос В7.

### 7.6 Дедлайн ризонера для первого трека

| Момент (124 BPM, такт ≈ 1,94 с) | Что |
|---|---|
| t≈1 с | превью звучит |
| граница 8 тактов (≈15,5 с) | 1-я точка замены: спека готова и валидна к `t − 1 такт` |
| граница 16 тактов (≈31 с) | 2-я точка |
| граница 24 тактов (≈46,5 с) | **последняя** точка; жёсткий дедлайн ризонера = 46,5 − 2 = **≈44 с** от старта превью |
| позже | превью доигрывает свою seeded-форму. В DJ-режиме опоздавшая спека **не выбрасывается**: она идёт как трек 2 с `expected_previous_token = token превью`. Для разового трека — выбрасывается с метрикой `reasoner_late` |

Цифры — предложение. Реальная латентность thinking **не измерена** (§8.4), поэтому ризонер сначала работает в shadow (PR-6) и собирает p50/p95 (§11).

### 7.7 Что говорит робот

- В момент превью — как сейчас, короткий ответ хода («Включаю!») или ничего, если команду исполнил роутер Ш2.
- На замене **ничего**. Трек просто раскрывается.
- Если ризонер выбрал другую мелодию, чем подумал бы юзер (Марио вместо «монстра»), робот об этом не объявляет. Название текущей темы появляется в `track_id`/`title` latched-состояния, и на вопрос «что играет?» ответ берётся оттуда (ADR-0141).
- Провал ризонера юзеру **не озвучивается** — превью и есть честный результат. В лог и метрики пишется всегда: `reasoner_outcome{result=ok|late|invalid|error|circuit_open}`. Голосовой стек деградирует молча (память проекта), поэтому счётчик `invalid/error` > 0 за сет — повод для алерта, а не для тишины.

## 8. Р5. Ризонер в фоне: конвейер, дедлайн, fallback, где исполняется

### 8.1 Конвейер DJ-сета

```
track N: started(token_N) ──► сразу: seeded-артефакт N+1 (всегда есть)
                         └──► reasoner(N+1, expected_previous_token=token_N)  [фон]
           … N играет passes·F долей …
nearly_finished(token_N) ──► берём reasoned N+1, если готов и валиден, иначе seeded N+1
```

Дедлайн ризонера N+1 = момент `nearly_finished` минус 1 такт. Для 32-тактовой формы при 124 BPM и `passes=1`: 62 с формы − 17,4 с (lead) − 1,9 с ≈ **42 с**. При `passes=2` ≈ 104 с. Трек 1 сета — это первый трек с превью (§7).

### 8.2 Инварианты (по образцу `DecisionOrchestrator`)

Берём **паттерн**, а не сам класс. У `DecisionOrchestrator` потолок `MAX_DEADLINE_MS = 2000` (`routing.py:41`) — он для решений до 2 с, а здесь десятки секунд. Гнуть его контракт не будем. Переиспользуются `CircuitBreaker` и `DecisionMetrics` из `rob_box_harness/decision/health.py`, если зависимость пакетов это позволяет (сверить в PR-6).

- дедлайн **один** на всю цепочку провайдеров;
- ретраев нет: следующий провайдер — это и есть ретрай;
- исключения провайдера наружу не выходят;
- детерминированный fallback — seeded-спека — есть всегда, и конфигом его не убрать;
- circuit breaker на провайдера: после N ошибок подряд провайдер пропускается на T минут, чтобы при кончившихся деньгах не ждать дедлайн на каждом треке.

### 8.3 Где исполняется

**Не в голосовом ходе и не в dialogue_node.**

| Вариант | + | − |
|---|---|---|
| **А (предлагаю).** Фоновая задача в процессе владельца плеера (mcp_server по #3133): отдельный поток со своим event loop | очередь, токены и клок — в одном процессе, нет IPC; `render` и `sanitize` уже там | сетевой LLM-клиент в процессе, который держит звук: нужен жёсткий таймаут и изоляция исключений; нагрузка на тот же CPU Pi (thinking идёт в облаке, локально только ожидание) |
| Б. Отдельная ROS-нода `music_composer` | изоляция падений; можно перезапускать отдельно | ещё один топик/сервис для спек, ещё одна копия состояния сета — ровно то, от чего уходит Ш1 |
| В. Внутри dialogue_node (как MusicSkill) | клиенты LLM уже там | **отклонено**: это и был провал сабагента (§9) — голосовой процесс, общий бюджет ходов, соблазн отдать ризонеру тулы исполнения |

### 8.4 Какая модель и провайдер

Что есть в стеке (прочитано в коде, ничего не измерено):

| Провайдер | Модель | Thinking сейчас | Где выключен |
|---|---|---|---|
| MiniMax (голос, primary: `llm_providers: "minimax,deepseek"`) | `MiniMax-M3` | **выключен**: `DEFAULT_THINKING_POLICY = {"type": "disabled"}` | `rob_box_llm/providers/minimax.py:82`, `rob_box_harness/providers/minimax.py:842-848` |
| DeepSeek (голос, fallback) | `deepseek-chat` | **выключен**: `extra_body["enable_thinking"] = False` | `rob_box_llm/providers/deepseek.py:375` |
| MiMo | `mimo-v2.5-pro` | в стеке голоса не используется; в ветке phase-3.2 thinking был **выключен** нами (`03.2-CONTEXT.md`: «default enabled, мы ставим disabled»), `tool_choice` только `auto` | `03.2-CONTEXT.md:62` |
| Jev / Laya (`decision/`) | — | Choice-решения до 800 мс, ключа Jev нет (NO-GO) | `routing.py` |

**Цена thinking по латентности не измерена.** В коде есть только комментарий: у MiniMax-M3 adaptive thinking даёт «+10-20с на turn» (`rob_box_harness/providers/minimax.py:846-847`). Это утверждение без замера в репо. Замеров p50/p95 thinking у DeepSeek и MiMo тоже нет.

Варианты:

1. **MiniMax-M3, thinking включён** (`thinking=None` → адаптивный дефолт модели, либо явное `{"type": "enabled"}`; какое значение принимает API — сверить). Плюсы: тот же ключ и клиент. Минусы: общий кошелёк с голосом — ризонер может съесть деньги, и голос «задумается».
2. **DeepSeek с thinking** (`enable_thinking=True` или reasoner-модель). Плюсы: другой кошелёк, чем у голоса. Минусы: fallback голоса — при падении MiniMax голос и ризонер пойдут в одно облако.
3. **MiMo `mimo-v2.5-pro`, thinking включён.** Плюсы: провайдер свободен от голоса. Минусы: нет истории на наших задачах со включённым thinking, `tool_choice` только `auto` (для read-only `search_melody` хватит).
4. **Новый провайдер** (например, Claude через Anthropic API). Новый ключ и новое облако в стеке, который и так молча деградирует. Только решением Шифу.
5. **Jev/Laya** — только для отдельных Choice-решений (ось грува из списка), не для спеки целиком. План качества §6, после ключа.

**Предложение:** цепочка `[mimo(thinking), deepseek(thinking)] → seeded`. Ризонер не тратит кошелёк голоса (MiniMax), а две независимые облачные дорожки дают шанс уложиться в дедлайн. **Решение за Шифу** (§12, В1): провайдер, бюджет на трек/сет, можно ли тратить кошелёк MiniMax.

### 8.5 Контракт вызова

- **Один ход рассуждения** + до 3 read-only вызовов `search_melody` + финальный вызов функции `submit_track_spec(spec)`. Это функция нашего кода, она ничего не исполняет, её `parameters` = `track_spec_schema()`. `response_format` в наших провайдерах нет, поэтому структурный выход идёт через tool call. Насколько строго модели держат схему — **не проверено**, это ловит валидатор.
- Промпт ризонера — отдельный файл (`prompts/music_reasoner.txt`), не `composer.txt`. В нём только ремесло спеки и правила интерпретации запроса (§7.5). Свою историю диалога ризонер не получает — только `TrackInput`.
- `max_tokens` и бюджет thinking — ограничены. Числа — после замеров в shadow (PR-6).

## 10. Р7. Диагностика #3112 и свободный код

### 10.1 Снимок фазы внутри `_rbx_next_track` (#3112 в fade)

- Владелец при бутстрапе Renardo кладёт в пространство имён `exec` функцию `_rbx_track_started(token, form_beats)`. Это Python-колбэк процесса сервера (Renardo живёт в том же процессе). Функция:
  1. снимает `clock_phase_snapshot(Clock, form_beats)` **сейчас**, то есть после `Clock.clear` → `set_time` → `bpm` нового трека;
  2. шлёт спуск gate=0 и `/g_freeAll` уходящих нод (перенос `d922ee836`; к этому моменту фейд уже отыграл);
  3. публикует `started` (§3.1) и пишет INFO `[#3112] старт трека token=… доля=… смещение в форме=… из F (внутри _rbx_next_track)`.
- Новый `wrap_with_fade` вставляет вызов **последней** строкой тела `_rbx_next_track`, а `execute_code` перестаёт слать `/g_freeAll` в начале фейда, если программа обёрнута.
- Имя без двойного подчёркивания, санитайзер его пропускает — закрепить тестом, как сделано для `_rbx_next_track`. Если колбэка нет в пространстве имён (старый рантайм), `NameError` внутри запланированной функции сорвал бы старт трека. Поэтому инъекция делается при бутстрапе и проверяется тестом бутстрапа. Защищать `try` в сгенерированном коде или нет — решить по санитайзеру в PR-1.
- Снимок «после exec» остаётся под своим именем (`exec_phase`), чтобы старые логи можно было сравнить.

### 10.2 Свободный Renardo-код от модели — только отдельной дорожкой

По умолчанию **выключен**. Включается флагом после слепого теста спек (§11, PR-8). Модель стабильно ошибается в свободном FoxDot (#2560, #3008, `lead=1.3`), поэтому основной выход — спека.

Код приходит полем `spec.code` вместе со спекой. Спека валидна сама по себе, и если код не прошёл, играет рендер спеки, а не seeded.

Валидатор `validate_free_code(code, spec)`:

1. `ast.parse`; разрешены только узлы `Module/Expr/Assign/BinOp/Call/Attribute/Name/Constant/List/Tuple/keyword/UnaryOp` и `>>`. Никаких `def/class/import/lambda/comprehension/while/for/with/try`, никаких dunder.
2. **Имена:** плееры `d1..d3, p1..p3` (`renardo_sanitizer._ALLOWED_PLAYER_SLOTS`); синты — `CRITICAL_SYNTHS` ∩ ключи `synth_traits.SYNTH_TRAITS` (у синта известны свойства хвоста); сэмплер `play` — символы шаблона из снимка каталога сэмплов renardo_lib 0.9.13 (снимок в `data/`, **его ещё нет** — задача PR-8); `loop()` — только из `data/sample_loops.json`; функции паттернов — `var, linvar, sinvar, P, PDur, PRand, PwRand, Pvar, Scale.*`; атрибуты плеера — белый список (`dur, sus, amp, amplify, lpf, hpf, room, mix, pan, oct, root, scale, echo, delay, sample, rate, fmod`).
3. **`Clock`** — только `Clock.bpm = <anchors.bpm>`. `clear/future/schedule/set_time` запрещены: прелюдию, выравнивание и конец формы добавляет рендер-обёртка.
4. **Пределы:** числовые литералы `amp` ≤ потолка роли × 1,0; `amplify` ≤ 0,85; статическая оценка суммы пиков по плеерам ≤ 1,2; `bpm` = якорь; длина формы — объявленная `FORM_BEATS = N` равна `spec.form`, и все `var`-периоды делят N (иначе фаза #3112 не держится); ≤ 6 плееров; размер ≤ 8 КБ.
5. **Опционально — офлайн-рендер** «не тишина / не клип»: NRT-прогон scsynth на 8 тактов, RMS > −50 dBFS, пик < −0,5 dBFS. **Не проверено**, есть ли NRT/sclang в образе и сколько это стоит по CPU на Pi рядом с живым scsynth. Замер — условие включения.
6. После всего — штатный `sanitize_renando`. Санитайзер изменил хоть одну строку → отказ (код должен быть чистым сам).

Не прошёл хоть один пункт → играет рендер спеки, а в лог пишется `free_code_rejected{rule=…}`.

**Слепой тест «seeded против ризонера» (acceptance PR-7):**

1. 6 пар на одних якорях: тема, персона, `bpm`, `root`, F одинаковы; 3 пары DJ-сета, 3 первых трека по запросу.
2. Обе версии записываются на роботе `jack_rec` по 60 с (или `tools/music_bench`).
3. Метки A/B внутри пары перемешиваются скриптом. Ключ сохраняется в файл, его sha256 публикуется в PR **до** прослушивания.
4. Шифу слушает и на каждую пару отвечает: какая лучше и 1–5 за каждую.
5. Ключ раскрывается после вердикта. Предлагаемое правило: ризонер по умолчанию, если он лучше в ≥4 из 6 и ни одна его версия не «сломана» (тишина, клип, не тот темп). Правило утверждает Шифу (В6). **Вердикт — только Шифу**, воркер его не пишет.

## 12. Открытые вопросы для товарища Шифу

- **В1. Модель и кошелёк ризонера.** MiMo/DeepSeek с thinking (предложение), MiniMax-M3 с thinking (общий кошелёк с голосом) или новый провайдер? Какой бюджет на трек и на сет?
- **В2. Речь на DJ-переходах.** Тишина (как Alexa `NearlyFinished`) или готовая `hype_line` от ризонера под флагом?
- **В3. Дедлайны первого трека.** Точки замены 8/16/24 такта и жёсткий дедлайн ≈44 с — принять как стартовые или ждать замеров shadow?
- **В4. Read-only тулы ризонера.** До 3 вызовов `search_melody` в одном ходе ризонера (предложение) или один проход с кандидатами, заранее собранными кодом по 2–3 переформулировкам?
- **В5. Откуда ризонер берёт слова юзера.** Новый параметр `request=` в `compose_music` (голосовая LLM может перефразировать) или dialogue_node прикладывает текст последней реплики к вызову тула (надёжнее, но меняет контракт MCP-вызова)?
- **В6. Правило слепого теста.** ≥4 из 6 — достаточно?
- **В7. Набор непрямых запросов для регресса ризонера** («8-битный монстр», …) с вашим ожиданием на каждый. «8-битный монстр → Марио» — это ваше ожидание из #3113, а не однозначный ответ; хотим список, где ожидание записано вами.
- **В8. Свободный код вообще нужен?** Или достаточно спеки с расширяемыми осями? NRT-рендер на Pi — только после замера CPU.
- **В9. Где исполняется ризонер** — в процессе владельца плеера (предложение, вариант А) или отдельной нодой (Б)?

## 13. Что не проверено

- Латентность thinking у MiniMax-M3, DeepSeek и MiMo на нашем пути — **не измерена**. «+10-20 с» у MiniMax — комментарий в коде, не замер.
- Какое значение `thinking` включает рассуждение у MiniMax-M3 API (`None` → адаптивно или `{"type": "enabled"}`) — не сверено с документацией.
- Держат ли модели JSON-схему в `submit_track_spec` — не проверено; поддержка `tool_choice` у MiniMax — не проверена (разбор §8).
- Переприсваивание плееров без `Clock.clear` посреди `var`-гейтов (замена превью) — щелчки, двойные ноты: на роботе не проверено.
- `Clock.schedule` на абсолютную долю после `set_time` в fade-пути и вызов Python-колбэка из запланированной функции Renardo — прочитано по исходникам, на роботе не проверено.
- Уважает ли classic-путь с `name=` параметр `root=` сейчас (ADR-0132 п.6) — не сверено.
- Есть ли NRT/sclang в образе voice-assistant — не проверено.
- Снимка каталога сэмплов renardo_lib для белого списка `play()` в репо нет.
- Доступен ли `rob_box_harness.decision.health` из `rob_box_mcp_tools` без новой зависимости пакета — не сверено.
- Контракт ADR-0141 взят из карточки #3133. Если поля там изменятся (`track_id`, `form_ends_at`, `dj`), §3 и §6.3 правятся под него.

## 14. Последствия

- Уходят: DJ-промпт перехода (`build_auto_prompt` для n>1), Bug B-ретраи перехода, `DJ_TURN_BUDGET_S`, `next_transition_sec` у модели, ярлыковый `set_plan` как источник.
- Появляются: очередь артефактов у владельца, `TrackSpec`/`SetPlan` (чистые модули), фоновая задача ризонера с метриками, колбэк `_rbx_track_started`.
- Качество и латентность разделены: звук через ~1 с всегда из seeded-пути, качество — из ризонера, когда он успел и прошёл валидатор. Без слепого теста «качество выше» остаётся гипотезой, и по умолчанию ризонер не включается до вердикта Шифу.
