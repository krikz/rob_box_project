- **status**: accepted
- **date**: 2026-09-23

- **supersedes**: —
- **fixes**: false-positive в `tests/unit/e2e_scripts/test_tts_provider_selection.py::TestHarnessContract::test_yandex_key_no_longer_unconditional_fatal`
- **issue**: #2803
- **kanban**: t_20825dc6

## Контекст

Тест `test_yandex_key_no_longer_unconditional_fatal` задуман как страж инварианта
«фатал `YANDEX_API_KEY не задан` обязан быть условным (только под
`--tts-provider=yandex`), иначе прогон обязан оставаться возможным с провайдером
silero». Docstring теста это и говорит. Но первая assert-строка:

```python
assert 'E2E_FATAL: YANDEX_API_KEY не задан"' not in text
```

ищет подстроку с **закрывающей кавычкой сразу после слова «задан»**. В
`.github/workflows/scripts/e2e_voice_test.sh` такой подстроки никогда не было —
между «задан» и закрывающей `"` стоит пробел и `(--tts-provider=yandex)`.

### Raw-evidence

```
$ grep -nF 'E2E_FATAL: YANDEX_API_KEY не задан"' \
    .github/workflows/scripts/e2e_voice_test.sh
(0 совпадений)

$ grep -nF 'E2E_FATAL: YANDEX_API_KEY не задан' \
    .github/workflows/scripts/e2e_voice_test.sh
303:    echo "E2E_FATAL: YANDEX_API_KEY не задан (--tts-provider=yandex)" >&2; exit 2

$ python3 -c '
text = open(".github/workflows/scripts/e2e_voice_test.sh").read()
print("старая assert:    ", "E2E_FATAL: YANDEX_API_KEY не задан\"" not in text)'
старая assert:     True   # ← мёртвая, всегда True
```

### Почему это страж с дырой (из карточки #2803)

- Если кто-то **уберёт условие** `[ "$E2E_TTS_PROVIDER" = "yandex" ] &&` и оставит
  фатал в безусловной форме — реальное сообщение в stderr останется тем же
  текстом `"...не задан (--tts-provider=yandex)"`. Первая assert останется
  зелёной, вторая — красной. **Половина теста всё-таки покраснеет.**
- Если кто-то **перепишет** фатал в любую другую форму (`"YANDEX_API_KEY is
  empty"`, `"нет ключа"` и т.п.) — обе половины покраснеют одновременно,
  непонятно, какая из них сработала.

Это типичный LLM-глюк: первая половина теста написана «по памяти» автора, а не
сверкой с реальным текстом скрипта.

### Историческая реконструкция (почему так вышло)

```
commit 02f4154c75fbbf9d46e32d56919746021d79edef   (создание скрипта)
63: if [ -z "${YANDEX_API_KEY:-}" ]; then
64:     echo "E2E_FATAL: YANDEX_API_KEY не задан" >&2; exit 2
                                          ^ закрывающая " сразу после «задан»

commit 2f7cf8b265d582e606e1bb266e3f45b6d302c035   (wip(review): baseline для review)
+ # в этом же коммите добавлен тест, который ищет ПО СТАРОЙ формулировке
+ и одновременно поменян скрипт на условный фатал:
+ if [ "$E2E_TTS_PROVIDER" = "yandex" ] && [ -z "${YANDEX_API_KEY:-}" ]; then
+     echo "E2E_FATAL: YANDEX_API_KEY не задан (--tts-provider=yandex)" >&2; exit 2
+                                                   ^ пробел + суффикс
```

Автор теста в одном коммите поменял скрипт и тут же добавил проверку по
**исходной** формулировке. С тех пор `2f7cf8b26` первая assert-строка всегда
`True`, не ловит ничего.

## Решение

### Принятое: проверка по соседству, а не по наличию подстроки в файле

Первая редакция этого ADR предлагала логическую связку
`'...не задан' not in text or '[ "$E2E_TTS_PROVIDER" = "yandex" ]' in text`.
Она тоже почти мёртвая: условие провайдера в скрипте уже есть (строка 302),
поэтому правая часть `or` истинна всегда, и безусловная копия фатала
рядом с условной проходит незамеченной. Проверено мутантом — вставка строки
`echo "E2E_FATAL: YANDEX_API_KEY не задан" >&2; exit 2` после `fi`:

```
старая связка на мутанте: assert1 = True assert2 = True   ← мутант не пойман
новая проверка:           AssertionError: строка 306: фатал без ключа Yandex
                          не под условием провайдера
```

Поэтому проверяется каждое вхождение фатала:

```python
guard = '[ "$E2E_TTS_PROVIDER" = "yandex" ]'
lines = text.splitlines()
for i, line in enumerate(lines):
    if "E2E_FATAL: YANDEX_API_KEY" not in line:
        continue
    prev = next(
        (p for p in reversed(lines[:i]) if p.strip() and not p.lstrip().startswith("#")),
        "",
    )
    assert guard in line or (prev.lstrip().startswith("if ") and guard in prev)
```

Вхождение допустимо, если условие провайдера стоит на той же строке
(однострочник `[ ... ] && { echo ...; }`) или на ближайшей значимой строке
выше, и та начинается с `if `. Если фатала нет вовсе — проверять нечего,
тест зелёный. Вторая assert (наличие условия `yandex && -z ключ`) остаётся.

| Регрессия | Связка через `or` | Проверка по соседству |
|---|---|---|
| Рядом с условным фаталом появилась безусловная копия | зелёная (дыра) | красная |
| Условие `&&` убрали, текст фатала оставили | красная только вторая assert | красная обе |

### Почему НЕ вариант 3 (вынести в отдельный sanity-test)

Ввести второй тест с именем `test_no_unconditional_yandex_fatal` означало бы
зафиксировать в кодовой базе **историческую** формулировку как самостоятельный
инвариант. Но такой формы больше нет (три коммита как нет), и проверять
отсутствие мёртвой подстроки — это архитектура ради архитектуры. Тест должен
стражить живой инвариант, а не исторический артефакт.

### Почему НЕ вариант «просто поправить подстроку на правильную»

`assert 'E2E_FATAL: YANDEX_API_KEY не задан (--tts-provider=yandex)' not in text`
проверяет «сообщения вообще нет» — это **противоположно** инварианту. Сообщение
должно быть — но только под условием. Нужен `or`.

## Альтернативы, рассмотренные и отвергнутые

1. **Regex с lookahead** — излишняя мощность для одного литерала.
2. **Тест на AST** (парсить bash) — overengineering, тесты на статический
   текстовый паттерн адекватны текущему уровню покрытия компонента.
3. **Один assert, проверяющий обе подстроки через `and`** — это тест на
   совместное присутствие, а не на условность. Эквивалентно старой
   «живой» assert, новой информации не даёт.
