> ⚠️ **Superseded (2026-08-11)**: См. ADR-0013 и issue #1117 round-2. A/B-тест round-1 был проведён на ошибочной гипотезе «Ch5-6 = AEC playback reference с чистой фразой». Round-2 (с реальным datasheet ReSpeaker Mic Array v2.0) показал: **Ch1 (1-индекс) = DSP-processed ASR** (AEC + beamforming + NS + AGC на XVF-3000), **Ch2-5 = сырые микрофоны**, **Ch6 = merged playback**. Правильный микшер = только Ch1 (= индекс 0) + аппаратная конфигурация HPFONOFF=1 (70 Hz, не 180 Hz default firmware) — иначе тихое «Р» в «Робот» режется и wake word теряется в STT.

> **Замечание для ревьюера.** Этот ADR закрывает документационный пробел, оставшийся после ретроспективы 09.08: код фикса в `audio_node.py` уже написан (PR #1093), unit-тесты добавлены (57 passed в `test_audio_node_echo.py`), но **README контракта, объясняющего новому разработчику «почему ВСЕ 6 каналов, а не только микрофоны»**, не существует. Task body дочерней карточки `t_523a1e60` описывал «минимальный фикс» (исключить Ch5-6) — это было **первое, откаченное решение**. **Round-2 supersede:** правильное решение — брать только Ch1 (DSP-processed), и это именно round-2 фикс.

## 1. Назначение

Зафиксировать **карту каналов** ReSpeaker Mic Array v2.0 в 6-канальном capture-режиме и **каноническую настройку `mix_channels`** для downstream-STT. Это нужно, чтобы:

1. **Новый разработчик**, видя в коде `mix_channels=[0,1,2,3,4,5]`, не считал это ошибкой и не «чинил» бы на `[0,1,2,3]` (что ломает Yandex STT — см. §3.2).
2. **AEC-референс** (Ch5/Ch6) использовался **намеренно** (несёт чистую цифровую копию фразы), а не «случайно попадал в микс» — это **фича**, не баг.
3. **Эхо-проблема** решалась на уровне **VAD/wake-word gate** (см. §3.4), а не на уровне микшера каналов — граница ответственности зафиксирована явно.
4. Все ссылки на «1-channel firmware» / «6-channels firmware» в `HARDWARE.md` и аудио-контракте указывали на **одну точку истины** — этот ADR.

## 2. Контекст и проблема

### 2.1 Что произошло в e2e (issue #1076)

E2E-прогоны голосового ассистента дают нестабильное распознавание:

```
yandex:empty(1322ms) → yandex:empty(1122ms) → vosk:ok
```

при этом Vosk распознаёт искажённо («рыбок» вместо «робот», «герметика» вместо «енотика»). На записи с микрофона робота (14с, чистая) — распознаёт стабильно. **Расхождение = качество прод-аудио на входе STT**.

### 2.2 Железо: ReSpeaker Mic Array v2.0 (UAC 1.0)

Чип XVF3800 (преемник XVF3000), 4-микрофонная решётка, **жёсткий лимит UAC1.0 full-speed + прошивки**:

| Параметр | Значение |
|---|---|
| Sample rate (нативно) | **16 kHz** (только 16k, 32k/44.1k/48k → re-интерполяция plughw, без качества) |
| Capture channels | **6** (4 микрофона + 2 playback-референса) |
| Playback channels | 2 |
| AEC на XMOS | Активен только в **1-channel firmware**; **в 6-канальном режиме отдаются сырые данные** |

### 2.3 Карта каналов (эксперимент, issue #1076 §3)

Тест: тон 440 Гц, amp 0.5, через `scsynth/jackd → ReSpeaker playback`:

| Канал (1-индекс) | Индекс (0-индекс) | RMS  | dB  | Что это |
|---|---|---|---|---|
| Ch1 | 0 | 288   | 49  | Микрофон 1 (тон через воздух, слабо) |
| Ch2 | 1 | 4514  | 73  | Микрофон 2 |
| Ch3 | 2 | 10622 | 80  | Микрофон 3 |
| Ch4 | 3 | 9969  | 80  | Микрофон 4 |
| **Ch5** | **4** | **11550** | **81** | **Playback reference — прямой эхо-референс (то, что играет робот)** |
| **Ch6** | **5** | **11550** | **81** | **Playback reference (клон)** |

Спектр подтверждает: Ch4/Ch5/Ch6 = чистый 440 Гц; Ch1 = 1319 Гц (микрофонный шум / гармоника). **В 6-канальном режиме аппаратный AEC к данным НЕ применяется — отдаются сырые микрофоны + playback-референс.**

### 2.4 Где ломалось: `audio_node.py` усреднял ВСЕ 6 каналов

`src/rob_box_voice/rob_box_voice/audio_node.py` (pre-#1076, ~строка 240):

```python
# Усреднение по каналам для получения моно
mono_data = audio_data.mean(axis=1).astype(np.int16)
```

Усреднялись **ВСЕ 6 каналов**, включая Ch5+Ch6 (playback-референс). Когда робот молчит — референс = тишина, всё ок. Когда робот **говорит (TTS) или играет музыка** (`supercollider → jackd → dmix_respeaker`) — голос робота/музыка **смешиваются в STT-сигнал** → Yandex `empty`, vosk галлюцинирует.

### 2.5 Наивный фикс (и почему он провалился)

PR #1079 (`4de3301a`) добавил `mix_channels` параметр и поставил дефолт `[0,1,2,3]` — **исключить Ch5/6**:

| Конфиг | Результат STT |
|---|---|
| `mix_channels=[0,1,2,3]` (только микрофоны) | `yandex:empty` **СТАБИЛЬНО** |
| `mix_channels=[0,1,2,3,4,5]` (все 6 каналов)   | `yandex:ok(1153ms)` **ПРИНЯТО!** |

**Root cause неочевидного поведения:** в e2e и реальной работе **фраза пользователя проигрывается через динамик робота** (paplay → ReSpeaker playback). Ch5/6 = **цифровой playback-референс = сама фраза в чистом виде** (без акустических потерь, шипения, комнатных отражений). Ch1-4 (микрофоны) получают только **ослабленную акустическую копию через воздух**. Усреднять только микрофоны = **выбросить самую чистую копию фразы** → слабый/грязный сигнал → Yandex `empty`.

PR #1079 был откачен (commit `826fc128`). PR #1093 (`9082e83d`) поставил канонический дефолт `[0,1,2,3,4,5]`.

## 3. Рассмотренные варианты

### Вариант А: «Исключить только микрофоны — усреднять Ch5/6» (теоретический)

- **Плюс**: максимально чистый сигнал (цифровой референс).
- **Минус**: STT буквально **не услышит ничего, кроме того, что сам только что проиграл** — это loop-back, а не пользовательская речь. Полностью ломает ассистента.

**Вердикт**: отклонён — это DBZ-решение (Dead By Zero).

### Вариант Б: «Минимальный — исключить только playback-референс (Ch5/6)» (PR #1079, ❌)

- **Плюс**: убирает эхо от TTS/музыки на уровне микшера.
- **Минус**: **выбрасывает саму фразу**, когда она проиграна через динамик робота (т.е. в e2e и реальной работе — **всегда**). Результат: `yandex:empty` стабильно (см. §2.5).
- **Дополнительный минус**: аппаратный AEC чипа (XVF3800) рассчитан на этот референс — без него попытки программного AEC в ноде не получают «сырой» эхо-сигнал для вычитания.

**Вердикт**: отклонён — откачен в `826fc128`, A/B воспроизводимо даёт `yandex:empty`.

### Вариант В: «Программный AEC — вычитать Ch5/6 из микса микрофонов» (issue #1076 §предложение 2)

- **Плюс**: полноценное эхоподавление на программном уровне; референс уже есть.
- **Минус**:
  - Усложняет `audio_node.py` (DSP, требует тонкой калибровки `gain`/задержки).
  - **Та же проблема, что в варианте Б**: в e2e фраза проиграна через динамик → референс = сама фраза → после вычитания получим тишину.
  - Дополнительная DSP-нода не нужна, пока VAD/wake-word gate решает проблему проще (см. вариант Г).

**Вердикт**: отложен — не нужен при текущей архитектуре (VAD/wake-word gate достаточны). Возможен follow-up, если в будущем понадобится barge-in / voice activity во время TTS.

### Вариант Г: «Все 6 каналов + эхо-защита на уровне VAD/wake-word gate» ✅ (PR #1093)

- **Плюс**:
  - **Сохраняет чистый цифровой сигнал** фразы (когда она через динамик).
  - **Сохраняет сырые микрофоны** (для случаев, когда фраза не через динамик — реальный голос пользователя в студийной тишине).
  - **Эхо-защита уже работает** на уровне VAD (`tts_grace_s=2.5` — игнорируем всё в течение 2.5с после TTS; `music_vad_threshold=6.0` — поднятый порог при музыке) и wake-word gate (`DialogueNode._on_stt` фильтрует по wake-word перед допуском в LLM).
  - **A/B-победитель**: `yandex:ok(1153ms)` — самое чистое и стабильное распознавание.
  - **Простой фикс**: одно поле `mix_channels` в `audio_node.py` + дефолт `[0,1,2,3,4,5]`.
- **Минус**:
  - Полностью зависим от **VAD/wake-word gate** — если они сломаются, эхо вернётся (но это **уже текущее состояние**, ADR не ухудшает).
  - Референс попадает в `/audio/audio` (RAW-стрим) — теоретически downstream-consumer (вне нашего кода) может на нём споткнуться. Наш единственный downstream — `stt_node` — фильтрует через `tts_grace_s` и Vosk fallback.

**Вердикт**: **принят** — лучший trade-off для текущей архитектуры и единственный A/B-валидированный вариант.

### Вариант Д: «1-channel firmware — аппаратный AEC в чипе» (issue #1076 §предложение 3)

- **Плюс**: AEC, beamforming, DoA, NS, dereverberation активны на XMOS — самый чистый сигнал «из коробки».
- **Минус**:
  - Теряем raw-доступ к 4 микрофонам (нужен для будущего beamforming-кастомизации и диагностики).
  - **Требует перепрошивки робота** — нельзя откатить удалённо, нужен физический доступ + DFU-режим + риск brick.
  - Не решает e2e-проблему «фраза через динамик» (см. §2.5) — там A/B уже дал ответ на железном уровне.

**Вердикт**: отклонён для текущего фикса — слишком invasive, не даёт дополнительной пользы поверх варианта Г.

## 4. Решение

Принимается **Вариант Г**: `audio_node.py` использует **все 6 каналов** (`mix_channels=[0,1,2,3,4,5]`), эхо-защита лежит на **VAD/wake-word gate**.

### 4.1 Канонические настройки

```yaml
# src/rob_box_voice/config/audio_node.yaml
audio_node:
  ros__parameters:
    sample_rate: 16000      # жёсткий лимит UAC1.0 (не 44.1k, не 48k)
    channels: 6             # все 6 каналов capture
    mix_channels: [0,1,2,3,4,5]  # PR #1093 default — все 6 (см. ADR-0012 §3.4)
    device_name: "ReSpeaker 4 Mic Array"
    device_index: -1
    chunk_size: 4096
    vad_threshold: 3.5
    tts_grace_s: 2.5        # анти-эхо: игнор 2.5с после TTS
    music_vad_threshold: 6.0  # при музыке поднятый порог (Fix C)
```

### 4.2 Карта каналов (каноническая)

| Индекс (0-индекс) | Имя (1-индекс) | Источник | Назначение |
|---|---|---|---|
| 0 | Ch1 | MEMS-микрофон 1 | Сырой микрофон (через воздух) |
| 1 | Ch2 | MEMS-микрофон 2 | Сырой микрофон |
| 2 | Ch3 | MEMS-микрофон 3 | Сырой микрофон |
| 3 | Ch4 | MEMS-микрофон 4 | Сырой микрофон |
| 4 | Ch5 | ReSpeaker playback ref L | **Цифровой playback-референс** |
| 5 | Ch6 | ReSpeaker playback ref R | **Цифровой playback-референс (клон)** |

> **Важно**: в 6-канальном capture UAC1.0 микрофоны **и** playback-референс мультиплексированы в один endpoint. Аппаратный AEC чипа **не работает** в этом режиме — отдаются сырые данные. См. [ReSpeaker wiki §Firmware](https://wiki.seeedstudio.com/ReSpeaker_Mic_Array_v2.0/#firmware).

### 4.3 Архитектурная диаграмма

### 4.4 Ключевые принципы

1. **Single Source of Truth для каналов**: этот ADR — единственная точка истины для карты каналов (0..5). `HARDWARE.md §3.4` ссылается сюда.
2. **Микшер ≠ анти-эхо**: `mix_channels` отвечает за **включение каналов**, не за эхо-защиту. Анти-эхо — на VAD/wake-word gate (отдельная ответственность).
3. **AEC-референс — фича, не баг**: Ch5/6 = самый чистый цифровой сигнал фразы (когда она через динамик). Исключение = потеря сигнала.
4. **A/B-валидация**: каждое изменение `mix_channels` дефолта должно пройти A/B на железе (робот 10.1.1.21) перед мержем. Логика: `[0,1,2,3]` ломает Yandex STT (см. §2.5).
5. **Референс доступен программно**: если в будущем понадобится программный AEC (вариант В из §3), Ch5/6 уже в массиве — нужен только DSP-блок.

## 5. Последствия

### 5.1 Положительные

- **`yandex:ok` восстановлен стабильно** (PR #1093, A/B 09.08: принято за 1153 мс).
- **Документация одноточечная**: новый разработчик видит ADR-0012 → понимает, почему `[0,1,2,3,4,5]`, а не `[0,1,2,3]`.
- **Тесты защищены**: `test_audio_node_echo.py` имеет `TestMixChannels` — покрывает дефолт `[0,1,2,3,4,5]`, opt-in `[0,1,2,3]`, legacy-пустой, невалидные индексы.
- **PR #1093 vs PR #1079**: объяснение, почему был откат, сохранено в git history (commit `826fc128`) и подытожено в этом ADR.

### 5.2 Отрицательные / компромиссы

- **Зависимость от VAD/wake-word gate**: если они сломаются — эхо вернётся. **Это унаследованный риск**, не регрессия. См. issue #989 (echo-loop fix `b64fb613`) — там же жила эхо-защита.
- **Playback-референс в `/audio/audio`**: любой внешний consumer (вне нашего кода) получит референс в данных. Наш единственный consumer — `stt_node` — обрабатывает корректно.
- **Не решает проблему «Barge-in» (перебивание TTS пользователем)**: для этого нужен программный AEC (вариант В, отложен). Текущая архитектура — turn-based (TTS → пауза → STT), barge-in не требуется.

### 5.3 Что НЕ меняется этим ADR

- **1-channel firmware** остаётся **возможной альтернативой** для будущей перепрошивки (вариант Д), но не канонической конфигурацией.
- **Аппаратный AEC** (XVF3800 в 1-channel режиме) не активируется — UAC1.0 multichannel capture несовместим с on-chip AEC.
- **Wake-word gate** (`DialogueNode._on_stt`) остаётся единственной защитой от случайного LLM-триггера эхом — НЕ переносится в микшер.
- **PR #1093** (юридически) ещё в очереди e2e — этот ADR фиксирует **намерение**, не факт merge. После зелёного e2e ADR остаётся; в комментариях у PR добавляется ссылка.

## 5.4 Как настроить `mix_channels` (quickstart для нового разработчика)

Этот раздел — прямой ответ на task `t_523a1e60` («как настроить `mic_channels`», буквально — `mix_channels`). Полный путь конфига:

```
src/rob_box_voice/config/audio_node.yaml   # канон для rob_box_voice
docker/vision/config/voice_assistant/voice_assistant.yaml  # оверрайд для compose
local_test/voice/*.launch.py              # локальные тестовые лаунчи
```

### 5.4.1 Канонический дефолт (НЕ трогать без A/B)

```yaml
audio_node:
  ros__parameters:
    sample_rate: 16000
    channels: 6
    mix_channels: [0, 1, 2, 3, 4, 5]   # ← канон (PR #1093, A/B-валидирован)
```

Почему **все 6**, а не `[0,1,2,3]`:

- `[0,1,2,3,4,5]` = Yandex STT OK за ~1153 мс.
- `[0,1,2,3]` = Yandex STT `empty` стабильно (PR #1079, откачен).
- Причина: в e2e фраза пользователя проиграна через динамик робота → Ch5/Ch6 = чистая цифровая копия фразы → её исключение = выбросить саму фразу (см. §2.5).

### 5.4.2 Если вы ДЕЙСТВИТЕЛЬНО хотите исключить Ch5/Ch6 (opt-in)

> **⚠️ A/B обязателен.** Меняйте только если на вашей инсталляции A/B показал иной результат, чем в issue #1076. Без A/B вы вернётесь к проблеме `yandex:empty`.

```yaml
audio_node:
  ros__parameters:
    sample_rate: 16000
    channels: 6
    mix_channels: [0, 1, 2, 3]   # только сырые MEMS-микрофоны
```

Что это означает на практике:

1. **Эхо от TTS / музыки НЕ попадёт в STT** (нет цифрового референса в миксе).
2. **Фраза, проигранная через динамик робота, тоже не попадёт** (тот же цифровой референс — он же «сама фраза в чистом виде»). Это и есть причина `yandex:empty` в e2e.
3. VAD/wake-word gate по-прежнему работает как анти-эхо (см. §3.4 вариант Г).

Если вы **отключаете TTS/music-воспроизведение через динамик робота** (например, вы тестируете изолированный STT без робота) — этот конфиг осмыслен и не приведёт к `empty`. В роботе в проде — **не включайте**.

### 5.4.3 Хотите аппаратный AEC — переключайтесь на 1-channel firmware

```bash
# Только если у вас есть физический доступ к роботу + DFU-кабель
# См. https://github.com/respeaker/usb_4_mic_array  →  dfu.py --download 1_channel_firmware.bin
```

В этом режиме:

- 1 канал обработанного аудио (AEC + beamforming + NS активны в чипе).
- `mix_channels: [0]` (единственный канал).
- Потерян raw-доступ к 4 микрофонам (нельзя сделать свой beamformer).
- Требует перепрошивки (brick-риск без DFU).

См. §3.4 вариант Д — почему это **не** канон для ROBBOX.

### 5.4.4 Программный AEC (если понадобится barge-in)

Если в будущем потребуется **barge-in** (прерывание TTS голосом пользователя), придётся:

1. Сохранить `mix_channels=[0,1,2,3,4,5]` (нужен референс Ch5/Ch6).
2. Добавить DSP-блок `audio_echo_canceller_node` между `audio_node` и `stt_node`: `out = mean(mics) - gain * mean(ref)`.
3. Тонкая калибровка `gain` и задержки — иначе артефакты.

Это ADR-0012 не покрывает — отложено (см. §3.4 вариант В, §6.3).
