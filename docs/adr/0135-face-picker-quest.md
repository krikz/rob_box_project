# ADR-0135 — Лицевые команды на капитанском мостике (Quest): список лиц + карточка с коллажом

**Дата:** 2026-09-25
**Статус:** Proposed
**Автор:** architect (товарищ Шифу, kanban t_0a407042 / issue #3026)
**Связанные:** issue #3026 (эта карточка), issue #3025 (парная Telegram-фаза, эталон коллажа и формата `/faces`/`/face`), ADR-0027 (§3 «единый multiplexed WSS», §3.1 транспорт, §2 latency-budget), ADR-0080 (§2.2 инвариант 3 — каталог как SSOT), ADR-0089 §8 (бывшая строгая политика лица), ADR-0123 (режимы приватности лиц), ADR-0129 (DJ/persona swap — пример JSON_CMD-расширения), `docs/architecture/captain-bridge.md`, `docs/architecture/meta-quest-api.md`.

## 1. Контекст

Telegram-фаза лицевых команд (#3025, в работе параллельно) добавляет оператору две команды — `/faces` (список) и `/face <id>` (карточка с коллажем 4×3 из последних встреч). Задача #3026 ставит тот же функционал в 3D-интерфейсе «капитанский мостик» (`src/rob_box_quest/webxr_client/`, Three.js + WebXR на Meta Quest). ADR-0123 §8 явно перечисляет «Quest: панель галереи и таймлайна встреч. Отдельная карточка, после Telegram» — это и есть реализация пункта 8 из ADR-0123 §9.

Ключевое отличие от Telegram (см. #3026 «Ключевое отличие от Telegram»): **Quest — отдельное устройство**, общего тома с Vision Pi нет. Данные лиц должны доехать через существующий канал `rob_box_quest` (aiohttp WSS на Vision Pi, порт 8765 в ADR-0027, §3.1 — WSS-фрейм с `stream_id`). Сервер `rob_box_quest` живёт на Vision Pi → физически МОЖЕТ читать `/data/faces` напрямую (примонтировать `./data/faces:/data/faces:ro`, тот же приём, что в #3025 для Telegram-бота). Это упрощает транспорт: сервер читает диск и отдаёт готовое.

Задача этой ADR — **спроектировать** (не реализовать) и зафиксировать выбор по пяти открытым вопросам #3026: (1) транспорт, (2) сборка коллажа (где живёт PIL), (3) UI в 3D, (4) гейт приватности, (5) объём данных / латентность, плюс отдельно (6) слияние дублей.

## 2. Решение (TL;DR)

| # | Вопрос | Решение |
|---|---|---|
| 1 | Транспорт | **Расширяем существующий WSS** (JSON_CMD + JSON_EVENT по `voice_list`/`preview_voice_audio`-шаблону). **Не** вводим HTTP-параллель рядом с `/healthz` и **не** заводим stream в `STREAM_CATALOG`. |
| 2 | Сборка коллажа | Общий чистый Python-модуль (без ROS, импортится из Telegram-бота и из `rob_box_quest`). Сервер отдаёт ОДИН готовый JPEG (4×3). |
| 3 | UI в 3D | Двухпанельная композиция по образцу `tts_picker_menu`: список лиц (floating panel, raycast через PointerSystem) → выбор → панель карточки с коллажем. |
| 4 | Гейт приватности | Уже существующая WSS-PIN-аутентификация = эквивалент `@authorized` для Telegram. Дополнительный гейт не нужен. Режим (`workshop`/`exhibition`/`strict`) — ответственность `FaceStore`, не Quest. |
| 5 | Объём/латентность | Список лиц — JSON единицы КБ; коллаж — один BINARY_FRAME ~150 КБ JPEG. Запросы по нажатию кнопки, не поток — не конкурируют с teleop-latency-бюджетом (ADR-0027 §2). |
| 6 | Слияние в Quest | **Не делаем в этой фазе.** Это пишущая операция с конфликтом против живой `vision_face_node` (ADR-0123 §6); правильное решение будет принято в #3025 §4 (один лёгкий канал к ноде или отказ). Quest повторит тот же выбор, не плодит второй механизм. |

Один общий принцип пронизывает все шесть решений: **архитектурная симметрия с уже работающими механизмами** (Telegram-фаза #3025, voice_picker в `rob_box_quest`, tts_picker_menu в WebXR-клиенте). Мы не плодим новые параллельные каналы и модули там, где уже есть рабочий шаблон. ADR-0080 §2.2 инвариант 3 («каталог — SSOT, никаких параллельных данных») трактуем расширенно: и для wire-каталога, и для «как сервер отдаёт медиа-данные клиенту».

## 3. Транспорт — почему WSS, а не HTTP и не STREAM_CATALOG

Три кандидата из #3026 §1:

### 3.1 Кандидат A: HTTP-эндпоинты на aiohttp (`GET /faces`, `GET /face/<id>/collage.jpg`)

- **Плюсы:** Просто клиентом (URL + fetch). Декодирование JPEG в Three.js тривиально (`THREE.TextureLoader` → `CanvasTexture`).
- **Минусы:** Ломает ADR-0027 §3 принцип 1 («единый multiplexed WSS, фреймы тегируются stream_id; проще балансировать, нет гонки за N портов, нет CORS»). Открывать второй endpoint рядом с `/quest` WSS и `/healthz` — это тот же класс «N портов», против которого ADR-0027 §3.1 явно высказался. Дополнительная поверхность для TLS-сертификата (у нас уже self-signed на WSS, второй endpoint удвоит предмет конфигурации). Параллельный канал без heartbeat — отдельный watchdog для лиц.
- **Вердикт:** **Отвергнут.** Идёт вразрез с ADR-0027 §3.

### 3.2 Кандидат B: расширение существующего WSS (JSON_CMD + JSON_EVENT + BINARY_FRAME)

Это уже работает для `voice_picker` (см. `src/rob_box_quest/rob_box_quest/quest_node.py:752` `list_voices_snapshot()` → `JSON_EVENT{type:"voice_list"}`; `src/rob_box_quest/rob_box_quest/server/ws_server.py:424-430` `set_voice`/`preview_voice` через `/avatar/set_voice` + `/avatar/preview_voice/audio`). Каталог команд — `rob_box_core.bridge_protocol` (ADR-0080 §2.2 SSOT). Сервер-инициатор BINARY_FRAME используется для потокового видео (`camera_rear` и т.п.), но формат не запрещает передать и одиночный JPEG-кадр — это будет всё тот же `stream_id`, выданный `subscribe_ack`-ом.

Предлагаемая схема (аналогия 1:1 с `voice_picker`):

```
# Каталог команд (rob_box_core.bridge_protocol, регенерация через tools/gen_bridge_protocol_ts.py)

JSON_CMD {cmd:"face_list"}                       → JSON_EVENT {type:"face_list", persons:[{person_id,name?,speaker_id,encounter_count,photo_count,gallery_cohesion,mode_recorded,has_collage}, ...]}
JSON_CMD {cmd:"face_get", person_id:"<id>"}      → JSON_EVENT {type:"face_get_ack", person_id, summary:{...}, stream_id:<allocated>}  # анонс «коллаж сейчас поедет»
JSON_CMD {cmd:"face_get", person_id:"<id>"}      → BINARY_FRAME на stream_id из ack, payload = JPEG bytes (4×3, max ~150 КБ)
                                                  → JSON_EVENT {type:"face_get_done", person_id, stream_id, bytes}
                                                  # или JSON_EVENT {type:"face_get_nack", reason:"no_photos"|"strict_mode"|"exhibition_stranger"|"unknown_person"}

# Если режим privacy == "strict" — server отдаёт NACK с reason:"strict_mode"
# (UI рисует честный «снимки отключены режимом приватности» — ADR-0018).
```

- **Плюсы:** Не плодит параллельные каналы (ADR-0027 §3). Heartbeat и watchdog уже есть. Гейт аутентификации (HELLO+session_pin, `_on_hello` в ws_server.py:1691) — бесплатно. Каталог команд расширяется через тот же `rob_box_core.bridge_protocol` SSOT, типы регенерируются в `wire/protocol_generated.ts` (ADR-0080 §2.2 инвариант 3). Точно повторяет образец `voice_list`/`preview_voice_audio`, который уже работает в проде.
- **Минусы:** Требует одной правки в каталоге + регенерации типов. Двухшаговая операция (`face_get` → ack со stream_id → BINARY_FRAME) чуть сложнее, чем HTTP GET — но она уже реализована для превью-голоса.
- **Вердикт:** **Выбран.** Прямая аналогия с работающим механизмом; единственный когнитивный overhead — обновление каталога и регенерация TS.

### 3.3 Кандидат C: новый `STREAM_CATALOG` stream_id («face_collage»)

- **Плюсы:** Внешне похоже на видео-поток.
- **Минусы:** `STREAM_CATALOG` (см. `src/rob_box_quest/rob_box_quest/streams/registry.py:11-16`) — это каталог непрерывных потоков (ROS-топики через Zenoh + camera_direct). Одиночный JPEG по запросу — это не поток, это RPC. Завести его в `STREAM_CATALOG` — значит расширить семантику каталога за пределы его смысла. Подписка/отписка на «коллаж» бессмысленна (он не идёт непрерывно).
- **Вердикт:** **Отвергнут.** Семантически не тот класс данных.

## 4. Сборка коллажа — общий модуль, серверная сторона

Решает #3026 §2.

### 4.1 Решение

Коллаж собирает **сервер** (`rob_box_quest`, где живёт PIL — Vision Pi уже имеет `python3-pil` в зависимостях). Сборка — **общий чистый модуль** без зависимости от ROS, импортируется двумя вызывающими:

1. Telegram-бот (`src/rob_box_telegram/...`, карточка #3025) — для команды `/face <id>` (уже запланировано в #3025 как «отдельная чистая функция, юнит-тестируемая без ROS»).
2. `rob_box_quest` (эта карточка) — для `face_get` → BINARY_FRAME.

Структура модуля (предложение — конкретное имя и путь уточнит карточка реализации):

```python
# src/rob_box_core/face_collage.py  (или src/rob_box_quest/face_collage.py —
# решает backend-воркер, ключевое требование: importable без ROS)
def build_face_collage(person_dir: Path, *, grid: tuple[int,int]=(4,3)) -> bytes:
    """JPEG bytes, 4×3 grid (reference + encounter crops), пустые ячейки — белый фон.
    Raises FaceCollageUnavailable (с reason) если режим privacy запрещает
    снимки или у человека нет ни одного фото."""
```

Чистый pytest без `rclpy`/`aiohttp`/`Zenoh`/`docker`. Это уже требование #3025 («оформить отдельной чистой функцией, как `rebuild_gallery()` в `face_store_admin.py`, чтобы юнит-тестировать без ROS/без железа») — повторяем требование, выполняем оба раза через один модуль.

### 4.2 Альтернативы, отвергнутые

- **Рендерить коллаж на клиенте из отдельных кропов.** PIL в TS нет; тащить canvas-композицию — лишний код, плюс 11 отдельных JPEG по сети вместо одного.
- **Генерировать коллаж в Telegram-боте, отдавать клиенту готовый JPEG через внешний URL.** Нарушает «всё — на Vision Pi» (ADR-0123 §11: «эмбеддинги и снимки не покидают Vision Pi, кроме сравнения из §7»). Да и хранить коллаж на диске только ради отдачи клиенту — лишнее состояние.

## 6. Гейт приватности

Решает #3026 §4.

### 6.1 Решение

Дополнительного гейта **не вводим**. Уже существующая WSS-PIN-аутентификация (`HELLO{session_pin}` → `_on_hello` в `ws_server.py:1691` → `mark_authenticated` в `session.py:178`; `AUTH_FAIL` → закрытие сокета с кодом 4001) — это **уже эквивалент** `@authorized` для Telegram: пока WSS не прошёл HELLO, клиент не получает ни одного `face_list`/`face_get_ack` события. Heartbeat/watchdog не пускают неавторизованную сессию долго (WATCHDOG_TIMEOUT_S = 0.6 с, `session.py:143`).

Это согласуется с ADR-0123 §11 «Эмбеддинги и снимки не покидают Vision Pi, кроме сравнения из §7» — данные лиц остаются внутри Vision Pi → rob_box_quest → WSS → Quest; наружу (интернет) не уходят.

### 6.2 Поведение по режимам (ADR-0123 §2)

| Режим | Список лиц | Коллаж знакомого | Коллаж незнакомого |
|---|---|---|---|
| `workshop` | все 7+ | да | да |
| `exhibition` | только знакомые (незнакомцы живут в памяти, не на диске — `FaceStore.gallery()` отдаёт пусто) | да | nack `exhibition_stranger` |
| `strict` | имена + эмбеддинги, без снимков | nack `strict_mode` (UI: «снимки отключены режимом приватности») | nack `strict_mode` |

Решение о том, отдавать ли JPEG, принимает **серверная сторона** (`FaceStore.gallery(person)` → проверка `mode_recorded`; ADR-0123 §5 «режим передаётся ему при создании, и каждое решение "писать ли на диск / отдавать ли в облако" принимается внутри него»). Quest-клиент не знает про режим — он только рисует `nack` честным текстом (ADR-0018).

### 6.3 Альтернативы, отвергнутые

- **Отдельный PIN-код для face-команд (как `@authorized` поверх WSS-PIN).** Удваивает auth-поверхность без пользы: WSS-сессия уже уникальна и закрыта. Оператора, попавшего в WSS, мы уже считаем авторизованным.
- **Передавать режим на клиент и решать там.** Нарушает ADR-0123 §5 («режим передаётся ему при создании, и каждое решение принимается внутри него»). Клиент тогда сможет случайно показать снимок в `strict` при баге в маппинге.

## 7. Объём данных и латентность

Решает #3026 §5.

### 7.1 Размеры

- **face_list**: JSON, ~1–2 КБ при ≤50 человек (типично), ≤10 КБ при 500 (предел ADR-0123 §10). Один раз при открытии меню, плюс re-fetch по требованию (после `merge`/`forget`).
- **face_collage**: JPEG 4×3, ~150 КБ при 11 кропах 200×200 + белый фон + подписи (оценка по аналогии с tts pregen 64 КБ). По сети Wi-Fi 100 Mbps это ~12 мс.
- **face_summary**: JSON, единицы сотен байт (метаданные из `meta.json`).

### 7.2 Латентность

ADR-0027 §2 задаёт budget «round-trip ≤200 мс комфортно, ≤400 мс терпимо» **для teleop-потока**. Наш сценарий — **запрос по требованию**, не поток. Один `face_get`:

1. Клиент шлёт JSON_CMD (≤ 100 байт).
2. Сервер: читалка диска `/data/faces/<id>/` + сборка коллажа PIL → JPEG (~50–100 мс на Vision Pi для 11 кропов; первый вызов может быть медленнее из-за disk cache).
3. Сервер шлёт BINARY_FRAME (~150 КБ) → клиент декодирует JPEG в `CanvasTexture` (~30 мс).

Итого end-to-end: **≤200 мс** в установившемся режиме. Это **укладывается** в тот же ≤200 мс бюджет, что и для teleop — но **не конкурирует** с ним: face-команды инициируются **только по нажатию кнопки** в VR (раз в несколько минут в худшем случае), а teleop-поток — 60 Гц видео. WSS-канал обрабатывает оба независимо (heartbeat 200 мс, см. `HEARTBEAT_INTERVAL_S` в `session.py:141`).

### 7.3 Альтернативы, отвергнутые

- **Стримить коллаж непрерывно (как видео-поток в `STREAM_CATALOG`).** Не имеет смысла — оператор смотрит карточку разово, потом листает дальше.
- **Предзагружать все коллажи при открытии списка.** Лишний трафик (десятки МБ при десятках человек), лишний расход диска PIL на стороне сервера. По требованию — дешевле.

## 8. Слияние дублей в Quest

Решает #3026 §6.

### 8.1 Решение

**Не делаем в этой фазе.** Это пишущая операция с тем же классом проблем, что и для Telegram (#3025 §4 «Слияние vs живая нода»): `vision_face_node` держит `/data/faces` в памяти и переписывает `meta.json` при следующей встрече, поэтому любой merge из «лёгкого канала к ноде» требует pgrep-гейта против живой ноды.

Решение по merge-каналу будет принято в #3025 (открытый вопрос §4, варианты a/b). Quest повторит тот же выбор, **не плодит второй механизм**. Если в #3025 выбран вариант «лёгкий командный канал к ноде» — этот канал расширяется на Quest в следующей карточке. Если выбран «только `face_store_admin.py` с остановкой ноды» — Quest его не реализует вовсе.

UI в этой фазе для merge: кнопок нет (только `OPEN` для карточки, `CLOSE` для закрытия). Сводка карточки показывает число встреч и число фото — оператор видит, что пора слить, и идёт в Telegram.

## 9. Связка с #3025 (Telegram-фаза)

| Часть | Telegram (#3025) | Quest (эта ADR) |
|---|---|---|
| Хранилище | `:ro` волюм `/data/faces` в `telegram-bot` | `:ro` волюм `/data/faces` в `rob_box_quest` |
| Сборка коллажа | общий модуль `face_collage.build_face_collage()` | тот же модуль |
| Список лиц | команда `/faces` → текстовая таблица | `JSON_CMD{cmd:"face_list"}` → JSON_EVENT → строки меню |
| Карточка лица | `/face <id>` → фото коллажа + сводка текстом | `JSON_CMD{cmd:"face_get", person_id}` → ack + BINARY_FRAME(JPEG) + JSON_EVENT `face_get_done` |
| Гейт доступа | `@authorized` (chat_id в белом списке) | WSS-PIN (`session_pin` в HELLO) |
| Merge | отдельная задача (открытый вопрос §4) | не в этой фазе (см. §8) |
| Suspicious | отдельная задача (открытый вопрос §4) | не в этой фазе |

## 10. Объём работ (карточки для реализации)

В духе ADR-0013 (incremental delivery) — отдельные карточки, не один большой PR.

1. **Сборка коллажа — общий модуль + юнит-тесты.** `face_collage.build_face_collage()` с тестами на разметку 4×3, подписи размеров, обработку `face_snapshot=null` (из #3025 §«Спека команд»). Без ROS, без `aiohttp`.
2. **Wire-каталог: face_list / face_get.** Правки в `rob_box_core.bridge_protocol` (новые `CommandSpec`/`EventSpec`), регенерация `protocol_generated.ts` (`tools/gen_bridge_protocol_ts.py`), добавление полей в `wire/messages.ts` (по образцу `VoiceInfo`). Тесты на каталог — обязательны (ADR-0080 §2.2 инвариант 3 + ADR-0057 namespace-collision-guard).
3. **Серверная сторона:** `FaceStore`-readonly-фасад в `rob_box_quest` (тонкая обёртка вокруг `face_collage.build_face_collage()` + обработка `mode_recorded` из meta.json → nack-причины). JSON_CMD-handler в `ws_server.py` (по образцу `set_voice`). Тесты на nack-причины (strict/exhibition-stranger/unknown-person).
4. **WebXR scene:** `scene/face_picker_menu.ts` + `scene/face_card_panel.ts` + `state/face_picker_state.ts`. Юнит-тесты на state (по образцу `tts_picker_state` тестов).
5. **E2E voice-команда:** «Робот, покажи лица» — готовится как e2e-команда в `.github/e2e/voice_commands/`, прогоняется отдельным e2e-процессом (НЕ этой карточкой; см. контракт воркера).
6. **Docker-compose:** добавить `./data/faces:/data/faces:ro` в сервис `rob_box_quest` (как в #3025 для `telegram-bot`).
7. **(Опционально, не блокер)** merge/suspicious — после решения в #3025.

## 11. Последствия

### Плюсы

- **Симметрия с работающими механизмами.** Один WSS-канал, одна схема каталога, один UI-шаблон, один auth-гейт. Когнитивная нагрузка на команду = ноль: «как голоса».
- **Переиспользование коллажа.** Один чистый модуль = одна кодовая база для PIL-сборки; тесты пишутся один раз.
- **Приватность без нового гейта.** Режим решается в `FaceStore` (ADR-0123 §5), Quest честно рисует `nack`.
- **Латентность не конкурирует с teleop.** Запросы по требованию, не поток.

### Минусы и риски

- **Двухшаговый протокол `face_get` → ack+stream_id → BINARY_FRAME.** Чуть сложнее, чем HTTP GET. Компенсируется тем, что образец `preview_voice_audio` уже работает.
- **Зависимость от `rob_box_core.bridge_protocol` SSOT.** Любая правка wire-каталога требует регенерации TS. Это не новое требование — уже так для `voice_*` (см. `wire/protocol_generated.ts` header).
- **`exhibition`/`strict` пока не имеют UI-обвязки на стороне Quest.** В этой фазе `nack` рисуется стандартным toast'ом (`createToast` в `main.ts:58`); полноценный режим-aware UI — отдельная карточка, потому что это уже про «как Quest показывает приватность вообще», а не только про лица.
- **Не закрывает merge/suspicious.** Это сознательное решение (§8); владелец может передумать — тогда это новая карточка, а не дописывание этой.

## 12. Что НЕ делаем в этой фазе

- Не вводим HTTP-эндпоинты на aiohttp (ADR-0027 §3 принцип 1).
- Не заводим stream в `STREAM_CATALOG` (семантически не поток).
- Не дублируем PIL-сборку между Telegram-ботом и Quest (один модуль).
- Не дублируем merge-механизм в Quest (ждём решения в #3025).
- Не вводим отдельный PIN/gate для face-команд (уже есть WSS-PIN).
- Не передаём режим приватности на клиент (ADR-0123 §5: решение принимает `FaceStore`).
- Не пишем реализацию в этой карточке — это design-ADR (см. задачу «продумать, БЕЗ реализации»).

## 13. Открытые вопросы для владельца

1. **Сортировка в списке.** Telegram сортирует «именованные первыми» (#3025 §«Спека команд»). В Quest — тот же порядок? Подтвердить, чтобы UI был предсказуем между платформами.
2. **Число строк в пейджере.** `tts_picker_menu` показывает до 8 строк (`MAX_VISIBLE_ROWS = 8`). Для лиц, где имён может быть мало и каждая строка несёт больше данных (имя + speaker_id + encounter_count), 6–8 строк выглядит разумно. Подтвердить конкретное число или оставить на усмотрение backend-воркеру.
3. **Голосовая активация.** E2E-команда «Робот, покажи лица» — очевидный кандидат. Другие команды («Робот, лица», «Робот, открой карточку Дэнчика»)? Если да — нужно ли поддержать «выбор лица голосом», или только кнопками в VR? **По умолчанию (рекомендация архитектора): только кнопками в VR**, голосом — только открыть/закрыть меню (как «Робот, открой настройки голоса» уже есть). Выбор лица голосом — это новая фича (отдельная карточка), а не часть этой.
4. **Иконка/аватар вместо текстового имени.** На Quest можно показать миниатюру 64×64 в строке списка (из того же JPEG, что и коллаж — кроп `reference.jpg`). Это улучшает узнаваемость, но +1 запрос на каждую строку. По умолчанию (рекомендация): **нет**, текстовое имя достаточно; иконку добавим отдельной карточкой, если попросят.
