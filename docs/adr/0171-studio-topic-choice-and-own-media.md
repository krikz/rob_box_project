# ADR-0171: Студия выбирает тему по интересности, а медиа берёт своё

| Поле | Значение |
|---|---|
| Статус | Accepted (реализуется в #4702) |
| Дата | 2026-11-13 |
| Автор | Архитектор (по разбору товарища Шифа от 13.11 и issue #4702) |
| Домен | Контент-студия (канал @robbox_project) |
| Контекст | Товарищ Шифу 13.11: «почему студия предложила всего один всратый пост? Там же за неделю было много работы, там и робот ездил по складу как пылесос, полно разных данных, а студия мне выдала скучный пост про то, что в окне на лицо робот ловит шум». Разбор #4702 нашёл, что отбор темы в студии есть только по виду факта, прогоны робота в факты не попадают вовсе, а картинка к посту не обязана быть про его тему |
| Затрагивает | `scripts/telegram/studio_topic.py` (новый), `studio_facts.py`, `studio_draft.py`, `studio_media.py`, `studio_jobs.py` |
| Родители | ADR-0148 (код решает, LLM говорит), ADR-0170 (студия готовит материал каждый день; молчание — не отказ), решение Шифа 06.11 (готовый пост с графикой; публикация только после кнопки), решение Шифа 07.11 (в постах нет внутренней кухни) |
| Связанные | #4702 (эта задача), #4700 (ADR-0170), #4492 (исходная задача студии) |

## Проблема

Сессия 13.11 собрала **44 видимых факта** и предложила **один** пост — и выбрала худший.
Факты были, отбора не было.

### Корень 1: отбора «интересного читателю» не существует

`studio_draft.pick_fact` сортировал факты только по **виду**:

```python
KIND_PRIORITY = ("merged_pr", "media", "adr", "decisions", "run", "closed_issue")
```

Внутри вида брался **первый** в списке, а список отсортирован как вернул GitHub — то есть
**по свежести**. Итог: побеждал самый свежий `fix(voice): keep rejected STT silent`
(PR #4697), и именно он стал темой поста. Тематический отсев `VISIBLE_TOPICS` отвечает
на вопрос «показывать ли вообще», а не на «что интереснее».

Скоринга нет: `grep -i 'score|rank|priorit|weight'` по `studio_facts.py` и `studio_draft.py`
находит только `KIND_PRIORITY`.

### Корень 2: прогоны робота в факты не попадают вообще

Материал богат, но лежит не в том слое, откуда берутся факты:

- `docker/studio/run/media/video/material/depot/` — 217 кадров камеры сверху,
  `maprec/poses.csv` (255 КБ), `route.log` (2480 строк, 7 целей маршрута);
- песочница `ros2@10.1.1.250:/home/ros2/rob_box_hilvideo/out` — 9 прогонов
  (`studio_material.runs_catalog`), у прогона `depot4495_20261111T182530Z` в
  `maprec/meta.json` лежат настоящие цифры: 915 снимков карты, 13 803 строки поз,
  1406 с симуляции.

`studio_facts.py` умеет пять сборщиков: `collect_merged_prs`, `collect_closed_issues`,
`collect_runs`, `collect_new_files_by_git`, `collect_new_files`. Прогонов робота среди них
нет. `studio_material.runs_catalog` вызывается только из `studio_motion.py` — то есть по
запросу ролика, а не как факт.

Итог: «склад Depot» — это **ролик по запросу**, а не тема поста. Модель его не видит.

### Корень 3: картинка к посту — таймлайн, а не то, о чём пост

`studio_media.options` для факта `pr:4697` даёт единственный вариант —
`infographic:timeline`: картинка «Что изменилось у РОББОКСа» со **списком из пяти последних
PR**, а не картинкой про распознавание речи. Пост про голос + картинка «список изменений»
= то самое скучное сообщение.

Правило «медиа поста — своё» (`studio_media.own_media`) работает только для медиа-фактов
**того же PR**. У прогона робота своего медиа-факта нет вообще: прогоны не факты.

## Решение

### 1. Отбор — по интересности, и по интересности решает код

Новый модуль `scripts/telegram/studio_topic.py`: чистые функции, без сети и без модели.
`rank(facts)` сортирует факты, складывая очки из названных величин:

| Очки | Что | Зачем |
|---|---|---|
| вес вида | `robot_run` > `merged_pr` ≈ `closed_issue` > `media` > `adr`/`decisions` > `run` | прогон робота — событие, `fix(...)` — правка |
| масштаб события (0…40) | прогон: цели маршрута и секунды симуляции; PR: число изменённых файлов | большая фича важнее правки в один файл |
| интерес читателю (0…20) | в claim есть поведение робота: навигация, локализация, карта, маршрут, склад, лицо, музыка, голос, микрофон, симуляция | читателю видно, что изменилось в роботе |
| картинка (+10) | у факта есть своё медиа | пост с картинкой своей темы |
| штраф за показанное | факт уже показывали (`attempts > 0`) | не предлагать одну и ту же тему дважды подряд; из очереди факт **не убирается** |
| свежесть | только последний tie-breaker | свежесть не вытесняет интересное |

Правило живёт в коде, а не в промпте (ADR-0148). Модель по-прежнему только пишет текст
выбранной темы.

### 2. Прогоны робота — факты первого класса

`studio_facts.collect_robot_runs` берёт каталог прогонов с песочницы тем же гейтом, что и
ролики (решение Шифа 06.11: студия сама берёт данные с хостов, только на чтение) и делает
по факту на прогон:

- `claim` — читательским языком и только своими числами: «Робот прошёл склад: 7 целей
  маршрута, 1406 с симуляции, 915 снимков карты»;
- `source` — читательская подпись («журнал прогонов РОББОКС»): она же идёт в подвал
  инфографики, поэтому проверяется тем же `is_public`;
- идентификатор прогона лежит в отдельном поле, которое модели не показывается
  (`studio_text.extract_fact_text` отдаёт модели только `claim`, `source`, `evidence`) —
  иначе модель перепишет его в текст, а проверка чисел отклонит пост;
- ключ факта устойчивый: `robot_run:<run_id>` (префикс `run:` уже занят прогонами Actions).

Коллектор не падает: нет ключа, хост недоступен, нет `meta.json` — пустой список и честная
строка в stderr. Дневная сессия из-за этого встать не может.

`VISIBLE_TOPICS` дополнен словами поведения робота (склад, депо, локализац, карта,
маршрут, заезд, проезд) — иначе материал есть, а в ленту не попадает.

### 2а. Незавершённая работа и отладочные прогоны — не материал

Проверка нового отбора на настоящих фактах сессии 13.11 вскрыла две дыры, которые
отбор сам по себе не закрывает.

**Незавершённые правки.** Заголовок, начинающийся с `WIP `, — это черновик: работу
ещё не доделали, показывать её читателю нельзя. Прежний отсев технических правок
(`is_boring`) смотрит на начало названия, а `WIP refactor(e2e): …` начинается с `WIP `,
а не с `refactor(` — поэтому такая правка проходила в ленту как видимая, и семь
изменённых файлов давали ей больше очков масштаба, чем содержательной правке о
музыке в голосе. Отсев WIP — на границе «что показывать», рядом с остальными
техническими правками.

**Слова репозитория — не интерес читателю.** `e2e`, `refactor`, `ci`, `chore` — про
стенд и репозиторий; читатель канала этого не видит и в интерес не входят.

**Отладочные прогоны.** Песочница содержит не только «чистые» прогоны, но и
отладочные варианты одного и того же замера (`…_debug_…_r3`, `…_r5`, `…_r7`,
`…_diag_…`, `…_recur1`): пять вариантов одного baseline, у каждого своя цифра.
Как отдельные факты они дают шум — пять одинаковых по смыслу тем. Считать
событием нужно один замер, а не его отладочные повторы.

### 3. Медиа — своё к теме; таймлайн — последний вариант

`studio_media.options` возвращает варианты в таком порядке:

1. своё медиа поста;
2. медиа-факты того же факта или того же PR;
3. **карточка цифр темы** (`infographic:numbers`) — если у выбранного факта есть свои числа:
   цели маршрута, секунды симуляции, снимки карты; каждая цифра со своим источником,
   как требует `infographic.validate_spec`;
4. `infographic:timeline` — **последним**. Сегодня он был единственным вариантом для PR
   без своего медиа, и это и давало «пост про голос + список изменений».

Картинка проходит ту же проверку публичности, что и таймлайн: если на неё попала бы
внутренняя кухня, код откажется рисовать.

### 4. Количество тем за сессию — один готовый пост

Решение Шифа 06.11 (PR #4504) заменило «список идей» готовым постом с графикой; оно
сохраняется. Одна сессия — один пост об одной теме. Остальные факты ждут очереди
(`studio_state.pending`), показанные раньше теряют приоритет, поэтому за неделю темы
разные, а не одна и та же.

## Ответы на вопросы issue #4702

Вопросы были заданы до реализации; ответы следуют из слов товарища Шифа 13.11
(«за неделю было много работы… робот ездил по складу… полно разных данных») и из
решения 06.11:

1. **Сколько тем за сессию?** Один готовый пост (решение 06.11). Материал при этом
   готовится каждый день (ADR-0170), и за неделю темы успевают смениться: показанное
   раньше теряет приоритет, непрочитанное ждёт очереди.
2. **Свежесть или масштаб?** Масштаб и интерес. Свежесть — только последний
   tie-breaker (пункт 1 таблицы очков).
3. **Прогоны робота в ленту по умолчанию?** Да, иначе половина работы над роботом
   читателю не видна (пункт 2).

## Отвергнуто

- **Список тем за сессию** — противоречит решению Шифа 06.11 (готовый пост с графикой)
  и правилу «одна тема — один пост»; отбор чинится ВНУТРИ одного поста, а не вместо него.
- **Скоринг моделью** — ADR-0148: выбор темы решает код; модель получает уже выбранный
  факт и пишет текст.
- **Автопостановка в очередь** — ломает решение 06.11 (публикация только после кнопки).
- **Новый источник данных (своя телеметрия робота)** — лишняя работа: прогон, карта,
  маршрут и цифры уже есть на песочнице, доступны read-only и проверяемы.

## Последствия

**Хорошо:**
- студия выбирает тему по интересности читателю, а не по свежести правки;
- «робот ездил по складу» становится темой поста, а не только роликом по запросу;
- картинка соответствует теме: цифры прогона вместо списка чужих PR;
- правило остаётся проверяемым кодом: очки — константы, порядок — детерминированный.

**Цена:**
- ещё один модуль в слое студии (`studio_topic.py`) и связь `studio_facts` → `studio_material`;
- сессия ходит на песочницу за каталогом прогонов (кеш метаданных на диске — повторно не качает);
- правило отбора — в коде, поэтому «а почему она выбрала это» отвечает код, а не модель.

## Проверка

`tests/unit/scripts/test_telegram_studio_topic_choice.py` — 8 тестов:

- из трёх фактов (два мелких `fix(...)` и один прогон) первым идёт прогон — регрессия 13.11;
- свежесть не вытесняет интерес: свежий скучный PR проигрывает более крупному роботному;
- показанный раньше факт опускается, но остаётся в списке;
- ключ прогона устойчив (`robot_run:…`);
- коллектор с подставным гейтом даёт факт со своими числами и без идентификатора прогона
  в claim/source/evidence;
- коллектор с падающим гейтом возвращает пустой список и не бросает исключение;
- для поста о прогоне `infographic:numbers` идёт раньше `infographic:timeline`;
- `numbers_spec` даёт 2…4 пункта с источником и проходит проверку публичности.

Плюс смоук студии `scripts/telegram/studio_smoke.py` и регресс-набор
`tests/unit/scripts/test_telegram_studio_daily_material.py`.
