## Проблема

Замер боевого состояния 27.11 показал четыре поломки. Три — механические, одна — архитектурная.
Первые три складывались в одну цепочку: сломанный TTL → черновики копятся → выбрать один
нечем → кнопка не строится → посты не одобряются → в очереди пусто → публикатор стоит.

### 1. Кнопка «post» не появляется (корневая поломка)

`reply_to_shifu` (`scripts/telegram/channel_studio.py:882`) спрашивает черновик через
`active_draft(state)` **без `reply_to`** (`channel_studio.py:894,908`), а `active_draft`
(`channel_studio.py:692-705`) ведёт в `studio_intent.target(state, "", None)`
(`studio_intent.py:176`). При четырёх черновиках на обсуждении `target` не может выбрать:
`reply_to` пуст, имя не названо, цитаты нет, «только что показанный» (< 30 мин) и
«недавний» (< 6 ч) — тоже пусто, потому что все четыре черновика старше. Возвращается
`("", [4 кандидата])`, `post_id` пуст, и условие `if draft and offer:`
(`channel_studio.py:910`) не срабатывает — **клавиатура не строится вообще**.

Замер на живом `docker/studio/state.json`:

```
target(state, '', None) -> post_id = '' candidates = ['p20261127-107', 'p20261124-192',
                                                        'p20261117-568', 'p20261109-810']
active_draft(state)      -> ''
target(state, '', 215)   -> 'p20261127-107'      # с reply_to выбор однозначен
```

Вторая половина поломки: `reply_to` **теряется на маршруте**. `studio_messages.decide`
считает `reply_to` из сообщения (`studio_messages.py:74`), но `studio_messages.route`
вызывает `cs.reply_to_shifu(bot, state_path, decision["note"], out)`
(`studio_messages.py:63`) — без `reply_to`, а такой параметр у `reply_to_shifu` и нет.
Ответ товарища Шифу на конкретный черновик не может его выбрать.

Журнал боевого `studio-watch` 27.11 — ровно эта картина:

```
13:54:47 сообщение от Шифу (talk): Ну покажи теперь что получилось
13:54:50 ответ отправлен: Нажми post — кнопка покажет собранный ролик целиком с исходн…
13:55:13 сообщение от Шифу (talk): Где блядь нажать пост?
13:55:49 сообщение от Шифу (talk): Нету там есть нихуя, просто не выебусь и пришли сам
13:56:51 сообщение от Шифу (talk): Ты долбоеб
```

Кнопки, которую обещал ответ, не существовало. Ответчик при этом — модель **без
инструментов**; обещание кнопки строил не код, а текст модели.

### 2. TTL черновиков не срабатывает — черновики живут вечно

`studio_state.expire_stale_drafts` (`studio_state.py:211`) читает метку появления
черновика так:

```python
created = record.get("created_at") or record.get("proposed_at")   # studio_state.py:231
if not created:
    continue                                                      # studio_state.py:232-233
```

А `register_post` (`channel_studio.py:1314`) переносит в состояние только поля из
`POST_FIELDS` (`channel_studio.py:1340-1355`) — `created_at`/`proposed_at` там **нет**.
Метку `created_at` пишет только другой путь, `produce_post_for_idea`
(`channel_studio.py:1094,1155`), а не боевой `studio_jobs.draft_job` → `register_post`.

Замер: у всех четырёх `proposed`-черновиков `created_at=None` и `proposed_at=None`.
Возраст (по `active_at`, unix-время): 305.9 ч, 249.8 ч, 79.5 ч, 8.1 ч при TTL 48 ч
(`studio_state.DRAFT_TTL_HOURS = 48`).

Симуляция фикса на копии боевого состояния:

```
expire_stale_drafts(ttl=48) -> протухло: ['p20261109-810', 'p20261117-568', 'p20261124-192']
target(state, '', None)      -> post_id = 'p20261127-107'   # кандидат снова один
```

Молчание товарища Шифу — четыре черновика, а не один, и потому выбор невозможен.

### 3. Публикация стоит с 17.11

Крон «публикация поста» (`job=1763e3998002`, `0 10 * * 2,4,6` UTC) упал шесть раз подряд:

```
932419af02ab4fe7be5ee285b772b6eb  failed  job=1763e3998002  2026-11-26T11:00:36+01:00
Публиковать нечего: нет approved-поста с наступившим not_before; последняя публикация
2026-11-17T10:00:39.191032+00:00, нужно ≥ 48 ч между постами
```

Пропущены слоты 19, 21, 24, 26.11. Причина видна в очереди: все 13 файлов
`docs/channel/queue/*.md` имеют `status: posted` — одобренных постов в очереди нет.
Одобрение (`ACTION_PUBLISH` → `apply_post_action`, `channel_studio.py:491-540`) кладёт файл
в очередь (`queue_post`, `channel_studio.py:447-480`) — то есть **по кнопке «Опубликовать»**.
Кнопка не строится (поломка 1) → посты не одобряются → очередь пуста → публикатор падает.
Замкнутый круг.

Отдельно: сообщение публикатора вводит в заблуждение. Прошло десять дней с последней
публикации, лимит 48 ч давно истёк; «нет approved-поста» — настоящая причина, а «нужно ≥ 48 ч
между постами» (`channel_post.py:44-50`) — приписка, которую `pick_next`
(`channel_lib.py:195`) не различает с пустой очередью.

### 4. Студия — не студия (архитектурная поломка)

Три крона студии работают в режиме `no-agent`:

```
studio: сессия анализа    0 2 * * *       studio_session.sh   no-agent (script stdout delivered directly)
studio: публикация поста  0 10 * * 2,4,6 studio_publish.sh   no-agent (script stdout delivered directly)
studio: опрос кнопок      * * * * *       studio_poll.sh      no-agent (paused с 06.11)
```

Профиль `studio` при этом полон инструментов, и они не задействованы: 27 записей скилов
и категорий (`social-media`, `media`, `creative`, `research`, `rob-box`, `web`, `github`),
`web` (ddgs), `browser`, `terminal` с томом `/home/builder/hermes-share`. Материал собирает
`studio_facts.py` — жёсткий список источников, а не агент, который «ходит куда надо».

Почему так вышло, записано в самом коде (`studio_reply.py:6-11`): «`hermes -t ""` НЕ
выключает инструменты… Такой агент дотягивался бы до `docker/studio/.env.secrets` (токен бота,
ключ MiniMax)». Отказ от агента был честным, но он оставил студию без агента и без гейта:
пока кнопки не работают, «публикует только одобренное» превратилось в «не публикуется
ничего» — канал молчит десять дней.

Граница секретов в текущем виде ещё и опасна: профиль `studio` монтирует
`/home/builder/hermes-share` целиком (`config.yaml`, `docker_volumes`), а секреты студии
лежат внутри этого тома — `docker/studio/.env.secrets` (`TG_STUDIO_BOT_TOKEN`,
`TG_SHIFU_CHAT_ID`, `TG_CHANNEL_ID`, `MINIMAX_API_KEY`, `GH_TOKEN`, права 0600). Агент с
терминалом в этом профиле достанет их. Значит, переводить студию в агентный режим можно
только вместе с изоляцией секретов.

## Решение

### Фаза 1 — починить сломанное (делается при любом выборе фазы 3)

1. **Метка появления черновика.** `register_post` пишет `created_at` при регистрации —
   либо новым полем в `POST_FIELDS`, либо в самой `register_post`. `expire_stale_drafts`
   начинает видеть метку, черновики протухают, факты возвращаются в `pending`
   (механика ADR-0170 уже есть и работает — сломана только запись метки).
2. **`reply_to` доходит до выбора черновика.** `reply_to_shifu` принимает `reply_to` и
   передаёт его в `active_draft`/`target`; `studio_messages.route` передаёт `reply_to`
   из сообщения. Ответ на конкретный черновик выбирает именно его.
3. **Кнопка строится всегда, когда черновик один.** При одном живом черновике `target`
   возвращает его по правилу «единственный»; при нескольких — кнопки выбора кандидата
   (`studio_intent.pick_keyboard`, `studio_intent.py:208`), а не пустота.
4. **Публикатор различает причины.** «Нет одобренного поста» и «не выдержали 48 ч» —
   разные сообщения; причина выводится из данных, а не склеивается.
5. **Регресс-тесты** (`tests/unit/scripts/test_telegram_studio_daily_material.py`):
   черновик без ответа протухает и возвращает факт; один живой черновик даёт кнопку;
   `reply_to` на сообщение черновика выбирает этот черновик; публикатор пишет правильную
   причину при пустой очереди.

### Фаза 2 — студия-агент

Крон «сессия анализа» переводится из `no-agent` в агентный режим: скрипт собирает сырьё
(факты, логи, медиа), его stdout инжектится в промпт агента, агент со скилами студии
(`social-media`, `media`, `creative`, `research`, `rob-box`) и инструментами (`web`,
`browser`, `terminal`) решает, о чём пост, пишет текст и готовит медиа.

Границы, которые это вводит, и как они закрываются:

| Граница | Решение |
|---|---|
| Агент не должен видеть `TG_STUDIO_BOT_TOKEN` и ключи | Отдельный профиль (`studio-agent`) **без** токена бота в `.env`; токен бота нужен только публикатору-скрипту, который читает `.env.secrets` сам. Том `/home/builder/hermes-share` в профиле агента не монтируется целиком |
| Модель не решает, что публикуется | ADR-0148: тема, проверка цифр по фактам, приватность, лимиты, теги — решает код; агент пишет текст и медиа |
| Материал — только чтение | Гейт `studio_ro_gate.sh` на хостах остаётся: агент ходит за материалом тем же read-only ключом `studio_ro` |
| Один пост — одна тема | Правило остаётся в коде (`studio_topic.rank`, ADR-0171) |

Ответчик в Telegram остаётся моделью без инструментов (секретная граница та же), но кнопку
строит код: обещание кнопки в тексте модели больше не считается её наличием.

### Фаза 3 — гейт публикации (решает товарищ Шифу)

Это единственный пункт, где нужен выбор: он меняет решение от 06.11 «публикация только
после кнопки».

| Вариант | Что значит | Цена |
|---|---|---|
| **А. Кнопка как сейчас** | Товарищ Шифу жмёт «Опубликовать»; кнопка починена | Нужно его присутствие; студия молчит, пока он не посмотрит |
| **Б. Агент публикует сам, кнопка — «отменить»** | Пост выходит по расписанию (вт/чт/сб 10:00) без нажатия; кнопка «отменить» — в течение окна | **Отменяет решение от 06.11** — нужно его слово; плохой пост уходит в канал сам |
| **В. Гибрид** | Агент публикует сам; кнопка остаётся как «переделать/отозвать»; правило «одна тема — один пост» и проверки кода — страховка | Тоже отменяет «только после кнопки» в части первого выхода |

**Рекомендация: В.** Товарищ Шифу прямо сказал «без всяких… тупых кнопок», а нынешнее
«только после кнопки» при неработающей кнопке даёт канал без единого поста за десять дней.
Страховки В: тема и факты — из кода, «одна тема — один пост», проверка чисел по фактам,
приватность и лимиты — до публикации, окно отзыва и удаление поста товарищем Шифу.
Если решение от 06.11 он не отменяет — выбираем А, фазы 1 и 2 всё равно делаются.

**Что устаревает при выборе Б/В** (править в том же PR, что и реализацию фазы 3):

- `CONTEXT.md:216` — «Публикует только после кнопки Шифу»;
- `CONTEXT.md:791` — «Публикуется только то, что Шифу одобрил кнопкой»;
- `docs/process/telegram-channel.md:227` — «Решение Шифа от 06.11 сохранено: публикация — только после кнопки»;
- `docs/adr/0170-studio-daily-material-and-draft-ttl.md:76` и `0171-…:167` — утверждения о неизменности решения 06.11;
- `docs/shifu-decisions.md:485` — запись от 12.11.2026, где решение 06.11 «действует»;
- сам ADR-0170 в части «Родители» (ссылка на решение 06.11) — заменяется ссылкой на ADR-0177.

## Последствия

**Хорошо:**
- кнопка появляется и работает; выбор черновика однозначен (TTL чинит корень, а не симптом);
- черновики не висят неделями; факты возвращаются в `pending` и переиспользуются;
- канал снова выходит по расписанию, а очередь объясняет, почему не вышла;
- студия получает скилы и инструменты: агент сам идёт за материалом, а не по жёсткому
  списку источников;
- секреты бота и ключи уходят из досягаемости агента.

**Цена:**
- агент в контуре — нужна изоляция секретов и своя проверка качества текста;
- в вариантах Б/В товарищ Шифу теряет право вето до выхода поста (в В остаётся отзыв);
- стоимость LLM на каждый прогон сессии.

**Отвергнуто:**
- «просто починить кнопку» — кнопка следствие: без метки появления черновик снова станет
  неразличимым, и через 48 ч история повторится;
- «оставить как есть, студия не критична» — канал молчит десять дней, шесть пропущенных
  слотов, четыре черновика-сироты в состоянии;
- «дать агенту терминал в текущем профиле `studio`» — профиль монтирует каталог с
  `docker/studio/.env.secrets`: токен бота и ключи уедут в агента;
- «оставить `reply_to` как есть» — ответ на конкретный черновик останется неоднозначным,
  когда черновиков несколько.

## Проверка

- Юнит-тесты фазы 1: `tests/unit/scripts/test_telegram_studio_daily_material.py` плюс
  новые случаи (TTL с `created_at`, выбор по `reply_to`, кнопка при одном черновике,
  сообщение публикатора при пустой очереди).
- Боевой клон: `studio-sync` доставляет фикс (ADR-0172), `studio-watch` перезапускается;
  в `state.json` появляется `created_at` у новых черновиков; старые протухают.
- Приёмка фазы 2: крон отрабатывает в агентном режиме, в журнале видно работу агента,
  пост приходит с медиа, публикация в канале — по гейту фазы 3.
- Приёмка фазы 3: в вариантах Б/В пост выходит без нажатия кнопки; в варианте А кнопка
  «Опубликовать» кладёт файл в очередь и пост выходит в слот.
