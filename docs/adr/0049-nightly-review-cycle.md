## 1. Контекст и бизнес-проблема

### 1.1 Что уже есть

| Контур | Скрипт | Что ловит | Горизонт |
|---|---|---|---|
| Триаж | `agent-flow-triage.sh` | issue → карточка | 1 issue |
| Merge-gate | `agent-flow-merge-gate.sh` | stale/conflicting PR, orphan-карточки | 1 PR |
| E2E-ротация | `agent-flow-e2e-process.sh` | `needs-e2e` очередь | 1 round |
| Heartbeat | `watchdog.sh` | зависший worker, provider exhaustion | 1 карточка |
| Mis-scope | `agent-flow-blocked-watchdog-scope.sh` | архитектурная задача не у того профиля | 1 карточка |
| Drift | `agent-flow-drift-detect.sh` | расхождение копий скриптов | 1 файл |
| Ретро | `kanban-retro-create.sh` | пост-фактум разбор аномалии | 1 аномалия |

Горизонт **каждого** контура — один объект. Ни один не отвечает на вопросы
«что вчера реально доехало» и «насколько хорош код, который вчера влили».

### 1.2 Два пробела

**Пробел A — нет дневного среза.** Шифу видит состояние конвейера только
глазами: открыть доску, открыть PR-лист, открыть Actions. Ретро-карточки
появляются, когда что-то уже сломалось. Классы проблем, которые видны
ТОЛЬКО на срезе суток: PR смержен, а issue висит открытой; карточка стоит
в `blocked` 9 часов и никто не заметил; один и тот же workflow краснеет
пятый раз за день; ретро-карточки третий день описывают один симптом
(ровно так родились ADR-0046 и ADR-0047 — по 8 и 6 повторов).

**Пробел B — никто не перечитывает свежий код.** Код пишут LLM-воркеры под
давлением зелёного CI. CI ловит падения, но не ловит:

- **дубликаты** — воркер не нашёл существующую функцию и написал свою
  (буквально причина существования `lib_agent_flow_common.sh`: «то же самое
  жило копипастой по шести скриптам и успело разъехаться дефолтами»);
- **глюки LLM** — мёртвые ветки, вызовы несуществующих полей, заглушки,
  всегда возвращающие успех, тесты вида `assert True`;
- **недоделки** — `TODO`/`NotImplementedError` в merged-коде, фича без
  теста, скрипт без регистрации в `install.sh`;
- **расхождение с контрактом** — код против README/ADR.

Всё это всплывает через ретро — то есть после того, как сгорели токены,
время воркеров и терпение Шифу.

## 2. Решение

Ночной cron-скрипт `agent-flow-nightly-review.sh` (`no_agent`, `every 1h`,
профиль `devops`), который **сам ничего не решает**, а готовит работу для
LLM-воркеров:

1. **Одна карточка «🌙 ночной ревью \<дата\>»** на `architect`
   (`NIGHTLY_REVIEW_ASSIGNEE`) с механическим дайджестом за сутки: merged
   PR, коммиты в `develop`, открытые/закрытые issues, красные CI-прогоны,
   kanban (закрытые / упавшие / висящие >6ч / ретро) и таблица churn по
   компонентам. Плюс задание: сверить «PR merged ↔ issue закрыта ↔ карточка
   не висит», разобрать зависшие, назвать приоритеты на новый день.
2. **До `COMPONENT_REVIEW_MAX` карточек «🔍 ревью компонента: \<comp\>»**
   на `analyst` — по компонентам, которые за сутки меняли, отсортированным
   по churn. В теле: список изменённых файлов с `+/-`, коммиты, и чек-лист
   из §1.2 (дубли / глюки LLM / недоделки / расхождение с контрактом).

Обе карточки создаются через `kanban-retro-create.sh` — то есть получают
все три слоя дедупа (pre-check по маркеру, idempotency-key, маркер в body).

### 2.1 Почему `every 1h`, а не «daily 02:00»

Час запуска зашит **в скрипт**, а не в расписание крона: тик вне окна
`[NIGHTLY_REVIEW_HOUR, +NIGHTLY_REVIEW_WINDOW_HOURS)` стоит один вызов
`date` и `exit 0`. Взамен получаем устойчивость, которой у `once`/`daily`
джобов в этом хозяйстве исторически не было (ретро 23.08+25.08
`t_98bb3a1d`/`t_24e645e7`: `once`-джоб e2e-ротации простоял 60+ часов после
первого тика). Если хост лежал в 02:00 или MAINTENANCE висел первый час
окна — ревью всё равно заведётся, пока окно открыто.

Sentinel `/tmp/agent-flow-nightly-review.<дата>.done` + дедуп по key
гарантируют «одна ночь = один комплект карточек».

### 2.2 Почему `no_agent`, а рассуждения — внутри карточки

Дайджест собирается механически (git/gh/kanban), без LLM. LLM работает
ВНУТРИ созданной карточки, где его вывод виден Шифу, привязан к `t_<id>`,
и его можно откатить. Обратный вариант (LLM-крон, который сам «смотрит и
решает») уже существует в хозяйстве в виде надзора/падаван-вахты — и уже
дал ретро `t_35ff29f1` (два дубля карточек одним тиком) именно потому, что
LLM вызывал `kanban create` без механической проверки.

### 2.3 Кулдаун вместо ежедневного спама

`src/rob_box_voice` меняется почти каждый день; ежедневная карточка на него
— это гарантированный шум, а шум дискредитирует надзор (ADR-0046 §«Шифу
видит опять те же 5 stale → перестаёт верить»). Поэтому компонент, на
который уже есть живая ревью-карточка или архивная моложе
`COMPONENT_REVIEW_COOLDOWN_DAYS` (default 7), пропускается — очередь
достаётся следующему по churn.

## 3. Контракт

### 3.1 Что скрипт делает и чего не делает

| Делает | НЕ делает |
|---|---|
| читает git / gh / kanban | не меняет метки, PR, issues |
| создаёт ≤ 1 + N карточек за ночь | не чинит код, не открывает PR |
| печатает дайджест в stdout | не зовёт LLM |
| ставит sentinel на ревью-сутки | не блокирует merge и не гейтит CI |

### 3.2 Контракт воркера-ревьюера (в теле обеих карточек)

- Каждая находка — с **raw evidence**: `file:line`, номер PR/issue,
  `t_<id>`, ссылка на run. Без raw находка не считается (AGENTS.md,
  ADR-0018).
- Подтверждённые дефекты — **отдельные GitHub issues** с меткой `hermes`,
  чтобы их подхватил штатный триаж. Ревью **не чинит** — иначе ночной
  ревьюер превращается в неконтролируемого воркера с правом писать в любой
  компонент.
- Находок нет → «находок нет» + перечисление проверенного. Честный пустой
  отчёт лучше выдуманного списка.

### 3.3 Деградация

Нет `gh` / нет `GH_REPO` / упал `hermes kanban list` → соответствующая
секция печатает `НЕТ ДАННЫХ (<причина>)`, тик продолжается. Пустой список
вместо «нет данных» был бы враньём: воркер прочтёт его как «за сутки
ничего не было».

## 4. Альтернативы

| Вариант | Почему не он |
|---|---|
| **Ревью каждого PR перед merge** (обязательный reviewer-воркер) | Дороже на порядок (карточка на каждый PR), и упирается в правило «merge только Шифу» — ревьюер всё равно не блокирует. Ночной срез даёт 80% пользы за 5% токенов. Не исключает будущего PR-ревью: ADR-0049 ему не мешает. |
| **LLM-крон, который сам смотрит и сам решает** | Уже есть надзор/падаван-вахта; ретро `t_35ff29f1` — дубли карточек одним тиком. Механический сбор + LLM в карточке разделяет «факты» и «суждение». |
| **Расширить существующий `blocked-watchdog`** | Другой горизонт (одна карточка vs сутки) и другой выход (comment vs карточка). Смешивание сделало бы оба нечитаемыми. |
| **Статический анализатор вместо ревью-карточки** | Линтеры уже стоят в `G-Lint Code` и не видят ни дублей смысла, ни «фича без теста», ни расхождения с ADR. Дополняет, не заменяет. |
| **Ревьюить весь репозиторий, а не изменённое** | Токены на компоненты, которые никто не трогал. Триггер «менялось за сутки» = там, где риск свежий. |

## 5. Trade-offs

| Плюс | Минус |
|---|---|
| Появляется дневной срез, которого не было | +1..4 карточки за ночь = токены (оценка: ~4 прогона воркера/сутки) |
| Свежий код перечитывается в тот же день | Ревьюер может нафантазировать находки — лечится требованием `file:line` |
| Дайджест механический → нечего галлюцинировать | Часть данных зависит от retention `gh run list` |
| Карточки идут через штатный дедуп | Компонент = 2 сегмента пути: монорепа-эвристика, для мелких пакетов грубовата |

## 6. Что НЕ покрывает

- **Ревью до merge.** Плохой код всё равно доезжает в `develop`; ночной
  ревью ловит его постфактум и заводит issue. Гейтом ревью не является.
- **Компоненты, которые не менялись.** Старый долг ночной ревью не найдёт.
- **Не-кодовые изменения** (`docs/`, `evidence/`, `.planning/` — см.
  `COMPONENT_REVIEW_EXCLUDE_RE`): попадают в дайджест, но карточку не
  получают.
- **Качество самого ревьюера.** Если воркер напишет «находок нет» не глядя
  — это ловится тем же способом, что и любое другое враньё в этом репо
  (Шифу + `validate_honesty.sh`).
