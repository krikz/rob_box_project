## 1. Контекст и проблема

### 1.1 Симптом

С 11.08 (воспроизводится стабильно) e2e голосовой тест даёт **противоречивые вердикты в одном и том же прогоне**:

- Round-50 (PASS) — `E2E_VERDICT PASS`, workflow ✓
- Round-55, Round-56 (FAIL) — `E2E_VERDICT PASS` × 2 в харнессе + `❌ ONLY GREETING: TTS был ДО команды — ответа на команду НЕТ` в workflow
- Round-51–54 — чередование `no_wake_word` / `only_greeting`

Пять done-карточек подряд закрыты как «причина не в коде робота, причина в харнессе», но фикса не случилось: `t_a13ea801`, `t_971027e6`, `t_15ceab12`, `t_c6235e42`, `t_5439cfe4`.

### 1.2 Архитектура e2e сегодня

```
┌──────────────────────────────────────────────────────────────┐
│  GitHub Actions workflow: L-E2E Voice Test.yml               │
│  • sshpass ssh ros2@249 → /tmp/e2e_remote.sh → docker run    │
│  • /tmp/e2e_remote.sh вызывает e2e_voice_test.sh             │
│  • e2e_voice_test.sh check_cycle() → E2E_VERDICT PASS|FAIL   │
│  • workflow собирает артефакты (recording, logs, model.json)  │
│  • workflow НЕ ВАЛИДИРУЕТ цикл (проверено grep'ом по yml —    │
│    нет строк stt_line/tts_line/validate/ONLY GREETING)        │
└──────────────────────────────────────────────────────────────┘
```

**Важная корректировка**: в исходной постановке задачи (`t_9d11200a` body) сказано «валидатор в workflow (step 'Validate e2e result')». Этого step-а **в текущей версии workflow нет**. Возможно, его добавляли и удаляли в одном из раундов или автор карточки ошибся; реальный второй валидатор существовал в более ранних версиях, но сейчас архитектурная проблема остаётся:

- харнесс (`e2e_voice_test.sh check_cycle`) имеет **ошибочный алгоритм**, который при определённой race с greeting-фразой даёт **ложный PASS**;
- любой валидатор в workflow или агенте, смотрящий в те же логи, неизбежно обнаружит то же, что не обнаруживает харнесс, — и **вступит с ним в конфликт**;
- агенты и Шифу не понимают, чему верить, и плодят done-карточки «проверь лог».

### 1.3 Корневая причина ложного PASS в `check_cycle`

Файл: `.github/workflows/scripts/e2e_voice_test.sh`, строки 119–147:

```bash
# 3) ПОРЯДОК: LLM INPUT команды должен быть ПОСЛЕ ПРИНЯТО,
#    а TTS finished — ПОСЛЕ LLM INPUT (иначе это приветствие/старый цикл)
local accept_ts llm_ts tts_ts
accept_ts="$(printf '%s' "$logs" | grep 'ПРИНЯТО' | head -1 | grep -oE '\[[0-9]+\.[0-9]+\]' | head -1 | tr -d '[]')"
llm_ts="$(printf '%s' "$logs" | grep 'LLM INPUT' | head -1 | grep -oE '\[[0-9]+\.[0-9]+\]' | head -1 | tr -d '[]')"
tts_ts="$(printf '%s' "$logs" | grep 'TTS finished' | head -1 | grep -oE '\[[0-9]+\.[0-9]+\]' | head -1 | tr -d '[]')"
# ...
if awk "BEGIN{exit !($tts_ts > $accept_ts)}"; then
    return 0  # ✅ полный цикл
fi
```

**Баг**: оба timestamp-а берутся `head -1` **без фильтра по окну теста**. Если в окне `--since BEFORE` присутствует TTS-событие **greeting-приветствия**, которое произошло до `BEFORE` (например, `BEFORE=12:00:00`, а TTS greeting случился в 11:59:45 и попал в окно `--since` из-за неточности docker-logs), то:

- `tts_ts = 11:59:45` (greeting)
- `accept_ts = 12:00:17` (команда)
- `tts_ts > accept_ts` → **true → ложный PASS**

В Round-56 это воспроизвелось: greeting был 5:14, accept команды 5:17, цикл «полный», ответ на команду **отсутствует** (робот ещё не закончил говорить приветствие, STT не услышал команду).

### 1.4 Почему `head -1` — структурная ошибка, а не просто опечатка

Логика `head -1` подразумевает, что в окне только одно TTS-событие. Это верно только если:
1. Greeting полностью завершился до `--since BEFORE`, и
2. LLM/TTS не отвечают ни на что кроме текущей команды.

Оба условия **не гарантированы**:
- docker logs `--since` округляется до минуты (`2024-08-12T05:18:00Z` → всё с 5:18), и greeting 5:14 **попадает** в окно, если `BEFORE=05:18:30` (а скрипт ставит `BEFORE` через `date` с секундами, но docker всё равно берёт минуту);
- робот может проиграть wake-word → короткий ответ «слушаю» → это TTS-событие **до** команды, и оно попадёт в окно.

То есть `head -1` ломается на любом тесте, где робот говорит **до** того, как e2e-тест положит BEFORE. Это не частный случай — это дизайн-баг.

### 1.5 Trade-off анализ

| Вариант | Что фиксит | Что создаёт |
|---------|-------------|-------------|
| **A. Skip-line фильтр в `check_cycle`** (sed `/ПРИНЯТО/,$p` после `ПРИНЯТО`) | root cause: TTS берётся **после** accept_ts команды, не greeting-а | Требует, чтобы в логах был именно один `ПРИНЯТО` для команды. Если greeting оставит `ПРИНЯТО` где-то ещё — сломается. Но greeting — это TTS, не STT, поэтому `ПРИНЯТО` от greeting нет. |
| **B. Удалить второй валидатор из workflow** (или sync с харнессом) | гонку между двумя вердиктами | Если A не зафикшен, workflow теперь **наследует** ложный PASS харнесса. |
| **C. Один валидатор в одном месте** (SSoT) | и гонку, и риск drift-а логики | Требует рефакторинга: вердикт вычисляется **один раз** и сохраняется в артефакт (`/tmp/e2e_v2_<run>/verdict.txt` уже есть), а workflow читает только этот файл. |
| D. Оставить как есть | ничего | 5+ карточек retro, round-50/55/56 повторятся |

**Решение: A + B + C**.

## 2. Решение

### 2.1 Принцип (SSoT — Single Source of Truth)

> **Вердикт e2e голосового теста вычисляется ровно один раз, в одном месте, и записывается в файл-артефакт. Все downstream-читатели (workflow, агенты, Шифу) сверяются с этим файлом, а не с логами.**

Файл-артефакт: `/tmp/e2e_v2_<run>/verdict.txt` (уже создаётся в `e2e_voice_test.sh`). Формат:

```
E2E_VERDICT PASS
exit_code=0
pass_steps=s1,s2
fail_steps=
notes=ok
```

Или:

```
E2E_VERDICT FAIL
exit_code=2
pass_steps=
fail_steps=s1
notes=only_greeting: tts[greeting]@11:59:45 < accept[command]@12:00:17
```

### 2.2 Конкретные изменения

#### Изменение A: Skip-line фильтр в `check_cycle` (root cause fix)

**Файл**: `.github/workflows/scripts/e2e_voice_test.sh`

**Сейчас** (lines 119–147):
```bash
local accept_ts llm_ts tts_ts
accept_ts="$(printf '%s' "$logs" | grep 'ПРИНЯТО' | head -1 | ...)"
llm_ts="$(printf '%s' "$logs" | grep 'LLM INPUT' | head -1 | ...)"
tts_ts="$(printf '%s' "$logs" | grep 'TTS finished' | head -1 | ...)"
```

**Должно быть** (skip строки до первого `ПРИНЯТО` команды):
```bash
local accept_ts llm_ts tts_ts logs_after_accept
# Сначала находим ПРИНЯТО команды (= ПРИНЯТО с НЕ-wake-word-паттерном, или просто ПЕРВЫЙ ПОСЛЕ BEFORE).
# Устойчивый фильтр: обрезаем логи до строки с ПРИНЯТО команды включительно,
# затем ищем LLM INPUT и TTS finished ТОЛЬКО в этом окне.
accept_ts="$(printf '%s' "$logs" | grep 'ПРИНЯТО' | head -1 | grep -oE '\[[0-9]+\.[0-9]+\]' | head -1 | tr -d '[]')"
if [ -n "$accept_ts" ]; then
    # Берём всё СО СТРОКИ accept_ts включительно — это «наш» цикл
    logs_after_accept="$(printf '%s' "$logs" | awk -v ts="[$accept_ts" 'index($0, ts){found=1} found')"
    llm_ts="$(printf '%s' "$logs_after_accept" | grep 'LLM INPUT' | head -1 | grep -oE '\[[0-9]+\.[0-9]+\]' | head -1 | tr -d '[]')"
    tts_ts="$(printf '%s' "$logs_after_accept" | grep 'TTS finished' | head -1 | grep -oE '\[[0-9]+\.[0-9]+\]' | head -1 | tr -d '[]')"
fi
```

**Семантика**: greeting/предыдущие циклы отсекаются, потому что их `ПРИНЯТО`-строки в `logs_after_accept` не попадают.

#### Изменение B: workflow = транспорт, не валидатор

**Файл**: `.github/workflows/L-E2E Voice Test.yml`

**Сейчас**: workflow НЕ валидирует (после корректировки исходной карточки). Но:
- Если в будущем кто-то добавит `Validate e2e result` step — он **должен** читать `/tmp/e2e_v2_*/verdict.txt`, а не парсить логи.
- В README workflow-а (или в комментарии в yml) пишем: «Валидация цикла — в `e2e_voice_test.sh`. Этот workflow только транспорт (запуск, артефакты). Дублировать парсинг логов здесь ЗАПРЕЩЕНО.»

#### Изменение C: агентский контракт — «trust the file»

**Файл**: `~/.hermes/kanban/boards/robbox/.../e2e-process` или `docs/agent-flow/AGENT_FLOW_PROPOSAL.md`

Правило для всех e2e-карточек: **всегда читать verdict из файла**, не парсить логи и не решать по факту «вижу/не вижу TTS после команды». Если в файле `E2E_VERDICT PASS` — тест прошёл. Если `FAIL` — тест не прошёл. Логи — для дебага, не для вердикта.

### 2.3 Когда принимать это решение

Решение нужно принять **сейчас**, потому что:
1. Пять done-карточек retro не помогли — никто не понимает, кто «главный» валидатор.
2. Round-50/55/56 подтвердили, что паттерн стабильный (не случайный flakе).
3. PR #1080 (UNSTABLE, 100 коммитов) подозрительно красен именно из-за этого — починка разблокирует его.

### 2.4 Что делать, если НЕ принять сейчас

Каждый новый e2e-round будет повторять round-50/55/56: харнесс скажет PASS, второй валидатор скажет FAIL, агенты не поймут, чему верить, Шифу скажет «почини лог». Стоимость: ~10 минут на каждый round + 1–2 done-карточки retro + блок связанных задач (`t_1d406ad2`, `t_0e8a5d18`).

## 3. Последствия

### 3.1 Положительные

- **Один источник истины**: вердикт записывается один раз, читается всеми одинаково.
- **Ложные PASS уходят в ноль**: skip-line фильтр гарантирует, что greeting не путается с ответом.
- **Агенты перестают плодить retro-карточки**: вместо «проверь лог» они читают файл.
- **PR #1080 может стать зелёным**: если этот баг был единственной причиной красных тестов.

### 3.2 Отрицательные / риски

- **Изменение A требует аккуратного тестирования**. Skip-line фильтр зависит от того, что в окне есть хотя бы один `ПРИНЯТО`. Если wake-word-эхо оставит `ПРИНЯТО: ...` без команды (теоретически), фильтр обрежет не там. Решение: в тестах проверить round-50 (был PASS) и round-55/56 (были FAIL) — после фикса оба должны показать корректные вердикты.
- **Дополнительная переменная окружения?** Нет. Всё в bash.
- **Что делать с уже накопленными stale round-50/55/56?** Ничего — это просто логи, они остаются как есть. Новые раунды будут говорить правду.

### 3.3 Что НЕ делается этим ADR

- Не переписывается e2e_voice_test.sh целиком — только check_cycle.
- Не добавляется новый валидатор в workflow — наоборот, явно запрещается.
- Не трогается голосовой пайплайн робота (dialogue_node, tts_node, stt_node) — баг в тестовой обвязке, не в production.
- Не отменяются ранее закрытые retro-карточки (`t_a13ea801` и др.) — они просто становились obsolete из-за этого же бага.

## 6. Открытые вопросы / допущения

- **Допущение 1**: в окне `--since BEFORE` всегда есть хотя бы одна строка с `ПРИНЯТО` для текущей команды. Если STT не принял команду вообще — `check_cycle` возвращает 1 (no_accept) ещё до skip-line фильтра, так что допущение безопасно.
- **Допущение 2**: `ПРИНЯТО` встречается только из STT-ноды для пользовательской команды, не из других мест. Грепом по `src/`: `ПРИНЯТО` есть только в `stt_node.py:370`. ✓
- **Открытый вопрос**: не возникнет ли после фикса A round-N, где `logs_after_accept` содержит LLM INPUT **от предыдущего цикла** (который мы как раз пытаемся исключить)? Нет: предыдущий цикл завершился раньше команды, и его LLM INPUT выше `ПРИНЯТО` команды. Skip-line по первой `ПРИНЯТО` отрезает всё, что выше — включая старый LLM INPUT. ✓
