## 1. Контекст и бизнес-проблема

Волна `scheduler-segments-merge` (#968) добавила сегментную модель
(`SchedulerTask.group_id`/`seg_idx`, `TaskScheduler.segments()`) и MERGE —
правку ещё не стартовавших (`PENDING`) сегментов группы через
`TaskScheduler.update()` (rewrite/replace/drop/append), не прерывая
`ACTIVE`-сегмент. Пример из дизайна — «и ещё про енота» во время куплета 1:
куплет 2 (ещё не озвученный `speak_text`-сегмент с тем же `group_id`)
переписывается на лету.

Естественный вопрос: работает ли то же самое для музыкального канала —
можно ли, например, на лету поменять следующий трек DJ-сета, пока текущий
ещё играет? **Ответ — нет, и это осознанное ограничение, не пробел.**

### 1.1 Почему музыкальные тулы не участвуют в MERGE

`tool_executor.py` (`channel_for_tool`, комментарий у `_MUSIC_TOOLS`,
строки ~70–86) явно исключает музыкальные «стартеры» из очереди
планировщика:

```python
_MUSIC_TOOLS: frozenset[str] = frozenset({"stop_music"})
```

Только `stop_music` идёт через `MUSIC`-канал планировщика (и то
отложенно — до опустошения `VOICE`-канала, чтобы не обгонять текущий
`speak_text`). Сами стартеры — `execute_music_code`, `set_vibe_preset`,
`load_track` — исполняются **напрямую, блокирующе, в обход
`TaskScheduler`** (`channel_for_tool()` возвращает `None` → bypass-путь в
`SchedulerToolExecutor.execute`).

Это не случайность и не недоделка W7 — это фикс регрессии **«party»
(live 19.08.2026)**: когда музыкальные стартеры были обёрнуты в
fire-and-forget queued-контракт планировщика («тулза поставлена в очередь»
вместо реального результата), DJ-LLM переставал видеть подтверждение, что
`execute_music_code` реально выполнился («Код выполнен успешно»), и
пропускал повторные вызовы на переходах между треками — DJ-сет разваливался.
Фикс — полностью вывести музыкальные стартеры из планировщика.

### 1.2 Следствие для MERGE

`TaskScheduler.update()` работает **только** с сегментами, зарегистрированными
в `self._groups[group_id]` (`task_scheduler.py:561-564`) — а туда сегмент
попадает исключительно через `TaskScheduler.submit()` с явным `group_id`.
Музыкальные стартеры никогда не проходят через `submit()` (bypass, §1.1) —
значит, у них физически не может быть `group_id`/`seg_idx`, и `update()`
(`TaskNotFoundError` при отсутствии группы) не может их «поймать».

MERGE сегодня применим только к **voice-каналу** — сценарию, где LLM
разбивает голосовую задачу (`sing`/`rap`/`narrate`) на серию `speak_text`
с общим `group_id` (куплет-за-куплетом). Музыкальный «канал» в терминах
MERGE не существует как редактируемая очередь сегментов — он либо играет
(через прямой bypass-вызов), либо останавливается (`stop_music`, единственный
музыкальный тул на самом планировщике).

---

## 2. Решение

**Фиксируем как архитектурную границу, не как временный пробел:** MERGE
(`task_delta` / `TaskScheduler.update()`) в текущей архитектуре scheduler-а
**не распространяется на музыкальный канал**. «Поменяй следующий трек
DJ-сета, пока играет текущий» — это **не MERGE-сценарий**. Если такая правка
нужна, она реализуется обычным повторным вызовом `execute_music_code`
(bypass-путь), который в силу §1.1 уже блокирующий и синхронный для LLM —
то есть LLM и так получает актуальный результат каждого вызова, просто не
через сегментную модель.

Это ограничение **намеренно узкое**: оно не запрещает будущую эволюцию (см.
§3), но фиксирует, что распространение MERGE на музыкальный канал — это
**новая задача с собственным анализом**, а не «доделать W7», и что попытка
завернуть музыкальные стартеры обратно в очередь планировщика ради MERGE
рискует повторить регрессию 19.08.

## 3. Альтернативы (отклонены/отложены)

| Вариант | Почему не сейчас |
|---|---|
| Завернуть `execute_music_code`/`set_vibe_preset`/`load_track` обратно в `TaskScheduler` с `group_id`, разрешить MERGE поверх них | Прямо отменяет фикс «party regression» (19.08) — LLM снова теряет синхронное подтверждение результата; конкретного acceptance-сценария в #968, требующего этого, нет (YAGNI). |
| Отдельная мини-модель сегментов для музыкального канала (по аналогии с voice, но не через `TaskScheduler.submit()`/bypass) | Не запрошено ни одним acceptance-критерием #968 (§11.2/§11.3 SCHEDULER_DESIGN.md); добавляет новый класс сегментов без реального сценария использования. Если появится конкретный юзкейс («смени трек, когда текущий доиграет», «выстрой очередь из 3 треков») — отдельная карточка с собственным ADR. |
| Разрешить MERGE только для `stop_music` (единственный музыкальный тул на планировщике) | `stop_music` — не многосегментная задача (нет `group_id`/серии сегментов), MERGE к нему неприменим по определению — не альтернатива, а не-вопрос. |

---

## 4. Trade-off

| Что получаем | Чем платим |
|---|---|
| Party-регрессия (19.08) не рискует повториться — музыкальный bypass остаётся неприкосновенным | «Хочу поменять следующий трек, пока играет текущий» — не решается через `task_delta`/MERGE сегодня; нужен отдельный дизайн, если появится реальный запрос |
| Явная документированная граница — будущий агент, ищущий «почему MERGE не работает для музыки», находит ответ за один grep по ADR, а не переоткрывает вопрос | Ограничение специфично для текущей архитектуры (`channel_for_tool` bypass) — если bypass-механизм когда-нибудь изменится, этот ADR нужно будет пересмотреть |

---

## 5. Статус

Accepted — документирует уже действующее в `develop` поведение (S12,
scheduler-segments-merge). Код этим ADR не меняется. Пересмотр требуется,
если появится конкретный сценарий/acceptance-критерий на MERGE для
музыкального канала — тогда это отдельная задача с собственным ADR, а не
ревизия этого документа.
