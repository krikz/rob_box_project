## 1. Проблема

Две несвязанные линии про «знание о мелодии»:

1. **Обогащение RTTTL из сети** — `scripts/music/enrich_melodies.py` (#3428/#3429, 751 строка + 21 тест): MusicBrainz + Wikidata + LLM-нормализация → `melody_facts.jsonl.gz` (`canonical_title, artist, composer, work_type, genre, year`). Ни разу не прогнан, артефакт никто не читает (`grep melody_facts src/` — 0). Спайк 05.10: чистый матч без LLM 9/26, с LLM-нормализацией 21/26, 1 ложный приём, полный прогон ≈ 6–11 ч сети и ≈ 2–4 M токенов.
2. **Партитуры** — ADR-0154: `ScoreMaterial`, PDMX, `score_index` в SQLite, выбор материала по теме (§3.5). Про MusicBrainz/Wikidata/факты — ни слова; про лицензии — вопрос В1.

Без общего реестра получится то, чего Шифу просил не делать: два индекса (RTTTL и партитуры) с разными полями, обогащение «на всякий случай» по всей библиотеке, повторные сетевые запросы при каждой переделке правил, и факты, которые код не читает.

## 3. Решение

### 3.1 Реестр произведений — одна запись `Work`, источники по полям

Новый модуль **`rob_box_music/works.py`** (frozen dataclasses, валидатор как у `Track`/`ScoreMaterial`; одно место знания — ADR-0148/0149 §2.1), данные — таблицы `works`, `work_sources`, `work_facts` в **той же SQLite**, что RTTTL-библиотека и `score_index` ADR-0154 §3.2 (`VOICE_MEMORY_DB_PATH`); на katana — тот же файл, собранный батчем.

```python
@dataclass(frozen=True)
class Fact:        value: str; source: str      # "rtttl" | "pdmx" | "derived" | "manual" | "wikidata" | "mb"
                   source_id: str; fetched_at: str; rules_version: str; verified: bool
@dataclass(frozen=True)
class WorkSource:  kind: str; material_id: str   # "rtttl:<name>" | "pdmx:<id>" | "local:<sha8>" (= ScoreMaterial.material_id)
                   link_level: str; link_score: float   # "exact_artist" | "exact" | "fuzzy" | "manual"
@dataclass(frozen=True)
class Work:
    work_id: str                      # sha8(нормализованное название + композитор/исполнитель)
    title: str; composer: str; artist: str; aliases: Tuple[str, ...]   # в т.ч. RU-алиасы (сегодня _ALIASES :59-88)
    genre: Optional[Fact]; year: Optional[Fact]; work_type: Optional[Fact]
    sources: Tuple[WorkSource, ...]   # хотя бы один
```

- `ScoreMaterial` (ADR-0154 §3.1) **остаётся** единицей материала одной партитуры (ноты, аккорды, бас, фразы, `key`). `Work` — надстройка: «что это за пьеса и где её материал». `score_index` ADR-0154 §3.2 становится `work_sources` (строка на партитуру со ссылкой на `work_id`), а не самостоятельным индексом с собственными `title/composer/genres`: **один индекс для поиска по теме** (RTTTL и партитуры), одна нормализация названий (`pdmx_coverage.norm` → `works.norm`).
- Записи RTTTL без пары в PDMX (≈ 90 %) — тоже `Work` с одним источником `rtttl:<name>`; группа версий (`terminat`, `theme_177`, `theme_178`) — один `Work` с несколькими источниками, канон — по `search.consensus_order` (контур 7 нот, уже в коде `search.py:200`), не из сети.
- У каждого поля — значение **и** источник с провенансом (`Fact`); поле без источника отсутствует, а не «пустая строка». Аранжировщик читает `Work` только через функции `works.py`; LLM `Work` не видит (ADR-0149 §5.1 — только `dj_set(theme)`/`request_music(text)`).

### 3.3 Правило «обогащать или нет» (код, не вкус)

Сетевой поиск (MusicBrainz, Wikidata, любой другой) по полю `F` запускается **только** если все три условия выполнены, и это проверяется в PR, который его включает:

1. **Потребитель есть**: функция в `rob_box_music`/`engine`, читающая `Work.F`, существует на `origin/develop` (в PR — `grep -n` с файл:строкой). Поле «для будущего» не обогащается.
2. **Дыра после офлайн-источников существенна**: доля записей **из рабочего множества** (не всей библиотеки: строки `THEMES` + `DEFAULT_HOOKS` + теги tv/movie/game/classical/anthem/christmas/folk + темы из журнала запросов `music_history` за 90 дней), у которых `F` не заполнен ни RTTTL/PDMX/локальной партитурой, ни вычислением из нот, **≥ 20 %**. Ниже порога — не обогащаем вовсе (ручная таблица, как `_ALIASES`).
3. **Точность источника доказана**: пилот ≤ 30 записей рабочего множества, правило приёма — детерминированный код (`accept_field` из `enrich_melodies.py:387`: MB score 100 + пересечение артиста + не remix/cover/live; Wikidata тип «музыкальное произведение» + композитор/исполнитель; год только P577), ложных приёмов ≤ 1/30 по проверке Шифу (не воркера).

Если делаем — **один комплексный проход на запись** (все поля с открытым гейтом за один запрос к каждому источнику), офлайн на katana, по готовому списку дыр (`works.py --holes F` → список `work_id`), с журналом §3.4; не в рантайме, не из текста LLM (ADR-0148, #3243).

**Состояние гейта сегодня (по замеру):**

| Поле | 1. потребитель | 2. дыра ≥ 20 % рабочего множества | 3. точность | Вердикт |
|---|---|---|---|---|
| название/композитор/исполнитель | да (поиск) | нет: по словам темы запись находится по названию; композиторские темы закрывает PDMX; категории-артисты чинятся без сети | спайк: LLM-нормализация 21/26, 1 ложный | **не обогащать**; починить `title`/`artist` офлайн (§5 K-2) |
| жанр | **нет** | да (74–87 %) | MB 1/16 | **не обогащать** — пока ADR-0153 не введёт «стиль от мелодии» (вопрос В4) |
| год | нет | да (100 %) | WD только синглы | **не обогащать** |
| RU-алиас | да (озвучка) | не мерено; работает руками | не мерено | **не обогащать**; ручная таблица |
| гармония/темп/форма | ADR-0154 | — | в сети нет | сеть неприменима; источник — партитуры |

Итог: **сегодня ни одно поле гейт не проходит**. Обогащение из сети не запускается. Что реально закрывает дыры: PDMX (материал по теме) и офлайн-чистка идентичности RTTTL.

### 3.4 Журнал запросов (чтобы не сканировать впустую и не переделывать)

Каждый внешний запрос — строка в таблице `lookups` той же SQLite на katana (`~/music_registry/registry.sqlite`, копия на робота `/data/music_v2/registry.sqlite` вместе с библиотекой; **вне git**):

```
lookups(source TEXT, query_norm TEXT, rules_version TEXT, fetched_at TEXT, http INTEGER,
        status TEXT,            -- "found" | "not_found" | "error"
        payload_sha TEXT, payload_path TEXT,   -- сырой ответ базы, файл рядом (нужен для цитаты accept_field)
        accepted INTEGER, decision TEXT,       -- что принято и почему/почему нет (правило кода)
        PRIMARY KEY (source, query_norm, rules_version))
```

- Повтор запроса — только при смене `rules_version` (версия правил нормализации запроса или приёма; константа в `works.py`) или по TTL **180 дней**; «не найдено» и ошибки (503/таймаут — `status="error"`, TTL 1 день) кэшируются так же.
- Это **тот же** кэш, что `enrich_state.sqlite` в `enrich_melodies.py` (HTTP-кэш + статус записи), только с ключом «нормализованный запрос + версия правил» вместо «имя записи», и один на все источники; второго кэша не будет (память: «не держать две реализации»).
- Отчёт по журналу — часть `works.py --report`: запросов всего / найдено / принято / отклонено по правилам, чтобы Шифу видел, что сеть не сканируется впустую.

### 3.5 Что коммитится, что нет

- В git: `works.py` (модель, нормализация, гейт, экспорт), тесты на синтетике, ручные таблицы (RU-алиасы, `BAD_ARTISTS`, `GENRE_STYLE_MAP` из `enrich_melodies.py` → `knowledge`), отчёты замеров (`docs/music/*.md`).

## 7. Решения товарища Шифу (06.10; приняты 2026-10-07 по рекомендациям автора — вопросы закрыты)

Ответ дан поручением «принять рекомендации автора», а не поштучным разбором; по В6 и точности §2.2 Шифу ничего не просматривал.

- **В1. Лицензия PDMX → (в) + (б)-лёгкий.** *Шифу лично подтвердил (в) 2026-10-07: партитуры только на роботе и katana, в git — одни статистические таблицы.* `no_license_conflict` — метка загрузившего (§2.4). PDMX — только на роботе/katana, в git — ничего, кроме статистических таблиц; стоп-список живых композиторов/студий — данные `knowledge.LICENSE_STOP_LIST` (растёт по факту), `Work.stop_listed` считает `works.py`.
- **В2. `enrich_melodies.py` → А: удалён** в K-2 (скрипт и `test_enrich_melodies.py`). Правила приёма (`accept_field`, `VARIANT_RE`, `GENRE_STYLE_MAP`) остались в истории репозитория: `scripts/music/enrich_melodies.py` @ `1f136b141`. - **В3. Реестр → одна SQLite** (та же, что RTTTL-библиотека): таблицы `works`/`work_sources`/`work_facts` — `works.write_registry`.
- **В4. «Стиль от мелодии» → не делаем сейчас** (после ADR-0154 PR-1…PR-5); поле `genre` потребителя не имеет, гейт закрыт.
- **В5. Гейт 20 % рабочего множества и TTL 180 дней — как в ADR** (`works.GATE_SHARE`, `works.LOOKUP_TTL_DAYS`).
