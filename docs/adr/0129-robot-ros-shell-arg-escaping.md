## 1. Контекст и бизнес-проблема

22.09.2026 в окне ревью компонента `.github/workflows` найден класс багов в
обёртке `robot_ros()` (e2e_voice_test.sh:353-355), добавленной в PR #2770
(issue #2763) и расширенной в PR #2787 (issue #2781):

```bash
robot_ros() {
    ${ROBOT_SSH} "docker exec voice-assistant bash -lc 'source /opt/ros/humble/setup.bash; source /ws/install/setup.bash; $*'"
}
```

Используется в **6 точках харнесса** (lines 397, 401, 420, 461, 465, 483) для
активации/деактивации e2e-изоляции БД дикторов и памяти:

```bash
robot_ros "ros2 param get /speaker_id_node e2e_mode --no-daemon"
robot_ros "ros2 param set /speaker_id_node e2e_mode true --no-daemon"
robot_ros "ros2 param set /mcp_server e2e_mode true --no-daemon"
# и т.д.
```

Эта обёртка **ломается в трёх разных ситуациях**:

1. **`$*` (НЕ `"$@"`) склеивает позиционные аргументы через первый символ IFS.**
   Текущие 6 вызовов передают ОДИН строковый аргумент, поэтому случайно
   работает — но контракт нарушен. Любая будущая правка с двумя+
   словами через пробел (`robot_ros ros2 param set /x e2e_mode true` без
   кавычек) потеряет разделители.

2. **`bash -lc '...$*...'` в одинарных кавычках даёт syntax error на любом
   аргументе с одинарной кавычкой.** Текущие аргументы — `ros2 param ...
   e2e_mode ...` — безопасны, но ЛЮБОЙ будущий вызов с апострофом или
   путём с `'` молча сломает весь прогон (regression-test
   `test_e2e_voice_robot_ros_quoting.sh` P2 сейчас красный именно на этом):

   ```
   robot_ros "echo it's broken"
   # → bash -lc 'source ...; echo it's broken'   ← bash: unexpected EOF
   ```

3. **`$(...)` в литерале разворачивается ЛОКАЛЬНО на 249**, не на роботе
   (regression-test P3). Это и дыра в безопасности, и неправильная
   семантика: оператор писал команду для робота, а она выполнилась на 249.

### Цена поломки

`activate_e2e_speaker_db()` / `activate_e2e_memory_db()` при syntax error
на роботе молча уходят в ветку FATAL exit 2 (`_read_e2e_mode()` возвращает
пусто), и **сценарий едет по боевой `/data/speakers.db`** мастерской —
ровно то, что закрывали issue #2750, #2763, #2764, #2781. Это уже третий
«молча сломался на shell-экранировании» баг в этой области за две
недели.

По ADR-0018 «честный FAIL > красивый PASS» и ADR-0022 §4.1 R1
«smoke-false-PASS»: хрупкие обёртки над критическими шагами — это
**архитектурный долг**, который надо явно зафиксировать, а не
передавать «по наследству» следующему воркеру.

### Репро

`docs/reports/repro_robot_ros_issue_2805.sh` — ручной repro (5 кейсов),
`scripts/agent_flow/tests/test_e2e_voice_robot_ros_quoting.sh` —
автоматический регресс-тест (4 кейса). Сейчас тест даёт
**PASS=1 / FAIL=4 (exit 1)** на текущем коде.

## 2. Инвариант (как должно быть)

```text
robot_ros <any-bash-command-with-any-shell-metachars>
    └─ итоговая ssh-команда доезжает до робота БЕЗ syntax error
    └─ $(...), ${}, ;, &&, || внутри аргумента НЕ разворачиваются на 249
    └─ shell-метасимволы внутри аргумента экранируются ОДИН РАЗ
    └─ на роботе bash получает исходную команду и eval'ит её как есть
    └─ контракт: «вызов работает так же, как если бы оператор написал эту
       команду прямо в bash на роботе»
```

Граница: `robot_ros` остаётся тонкой обёрткой над `ssh → docker exec →
bash -lc` с фиксированной преамбулой `source ...; source ...`. Никакой
новой семантики (не async, не retry, не логирование) — только
корректная передача аргументов.

## 3. Рассмотренные варианты

### Вариант A: «Один аргумент-строкой, зафиксировать контракт комментарием»

```bash
# ВАЖНО: $1 — единая команда целиком, без shell-метасимволов ('$(;).
# Сейчас все 6 вызовов так и пишут; если в будущем понадобится
# апостроф — используй printf %q на стороне вызывающего.
robot_ros() {
    ${ROBOT_SSH} "docker exec voice-assistant bash -lc 'source /opt/ros/humble/setup.bash; source /ws/install/setup.bash; $*'"
}
```

| | |
|---|---|
| Бизнес-проблема | Не решает. Контракт «не используй shell-метасимволы» — это регресс в 2027: добавили новый `activate_*_db`, передали строку с апострофом → сломалось, как уже было 3 раза. |
| Простота | Максимальная: меняем только комментарий. |
| Trade-off | Дешевле сейчас, дороже потом. Нарушает ADR-0018 (явность) и ADR-0022 R1 (smoke-false-PASS). |
| Что будет, если НЕ делать | То же, что уже произошло с #2750/#2763/#2781: очередной «молча сломался» баг через 2-4 недели. |

### Вариант B: printf %q + eval на стороне робота (ВЫБРАН)

```bash
robot_ros() {
    local cmd
    cmd="printf %q " "$@"
    ${ROBOT_SSH} "docker exec voice-assistant bash -lc 'source /opt/ros/humble/setup.bash; source /ws/install/setup.bash; eval \"\$cmd\"'"
}
```

Как это работает:

1. `printf %q "ros2 param get /x e2e_mode"` → `ros2\ param\ get\ /x\ e2e_mode`
   (экранирование пробелов обратным слэшем, как требует shell).
2. Полученная строка подставляется в ssh-команду; на стороне робота
   bash получает `eval ros2\ param\ get\ /x\ e2e_mode`.
3. eval разворачивает `\ ` в пробелы и выполняет команду.

| | |
|---|---|
| Бизнес-проблема | Решает все три класса багов сразу: апострофы, `$(...)`, многословные аргументы. |
| Простота | Средняя: 5-7 строк, нужен регресс-тест (он уже написан — `test_e2e_voice_robot_ros_quoting.sh`). |
| Trade-off | diff больше, но **фикс корневой**, а не косметический. Соответствует ADR-0018 + ADR-0022. |
| Что будет, если НЕ делать | Возвращаемся к классу багов #2750/#2763/#2781. |

### Почему НЕ вариант C: «вызывающий сам экранирует»

Можно было бы потребовать, чтобы все 6 вызовов переписывались в стиле
`robot_ros "$(printf %q "...")"`. Это размазывает ответственность
по 6 точкам и не лечит корень: следующий воркер, добавляющий седьмой
вызов, забудет про printf %q.

## 4. Решение

**Принять вариант B.** Изменения:

### 4.1 Файл: `.github/workflows/scripts/e2e_voice_test.sh`, lines 353-355

**Сейчас:**

```bash
robot_ros() {
    ${ROBOT_SSH} "docker exec voice-assistant bash -lc 'source /opt/ros/humble/setup.bash; source /ws/install/setup.bash; $*'"
}
```

**После:**

```bash
# robot_ros <bash-cmd> — выполняет <bash-cmd> на роботе через docker exec
# в bash-login окружении с sourced ROS humble и /ws/install.
#
# Контракт (ADR-0129):
#   * Принимает 1..N аргументов; собираются через printf %q, чтобы
#     пробелы, кавычки и $() в аргументе не сломали удалённый shell.
#   * eval на стороне робота разворачивает printf %q в исходную команду.
#   * Поддерживает shell-метасимволы в аргументе: ', ", $, ;, &&, ||,
#     пробелы, переводы строк и т.д.
#   * Не разворачивает $(...) на стороне 249 — только на роботе.
#
# До этого фикса (issue #2805) использовался $* + bash -lc '...$*...' —
# ломался на апострофах (syntax error) и разворачивал $(...) локально
# на 249 (security + семантика).
robot_ros() {
    local cmd
    cmd="printf %q " "$@"
    ${ROBOT_SSH} "docker exec voice-assistant bash -lc 'source /opt/ros/humble/setup.bash; source /ws/install/setup.bash; eval \"\$cmd\"'"
}
```

### 4.2 Файл: `scripts/agent_flow/tests/test_e2e_voice_robot_ros_quoting.sh`

Уже создан в WIP-коммите `82e90ebec`. Текущий код даёт **PASS=1 / FAIL=4**
(красный), после применения §4.1 — **PASS=4 / FAIL=0** (зелёный). Этот
тест должен стать блокером для PR.

### 4.3 Что НЕ меняется

- Сигнатура вызова: `robot_ros "<one-bash-line>"` — все 6 существующих
  вызовов остаются как есть (один строковый аргумент в двойных кавычках).
- Преамбула `source ...; source ...` — без изменений.
- Поведение на роботе — те же команды, что и сейчас, выполняются.

### 4.4 Обратная совместимость

Старые вызовы вроде `robot_ros "ros2 param set /x e2e_mode true"` после
printf %q превращаются в `printf %q "ros2 param set /x e2e_mode true"` →
`ros2\ param\ set\ /x\ e2e_mode\ true`, eval разворачивает обратно.
**Семантически идентично** для существующих аргументов.

## 5. Trade-off и риски

- **+1 indirection (`eval`)** на стороне робота — но это та же самая
  команда, что вызывающий хотел выполнить, просто shell-экранированная.
- **`printf %q` не покрывает ВСЕ классы метасимволов одинаково хорошо**
  (см. bash man page: «Quote ARGUMENT in a format that can be reused as
  shell input»). Это **намеренно** — мы хотим ровно ту же semantics, как
  если бы оператор написал команду в shell. Если выяснится edge case
  (например, NUL byte), это будет видно как regression в тесте.
- **6 вызовов остаются без изменений** — снижается риск регрессии в
  существующих сценариях.
- **Размер diff** — ~10 строк включая комментарий-контракт. Это
  наименьший возможный фикс корневой проблемы.

## 6. План реализации

Этот ADR — **архитектурное решение**. Имплементация (задача assign в
issue body: backend) делается в отдельной карточке на backend. Шаги:

1. **Этот PR** — ADR-0129 + repro-скрипт + регресс-тест (уже в WIP-коммите
   `82e90ebec`).
2. **Backend-карточка** — применяет §4.1, прогоняет §4.2 (должен стать
   зелёным), добавляет `test_e2e_voice_robot_ros_quoting.sh` в CI.
3. **Ручная проверка Шифу** — `robot_ros "echo it's broken"` на 249
   должен вернуть `it's broken` (не syntax error).
4. **Merge** — после CI зелёного + ручной проверки Шифу.

## 7. Когда применять / НЕ применять

- **Применять:** ко всем харнесс-обёрткам над `ssh + bash -c`, где
  аргумент может содержать shell-метасимволы. Текущая область — только
  `robot_ros`, но если в будущем появятся похожие обёртки
  (например, `robot_db_query` для прямого sqlite3), они ОБЯЗАНЫ
  использовать тот же паттерн printf %q + eval.
- **НЕ применять:** к вызовам, где аргумент — фиксированный литерал
  без shell-метасимволов и контролируется одной командой. Там
  `printf %q` — overkill.
- **НЕ применять retroactively** к уже-merged сценариям: они работают,
  их никто не трогает. Тест ловит только новые изменения.

## 8. Что НЕ делается этим ADR

- Не вводится retry-логика для `robot_ros` — отдельная задача, если
  понадобится (текущий контракт e2e — fail-fast, см. ADR-0022).
- Не вводится таймаут — `bash -c` блокирующий; уже есть верхний
  таймаут в `agent-flow-e2e-process.sh`.
- Не рассматривается замена `bash -lc` на `bash -c` без `-l` — это
  ломает sourced ROS-env (только login-shell подхватывает
  `/opt/ros/humble/setup.bash`).
