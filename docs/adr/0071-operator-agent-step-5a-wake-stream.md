## 0. Что внутри и что — нет

**Не внутри.** Переход на `AudioWorklet` (шаг 5а-0, #1991 — реализован отдельно, PR #2013, влит). Маршрутизация вейка на стороне `stt_node` (шаг 5 — отдельная карточка, статус на момент актуализации не проверялся этим документом). ## 1. Контекст и бизнес-проблема

### 1.1 Что было на момент design-сессии (2026-09-07 утро)

Микрофон шлема стримился **только пока зажат грип**:
`voiceCapture.start()` вызывался в `applyVoicePtt` (`src/rob_box_quest/webxr_client/src/main.ts`)
и `voiceCapture.stop()` при отпускании. То есть робот слышал оператора
ровно столько, сколько оператор держал грип. Вейк-слово «ТАРС» на таком
транспорте физически невозможно.

Сервер (`src/rob_box_quest/rob_box_quest/server/ws_server.py`) принимал
только `voice_ptt_start/stop{mode}` и `voice_mode` — никакого «всегда-включён»
контура не было.

`voice_capture.ts` использовал `createScriptProcessor(4096,1,1)` —
устаревший API, работающий в **главном потоке**. Для PTT это терпимо: захват
живёт секунды. Для всегда-включённого потока он конкурировал бы
с рендер-циклом three.js в VR — отдельная карточка 5а-0 закрыла это до
включения wake по умолчанию.

### 1.2 Что требовалось

Целевая архитектура (`target-operator-agent-and-dialogue.md §7.2`) требует
**второй поток с того же захвата** (`stream_id=2`), отличаемый по `stream_id`,
с локальным VAD-гейтом (тишина не шлётся), командами `voice_listen_start/stop`
(по умолчанию включён при HELLO, выключается тумблером панели), и подавлением
потока `wake` при зажатом грипе (одна фраза — один маршрут).

| поток | `stream_id` | когда идёт | назначение |
|---|---|---|---|
| `ptt` | `1` | пока зажат левый грип | фраза целиком, вейк не нужен |
| `wake` | `2` | пока сессия жива, гейт по локальному VAD | поиск «ТАРС» в `stt_node` |

### 1.3 Почему VAD-гейт на клиенте, а не на сервере

| вариант | почему отклонён |
|---|---|
| Шлём всё, гейтим на сервере | Удвоение трафика WS → Quest по WiFi 5 GHz, лишние ~32 КБ/с/поток int16 PCM 16 kHz; серверный VAD уже есть (`audio_node.py` `_vad_gated`), но он отбрасывает для `/audio/vad`, а не для шлема |
| Wake detector на клиенте (Porcupine/openWakeWord/vosk-browser) | См. §7.2 архитектуры: Porcupine — нет русского, openWakeWord — нет web-сборки, vosk-browser — это STT, не keyword-spotter. **Главное**: на роботе уже крутится STT с русским и списком вейк-слов, там «ТАРС» добавляется строкой в YAML |
| **Клиентский RMS-VAD** (этот ADR) | Дешёво (O(N) на чанк 320 семплов), нативный `AudioWorklet`-ready, не зависит от языка, не требует модели |

Клиент режет тишину **до** WS-отправки — `stt_node` получает только озвученные
сегменты, и внутри них уже ищет вейк-слова по своему YAML.

### 1.4 Почему `stream_id`, а не два фрейм-типа

Wire-протокол (`frame.py`, `protocol.ts`) уже кодирует 1 байт type + 4 байта
`stream_id`. Один `FrameType.VOICE_AUDIO = 0x13` с разными `stream_id` —
минимальное расширение, не требует нового кода на сервере и не ломает
существующих подписчиков.

## 2. Решение

### 2.1 Поток `stream_id=2` (`wake`)

```
int16 PCM 16 kHz mono, чанки 320 семплов (20 мс),
gate перед отправкой:
  rms(чанк) ≥ VAD_RMS_THRESHOLD   → отправить как VOICE_AUDIO(0x13, stream_id=2, payload=чанк)
  rms(чанк) <  VAD_RMS_THRESHOLD   → drop
HDR (выкл/вкл) + паника при грипе — см. 2.4
```

Параметры VAD, как реализовано (`voice_capture.ts`, `VAD_RMS_THRESHOLD_DEFAULT`/`VAD_HANGOVER_MS_DEFAULT`):

```typescript
const VAD_RMS_THRESHOLD_DEFAULT = 200;        // int16 единиц (~0.0061 от максимума)
const VAD_HANGOVER_MS_DEFAULT   = 200;        // мс — после детектирования речи ещё
                                               // 200 мс шлём, чтобы не рвать слоги
```

**Эти числа — стартовая точка, не проверенная на устройстве замером батареи**
(см. §6, DoD-пункт про 2ч — статус: **не подтверждён raw-цифрами** на момент
актуализации этого документа).

### 2.2 Команды `voice_listen_start` / `voice_listen_stop`

Семантика — **включение/выключение always-on потока целиком**, не per-чанк:

| команда | эффект на клиенте | эффект на сервере |
|---|---|---|
| `voice_listen_start` (default при HELLO) | `wakeGate.enabled = true`; чанки из VAD идут в WS с `stream_id=2` | `set_wake_stream_state(active=True)` — ack `voice_listen_ack{state:"active"}` |
| `voice_listen_stop` | `wakeGate.enabled = false`; чанки дропаются **до** VAD; mic **не закрывается** | `set_wake_stream_state(active=False)` — ack `voice_listen_ack{state:"paused"}` |

**Дефолт при HELLO.** Поток `wake` включается автоматически (`voiceCapture.setWakeGate({enabled:true, suppressed:false})` сразу после создания `voiceCapture` в `main.ts`) — иначе оператору пришлось бы каждый раз лезть в панель.

### 2.3 Подавление `wake` при зажатом грипе

Одна фраза не должна попасть и в пайплайн грипа (`stream_id=1`), и в агента
(`stream_id=2` — wake). Решение — **client-side gate на уровне стрима**,
в `applyVoicePtt` (`main.ts`): при зажатии любого грипа —
`voiceCapture.setWakeGate({suppressed:true})`; при отпускании обоих —
`{suppressed:false}`. `enabled` при этом не трогается — gate прокидывается
внутрь, а не гасит капчур.

**Почему НЕ server-side.** Сервер не знает, что грип зажат, только получает
`voice_ptt_start/stop`. Окно между кликом грипа и командой — источник
лишних `wake`-чанков за тот же фрагмент фразы. Подавление на клиенте, до
отправки — единственный способ гарантировать «одна фраза — один маршрут».

### 2.4 Тумблер в панели

По §7.2 «выключается тумблером панели». `main.ts` экспортирует `setWakeListen(on)`
из `bootstrap()`, которая шлёт `voice_listen_start/stop` на сервер и
переключает gate локально. **UI-обвязка (сам чекбокс в панели) на момент
актуализации этого документа не найдена в `main.ts` — `setWakeListen`
экспортируется, но не вызывается ниоткуда внутри модуля.** Это совпадает
с исходным design-планом («UI — отдельная маленькая карточка, не блокирует
DoD шага 5а», см. §7 старого текста) — то есть не регрессия, а
незакрытый follow-up. См. открытый вопрос §9.3.

### 2.5 Один `getUserMedia`, два потока

`voice_capture.ts` возвращает один `VoiceCapture` с колбэком
`onChunk: (pcm: Int16Array, channel: "ptt" | "wake") => void` и публичными
методами `setWakeGate({enabled?, suppressed?})` / `setPttEnabled(on)`.
Один и тот же PCM-чанк уходит в оба канала с разным gate — `ptt` без VAD
(нужен непрерывный поток для `sound_node`), `wake` — под VAD + hangover.

### 2.6 Серверная сторона: `ws_server.py` + `quest_node.py`

```python
elif ftype == FrameType.VOICE_AUDIO:
    # stream_id ∈ {1: ptt, 2: wake} (0 — легаси, тоже идёт в ptt-канал).
    if frame.stream_id == 2:
        self.bridge.publish_quest_wake_audio(payload)
    else:
        self.bridge.publish_voice_audio(payload)
```

`QuestBridge.publish_quest_wake_audio` публикует `AudioData` в ROS-топик
`/audio/quest_wake` (`BEST_EFFORT`/`VOLATILE`/`KEEP_LAST depth=10`), который
читает `stt_node.quest_wake_audio_callback` — контракт устоялся в PR #2106
(см. §11; до этого метод был заглушкой, возвращавшей `None`, вопреки
докстрингу, утверждавшему обратное).

`ws_server.py` также обрабатывает `voice_listen_start/stop` — переключает
серверный флаг `_wake_active` и шлёт `voice_listen_ack`.

## 3. Альтернативы, которые отклонены

| альтернатива | почему отклонена |
|---|---|
| Wake detector на клиенте (Porcupine/openWakeWord/vosk-browser) | См. §1.3 — нет русского / нет web-сборки / это STT, не keyword-spotter |
| Два независимых `getUserMedia` | Удвоение OS-ресурсов, риск конфликта с audio-routing Quest, лишний расход батареи |
| Гейтить только на сервере | Лишний трафик WS (~32 КБ/с × 2 ч = 230 МБ на сессию), батарея, латентность |
| Отдельный `FrameType.VOICE_WAKE_AUDIO` | Ломает совместимость с подписчиками `VOICE_AUDIO`; тот же `stream_id` дешевле |
| Шаг 5а-0 (`AudioWorklet`) внутри этой карточки | ADR-0013 — incremental delivery. `AudioWorklet` — отдельная карточка (#1991, PR #2013); шаг 5а явно **зависит** от него, но это не повод мержить вместе |
| VAD с обучением (energy + ZCR + спектральные признаки) | Избыточно для шлема; RMS+hangover достаточно для «режь тишину» (детект «ТАРС» — на сервере) |

## 4. Trade-off

**Выигрыш:**
- Вейк-слово «ТАРС» физически достижимо без зажатого грипа → разблокирует шаги 5б/6/7+.
- Один mic-захват на две задачи → нет конфликта OS audio-routing.
- VAD-гейт до WS → трафик только когда есть речь → экономия батареи и канала.

**Цена:**
- Постоянный `AudioContext` живёт всю сессию → расход батареи Quest. **Не измерен** ни на момент design-сессии, ни на момент актуализации этого документа (2026-09-08) — DoD остаётся открытым, см. §6.
- RMS-VAD режет тишину — первый звук фразы теряется, если порог слишком высокий. Hangover 200 мс — компромисс, не откалиброван на устройстве.

**Что НЕ делаем (anti-scope):**
- Wake detector на клиенте — отклонён, см. §1.3.
- Список STT-искажений «ТАРС» — собирается по e2e-логам (не выдумывается).

## 7. Что здесь считается закрытым, а что — нет

Design-фаза (этот ADR) и функциональная реализация (три PR, §11) — закрыты.
Не закрыто: замер батареи/стабильности на устройстве (hardware-required,
никогда не блокировался явно через `kanban_block` — issue просто закрыли
раньше), UI-тумблер панели.

## 8. Риски и что из них реализовалось

| риск (design-сессия) | что оказалось по факту |
|---|---|
| `getUserMedia` отваливается через ~30 мин на Quest | Не проверено (нет замера) |
| RMS-VAD режет начало фразы | Не откалибровано на устройстве, но функционально работает (подтверждено на роботе после PR #2110) |
| Расход батареи > 30% за сессию | Не измерено |
| Конфликт PTT при пересечении grip+wake | Не случился — подавление клиентское сработало как задумано |
| `bridge.publish_quest_wake_audio` пишет в топик, которого нет | **Материализовался буквально** — метод был no-op-заглушкой почти сутки, пока PR #2106 не подключил реальный publisher. Хуже: issue закрыли по `git grep`, который находил метод, но не проверял, что он что-то публикует (см. §11.1 — прямая иллюстрация «честный FAIL» из ADR-0018) |
| (не был предвиден) Капчур мог вообще не запускаться вне грипа | **Материализовался** — см. §11.3, корневой баг PR #2110. Это худший случай риска выше на клетку: не «топик неверный», а «клиент физически не мог отправить ни одного wake-чанка ни при каких обстоятельствах» |

## 11. Хронология реализации (добавлено при перенумеровании 2026-09-08)

Design-сессия (этот ADR) была принята утром 2026-09-07 как чистый
документ без кода («Никакого кода в этом PR», исходный §11). Реализация
заняла тот же день тремя отдельными PR — не потому что план был неверным,
а потому что первая же попытка проверить фичу на роботе показала: она
не работает вообще, и не по той причине, которую предполагал первый фикс.

### 11.1 PR #2052 — `feat(quest): wake stream + VAD gate + voice_listen_* commands`

Реализованы: `rmsInt16`/`setWakeGate`/`setPttEnabled` в `voice_capture.ts`,
`sendVoiceAudio(payload, streamId)` в `connection.ts`, routing по
`stream_id` в `ws_server.py`. 18 unit-тестов (9 RED → 18 GREEN на клиенте).

Issue #1992 был закрыт в тот же день комментарием «Закрыто по факту кода»
на основании `git grep -l 'stream_id|voice_listen'` — **это было ложное
подтверждение**: grep находит наличие кода, а не то, что он на самом деле
передаёт аудио до ROS. Ровно тот антипаттерн, о котором предупреждает
ADR-0018 («честный FAIL лучше красивого PASS»). Два следующих PR это
вскрыли.

### 11.2 PR #2106 — `fix(quest #1992): wake-канал шлема доезжает до /audio/quest_wake`

`QuestBridge.publish_quest_wake_audio` был заглушкой (`return None`,
`# TODO ADR-0054 step-5`) — метод существовал (поэтому grep из §11.1
находил совпадение), но ничего не публиковал. Оператор говорит «ТАРС» —
робот не отвечает, потому что мост никуда не шлёт аудио дальше WS-сервера.

Фикс: `QuestBridge` получает реальный ROS-publisher `/audio/quest_wake`
(`AudioData`, `BEST_EFFORT`/`VOLATILE`/`KEEP_LAST depth=10` — совпадает
с подпиской `stt_node.quest_wake_audio_sub`). Заодно поправлен неверный
комментарий в `main.ts`/`connection.ts`, называвший несуществующий топик
`/avatar/quest_wake` (правильно — `/audio/quest_wake`).

### 11.3 PR #2110 — `fix(quest #1992): wake-микрофон никогда не мог слать аудио — start()/stop() привязаны к грипу наоборот`

Диагностика на роботе (владелец произнёс «ТАРС» несколько раз, 0 строк
`wake`/`voice_listen`/`VOICE_AUDIO` в `docker logs`): единственный вызов
`voiceCapture.start()` во всём `main.ts` жил внутри `applyVoicePtt()` и
срабатывал **только на зажатие грипа** — то есть ровно в момент, когда wake
уже принудительно подавлен (`setWakeGate({suppressed:true})`, см. §2.3).
При отпускании грипа вызывался `voiceCapture.stop()`, обрывающий общий
`getUserMedia`-стрим целиком (ptt и wake делят один mic-захват).

Итог: `capturing === true` и `!wakeGate.suppressed` **никогда не были
истинны одновременно** ни при каких условиях — `push()` в `voice_capture.ts`
не мог пропустить wake-чанк ни разу с момента первого мержа. Комментарий
в коде «wake-канал включается автоматически при создании voiceCapture»
был неправдой: `setWakeGate` действительно вызывался при создании, но
реального `start()` там не было — always-on микрофон **не существовал
физически**, несмотря на то что весь остальной контракт (VAD, gate,
routing, топик) к этому моменту уже был на месте и правильно протестирован
изолированно.

Фикс: `voiceCapture.start()` теперь вызывается один раз при boot,
независимо от грипа; `applyVoicePtt()` больше не глушит общий mic-захват
на отпускание (только ptt-канал и suppression); `stop()` остаётся только
на `dispose()` сессии. Добавлен `onError` на `createVoiceCapture` — раньше
сбой `getUserMedia`/`AudioWorklet` проглатывался молча даже в консоли.
Добавлена observability (счётчики приёма/публикации per `stream_id`,
throttled-логи), чтобы «клиент не шлёт» и «мост не публикует» больше не
выглядели в логах одинаково (тишина в обоих случаях — ровно то, что
затруднило диагностику в §11.2).

**Урок для следующего читателя.** Юнит-тесты на изолированные функции
(`rmsInt16`, `setWakeGate`, routing по `stream_id`) были зелёными на
каждом из трёх PR и ничего не говорили о том, вызывается ли вообще
`start()` в правильном месте — это чисто интеграционный баг на уровне
«кто кого дергает», который проявляется только сквозным тестом (PR #2110
добавил именно такой — `voice_capture_wiring.test.ts`, тестирующий сам
`main.ts` без моков `bootstrap()`). Наличие кода (grep) и прохождение
юнит-тестов — это не доказательство того, что функция работает
end-to-end; issue #1992 закрывали по этому ложному основанию дважды за
один день, пока не проверили на реальном роботе.

## 12. Перенумерование 0054 → 0071 (2026-09-08)

Этот документ существовал только в архивной ветке архитектора
(`archive-zagent1992operatoragent05astreamidwakevad`, коммит
`5c3bf1b1`) и никогда не попадал в `develop` под своим номером — слот
`ADR-0054` в `develop` заняла другая карточка того же эпика
(`0054-operator-agent-step-7b-eventbus-bridge.md`, шаг 7б, PR #2048),
хотя код фичи 5а (реализация, §11) успешно влился в `develop` со всеми
комментариями вида `ADR-0054 step 5a`, ссылавшимися в пустоту.

Найдено при разборе архивов `docs/plans/2026-09-08-archive-triage.md`
(находка №1). Восстановлено из архивной ветки и перенумеровано в 0071
(первый свободный номер после максимума 0070 в `develop` на 2026-09-08,
правило ADR-AF-0030 §2.2 — `next = max(existing) + 1` в RT-домене).
Ссылки в коде (`voice_capture.ts`, `main.ts`, `connection.ts`, `ws_server.py`,
`quest_node.py`, тесты) обновлены на `ADR-0071` везде, где комментарий
по смыслу про wake stream / `stream_id=2` / `voice_listen_*`; ссылки на
`enable_reflex_layer` / `ReflexLayer` остались `ADR-0054` (7б) — это
разные документы.

Impl-план (`0054-operator-agent-step-5a-impl-plan.md`, 176 строк, тоже
в архивной ветке) **не восстановлен**: он был инструкцией «как
реализовать» для ещё не написанного кода, и с тех пор код полностью
реализован (и один раз переделан — §11). Разбивка на коммиты, которую
он описывал, устарела и не совпадает с реальными тремя PR. Прецедент
(`ADR-AF-0030 §2.6`): impl-план для другого шага той же серии
(`0055-operator-tts-headset-channel-impl-plan.md`) был перенесён в
`docs/plans/`, а не восстановлен как ADR — impl-планы не являются
архитектурными решениями сами по себе. Здесь тот же принцип: раз
реализация случилась и задокументирована в §11 этого ADR, отдельный
impl-план не добавляет ценности и не восстанавливается.
