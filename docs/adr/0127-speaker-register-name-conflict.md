# ADR-0127 — Регистрация диктора не переименовывает чужой профиль: конфликт имён важнее похожести голоса

**Дата:** 2026-09-22
**Статус:** Accepted — реализовано, юнит-тесты зелёные; e2e-подтверждение на роботе ЕЩЁ НЕ прогонялось (см. §7)
**Автор:** владелец + Claude Code
**Уточняет:** ADR-0097 (UPSERT-семантика `register()`; его фикс входит в этот же PR — он был принят 15.09, но в код так и не попал), issue W5-4 (`register_or_merge` как лекарство от дублей), issue #2348 (калибровка порогов 0.75/0.72)
**Связанные:** issue [#2469](https://github.com/krikz/rob_box_project/issues/2469) (INSERT OR REPLACE затирает эпитеты — закрыт как COMPLETED, но фикса в коде не было), issue #2346 (n308 Борис не опознан), issue #1787 (эпитеты), run [35667281570](https://github.com/krikz/rob_box_project/actions/runs/35667281570) (night-marathon, акт 2), PR [#2736](https://github.com/krikz/rob_box_project/pull/2736) (до него реплики акта 2 не проигрывались вовсе, и баг был невидим)

## 1. Что случилось

Акт 2 ночного марафона регистрирует двух людей подряд: Сашу (TTS `anton`) и Бориса (TTS `ermil`). База дикторов была очищена перед прогоном.

```
📝 Registering 'Саша' from embedding ...
🔍 identify candidates: best='Саша'(dc417cef) score=0.895
👤 Speaker: 'Саша' confidence=0.895
📢 Publishing: is_known=true name='Саша' epithet='Странник' conf=0.895
...
📝 Registering 'Борис' from embedding 5.6s ago
🔗 Speaker 'Борис' merged into existing profile (id=dc417cef) — voice matched an already-known speaker, no duplicate created
✅ [issue 1077] Speaker registered: 'Борис' id=dc417cef
```

Итог в `/data/speakers.db`:

```
speakers: 1 | embeddings: 2
   Борис        dc417cef  эмбеддингов: 2
```

**Вместо двух дикторов остался один, и он переименован.** `dc417cef` — профиль Саши; Саша как личность исчез, его эмбеддинг приписан Борису. Шаг сценария при этом просил ровно обратного: «Запомни мой голос отдельно от Сашиного, мы очень по-разному звучим, и я не хочу, чтобы ты нас путал».

Измерение на том же роботе (два эмбеддинга, оставшиеся в профиле `dc417cef`):

```
emb id=1 sid=dc417cef dim=256 ts=1790033037.6 norm=1.0000     # Саша, anton
emb id=2 sid=dc417cef dim=256 ts=1790034012.9 norm=1.0000     # Борис, ermil
cos(emb1, emb2) = 0.8464
```

0.846 — выше и `IDENTIFY_THRESHOLD=0.72`, и `REGISTER_MATCH_THRESHOLD=0.75`. Для resemblyzer это один человек. Код отработал ровно так, как был написан.

## 2. Корневая причина

`SpeakerDatabase.register_or_merge()` принимал решение «слить или завести новый профиль» ТОЛЬКО по голосу, а имя потом молча перезаписывал:

```python
match = self.identify(embedding, threshold=REGISTER_MATCH_THRESHOLD)
if match is not None:
    return self.register(name, embedding, speaker_id=match.speaker_id), True
```

`register(name, ..., speaker_id=...)` — это и есть переименование (плюс, до фикса ADR-0097, `INSERT OR REPLACE`, обнулявший эпитет, историю кличек, теги и `created_at`).

Такое поведение было осознанным: issue W5-4 лечила обратный симптом — «один человек заводится как два профиля» (денчик/эйджик), и сценарий «LLM расслышал имя иначе» там считался основным. Цена не была оценена.

### 2.1 Что говорит прод-база

Бэкап перед очисткой (`/data/speakers.db.bak-20260921T224624Z`, 44 профиля / 45 эмбеддингов, 946 пар):

- медиана max-cos по парам профилей — 0.5568, но **175 пар из 946 (18 %) выше 0.75**, то есть были бы слиты при регистрации;
- среди пар с РАЗНЫМИ именами и cos >= 0.75 есть и настоящие дубли одного человека (`Денис`/`Денчик` 0.797, `Эйджик`/`Денчик` 0.816), и заведомо разные люди (`Иван`/`Анна` 0.808, `Саша`/`Антон` 0.869, `Антон`/`Шифу` 0.865);
- в базе живут профили с именем `Зовут` (2 шт.) — мусор, пойманный из фразы «меня зовут…» до валидатора issue #2348.

Вывод, который здесь важен: **по одному только голосу отличить «тот же человек под другим именем» от «другой человек с похожим голосом» невозможно** — обе картины выглядят одинаково (высокий cos + новое имя). Порог не выбирается: и 0.75, и 0.82 режут по живому.

## 3. Решение

`register_or_merge()` сливает эмбеддинг в существующий профиль **только если совпало и имя**:

| Голос | Имя | Что делаем |
|---|---|---|
| cos >= `REGISTER_MATCH_THRESHOLD` | совпадает (с точностью до регистра/пробелов) | дописываем эмбеддинг в найденный профиль, имя в БД НЕ трогаем |
| cos >= `REGISTER_MATCH_THRESHOLD` | другое | **конфликт**: заводим отдельный профиль, чужое имя не трогаем, громко логируем |
| cos < порога | любое | новый профиль (как и раньше) |

Явно переданный `speaker_id` по-прежнему обходит проверку: там вызывающий код сам утверждает, кто это (rename-поток `/voice/speaker/rename`).

Мусорное имя (`_validate_speaker_name` → `""`) не совпадает ни с чем, включая другое мусорное: легаси-профиль «Зовут» не должен собирать в себя чужие голоса.

### 3.1 Почему именно так, а не иначе

**Из двух возможных ошибок выбираем обратимую.** Лишний профиль чинится одним вызовом `merge_speakers()` (и `/voice/speaker/merge` у ноды, и шов идентичности перенесёт факты — issue #2440). Затёртое имя не восстановит никто: в БД не остаётся следа, что профиль раньше звали иначе.

Плюс: поток «LLM расслышал имя иначе» УЖЕ имеет свой честный инструмент — `/voice/speaker/rename` с `old_name`/`new_name` (issue #1101). Переименование через регистрацию было не фичей, а побочным эффектом.

### 3.2 Рассмотренные альтернативы

**A. Не переименовывать, но сливать; хранить список имён/алиасов.**
Имя формально не теряется, но два ЧЕЛОВЕКА по-прежнему сливаются в один профиль — вместе с фактами (акт 2 сохраняет «Саша не ест лук» и «Борис болеет за Спартак» в один scope). Проверки акта 3 (`speaker='Саш'` vs `speaker='Борис'`) всё равно не проходят, а робот на вопрос «как меня зовут» получает два имени и должен как-то выбрать. Отклонено: лечит симптом (потерю строки), а не конфликт личностей. Схема алиасов остаётся вариантом на будущее ДЛЯ ПОДТВЕРЖДЁННЫХ склеек (оператор сказал «это один человек»).

**B. Поднять `REGISTER_MATCH_THRESHOLD` выше порога опознания.**
Не работает по числам: боевая пара Саша/Борис дала 0.846, а калибровка issue #2348 уже показала, что при 0.82 через merge проходит лишь 38 % повторов одного голоса. Порог пришлось бы задрать выше 0.85 — тогда merge не срабатывает почти никогда, и мы возвращаемся к багу W5-4, сохранив при этом возможность затереть имя на редком ложном совпадении. Отклонено.

**C. Спрашивать у человека («ты Саша или Борис?»).**
Правильное поведение продукта и, вероятно, следующий шаг: у ack теперь есть поле `voice_conflict`, dialogue_node может на него отреагировать репликой. Но это не замена инварианту БД: пока ответа нет, данные уже должны быть целы. Отложено в отдельную карточку.

### 3.3 Сопутствующий фикс (ADR-0097)

В том же изменении `register()` перестаёт использовать `INSERT OR REPLACE` — он был `DELETE + INSERT` и обнулял `epithet`, `epithet_history`, `tags`, `sentiment_score`, `last_epithet_review`, а `created_at` переписывал на «сейчас». Целевой код описан в ADR-0097 §2.1; здесь он реализован дословно, плюс WARNING в лог при переименовании по явному id.

## 4. Контракт для вызывающего кода

`register_or_merge()` возвращает `RegisterOutcome` — двухэлементный кортеж `(speaker_id, reused)` (весь существующий код `sid, reused = ...` работает без правок, как и требовал ADR-0097 §5.5) с дополнительными атрибутами:

- `name_conflict` — `True`, если голос совпал, а имя нет;
- `conflict_name` / `conflict_speaker_id` / `conflict_score` — чей голос похож и насколько.

Поля живут атрибутами, а не третьим элементом кортежа, именно ради обратной совместимости.

Предупреждение оператору печатает **нода**, а не модуль БД: `logging`-строки из `utils/speaker_embeddings.py` в `docker logs voice-assistant` не видны (в разборе run 35667281570 видно только то, что пишет `node.get_logger()`). `speaker_id_node._do_register` логирует конфликт на WARNING с готовой командой для ручной склейки и кладёт `voice_conflict` в ack `/voice/speaker/result`.

## 5. Что теперь ломается (честная цена)

- Если LLM в самом деле расслышал имя иначе («Денис» → «Денчик»), появится второй профиль вместо слияния. Это регресс относительно W5-4 — ровно в том сценарии, ради которого W5-4 делалась. Чинится `merge_speakers()`; в логе есть готовая команда.
- Тесты, которые фиксировали старое поведение («Денчик» → «Эйджик» сливаются, имя обновляется на последнее услышанное), переписаны под новый контракт. Это осознанная смена контракта, а не подгонка тестов под реализацию.

## 7. Чего НЕТ (не сделано)

- **E2E на роботе не прогонялся.** Акт 2 после фикса должен оставить в `/data/speakers.db` ДВА профиля; это не проверено — нужен прогон марафона. Метку `e2e-done` не ставить.
- Уже слитые профили в проде не разъезжаются обратно: `dc417cef` остаётся одним профилем с двумя эмбеддингами. Бэкап до очистки — `/data/speakers.db.bak-20260921T224624Z`.
- Различимость голосов TTS — отдельная история (см. комментарий к `map_tts_voice` в `.github/workflows/scripts/e2e_voice_lib.sh` и `evidence/tts-voice-distinctness-2026-09-22/`). Даже при идеальной БД minimax со старой таблицей давал Саше и Борису один голос, и акт 3 не мог пройти в принципе.
