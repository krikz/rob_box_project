## 1. Проблема

Товарищ Шифу (30.09): «робот преимущественно играет одно и то же, одни и те же сэмплы и паттерны; настоящий диджей пробует разные штуки … помнить, что уже использовали».

Живой лог одного сета (10 club-треков, тема не нашлась → `name` не передан):

| seed | root | прогрессия | шаблон | бочка |
|---|---|---|---|---|
| 6261504 | A# | VI-VII-i-i | dj_dave_32 | breakbeat |
| 6261504 | A# | VI-VII-i-i | dj_dave_32 | breakbeat |  ← повтор 1-в-1

`VI-III-VII-i` — 5 из 10, bpm всегда 124, лад только minor. Причина в устройстве выбора:

1. `club_kit` и `_pick_progression` — `rng.choice` по сиду; о том, что уже играло, они не знают.
2. `_repeat_warning` сравнивает только с ОДНИМ прошлым вызовом и только для classic.
3. `DJState.played_names` живёт в пределах сета и пропадает с перезапуском.

Персистентной истории сыгранного не было нигде.

## 2. Решение

### 2.1 Память: `music_history`

Таблица `music_history` в `voice_memory.db` (`VOICE_MEMORY_DB_PATH`, тот же файл, что у `RtttlLibrary`; схема создаётся кодом `CREATE TABLE IF NOT EXISTS` — тем же способом, что соседняя `rtttl_melodies`, без SQL-миграции: миграции `migrations/*.sql` относятся к `music_tracks`, а RTTTL-таблица живёт в коде). Поля: `ts`, `set_id`, `style`, `melody_name`, `fragment_offset`, `hook_fingerprint`, `progression`, `template`, `kick`, `hats`, `lead`, `bass`, `pad`, `root`, `bpm`, `scale`. Поля `set_id`, `fragment_offset`, `hook_fingerprint` пока не заполняются — их берут карточки (б)–(г).

`MusicHistory.record(**fields)` / `recent(limit, within_sec)` (свежие первыми). БД недоступна → WARNING в логе, `available=False`, выбор идёт без памяти. Это громкая, а не молчаливая деградация.

### 2.2 Выбор: `weighted_pick`

Чистая функция `weighted_pick(options, recent_values, rng, *, decay=0.7, floor=0.03)`. Вес опции = `max(floor, 1 − Σ decay^i)` по позициям `i` (0 — самое свежее), где опция встречалась. Свежий повтор — штраф 1.0 (вес `floor`), старый — почти нет; пол `floor > 0` оставляет любой выбор возможным.

### 2.3 Подключение к club

* `club_kit(seed, template, kick, recent=None)`: каждая роль (шаблон, бочка, хэты, lead/bass/pad) — `weighted_pick` по значениям роли из `recent`. Каркас, равный предыдущему, перебрасывается (до 8 попыток отдельными ГСЧ `club-kit:<seed>:<n>`, затем принудительная смена бочки) — «одинаковый каркас подряд никогда».
* `club_progression(seed, recent=None)`: прогрессия со штрафом; отдельный ГСЧ `club-prog:<seed>` не сдвигает поток рифа.
* `render_club(..., recent=None)` передаёт историю в оба выбора.
* **Инварианты:** без `recent`/при пустом `recent` результат побайтно прежний (закреплено sha256 старого вывода в тесте); `seed=0` (эталон, снимок `club_arranger_seed0.foxdot`) и явные `template`/`kick` побеждают историю.
* `ComposeMusicTool._execute_club` читает `recent(20)`, после успешного рендера пишет каркас + прогрессию + root/bpm/scale/имя хука и логирует одну INFO-строку: что выбрано и сколько записей истории учтено. С RTTTL-хуком прогрессию задаёт хук, в историю она пишется как `NULL`.

## 3. План карточек umbrella #3223

* (а) — этот ADR: история + штраф за недавнее.
* (б) — RTTTL-фрагменты как хук, когда тема не найдена (`melody_name`, `fragment_offset`, `hook_fingerprint` — в историю).
* (в) — расширение пулов + движение тональности/темпа по сету (root/bpm/scale уже пишутся).
* (г) — материал из сообщения (Strudel/RTTTL/ноты) → хук следующего трека.
* (д) — `search_web` как источник мелодии для темы, которой нет в архиве.

## 4. Trade-offs и альтернативы

* **Детерминизм сида теперь зависит от истории.** `render_club(seed=N)` с историей даст не то, что без неё. Воспроизводимость — через лог: строка `[#3224] club выбор: seed=…, progression=…, template=…` содержит полный выбранный каркас, его можно передать явно (`render_club_kit(kit, seed, progression=…)`). Без истории (тесты, CI, `seed=0`) детерминизм прежний.
* **Не гарантия, а склонность.** Штраф вероятностный (пол > 0); жёсткая гарантия дана только для «каркас не равен предыдущему». Ограничение «ни одна прогрессия > 3 из 10» подтверждается тестом на нескольких базовых сидах, а не доказано аналитически.
* **Альтернатива: жёсткое исключение последних N** — предсказуемо, но при малых пулах (5 прогрессий, 3 шаблона) быстро выбивает пул целиком; экспоненциальное затухание мягче.
* **Альтернатива: только в памяти процесса** — не переживает перезапуск (а перезапусков много); отвергнуто.
* **Альтернатива: SQL-миграция** — соседняя RTTTL-таблица создаётся кодом; отдельный механизм миграций ради одной таблицы дал бы два способа в одном модуле.
* История общая на все стили и сеты (окно последних 20); `set_id` под фильтр по сету не используется, пока карточки (б)–(в) не решат, нужен ли он.
* Рост таблицы не ограничен (запись ≈ 100 байт на трек); очистка/ротация не сделана — отдельная задача, если понадобится.
