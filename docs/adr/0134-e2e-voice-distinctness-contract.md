## 1. Контекст

Issue #2754 фиксирует регрессию e2e-сценария `night_marathon_act2_acquaintance_v1.json`, шаг `n210_grisha_no_name`: дядя Гриша (TTS `zahar`) намеренно не называет имя — это контрольная группа «незнакомец» для акта 3. На роботе идентификация даёт `best='Борис'(...) score=0.816 → Speaker: 'Борис'` — при `identify_threshold=0.72`. Шаг при этом **зелёный**, потому что проверяется только `must_not_call: register_speaker` (запрет регистрации без имени). Сам факт «identify candidates: best='Борис'» в логе не ассертится.

Это **не регрессия `identify()`** (порог не менялся, код тот же), и **не регрессия `register_or_merge`** (ADR-0127 уже разделил конфликт голоса и имени). Это **свойство тестовых данных**, ставшее невидимым из-за дыры в проверке:

- Полная матрица по 28 парам Russian*-голосов (`evidence/tts-voice-distinctness-2026-09-22/minimax_voices.json`): в ЛЮБОМ наборе из 4 голосов минимум **две** пары выше 0.6. Лучший набор `{ReliableMan, PessimisticGirl, CrazyQueen, AttractiveGuy}` даёт худшую пару 0.710.
- После правки таблицы голосов (PR #2743) `zahar → Russian_CrazyQueen`, `ermil → Russian_PessimisticGirl` — пара 0.684 в файлах, 0.846 на роботе (микрофонный канал поднимает косинус).
- Боевая пара «антон↔ермил»: файлы 0.684 → робот 0.846 (тот же сдвиг).
- **Порогом это не правится** (#2747): 0.72 одновременно слишком высок для живого и слишком низок для синтетики. Поднять — сломать живых, опустить — слить дикторов e2e.
- `speaker_db_admin.py list` (прямой замер по боевой `/data/speakers.db`, 22.09.2026):
  ```
  ⚠ Возможные дубли одного человека (макс. косинус галерей >= 0.72):
    'Ночной инженер' (10208fea) ~ 'Саша'          (dc76d659): 0.929
    'Борис'          (05ff0881) ~ 'Ночной инженер'(10208fea): 0.723
    'Дэнчик'         (1ae4b0ac) ~ 'Деньчик'       (d9b91d1c): 0.872
  ```
  0.929 между «Сашей» и «Ночным инженером» — **четырехкратный** зазор до порога: разрыв между голосами (0.071) вчетверо меньше зазора до порога (0.209). НИКАКОЙ порог их не разведёт, не сломав при этом узнавание живых.

**Следствие:** акт 2, требующий различить 4 персонажа подряд по голосу, **красный по построению** при `E2E_TTS_PROVIDER=minimax`. Это не баг — это неотъемлемое свойство тестовых данных, которое нужно явно признать, а не лечить порогом или подменой провайдера.

**Главное в issue:** «Шаг при этом зелёный — он проверяет только `must_not_call: register_speaker`, **то, что робот считает незнакомца известным, не проверяет никто**». Дыра в проверке — единственное, что надо закрыть.

## 2. Решение

### 2.1 B — Инвариант на шаге: «незнакомец НЕ опознан как известный»

`scripts/e2e/gen_night_marathon.py:step(...)` получает kw-only параметр `must_not_identify_as: list[str] | None = None`, который записывается в `acceptance` шага как `must_not_identify_as`. Для `n210_grisha_no_name` список = `["Борис", "Саша"]` (оба реально зарегистрированы в `n201`/`n204` до этого шага).

Семантика для GATE-1/GATE-2 парсера:
- В лог-стриме шага ищем формат `👤 Speaker: '<NAME>'` (эта строка живёт в dialogue_node и speaker_id_node и меняется редко; если эволюция формата — расширяем grep, не инвариант).
- Если для ЛЮБОГО `NAME` из `must_not_identify_as` строка нашлась — шаг КРАСНЫЙ.
- Пустое (`👤 Speaker: 'unknown'`, `is_known=false`) — зелёное.
- Допустимы промежуточные строки `🔍 identify candidates: best='Борис'(...) score=...` — это **только кандидаты**; финальный вердикт один.

Поле строго per-step — для других шагов это YAGNI, расширение — отдельная фаза, если понадобится.

### 2.2 C — Provider-aware generator guard

`scripts/e2e/gen_night_marathon.py` сегодня синтезирует JSON без знания, разводятся ли голоса у текущего провайдера. Добавляем helper `_validate_voice_distinctness(steps, provider, threshold)`:

1. Собрать уникальные `voice=` из шагов сценария.
2. Загрузить `evidence/tts-voice-distinctness-2026-09-22/<provider>_voices.json` (он уже в репо, воспроизводимо).
3. Построить матрицу max-cos между КАЖДОЙ парой голосов из `inter_voice_max_cos`.
4. Если хоть одна пара `>= threshold` — `raise SystemExit(2)` с диагностикой: какие именно голоса в каких именно шагах конфликтуют.
5. Если файла замера для провайдера нет — **warning, не error** (greenfield).

Где запускается:
- В самом `gen_night_marathon.py` (на CI в `L-E2E Voice Test` шаге `generate_scenarios`).
- Локально при ручной перегенерации.
- Threshold по умолчанию — `identify_threshold` из `rob_box_voice.utils.speaker_embeddings.IDENTIFY_THRESHOLD` (тот же, что в проде, а не изобретён заново).
- Переопределяется через CLI-флаг `--voice-distinctness-threshold` (на случай если для нового провайдера хотим ослабить/усилить).

**NB по текущему сетапу:** сценарий заточен под `voice_provenance.tts=yandex` (см. `gen_night_marathon.py:1554`). Yandex — исходный каталог, голоса `anton`/`ermil`/`zahar`/`filipp` НЕ переводятся. Замер для yandex в `evidence/tts-voice-distinctness-2026-09-22/` **отсутствует** (ключ робота отвечает `PERMISSION_DENIED`, см. комментарий issue #2754). Это значит:
- Guard для `provider=yandex` уйдёт в warning (файла нет) — поведение по умолчанию для greenfield.
- Для `provider=minimax` guard СРАБОТАЕТ (есть `minimax_final.json` с таблицей). Это именно то, что мы хотим: смена провайдера на minimax без переписывания сценария теперь видно КРАСНЫМ на этапе генерации, а не на этапе e2e.

### 2.3 Регрессия `n210` (Борис/Саша/оба) теперь ловится двумя гейтами

1. GATE-1 (`must_not_identify_as` + `must_not_say` + `must_not_call`) — на уровне шага.
2. GATE-2 (`acceptance*.json`, `expected_tool_calls`/`must_not_call` сверху) — на уровне акта.

Если оба зелёные, а робот всё равно назвал незнакомца Борисом — это уже отдельный класс бага (например, race `register_or_merge` или старая запись из `harness_voice.db` через MCP, ADR-0055/#2000). ADR-0134 это не покрывает и не пытается (принцип: чиним ровно то, на что показывает issue, не размазываем scope).

## 3. Отклонённые альтернативы

### 3.1 A — Разнести персонажей по разным TTS-провайдерам/голосам

Идея: «Саша=Yandex, Борис=Edge, Гриша=MiniMax, Филипп=Yandex», зафиксировать в `voice_provenance.tts` каждого шага. Это решает различимость через гетерогенность источников и формально лечит симптом.

**Отклонено по KISS / YAGNI:**

1. **Не нужно для теста.** Тест проверяет логическую корректность шага (незнакомец остался незнакомцем), а не свойство «робот умеет различать 4 голоса подряд». Это РАЗНЫЕ свойства; первое — инвариант шага, второе — свойство тестовых данных, и для e2e оно не требуется. Подменять тестовые данные ради свойства, которое тесту не нужно — overfitting.
2. **Расход на поддержку нелинеен.** У каждого провайдера свои лимиты, ретраи, таймауты, формат ошибок; e2e должен воспроизводить флейк, а микс из 3 провайдеров в одном прогоне даёт декартово произведение режимов отказа. Каждое утро CI-стенд будет падать на чём-то новом, и трейс будет невозможно повторить.
3. **Ложное обещание качества.** Если в боевой системе тоже когда-нибудь смешаются провайдеры (как fallback), способность «один персонаж = стабильный голос» важнее способа синтеза. Сценарий, где стабильность привязана к конкретному провайдеру, проверяет не ту систему.
4. **Если когда-то понадобится** — отдельный ADR, с конкретным use-case (что именно за провайдерское разнесение проверяем), с замером для конкретной конфигурации, с обоснованием, что однородного решения нет. Сейчас такого use-case нет.

### 3.2 B' — Снять требование различать 4 персонажа, оставить только ранжирование

Идея: акт 2 проверяет только «узнал Сашу», «узнал Бориса», «не узнал Гришу как Сашу» — без явного ранжирования всех 4.

**Уже реализовано** в текущем сценарии как раз через `must_not_say=["Борис", "Саш", ...]` (см. `gen_night_marathon.py:472-478`). Это именно проверка семантики, а не различимости голосов. ADR-0134 просто закрывает параллельную дыру на уровне speaker_id (`must_not_identify_as`), а не на уровне речи робота (`must_not_say`). Они измеряют разное; нужно оба.

### 3.3 С' — Поднять `identify_threshold` для minimax-прогонов

Идея: при `E2E_TTS_PROVIDER=minimax` использовать `identify_threshold=0.95` — выше, чем любая inter-voice пара в измерении.

**Отклонено**, потому что:
- Это НЕ решает дыру `n210`: под порог 0.95 попадают И «Саша» (intra 0.95–0.98) И «Гриша» (intra 0.95–0.98). Зарегистрированный диктор тут же перестаёт узнаваться — регрессия из #2747.
- Это плодит per-провайдер конфиги, и каждый новый провайдер будет ломать договоренности.

### 3.4 D — Отказаться от MiniMax в пользу Yandex для act 2

Идея: форсировать `voice_provenance.tts=yandex` для всех марафонов, MiniMax оставить только как research.

**Отклонено** потому что:
- Противоречит ADR-0009 (мульти-провайдерность — базовая фича harness, от неё не отказываемся в одном сценарии).
- Перевод act 2 на yandex требует РАБОТАЮЩЕГО yandex-ключа (сейчас в issue: `PERMISSION_DENIED`). Это отдельный enabler — не задача ADR-0134.
- Даже если yandex заработает, это лечит симптом для act 2, но не учит сценарий валидировать, что провайдер вообще пригоден для act 2.

## 4. Что входит в PR

1. **`scripts/e2e/gen_night_marathon.py`** — kw-only `must_not_identify_as` в `step()`, propagate в `acceptance`. Helper `_validate_voice_distinctness(...)`. Вызов helper перед `with open(...)` для каждого scenario-файла. Уважительный warning при отсутствии файла замера. CLI-флаг `--voice-distinctness-threshold` для override.
2. **`.github/workflows/scripts/e2e_voice_test.sh`** — парсер `acceptance.must_not_identify_as` в GATE-2, fail шага с понятным сообщением.
3. **`.github/e2e/scenarios/night/night_marathon_act2_acquaintance_v1.json`** (регенерация) — у `n210_grisha_no_name` появится `must_not_identify_as=["Борис", "Саша"]`. Остальные 11 scenarios регенерируются автоматически (без изменений, кроме возможной косметики порядка полей — сохраняем diff минимальным).
4. **`tests/unit/test_gen_night_marathon_voice_guard.py`** — синтетический сценарий с 4 одинаковыми голосами → `SystemExit(2)`; с 4 различными yandex-голосами → OK.
5. **`tests/unit/e2e_scripts/test_e2e_voice_test_must_not_identify_as.py`** — синтетический лог с `Speaker: 'Борис'` + список `must_not_identify_as=["Борис","Саша"]` → красный; с `Speaker: 'unknown'` → зелёный.

`evidence/tts-voice-distinctness-2026-09-22/` — без правок.

## 6. Trade-offs / Риски

1. **Guard слишком строгий для greenfield-провайдеров:** подключаем нового TTS-провайдера, файла замера ещё нет — guard уйдёт в warning. Документировано в §2.2; путь снятия warning — `python3 scripts/e2e/measure_tts_voice_distinctness.py --provider X` + коммит файла под `evidence/tts-voice-distinctness-2026-XX-XX/<X>_voices.json`.
2. **Якорная строка лога `👤 Speaker: '<NAME>'`** может эволюционировать — это контракт по логу, а не API. Смягчение: парсер пишем с обоими паттернами (`👤 Speaker: 'NAME'` И `Speaker: 'NAME' confidence=` — оба встречаются в разных версиях dialogue_node/speaker_id_node). При изменении формата лога в коде — расширяем grep, не инвариант ADR-0134.
3. **`must_not_identify_as` не различает «обознался Сашей» vs «обознался Борисом» в терминах репорта:** оба равно плохи, оба попадут в одну строку диагностики. Это правильное поведение — обе ошибки одинаково wrong.
4. **Расход на регенерацию:** все 12 JSON-сценариев будут регенерированы в одном коммите. Diff минимизирован (только добавление нового поля в `n210`); если CI-парсеры критичны к порядку ключей — закрепляем через `json.dump(..., sort_keys=True)` (сейчас в генераторе не используется, см. `gen_night_marathon.py:1565-1567` — нужно ВНИМАНИЕ, изменение sort_keys изменит диффы ВСЕХ 12 файлов).
5. **Не покрывает гонку `register_or_merge`:** если регрессия ADR-0127 вернётся и Гриша каким-то образом «прибьётся» к Борису — `must_not_identify_as` это не поймает (Гриша реально зарегистрируется под name='Борис'). Но это уже отдельный класс бага, и ADR-0127 закрыт юнит-тестами. Сейчас мы чиним ровно то, что issue #2754 показывает.
6. **Стоимость helper `_validate_voice_distinctness`:** O(V²) пар, где V — уникальных голосов в сценарии (4 в act 2, до ~10 в самых «многоголосных» актах). Каждая пара — два `dict.get()` в загруженном JSON. Микросекунды. Бесплатно.
