## 0. TL;DR

**Проблема.** Контракт топика `/audio/quest_wake` нарушен: продьюсер публикует **чанки** (640 байт = 20мс), а консьюмер `stt_node` интерпретирует их как **фразы**. STT на 20мс фрагментах возвращает пустоту → вейк-роутер не видит «ТАРС» → оператор молчит.

**Решение.** Буферизовать чанки в `QuestBridge.publish_quest_wake_audio` и публиковать **одну** `AudioData` на фразу целиком. Сегментация — по паузе в потоке: пауза ≥ `WAKE_SEGMENT_SILENCE_TIMEOUT_MS` (старт 500мс, см. §4.2) → флаш. По `voice_listen_stop` или shutdown — флаш принудительный.

**Где фикс.** В `quest_node.publish_quest_wake_audio`, **а не** в `stt_node.quest_wake_audio_callback`. Обоснование в §3.

**Плюс.** Поправить сообщение в логе `stt_node.py:704-705` — сейчас оно вводит в заблуждение, говоря «Сегмент без operator-вейка» даже когда STT просто вернул пустоту на 20мс чанке.

## 1. Контекст и бизнес-проблема

### 1.1 Что было задумано (ADR-RT-0071 §1.2)

Wake-поток шлема (`stream_id=2`) проектировался как всегда-включённый поток PCM, в котором `stt_node` сам находит вейк-слово «ТАРС» по YAML (ADR-RT-0065 SSoT) и публикует результат в `/avatar/stt/result`. Клиент (Quest-шлем) применяет RMS-VAD с hangover 200мс, чтобы **не забивать WS тишиной**, и шлёт только озвученные чанки.

### 1.2 Что есть на самом деле (live, 2026-09-08)

Оператор в шлеме произносит «ТАРС ты здесь». `docker logs voice-assistant`:

```
[stt_node] 🎤 Получена фраза: 0.02с (640 bytes)        ← поток шлема
[stt_node] ❌ ОТКЛОНЕНО (пустое)
[stt_node] 🔇 [wake] Сегмент без operator-вейка/отклонён — молчу
[stt_node] 🎤 Получена фраза: 0.02с (640 bytes)
[stt_node] ❌ ОТКЛОНЕНО (пустое)
... (×~50)
[stt_node] 🎤 Получена фраза: 4.57с (146304 bytes)       ← ReSpeaker, для сравнения
[stt_node] ✅ ПРИНЯТО (respeaker): да ты здесь
```

Каждый чанк шлема — ровно 0.02с / 640 байт (= 320 семплов int16 @ 16кГц). STT-вызов на 20мс аудио **физически не может** вернуть текст: даже вейк-слово «ТАРС» (≈0.3с) не помещается. ReSpeaker-фразы в том же логе — 4.57с / 146304 байт, и они распознаются штатно.

Транспорт при этом исправен (`docker logs rob-box-quest`):
```
quest: wake audio first packet published to /audio/quest_wake (640 bytes)
quest: wake audio publish summary: 153 packets / 97920 bytes in 20.1s (total 405)
```
~50 публикаций/сек × 640 байт = 32кБ/с → ровно «поток 16кГц, чанк 20мс», как и заявлено в `publish_quest_wake_audio:518`.

### 1.3 Два контракта одного топика

Документация (ADR-RT-0071 §2.6) и `stt_node.quest_wake_audio_callback:530` предполагают, что в сообщении лежит **VAD-сегмент** («распознаём VAD-сегмент (клиент гейтит локальным VAD)»). Фактически приходит **один 20мс чанк** — потому что:
1. RMS-VAD на клиенте (`voice_capture.ts:174-179`) режет **тишину**, а не **фразу**. После 200мс тишины gate закрывается, и следующий звук начнёт **новую** последовательность чанков, но между ними в `WS` будет пусто (топик `/audio/quest_wake` пустой).
2. `stt_node.quest_wake_audio_callback` запускает `_recognize_with_fallback` на каждом сообщении (`stt_node.py:622`), не накапливая.

То есть **никто не собирает фразу**. В этом суть бага.

### 1.4 Побочный дефект: лог вводит в заблуждение

`stt_node.py:704-705`:
```python
if source == _SRC_WAKE:
    self.get_logger().info("🔇 [wake] Сегмент без operator-вейка/отклонён — молчу")
```
Это сообщение печатается, когда `_recognize_with_fallback` вернул пустоту **или** короткий текст. В нашем случае STT возвращает пустоту не потому что «нет вейка», а потому что «20мс — мало для распознавания вообще». Именно эта неоднозначность маскировала корень: в логах выглядело как «оператор что-то говорит, но не вейк-слово», а не как «20мс чанки не имеют права возвращать текст, никогда не должны были сюда попадать».

## 2. Решение

### 2.1 Сегментация в `QuestBridge.publish_quest_wake_audio` (вариант A)

```
int16 PCM 16 kHz mono чанки по 320 семплов (= 640 байт = 20мс),
приходят из WS по одному на каждый wake-кадр;

в QuestBridge:
  wake_buf: list[bytes]            # накопитель
  wake_silence_ms: float = 0.0     # счётчик тишины

  на каждый publish_quest_wake_audio(payload):
    if _chunk_is_silent(payload):          # уже есть в quest_node.py:149
      if wake_buf and wake_silence_ms >= WAKE_SEGMENT_SILENCE_TIMEOUT_MS:
        _flush_wake_buf()                  # одна AudioData в /audio/quest_wake
      if wake_buf:
        wake_silence_ms += chunk_ms
    else:
      wake_buf.append(payload)
      wake_silence_ms = 0.0

  на voice_listen_stop / shutdown:
    _flush_wake_buf()                      # финальный флаш, не теряем хвост
```

Параметры (стартовые, см. §4.2):
- `WAKE_SEGMENT_SILENCE_TIMEOUT_MS = 500.0` — столько тишины считать концом фразы
- `WAKE_SEGMENT_MAX_DURATION_MS = 10000.0` — safety: длиннее 10с = флаш принудительно (защита от «оператор говорит без пауз»)

После фикса контракт топика `/audio/quest_wake`:
- **до** фикса: одно сообщение = один 20мс чанк (~50/сек)
- **после** фикса: одно сообщение = одна фраза (обычно 0.5с – 3с), `AudioData.data = list(concatenated_pcm)`, `sample_rate = 16000`, `channels = 1` уже предполагается консьюмером (`stt_node.py:557: len(audio_bytes) / (sample_rate * 2)`)

### 2.2 `stt_node` остаётся как есть

`stt_node.quest_wake_audio_callback` **не трогаем** — он уже правильно работает с фразами (на ReSpeaker-данных это подтверждено, см. §1.2). После фикса `publish_quest_wake_audio` он будет получать ровно то, что задокументировано: VAD-сегмент.

### 2.3 Поправить лог в `stt_node.py:692-705`

Три разных случая — три разных сообщения, чтобы будущие ретро не путались:

| случай | текущее | предлагаемое |
|---|---|---|
| STT пуст, source=wake | `❌ ОТКЛОНЕНО (пустое)` + `🔇 [wake] Сегмент без operator-вейка/отклонён — молчу` | `❌ [wake] STT пуст на сегменте {duration:.2f}с ({bytes} bytes) — проверь upstream-сегментацию (issue #2135)` |
| STT пуст, не wake | `🔇 [issue 989] Пустой STT (эхо/музыка) — молчу, без «не расслышал»` | оставить как есть |
| STT не пуст, но короткий и не wake-слово | `❌ ОТКЛОНЕНО (короткое)` + `🔇 [wake] Сегмент без operator-вейка/отклонён — молчу` | `❌ [wake] Нет operator-вейка в {text!r} — drop` (только если есть текст) |

Логика: «нет wake» ≠ «STT пуст». Это разные стадии, и ретро-инженер должен видеть разницу.

### 2.4 Не меняем (anti-scope)

- Клиент (`voice_capture.ts`, `voice_listen_*`) — продолжает шлать чанки. Менять протокол не нужно.
- `stt_node.quest_wake_audio_callback` — остаётся без изменений.
- STT-искажения слова «ТАРС» — отдельный вопрос (ADR-RT-0065 §wake_words, шаг 5а-2), этот ADR только про сегментацию.
- `audio_node` (VAD для ReSpeaker) — не наша зона, паттерн другой (`speech_continuation` в нём работает по фразам — и это референс, см. §4.1).

## 3. Альтернативы, которые отклонены

### 3.1 Альтернатива B: сегментация в `stt_node.quest_wake_audio_callback`

Буферизовать `/audio/quest_wake` **на стороне STT** и собирать фразу там.

| плюс | минус |
|---|---|
| один источник истины для «что считать фразой» (stt_node) | размазывает ответственность: VAD-гейт уже отрезал тишину на клиенте, но wake-чанки между фразами всё равно нужно собирать |
| можно использовать тот же сегментатор, что для ReSpeaker (`audio_node.speech_continuation`) | wake-сегменты физически не приходят в `audio_node` (он работает с `/audio/vad`, не с `/audio/quest_wake`) — пришлось бы дублировать сегментатор в `stt_node` |
| | `stt_node` уже большой (~1200 строк, по `ls -la`); добавление ещё одного буфера увеличивает сложность без явной выгоды |
| | ломает контракт ADR-RT-0071 §2.6 («`/audio/quest_wake` — VAD-сегмент»), который сейчас и так считается правильным всеми, кроме фактической реализации |
| | проблему проще починить у продьюсера, чем заставить консьюмера компенсировать |

**Вердикт.** Отклонено. ADR-RT-0071 §2.6 уже зафиксировал контракт «VAD-сегмент на стороне топика»; чинить контракт у продьюсера — это **приведение реализации в соответствие с уже принятым контрактом**, а не изменение контракта.

### 3.2 Альтернатива C: флаг `segment=true` в `AudioData` (передавать метаданные)

`AudioData.data` (Uint8Array) — без места для флагов. Расширять до `AudioData { data, segment_start_ms, segment_end_ms, has_wake_word? }` = менять IDL `.msg` + сериализацию в обе стороны.

**Вердикт.** Отклонено. Избыточно: «один сегмент = один `AudioData`» — достаточно; маркер сегмента — сам факт единственного сообщения на фразу.

### 3.3 Альтернатива D: вообще убрать wake-топик, слать весь поток в `audio_node`

Дублировать wake-поток как ещё один источник `/audio/vad_wake` для `audio_node`.

**Вердикт.** Отклонено. (а) `audio_node` рассчитан на ReSpeaker + AEC, не на шлем; (б) размытие wake-роутинга; (в) это **новая фича**, а не фикс.

## 4. Trade-off

### 4.1 Выигрыш

- Wake-слово «ТАРС» наконец-то будет слышно: STT получит фразу (≥0.5с) и сможет распознать wake + команду.
- Контракт `/audio/quest_wake` приводится в соответствие с ADR-RT-0071 §2.6 — оба конца (продьюсер и консьюмер) уже ожидают VAD-сегмент, просто реализация пока нет.
- Латентность «конец фразы → распознано» вырастет на `WAKE_SEGMENT_SILENCE_TIMEOUT_MS` (500мс по умолчанию) — приемлемо для wake-сценария, где задержка не критична (оператор ждёт 0.5с — не страшно).
- Шаблон сегментации уже есть (`publish_voice_audio` robot_voice, `quest_node.py:475-498`) — не изобретаем новый алгоритм, копируем проверенный.

### 4.2 Цена

- **+500мс латентность** на wake-фразу. Для wake — терпимо; для barge-in (TARS во время TTS) — тоже терпимо (TARS — это и так «прерывание», небольшая задержка не меняет UX).
- **Сложность стыка с hangover 200мс** на клиенте: клиент шлёт чанки ещё 200мс после последней речи (чтобы не рвать слоги внутри фразы), потом gate закрывается. Эти 200мс дойдут до `quest_node` как «тишина сразу после голоса», но при наличии реальной паузы >500мс ничего не сломается — просто первая «тихая» порция войдёт в буфер фразы. Шум не критичный: внутри фразы `_chunk_is_silent` редко true (hangover 200мс — это и есть «добавка после голоса», а 0.5с тишины после фразы пройдут через `wake_silence_ms >= 500`).
- **`WAKE_SEGMENT_MAX_DURATION_MS = 10с`** — safety: при длинной монологе (оператор не делает паузы 10+ секунд) буфер сбрасывается принудительно. ReSpeaker-фразы обычно 0.5–3с; 10с — страховка.
- **Дополнительные 30 строк в `quest_node.py`** (новый буфер + счётчик + `_flush_wake_buf`) — копия `publish_voice_audio` robot_ветки, дешёво.
- **Тесты:** нужно переписать `test_publish_quest_wake_audio_multiple_chunks_publish_individually` (сейчас фиксирует «чанки публикуются по отдельности» — это и есть баг).

### 4.3 Что НЕ делаем (anti-scope)

- Не трогаем `voice_capture.ts` (клиент продолжает шлать чанки — это его контракт).
- Не трогаем `stt_node.quest_wake_audio_callback`.
- Не добавляем wake-word recognition на клиенте (отклонено ещё в ADR-RT-0071 §1.3).
- Не расширяем `AudioData` IDL.

## 6. Definition of Done (проверяемые факты, ADR-0018)

- [ ] В `docker logs voice-assistant` для wake-источника строки «Получена фраза» имеют длительность порядка 0.5–3с (не 0.02с). Raw-лог приложен.
- [ ] Оператор в шлеме говорит «ТАРС, ты здесь» → в логах строка `✅ [wake] /avatar/stt/result` или эквивалент успешной маршрутизации. Raw-лог приложен.
- [ ] Оператор в шлеме говорит «привет» (без вейка) → в `/avatar/stt/result` НЕ публикуется; в логах — `🔇 [wake] Нет operator-вейка в ... — drop` (новое сообщение, см. §2.3). Raw-лог приложен.
- [ ] Переписанный `test_publish_quest_wake_audio_buffers_phrase_until_silence` зелёный; прежний `..._publish_individually` удалён. `pytest src/rob_box_quest` локально: PASS, raw-вывод с числом тестов приложен.
- [ ] Сообщение `❌ [wake] STT пуст на сегменте` появляется, только если сегмент ≥ 100мс (защита от регресса: если wake-буфер починен, а кто-то снова сломал и шлёт чанки — мы это увидим как «сегмент 0.02с»). Лог проверен вручную на старом и новом коде.

## 8. Хендофф (карточки)

Этот ADR — **только design**, как и ADR-RT-0071. Реализация — отдельные карточки:

1. **Реализация сегментатора** (developer): правки `quest_node.py` + `stt_node.py:692-705` (логи) + новые тесты. Карточка `t_cf3c37cc` после approve этого ADR.
2. **Update существующего теста** (developer): `test_publish_quest_wake_audio_multiple_chunks_publish_individually` → новый контракт.
3. **Проверка на роботе** (e2e — отдельный процесс): оператор в шлеме «ТАРС ты здесь» → wake работает → агент отвечает. Без этой проверки DoD-пункт «оператор в шлеме → /avatar/stt/result» не считается выполненным.

## 9. Открытые вопросы

1. **`WAKE_SEGMENT_SILENCE_TIMEOUT_MS = 500`** — стартовая точка. На устройстве не замерена. Если окажется слишком короткой (рвёт фразу «ТАРС, ты здесь» на «ТАРС» + «ты здесь») — увеличить до 800мс. Если слишком длинная (задержка ощутима) — уменьшить до 300мс. Финальное значение — в issue `#2135-comment-on-deploy`.
2. **`WAKE_SEGMENT_MAX_DURATION_MS = 10000`** — аналогично. ReSpeaker-фразы обычно <3с; 10с — safety. Можно опустить до 5с если подтвердится, что длинных монологов нет.
3. **Логирование количества склеенных чанков** — полезно для retро («сколько в среднем чанков на фразу?»). Решение: добавить в `_note_wake_audio_publish` опциональный параметр или новый метод `_note_wake_audio_segment` с `chunk_count`. **НЕ блокирует** этот ADR, можно добавить в реализации.
