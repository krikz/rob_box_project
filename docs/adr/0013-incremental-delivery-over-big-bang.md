## 1. Назначение

Зафиксировать разбор аномалии PR #876 и закрепить **процессные правила**, которые не дают большим feature-веткам блокировать pipeline. Документ отвечает на три вопроса:

1. Что произошло и почему PR #876 стал CONFLICTING на 16 дней?
2. Почему «закрыть PR и портировать инкрементально» — правильное решение, а «rebase и merge» — нет?
3. Какие правила процесса не дают этому повториться?

---

## 2. Контекст и проблема

### 2.1 Хронология

| Дата | Событие |
|------|---------|
| 2026-06-13 | Создан PR #876 `feature/phase-3.2-music-testing` → `develop`. 100 коммитов, +7156/−1081 строк |
| 2026-06-13 … 2026-06-14 | Активная разработка: ~90 коммитов за 2 дня (search_artist_style, TrackLibrary, anti-click фиксы, DJ-промпты) |
| 2026-06-14 … 2026-07-26 | Единичные CI-коммиты (`ci: main SHA tags`), содержательной разработки нет |
| 2026-07-26 | Последний коммит ветки (`f7d51c35`, 12:32Z) |
| 2026-08-05 | Создана issue [#1000](https://github.com/krikz/rob_box_project/issues/1000) — портировать music-tooling инкрементально (research gate / track library / anti-click) |
| 2026-08-11 | PR #876: `mergeable=CONFLICTING`, `mergeStateStatus=DIRTY`, ~16 дней без содержательных коммитов. Товарищ Шифу закрыл PR без merge |

### 2.2 Факты на момент ретро (собрано 11.08 16:55, подтверждено повторно)

```
gh pr view 876 --json mergeable,mergeStateStatus,commits,additions
→ mergeable=CONFLICTING, mergeStateStatus=DIRTY, commits=100, additions=7156

git log origin/feature/phase-3.2-music-testing -1 --format='%ad'
→ 2026-07-26 (последний коммит; проверено через GitHub API: 2026-07-26T12:32:28Z)

gh issue list --label music --state open
→ #1000 (port music-tooling), #986, #942, #937, #935
```

Признаки аномалии:
- **Ветка росла вне develop 43 дня** (13.06 → 26.07), при этом активная разработка шла только 2 дня.
- **PR пытался затащить всю фазу одним куском**: 100 коммитов, 7156 строк — нереально ревьюить и невозможно проверить e2e в пределах одного прогона.
- **Конфликт с develop** (DIRTY) — неизбежен после 16 дней дрейфа; каждый merge в develop увеличивает дистанцию и цену rebase.
- **Правильный путь уже существовал**: issue #1000 (05.08) явно декомпозировала перенос на компоненты (research gate → track library → anti-click синт-фиксы → DJ-промпты).

### 2.3 Root cause

1. **Нет правила размера PR** — ничто не остановило «big-bang» из 100 коммитов.
2. **Нет правила возраста feature-ветки** — ветка жила 43 дня, из них 16 — в состоянии «мёртвого груза» без содержательных коммитов.
3. **Конфликт не эскалировался автоматически** — PR висел DIRTY, никто системно не реагировал.

## 3. Рассмотренные варианты

### Вариант A: Закрыть PR #876, портировать инкрементально через #1000 ✅ выбран

- Разблокирует реестр PR немедленно, без rebase-работы.
- Перенос идёт компонентами, каждый проходит e2e в пределах 1 PR.
- Работа ветки не теряется: issue #1000 содержит полный аудит (18 пунктов) и ссылки на конкретные коммиты ветки (`508cc53f`, `a64c678e`, `9554ed75`, `d922ee83`, …).

### Вариант B: Оставить PR, сделать rebase на develop

- Требует разбора конфликтов ~100 коммитов против 16 дней дрейфа — часы ручной работы.
- Не решает проблему инкрементальности: после merge всё равно останется монолит, который невозможно e2e-проверить отдельными компонентами.
- Оставляет большой «мёртвый» PR в реестре до момента разбора.

### Вариант C: Merge как есть (force)

- Нарушает e2e-контракт: 7156 строк без проверки одним куском.
- Риск регрессий в голосовом стеке (DJ/музыка) без возможности изолировать виновника.

---

## 4. Решение

1. **PR #876 закрыт без merge** с формулировкой «superseded by #1000 incremental porting, please re-submit per-component» (исполнено товарищем Шифу 11.08 15:01Z).
2. **Перенос наработок ветки — инкрементально через issue #1000**, компонентами, с e2e-проверкой каждого PR.
3. **Процессные правила** (закреплены в `CONTRIBUTING.md`):
   - **PR > 50 коммитов ИЛИ > 3000 строк** запрещён без явной метки `big-bang-override` (метку ставит товарищ Шифу).
   - **Feature-ветка старше 7 дней** должна быть разбита на части (или синхронизирована rebase'ем на develop); «мёртвые» ветки без коммитов >7 дней — кандидаты на закрытие.

### 4.1 Почему это правильно (trade-off)

| Критерий | Big-bang merge (вариант B/C) | Инкрементальный порт (вариант A) |
|----------|------------------------------|-----------------------------------|
| Скорость до первого merge | Быстро, но с риском | Медленнее (несколько PR), но предсказуемо |
| Возможность e2e-проверки | Один прогон на всё — слепой | Каждый компонент отдельно |
| Стоимость конфликтов | Растёт с каждым днём дрейфа | Ограничена размером компонента |
| Откат при регрессии | Почти невозможно (100 коммитов) | Тривиален (1 компонент) |
| Нагрузка на ревьюера | 7156 строк за раз | Порции по 200-800 строк |

Сложность/выгода: правило размера PR — это 2 строки в CONTRIBUTING.md, выгода — защита от повторения 16-дневного DIRTY-блокера. Правило возраста ветки — 1 строка, выгода — ветки не живут дольше недели вне develop.

## 5. Что НЕ делаем

- ❌ Не ребейзим `feature/phase-3.2-music-testing` в worktree архитектора (это работа владельца/Шифу, не воркера).
- ❌ Не создаём follow-up PR поверх #876 — перенос идёт через #1000.
- ❌ Не мержим #876 (закрыт).

---

## 6. Дальнейшие шаги

1. **Владелец #1000** (`port music-tooling`): последовательно портировать компоненты (research gate → track library → anti-click → DJ-промпты), каждый отдельным PR с e2e.
2. **Merge-gate/e2e-process**: учесть правило размера PR при проверке (метка `big-bang-override` как исключение).
3. **CI/CD**: при желании добавить автоматическую проверку размера PR (commits > 50 или additions > 3000 → comment/check-fail без метки).

---

## 7. Вывод

PR #876 — учебный пример «Big Bang vs инкрементальность»: 43 дня жизни ветки, 16 дней DIRTY, 100 коммитов, 7156 строк — и ноль e2e-проверок за всё время. Правильное решение — закрыть и портировать компонентами (уже исполнено). Процессные правила из §4 закрывают системную дыру, которая позволила этому случиться.
