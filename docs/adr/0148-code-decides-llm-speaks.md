## 2. Решение

### 2.1 Принцип: код решает, LLM говорит

- **Детерминированное — коду.** Если параметр, порядок действий или момент события вычисляет код, LLM его не пересказывает и не переписывает. Код исполняет сам.
- **LLM отвечает за смысл и речь**: понять просьбу человека, выбрать намерение из небольшого набора, сказать реплику, придумать «вкус» (тему, персону, план) — в структурном виде, который проверяет валидатор.
- **Фразу об успехе действия строит код из результата исполнения.** LLM не утверждает, что действие произошло.
- **Состоянием владеет один модуль** и публикует события. Остальные читают снимок или подписываются на событие; копий с собственной логикой нет (ADR-0141).

### 2.2 Мораторий

С принятия этого ADR и до исполнения §2.3 баг, где LLM ошиблась на пути решения, чинится одним из двух способов:

1. **Вынести решение из LLM в код** (детерминированная функция, событие владельца состояния, структурный вызов вместо текста).
2. **Сузить выбор LLM структурой**: узкая схема тула, перечисление, валидатор входа с понятной ошибкой.

Новые регексы по тексту ответа, новые синтетические ретраи, новые пары «правило в промпте + гард в коде» и новые списки-копии (тулов, ладов, синтов) в этот период не добавляются. Если без такой заплатки робот опасен или молчит на сцене — заплатка допустима как временная, с пометкой `TEMP(ADR-0148)` и ссылкой на карточку, которая её удаляет.

### 2.3 Новый аранжировщик и DJ-движок — с чистого листа, рядом со старым

Строится новый пакет; старый путь остаётся рабочим до переключения и удаляется целиком после приёмки (strangler), а не правится по кусочку. Обязательные свойства:

- **Музыка — модель данных** (паттерны, партии, секции, энергия), одна чистая функция рендера в код движка; знание о треке берётся из модели, не разбором строки.
- **DJ-движок детерминированный** (ADR-0142 без ризонера на первом шаге): очередь треков, предгенерация следующего, переход по событию плеера «трек почти доиграл». LLM участвует асинхронно: план сета один раз в структурном виде и реплики.
- **Одна таблица знания** (лады, тоники, синты, потолки громкости, «музыкальные тулы») — один модуль, остальные импортируют.
- **Приёмка — замером**, не тестом на строку: живой прогон серии сетов, сравнение с эталоном (стерео, размах громкости, темп, тишина), прослушивание товарищем Шифу. Метрики «захват сетки 16-х» и «доля энергии вне лада» качество не меряют (у живого диджея они хуже, чем у робота) — критерием не являются.
- **Уроки** из всей истории music/DJ-issue (каталог отказов, инварианты, что сохранить) — входной документ дизайна.

Дизайн нового пакета — отдельный ADR после каталога уроков.

### 2.4 Немедленные шаги, совместимые с принципом

- Включить `skill_tool_narrowing`; дать club узкую схему вместо общей на 44 параметра.
- Выключенный слой гардов (`TurnGuards`) — либо включить вместо параллельного, либо удалить; мёртвые легаси-функции удалить.
- Разобрать реестр ADR: Proposed старше двух недель — принять, отклонить или пометить Superseded; коллизии номеров развести.

## 3. Последствия

- Временные страховки на старой схеме (например #3136 «трек зациклен в DJ-режиме») доводятся, но новых слоёв на неё не кладётся.
- Часть существующих гардов становится мёртвой по мере переноса решений в код — их удаление входит в те же PR, а не откладывается.
- Тесты пишутся на поведение модуля (вход → решение/событие), а не на текст промпта и не на номер issue.
- Скорость «закрыть баг за час» падает; число повторных багов того же класса должно падать сильнее.

## 4. Альтернативы

- **Продолжать латать по месту.** Отклонено: сентябрь показал 3:1 fix к feat и рост гард-слоёв быстрее функциональности.
- **Переписать весь голосовой стек сразу.** Отклонено на этом шаге: начинаем с аранжировщика и DJ-движка, где симптомы самые слышимые; `DialogueNode` — следующая волна по ADR-0021 на тех же принципах.
