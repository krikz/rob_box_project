# ADR-0072: Captain Bridge — центр сферы драга = позиция камеры, radiusOf = честное 3D

| Поле | Значение |
|---|---|
| Статус | **Accepted** |
| Дата | 2026-09-08 |
| Автор | architect (Hermes Agent), kanban t_7bb91130, issue #2143 |
| Контекст | PointerSystem в Captain Bridge сцене Quest UI: голосовая панель (Voice Pipeline Panel) при захвате притягивается к оператору. Чем дальше оператор уходит от стартовой точки (0, 1.6, 0) и чем больше раз повторно хватает панель — тем ближе она «прилипает». |
| Затрагивает | `src/rob_box_quest/webxr_client/src/interaction/pointer.ts`, `src/rob_box_quest/webxr_client/src/scene/captain_bridge.ts`, тесты `tests/pointer.test.ts` |
| Родители | ADR-0032 (WebXR stack & assets), ADR-0018 (honesty) |
| Связанные | issue #2143 (владелец: Шифу, скриншот капитанского мостика 2026-09-08) |
| Заменяет | Неявное допущение «центр = (0, 1.6, 0) навсегда» в `PointerSystem` |

> **TL;DR.** В `PointerSystem` две связанные ошибки:
> 1. **`PointerSystem.setCenter()` объявлен, но никогда не вызывается** — центр сферы драга зашит на (0, 1.6, 0). В VR `local-floor` оператор может уйти от старта на 1–2 м, и панели продолжают кататься вокруг точки спавна, а не вокруг него.
> 2. **`radiusOf()` возвращает `horizontalRadius`** (только `x, z`) и этот скаляр передаётся в `dragTargetPosition()` как радиус 3D-сферы (`intersectRaySphere`). Для панелей на `y≠center.y` (а голосовая панель стоит на `VOICE_PIPELINE_Y_M=1.4`, центр `y=1.6`) 3D-радиус меньше истинного 3D-расстояния, и каждый последующий захват «укорачивает» панель.
>
> Фикс: (a) в `updatePointer()` мостика каждый кадр вызываем `pointer.setCenter(camera.position)` перед `pointer.update(ray)`; (b) в `radiusOf()` возвращаем честное 3D-расстояние. Тесты: добавлены два регрессионных теста, описывающих инвариант «расстояние до оператора не накапливается при повторных update с тем же лучом» и «после `setCenter` drag держит панель относительно НОВОГО центра».

---

## 1. Контекст и проблема

### 1.1. Что наблюдал владелец (Шифу)

Скриншот капитанского мостика Quest 2, 2026-09-08: «окно голосового пайплайна когда я его захватываю, оно притягивается ко мне очень близко, и это неудобно». Эффект накопительный: первый захват — терпимо, после 3–4 захватов подряд панель оказывается в 0.3 м от лица.

### 1.2. Где это в коде

`PointerSystem` (`src/.../interaction/pointer.ts`):

```ts
const DEFAULT_CENTER: Vec3 = { x: 0, y: 1.6, z: 0 };
// ...
constructor(opts: PointerSystemOptions = {}) {
  this.center = opts.center ?? DEFAULT_CENTER;
  // ...
}
setCenter(center: Vec3): void { this.center = center; } // ← объявлен, но НЕ вызван
```

`grep -rn "setCenter" src/` находит **только** само объявление в `pointer.ts` и одноимённый метод у `LidarOverlay` (несвязанный). В `captain_bridge.ts` `new PointerSystem({ center: { x: 0, y: 1.6, z: 0 }, ... })` — статика на всю сессию.

`radiusOf()` (`pointer.ts:250`):

```ts
private radiusOf(id: string): number {
  // ...
  return horizontalRadius({ x: p.x, y: p.y, z: p.z }, this.center);
}
```

`horizontalRadius()` (`pointer_math.ts:103`) — это **только `dx, dz`**:

```ts
export function horizontalRadius(position: Vec3, center: Vec3): number {
  const dx = position.x - center.x;
  const dz = position.z - center.z;
  return Math.hypot(dx, dz);
}
```

Используется скаляр в `dragTargetPosition()` (`pointer.ts:203` → `pointer_math.ts:75`) как радиус 3D-сферы в `intersectRaySphere()` (`pointer_math.ts:45`). То есть **горизонтальное расстояние мимикрирует под 3D-радиус**.

### 1.3. Геометрия накопительного эффекта

Голосовая панель создаётся с константами:

```ts
// voice_pipeline_panel.ts
export const VOICE_PIPELINE_ANGLE_DEG = 60;
export const VOICE_PIPELINE_RADIUS_M = 2.4;  // ← horizontal, по раскладке
export const VOICE_PIPELINE_Y_M = 1.4;
```

В момент захвата `radiusOf()` возвращает `horizontalRadius(panel, center)` = 2.4 (если оператор на (0, 1.6, 0); если ушёл — будет другое значение, но всё ещё горизонтальное).

Истинное 3D-расстояние панели от центра: `√(2.4² + (1.4−1.6)²) = √(5.76+0.04) = √5.8 ≈ 2.408`.

`dragTargetPosition()` режет луч по 3D-сфере радиуса 2.4 (а не 2.408). При наклоне луча вниз горизонтальная проекция целевой точки становится **меньше** истинного горизонтального расстояния панели. После `panel.setPosition(...)` mesh.position реально подтягивается ближе к оператору.

На следующем захвате `radiusOf()` уже возвращает меньшее число (новое горизонтальное расстояние), и цикл повторяется. Эффект накапливается.

### 1.4. Что должно быть (DoD из issue)

1. **`radiusOf → dragTargetPosition`:** расстояние до центра совпадает с исходным (текущий код проваливается).
2. **Оператор смещён от начала координат:** панель при перетаскивании остаётся на своём расстоянии **от оператора** (текущий код катит вокруг (0, 1.6, 0)).
3. **Грубая проверка:** захват и отпускание без движения луча не уменьшает расстояние (текущий код — уменьшает).

## 2. Рассмотренные альтернативы

### 2.1. Вариант фикса A (выбран): согласовать метрику в `radiusOf`

Меняем только `radiusOf()` — возвращаем честное 3D-расстояние. `intersectRaySphere` уже работает с 3D-сферой, и его семантика «расстояние от центра по прямой» теперь согласована с «расстоянием, на котором панель стоит».

| Pros | Cons |
|---|---|
| Минимальный дифф (1 функция, ~10 строк) | Меняет инвариант: раньше панели стояли на «полусфере» радиуса `horizontal`, теперь — на полной сфере. Для видео-панелей на `y=1.6` это совпадает. Для vpl на `y=1.4` — разница в 0.2 м, но и в старом коде реальная 3D-геометрия была в районе 2.4, а не 2.0. |
| Не трогает API потребителей (PanelManager.move, voicePipeline.setPosition) | |
| Совместимо со всеми существующими тестами (mesh на `y=CENTER.y`) | |

### 2.2. Вариант B: оставить `horizontalRadius`, но проецировать результат `dragTargetPosition` на горизонтальный цилиндр

| Pros | Cons |
|---|---|
| Семантика «панели на полкруге радиуса 2 м» остаётся буквальной | Меняет геометрию `dragTargetPosition` → больше кода, больше шанс сломать смежные потребители (`panel_layout_store`, `panelManager.move`, видео-панели на `y≠1.6`). |
| | Не решает проблему «оператор ушёл от старта» — это отдельная ось. |
| | Прячется баг под новой моделью: пользователь видит панель на `y=1.4`, а считается проекция с `y=1.6`. |

**Решение: вариант A.** Минимальный, явный, не прячет семантику. Вариант B оставляем как запасной путь, если в будущем понадобится «панели на полукруге» для специализированных раскладок.

### 2.3. Где вызывать `setCenter`

| Точка вызова | Pros | Cons |
|---|---|---|
| В `captain_bridge.ts → updatePointer()` (выбран) | Камера уже в closure; один раз на кадр, перед `pointer.update(ray)`; покрывает desktop и VR пути; поведение прозрачно | Дубликат строки в одном файле |
| В `main.ts` рядом с `bridge.updatePointer(...)` | Меньше связности мостика | Нужен импорт `camera` или API `bridge.getCamera()`; новый публичный метод в `CaptainBridgeHandle` |
| Внутри `PointerSystem.update(ray, center?)` | Самодостаточный класс | Лишний параметр в hot-path; вынуждает всех потребителей (`desktop_pointer`, `xr_pointer`) что-то передавать |
| По событию `renderer.xr.session.start` | Меньше вызовов | Не учитывает наклон / сдвиг в local-floor между кадрами |

**Решение: в `updatePointer()` мостика.** Простое, явное, и место рядом с тем, где центр физически используется.

## 3. Решение (детально)

### 3.1. `pointer.ts`

```ts
// было:
private radiusOf(id: string): number {
  // ...
  return horizontalRadius({ x: p.x, y: p.y, z: p.z }, this.center);
}

// стало:
private radiusOf(id: string): number {
  const target = this.targets.find((t) => t.id === id);
  if (!target) return 2;
  const p = target.object.position;
  return length({
    x: p.x - this.center.x,
    y: p.y - this.center.y,
    z: p.z - this.center.z
  });
}
```

Импорт `length` из `pointer_math.ts` (уже экспортируется). Импорт `horizontalRadius` убран из `pointer.ts` — функция остаётся публичной и используется в тестах напрямую (импорт из `pointer_math`).

### 3.2. `captain_bridge.ts`

```ts
function updatePointer(ray: PointerRay | null): void {
  pointer.setCenter({
    x: camera.position.x,
    y: camera.position.y,
    z: camera.position.z
  });
  pointer.update(ray);
  pointerBeam.update(ray, pointer.getHit());
}
```

`pointer.setCenter` вызывается **до** `pointer.update(ray)`. Это важно: `radiusOf()` вызывается в момент `justPressed` (внутри `update(ray)`), и если бы `setCenter` шёл после — `dragRadius` всё равно посчитался бы от старого центра для первого захвата.

`new PointerSystem({ center: { x: 0, y: 1.6, z: 0 }, ... })` оставляем как есть — это **fallback для unit-тестов** и для краткого окна до первого `updatePointer` (там камера ещё ровно в (0, 1.6, 0)).

### 3.3. Тесты (`tests/pointer.test.ts`)

Добавлены два теста:

1. **`does not creep inward across repeated updates with the same ray (#2143)`** — сценарий из issue: панель на `y=1.4`, луч зафиксирован после старта drag → несколько `update()` → 3D-расстояние до центра не должно уменьшаться. До фикса: уменьшалось бы на каждом кадре.

2. **`drags around the operator's actual position, not the spawn origin (#2143)`** — после `setCenter({x:1, y:1.6, z:0})` `update()` с лучом из новой точки → drag должен удерживать панель на 3D-расстоянии от НОВОГО центра, а не от (0, 1.6, 0).

Существующий тест **`keeps the dragged panel at its original radius`** сохранён без изменений: mesh в нём стоит на `y=CENTER.y`, поэтому `horizontalRadius` и 3D-расстояние дают одно число (2.0) — тест зелёный в обеих версиях.

### 3.4. Out of scope (явно)

- **Раскладка панелей по умолчанию и `panel_layout_store`** — не при чём. Голосовая панель создаётся с `VOICE_PIPELINE_ANGLE_DEG=60`, `VOICE_PIPELINE_RADIUS_M=2.4`, `VOICE_PIPELINE_Y_M=1.4`. Эти константы остаются.
- **Жест захвата** (CLICK_SLOP_M, выбор trigger vs grip) — не трогаем.
- **`panel_layout_store`** — не правим: текущая запись перетаскивания (`onDrag` → `panelMgr.move(...)`) уже передаёт координаты в мировом пространстве, никаких изменений не требуется.

## 4. Trade-offs (явные)

### 4.1. Что мы теряем

- **«Горизонтальный полуслой»** — формально панели теперь стоят на полной 3D-сфере, а не на полкруге. Для текущих раскладок (все панели в `y∈[1.4, 1.6]`) разница ≤ 0.2 м, и владелец её уже видит как «очень близко» — то есть фактическое поведение становится лучше, не хуже. Если когда-нибудь появится раскладка с панелями на `y=0.5` (пол) и `y=2.5` (потолок), им придётся жить на сфере — что геометрически правильно.

### 4.2. Что мы НЕ делаем (и почему)

- **Не вызываем `setCenter` из `renderer.xr.session.start`** — `local-floor` reference space может обновлять позицию камеры каждый кадр (особенно после `XRFrame` с новой позой head). Один раз на старте сессии недостаточно.
- **Не передаём `center` в API `PointerSystem.update(ray, center)`** — лишний параметр в hot-path и нулевая выгода: `setCenter` уже дешёвый (одна запись в поле).
- **Не вводим `dragRadiusMode` флаг** — единственный осмысленный режим сейчас — 3D. Горизонтальный/вертикальный/цилиндрический — это будущие фичи, и под каждый заведём ADR, если они понадобятся.
- **Не правим `panel_layout_store`** — текущий формат хранения панелей по мировым координатам остаётся.

## 8. Honest gaps (что мы НЕ знаем)

- **Реальное устройство:** этот фикс проверен unit-тестами. Живая проверка на Quest 2 — отдельный этап после merge. Если в шлеме эффект останется (например, из-за другого reference space или XR-специфики `local-floor`), нужен второй раунд с логами `docker logs` от Vision Pi.
- **Видео-панели на `y≠1.6`:** текущий код создаёт их с `y=CENTER.y` (`panelManager` раскладка). Если в будущем `panel_layout_store` начнёт сохранять `y` отличный от 1.6, изменение `radiusOf` отразится на них — но в правильную сторону (3D-сфера вместо полукруга).
- **`panels` (видео-панели), которые наследуют старый layout:** старые сохранённые позиции в `localStorage` могут оказаться на `y≠1.6` — это не баг (мы теперь корректно работаем с 3D), но если кто-то заметит «раньше панель стояла ровно на 2 м, теперь на 2.4 м», это объяснение.
