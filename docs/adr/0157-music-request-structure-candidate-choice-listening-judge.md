## 1. Проблема

Две независимые линии дали один вывод: **решения, которые влияют на то, что робот сыграет и как это прозвучит, принимаются там, где их нельзя проверить** — свободным выбором LLM на хвосте грамматики и «первым подходящим» в коде без памяти и без перебора, а оценка качества держится на слухе товарища Шифу и на судье, которому нельзя верить без проверки.

### 1.2 Почему — по коду (воркер, `develop @ 32ddc94b7`)

1. **Сущностей «произведение», «композитор», «инструмент» на входе нет.** Весь запрос — строка `text`/`theme`; тема = реплика минус стоп-слова (`engine/theme_grounding.heard_theme`, `theme_grounding.py:42`, #3493). У тулов `dj_set` (`_tool_catalog_data.py:146–211`) и `request_music` (`:1678–1721`) нет поля инструмента; слов «балалайка/тромбон/ксилофон» в `src/` нет вообще (единственное — основа `балалайк` в строке темы `slavic`, `knowledge.py:192`). Неизвестное слово ломает поиск названия: `search.find` (`search.py:212–224`) → `ignored` непуст → `named_play.melody_hit` промах (`named_play.py:117–119`) → **реплика уходит LLM**.
2. **Сет vs пьеса** решает грамматика по слову «сет/диджей» (`media_command_grammar.py:741,768`), а хвост — свободный выбор LLM по тексту скиллов `dj.txt`/`composer.txt`. Именно на хвосте LLM трижды вызвала `dj_set` на «сыграй … на <инструменте>» (у неё в контексте 10 подряд «включи … сет», §1.1 #1) и трижды пообещала без тула. Гард `honest_launch_reply` — `TEMP(ADR-0148)`, #3461.
3. **Выбор пьесы по композитору — «первый по рангу, который сложился», без памяти.** `ScoreLibrary.search` ранжирует по рейтингу PDMX (`score_library.py:70–72`); `pick_score` перебирает материалы по порядку и берёт **первый сложившийся** (`classic.py:84–98`, `HookError` копится в `reasons`); если не сложился ни один — `pick_classic` → `search.find(**сырой текст запроса**)` (`classic.py:73–81`, `search.py:212–222`): слова «на ксилофоне»/«Баха» не из архива → промах → `not_found` (`tools_v2.py:568–569`). Хуки, которые `theme_links` уже подтвердил по каталогу (`toccata`, `fugueind`), в этот путь не передаются. Истории сыгранного одиночный заказ не читает: `HistoryKey("classic_v2")` только пишется (`song.py:142,308`); `seed` влияет на аранжировку, не на выбор записи; `music_history`/`recent_hooks`/`weighted_pick` (ADR-0146, `diversity.py:162,303`) работают только для сетов.
4. **Совпадение по подстроке и целому слову без поля «композитор».** `search._in` (`search.py:179–183`): слово > 4 букв — подстрока в name/title/artist (`_IDENTITY`), ≤ 4 — целое слово. «Bach» — целое слово в «Mundian To **Bach** Ke» (это не Бах), «минор» → транслит «minor» → подстрока/префикс в «**Minor**ity» (`_PREFIX_SLACK = 4`, `search.py:46,141–151`). `ScoreIndex._keys` индексирует слова композитора наравне с названием (`score_library.py:80`). Реестр `works.py` (ADR-0155) есть, но поле `composer` никто не читает (`works.py:50–53` `FIELD_CONSUMERS` пусты), читаются только алиасы из `theme_link_seeds.json`.
5. **Фраза об успехе строится LLM.** «Просто играю Баха на трамбоне, сет идёт» и список «произведений Баха» — текст модели, а не результат исполнения (нарушение ADR-0148 §2).
6. **Порог годности материала 0.8** (`knowledge.py:1316 THEME_REF_MATCH_MIN`) сверяет партитуру с RTTTL-эталоном **другой** пьесы того же композитора → 8/8 отбраковок на «Токкате» и на «Моцарте» (#3546, #3526).

| **`lpf=0` «фильтр закрыт 240 долей»**, **`tempo=137` у амен-лупа «рассинхрон»**, **`pshift` «расстроенность»**, **`delay=0.1` «100 мс не в темпе»** | — | `LPF_OPEN = 0.0` «фильтр снят» (`knowledge.py:877–882`, `renardo.py:127–128`; семантика внутри Renardo в репо не подтверждена); `tempo=` — родной темп сэмпла для стретча, вычислен из длины файла (`renardo.py:313–316,326`, `knowledge.py:623–636`); `pshift=0.125` — `PAD_DETUNE` намеренно, у 6 стилей (`knowledge.py:1217,1225…`); `delay` — в **долях** (свинг/Хаас, `renardo.py:156–164`) | **ложные чтения** API рендера |

### 1.4 Надёжность судьи: что он подтвердил, что выдумал

Это главный методический результат эксперимента с критиком.

| Тип утверждения | Пример | Проверка | Вердикт |
|---|---|---|---|
| Структурные (окна ролей, старт B, длины) | rock: «15 с без мелодии 133.9–148.8», «B стартует за 32 доли» | арифметика по `amp=var`/BPM и таблицы форм сходятся | **верно**, воспроизводимо кодом |
| Арифметика по спискам нот | «64 `None` у баса = 16 тактов» | `dur=1/4` → 4 такта | **ошибка** в 4 раза |
| Единицы параметров | «хэты 0.85 громче брейка 0.119», «`delay=0.1` с», «`sus=28` → 7 тактов висит» | `amp` нормирован по `LAYER_MEASURED_DB`; `delay` и `sus` — доли | **ложно**: судья читает числа как «сырые» |
| Чтение API рендера | «`lpf=0` закрыт», «`tempo=137` при 170 BPM — рассинхрон» | §1.3, последняя строка | **ложно** |
| Гармония по нотам против заявленной тональности | rock: «G♮ в C# minor — мимо»; breaks: «C major в G# major — расхождение центра» | в теме Грига (B minor) F♮ — авторская хроматика, +2 → G♮ — **правильно**; совет «фильтровать по `Scale.minor`» уничтожил бы тему; C-E-G — авторский V/vi | **ложно** в выводе, хотя факт (нота/аккорд вне диатоники) верен |
| Слух без кода | chiptune без кода: «полный хаос, случайные байты»; с кодом: «предыдущий разбор был ошибочным, система детерминирована, ноты верные» | сам критик отозвал | **ненадёжно**: без кода судья выдумывает ноты и «сбои» |
| Таймкоды «фальшивой ноты» без кода | rave «02:21 нота выбивается из сетки и лада» | нечем проверить; по бенчмаркам 2026 лучшие audio-LLM слышат высоту на 14–48 %, полифонию — 0 % | **не проверено**, доверять нельзя |
| Пробелы дизайна | «нет кроссфейда/EQ на стыке», «нет сайдчейна у lofi/rock/jazz», «8 тактов без темы» | код: `filter_in` не читается, `duck_roles` пусты у трёх стилей, формы без лида на стыке | **верно** — и это самое ценное, что дал судья |

Вывод: судья полезен как **генератор гипотез с таймкодами и классами**, когда ему дают код/модель трека и когда каждое утверждение сводится к проверке; как арбитр нот, лада, размера и единиц параметров — нет. Из ≈ 40 конкретных «ошибок кода», названных критиком по 10 стилям, кодом подтверждены 4 класса (стык без EQ/дакинга, нет сайдчейна у трёх стилей, нет HPF по ролям, нет гарда ролей в дропе), 3 — «по дизайну, вопрос вкуса», остальное — ложные чтения или непроверяемо.

## 2. Решение

Пять принципов, все — продолжение ADR-0148 «код решает, LLM говорит».

### 2.1 Запрос — структура, а не строка (`MusicRequest`)

Любая музыкальная реплика превращается кодом в одну структуру до любого решения:

```python
@dataclass(frozen=True)
class MusicRequest:
    mode: Literal["set", "piece", "song", "stop", "volume", "now_playing", "theme_switch"]
    work: WorkRef | None          # composer, title, aliases, candidates (из реестра ADR-0155)
    instrument: str | None        # ключ таблицы INSTRUMENTS (§3.4), None = не просили
    style: str | None             # ключ STYLES (ADR-0153) или None
    theme: str | None             # «на тему X» — только то, что осталось после выделения слотов
    mood: str | None
    tracks: int | None
    heard_text: str               # дословно
    slots_source: dict[str, Literal["grammar", "registry", "llm"]]  # кто заполнил слот
```

Заполняют по очереди: **грамматика** (положительное выделение слотов — «сыграй/поставь/включи [произведение] [композитора] [на инструменте] [в стиле] [сет] [на тему]», #3493), **реестр** (алиасы/композиторы → `WorkRef` с кандидатами), и только пустые слоты — **LLM из перечня** (enum, не строка). Правило режима — детерминированное: **без слова «сет/диджей/вечеринк» и без явного стиля `mode="piece"`**; `dj_set(start)` с `heard_text` без этих слов отвергается кодом (`not_a_set_request`) — LLM не может «уйти в сет» по инерции контекста (§1.1 #1, #8). Это закрывает `TEMP(ADR-0148)` #3461: регекс по ответу LLM больше не нужен, потому что ответ строит код.

### 2.2 Выбор — ранжирование кандидатов кодом, модель — только среди них

Везде, где сегодня «первый по рангу» или свободный выбор LLM, появляется один интерфейс:

```python
class Chooser(Protocol):
    def choose(self, q: ChoiceQuestion, *, deadline_ms: int) -> Choice  # Choice(id, confidence, provider)
```

`ChoiceQuestion` = контекст (слоты запроса, что играли недавно из `music_history`, стиль, время суток не нужно) + **кандидаты, построенные кодом** с признаками (совпадение названия/композитора по алиасам, давность последнего исполнения, годность материала, рейтинг, длина). Контракт вопросов — тот же, что у System One (`ChoiceQuestion`/`ScoreQuestion`: state + вопросы с перечнем вариантов → `choice`, `confidence`), чтобы провайдер менялся без правки вызывающего кода. Провайдеры: `deterministic` (взвешенная сумма признаков — **по умолчанию и всегда fallback**), `llm_harness` (обычная чат-LLM под специальным харнессом: тот же контракт state/questions, строгая JSON-схема с enum из id кандидатов, без свободного текста, температура 0 — **решение Шифу 09.10: «можно Jev, можно обычную LLM со специфическим харнессом», ключ даст позже**), `jev` (TypeSafe Choice), `laya` (self-hosted). Оркестратор, дедлайн, circuit breaker, метрики и shadow-режим уже написаны в спайке #3084 (`rob_box_harness/decision/`) — переиспользуются, а не пишутся заново (ADR «не держать две реализации»). Модель **не может расширить список кандидатов** и не видит ничего, кроме контекста (защита от «Мессии си минор»).

Точки выбора и кто решает после ADR:

| Точка | Сегодня | После ADR | Нужна ли модель |
|---|---|---|---|
| сет / пьеса | грамматика + хвост LLM | грамматика; хвост LLM ограничен гардом `not_a_set_request` | нет |
| какое произведение (композитор назван) | первый по рейтингу PDMX, без памяти | кандидаты из реестра по **алиасам и полю `composer`** (не подстрока), штраф за недавнее (`music_history`), годность материала → `Chooser` | **да, здесь** (shadow-эксперимент §4) |
| хуки темы сета | код + LLM из перечня (ADR-0152) | без изменений; штраф «паразитов» подстроки (`minority`) через совпадение по словам/алиасам | нет |
| материал партитуры | первый подходящий, иначе `not_found` | перебор всех кандидатов по рангу годности, затем RTTTL, затем честный отказ (§2.3) | нет |
| стиль по умолчанию для темы | таблица/`club` (ждёт Шифу, ADR-0153 В4) | таблица Шифу; для темы вне таблицы — `Chooser` среди `STYLES` | да, вкусовой выбор (shadow) |
| лад (theme_mode keep/minor) | seeded + LLM-уточнение | данные: тональность из партитуры/RTTTL; правило Шифу (§8 В3) — **без классификатора** | нет |
| тембр лида | семья по строке темы/сид | инструмент → семья/синт по таблице (§2.4); без инструмента — как сегодня | нет |

### 2.3 Одна цепочка для пьесы, fail-open

`request_music(mode=piece)`: кандидаты произведения → для каждого по рангу: партитуры (перебор всех уже есть, `classic.py:84–98`) → **RTTTL-хуки этого произведения** (те, что `theme_links` уже подтвердил по каталогу — сегодня запасной путь ищет по сырой фразе и промахивается на любом лишнем слове) → следующий кандидат → если пусто: **играть ближайшее по композитору и сказать это** («Токкаты в нотах нет, играю Фугу ре минор»). `not_found` разрешён только когда нет ни одного кандидата по композитору/названию. Порог годности материала `THEME_REF_MATCH_MIN = 0.8` при лучшем 0.73 на «Токкате» — вопрос §8 В1. История исполнения пишется и **читается** в этом пути (ADR-0146 для одиночных пьес): штраф за последние `HOOK_FRESH_SETS` исполнений того же произведения — «почему всегда одно и то же» исчезает по построению.

### 2.4 Инструмент — сущность с честной деградацией

Таблица `INSTRUMENTS` в `knowledge.py` (одна таблица знания): основа слова (все падежи, типичные ошибки STT: «трамбон», «кселофон») → `{family, synth | None, octave_shift, articulation}`. Если синта нет — ближайшая семья и **фраза от кода**: «балалайки у меня нет, сыграю щипковым». Инструмент влияет на лид, не на стиль и не на темп (ADR-0152: тема фиксирует характер, трек — материал).

### 2.5 Судья предлагает, код проверяет

Слушающий критик встраивается как инструмент dev-цикла и воркеров, а не как метрика приёмки:

```
запись (jack_rec) + Track-модель  ──► бандл (уже есть: _method/build_critic_bundle.py)
        ──► судья (audio-LLM, JSON-схема: [{t0,t1,kind∈ENUM,claim,confidence}])
        ──► верификатор (код): каждое утверждение сводится к проверке по модели трека
              kind=hole/overlap/level/sustain/phrasing → арифметика по Track (детерминированно)
              kind=out_of_key/chord_clash → теоретический аудит Ф1–Ф3 по нотам
              kind=mix/masking → A9/A10/LR/band-замеры записи
        ──► отчёт: подтверждено / опровергнуто / не проверяемо (→ слух Шифу с таймкодом)
```

Правила: судья **всегда** получает модель трека (без кода он выдумывает, §1.4); вопросы — узкие, с перечнем классов (MCQ-формат даёт +24–39 п.п. по бенчмаркам); таймкоды — ±5 с; ни одно утверждение судьи не становится карточкой или числом приёмки, пока верификатор не подтвердил. Воркеры-скоринг вызывают `scripts/music/critic/judge.py` с ключом из секретов и бюджетом на прогон; ответ кешируется по sha256 записи и кладётся рядом с записью.

### 2.6 Инварианты сета — числами, а не ушами

Из §1.3 следуют детерминированные проверки по `Track`-модели и плану сета, которые ловят то, что судья нашёл и код подтвердил (§5 H1–H7): гард ролей в дропе, окно без темы на стыке (сегодня 32 доли по дизайну — решение §8 В5), конфликт тональностей на стыке (узкий случай авторских аккордов/нестандартных ладов), сплошные 16-е без пауз, маскировка слоёв по записи (а не по `amp`), сустейн не у пэда, и **долг ADR-0149 §3.12**: `Transition.filter_in` читается рендером (HPF входа B), дакинг баса/пэда под бочку есть у всех стилей, а не только у club/dnb. Проверки по модели считаются офлайн за миллисекунды (как `arranger_theory_audit.py`) и входят в CI как гард на сид-серии; проверки по записи — в приёмку на katana.

## 3. Детализация

### 3.1 Грамматика слотов (расширение `media_command_grammar`)

- Положительное выделение вместо вычитания стоп-слов (#3493): глагол заказа → `[название]` → `[композитор (род. падеж, алиасы реестра)]` → `на <инструмент>` → `в стиле|<стиль>` → `сет|сэт|диджей` → `на тему <тема>`.
- Слово инструмента опознаётся по `INSTRUMENTS` до поиска названия: «сыграй Баха на балалайке» → `work=Bach (кандидаты), instrument=balalaika, mode=piece` — в `search.find` слово инструмента **не попадает**, промаха «слово вне поиска» нет.
- Опечатки STT/клавиатуры: «сфграй», «свграй», «Токкато», «кселофон», «трамбон» — нормализация по расстоянию ≤ 1 к словарю глаголов/инструментов/алиасов (словарь закрытый, регекс не растёт — мораторий #3132 соблюдён, это таблица).
- Полное совпадение `melody_hit` больше не требует, чтобы **все** слова были словами архива: слова, занятые слотами, исключаются.

### 3.2 Кандидаты произведения

`works.py` (ADR-0155): `WorkRef.candidates(composer, title_words)` → список `(work_id, sources: scores[], rtttl[], title, composer_match: exact|alias|none, title_match: exact|partial|none, last_played_at, fit_cached)`. Совпадение — по токенам названия и полю `composer`; подстрока внутри слова не считается («Bach» ≠ «Mundian To Bach Ke», «минор» ≠ «Minority»). Поле `composer` получает первого потребителя (`FIELD_CONSUMERS`, `works.py:50–53`).

### 3.3 `Chooser` и признаки

Детерминированный провайдер: `score = 3·title_match + 2·composer_match + 1·fit − 2·recent(≤3 последних) + 0.5·rating`; при разрыве между первым и вторым ≥ 1.0 модель не вызывается вовсе (экономия и предсказуемость). Модельные провайдеры — только когда разрыв меньше («неоднозначно») и только в shadow-режиме до прохождения §4. Дедлайн на выбор — 500 мс внутри бюджета быстрого старта 2.5 с (#3491); истёк → детерминированный ответ.

|---|---|---|---|

### 3.5 Стык дек и дыры (уточнение ADR-0149 §4.5 / ADR-0147)

Что есть сегодня (код): блэнд 8 тактов, своп kick/bass на 4-м такте, LPF-свип хвоста A, дуга `trim`; тональности соседей — по квинтам; хвост A и начало B — без лида по таблицам форм; `filter_in` не читается; дакинг только club/dnb; гарда ролей нет.

Правила, проверяемые по модели (цифры — предложения, §8 В5):
- **окно без темы на стыке** (сегодня 32 доли: `outro`+`outro_tail` A и `intro`+`intro_low` B без лида) — либо оставить как дизайн, либо лид B входит в `intro_low` (≤ 16 долей без темы), либо лид A держится до `outro_tail`; решает Шифу на слух;
- в блэнде рендер читает `Transition.filter_in`: HPF входа B открывается за 4 такта (как обещано в ADR-0149 §3.12), бас/пэд A дакаются под бочку B после свопа;
- тональность B относительно A — круг квинт сохраняется; дополнительно проверка H3 на авторские хроматические аккорды в первых 8 тактах B и на хуки не в major/minor;
- в секциях `drop*` хотя бы один из {kick, snare, bass} звучит в каждом такте — рантайм-гард в `model.py`, а не только таблицы форм; брейк вне `break*` ≤ 8 долей;
- роль с `sus` дольше 2 тактов — только `pad` (`held`/педаль); у лида/клавиш — `HOLD_LAST_BEATS`;
- дакинг (`duck_roles`) есть у всех стилей, где есть бочка, — значения в `STYLES`, по умолчанию как у club;
- маскировка слоёв проверяется **по записи** (доли полос слоя относительно соседей, NRT на katana), а не по `amp`.

### 3.6 Пайплайн критика (`scripts/music/critic/`)

`bundle.py` (переезд `_method/build_critic_bundle.py` и `render_track_code.py` из артефактов в репо), `judge.py` (провайдер по env: первым — **Qwen3.8 Omni Max**, тот же судья, что дал бандл 08.10, API обещал товарищ Шифу; вторым — Gemini 2.5 Pro/Flash через Files API, по исследованию; схема ответа фиксирована, промпт — тот же, что в `<стиль>/<стиль>.md` бандла, плюс факты от кода), `verify.py` (сведение утверждений к проверкам §2.5; выход — таблица «подтверждено/опровергнуто/не проверяемо» + J-метрики), `report.md` рядом с записью. Воркер получает право вызывать `judge.py` в карточке явно; стоимость одного вызова ≈ $0.01 (3 мин, по чужим ценам) — лимит на прогон задаётся переменной.

## 4. Модель в выборе: Jev, LLM-enum, Laya — условия включения

Честная позиция по исследованию: музыкальных применений Jev с измеренным качеством нет (Jevthoven — символьная MIDI-студия без оценки); калибровка Jev на чужих данных противоречива; латентность p95 0.5–0.8 с по чужим замерам; Laya на Pi не мерена; у чат-LLM с enum больше музыкальных знаний, но нет вероятностей. Поэтому ADR **не выбирает провайдера**, а задаёт эксперимент, после которого выбор сделает товарищ Шифу:

1. **Размеченный набор** `src/rob_box_music/test/data/music_requests.yaml`: 20 фраз прогона 09.10 + 10 фраз приёмки S7 + фразы из закрытых issue (#3348, #3264, #3455, #3410, #3176) — для каждой ожидаемые `mode/work/instrument/style`; плюс 30 «композиторских» запросов с кандидатами и правильным ответом (разметка — Шифу, по одной строке на запрос).
2. **Офлайн-прогон** `scripts/research/jev_eval.py --provider {deterministic|llm_harness|jev|laya}` на этом наборе: точность, доля неоднозначных, p50/p95, цена.
3. **Shadow на роботе** неделю: `Chooser` исполняет детерминированный ответ, модельный пишет в лог; расхождения смотрит Шифу.
4. **Go** для провайдера: точность на «неоднозначном» подмножестве ≥ детерминированной + 10 п.п., ни одного выбора вне кандидатов, p95 ≤ 500 мс с робота, цена ≤ $1/день. Иначе остаётся детерминированный — и это нормальный исход.

Безопасность: как в спайке #3084 — hard-rules до модели, модель не расширяет кандидатов, circuit breaker, `stop`/`volume` модели не касаются.

**Решение товарища Шифу (09.10):** классификатор закрывается интерфейсом; за ним — либо Jev, либо обычная LLM со специфическим харнессом; ключ будет дан позже. До ключа `Chooser` работает на `deterministic`, а `llm_harness`/`jev` пишутся против фейкового провайдера (как `FakeDecisionProvider` в спайке) и включаются shadow-режимом, когда ключ появится.

## 8. Открытые вопросы для товарища Шифу

> **Ответы товарища Шифу 09.10:** «Классификатор надо закрыть интерфейсом, можно использовать Jev, а можно и обычный LLM просто со специфическим харнессом — ключ на него дам позже. Судьёй в этом прогоне был Qwen3.8 Omni Max, запросы отдавал вручную, в теории могу дать API к нему.» → В8 закрыт (интерфейс + провайдер по ключу), В7 сужен до бюджета и очерёдности (Qwen первым).

- **В1. Что считать «той самой» пьесой и порог годности.** «Сыграй Токкату» при 8 партитурах (лучшее совпадение с RTTTL-эталоном 0.73 при пороге 0.8) и 5 RTTTL-версиях: брать партитуру с лучшей годностью, или всегда RTTTL-эталон (узнаваемость выше), или чередовать по истории? Опустить порог до 0.7 для одиночной пьесы (в сете остаётся 0.8)? Предложение: партитура, если годность ≥ 0.7, иначе RTTTL того же произведения; чередование — только между разными произведениями.
- **В2. Инструмент без синта.** «На балалайке» при отсутствии балалайки: играть ближайшим и сказать об этом (предложение), или отказать, или спросить? И список инструментов первой очереди (§3.4) — дополнить/вычеркнуть.
- **В3. Лад темы.** Тема в своём ладу (keep) или в ладу стиля (minor для club/rave)? Это уже висит с ADR-0153 В4; здесь важно, что классификатор на это **не** ставится — нужна одна строка правила.
- **В4. Разметка набора §4.1** — 30 композиторских запросов с правильным ответом; без неё модельные провайдеры не получат оценки, и `Chooser` останется детерминированным (приемлемый исход).
- **В5. Окно без темы на стыке.** Сегодня по таблицам форм каждый стык — 8 тактов (32 доли) без лида: хвост A и начало B без темы, это дизайн, и критик услышал это во всех 10 стилях как «обрыв». Оставить (сет «дышит»), сократить до 4 тактов (лид B входит в `intro_low`), или держать лид A до `outro_tail`? Предложение: 4 такта. Остальные цифры §3.5 (HPF за 4 такта, дакинг как у club) — утвердить или дать свои.
- **В6. Фразировка**: доля пауз в лиде по стилям (предложение: club/rave ≥ 15 %, synthwave ≥ 20 %, jazz ≥ 30 %, chiptune ≥ 10 %) — или оставить на слух после PR-6.
- **В7. Судья**: первым — Qwen3.8 Omni Max по API от Шифу (тот же, что слушал бандл), Gemini — вторым для сверки; остаётся решить бюджет на прогон (предложение: ≤ $1/день) и куда класть ключ (secret store CI + env робота не нужен — судья работает офлайн на katana/рабочей станции).
- **В8. Провайдер классификатора** — закрыт 09.10: интерфейс, за ним Jev или LLM-харнес, ключ позже. Остаётся мелочь: Laya на katana — ставить ли контейнер для замера p95 (предложение: нет, пока не нужен офлайн-вариант).

## 9. Что не проверено

- Утверждения критика сверены с кодом воркером (§1.3), **кроме**: семантики `lpf=0` внутри самого Renardo (в репо только комментарии «фильтр снят» — подтвердить на роботе одной нотой с `lpf=0` и `lpf=20000`); реальной `harmony.progression` трека `set52930:01:A` (пэд C major «77 с» — по формам не следует, нужен `track_json` этого трека из `music_v2_tracks_dir`); происхождения «хэты выключены 64 доли» (в клубных формах хэты есть во всех секциях — вероятно, судья смотрел песенную форму `SONG_VERSES`); механизма сплошных 16-х у лида/арпа (видно по модели, генератор не разобран).
- Не проверено, что `pick_score` при `HookError` на всех 8 материалах тратит приемлемое время: в логе 09.10 отбор 8 партитур занял 334 мс в сете (`set32644`) и ≈ 0.66 с в `[classic]` (07:54:04.19 → 04.85) — в бюджет 2.5 с укладывается, но при 20+ кандидатах нужен замер.
- Не измерено: p95 `Chooser` на роботе; цена и латентность судьи; точность любого модельного провайдера на наших фразах; не прослушаны Шифу таймкоды критика.
- Не проверено, что `works.py` при 138 627 партитурах выдаёт кандидатов за ≤ 100 мс (ADR-0154 M7) при поиске по `composer` + токенам — замер в PR-3.
- Записи критика сделаны при посторонней речи и 30 late-бандлах; стык дек в чистом прогоне может звучать иначе — H2/H3 считаются по модели, а не по записи, поэтому на выводы §2.6 это не влияет.
