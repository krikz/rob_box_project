# ADR-0172: Студия сама обновляет свой код после мержа в develop

| Поле | Значение |
|---|---|
| Статус | Accepted (реализуется в #4703) |
| Дата | 2026-11-13 |
| Автор | Архитектор (сессия Hermes) |
| Отношения | Продолжает ADR-0171 (тема по интересности). Корневая причина #4703, найденная при разборе #4702 |

## Проблема

У контент-студии **два** разных источника материала, и они могут быть разной свежести:

| Что | Откуда берётся | Свежесть |
|---|---|---|
| факты и медиа | отдельный worktree `origin/develop` (`studio_develop.ensure_develop_worktree`) | обновляется сам в начале каждой сессии |
| **исполняемый код** | живой клон `/home/builder/hermes-share/rob_box_project` | **обновляется только вручную** |

Итог: студия читает свежие факты, но считает по старому коду. Расхождение невидимо —
ошибок нет, сервис активен, `studio-watch` в `active`. Просто логика старая.

Это не теория. 13.11 в 03:00 UTC сессия отработала кодом от 11.11, а merge #4701
(ежедневная подготовка материала) в `develop` был в 08:58 того же дня. Фикс был в
`develop`, но не в бою: 10, 11 и 12.11 сессии вышли с «молчу до окна в 48 ч», не
собрав ни одного факта. За неделю до Шифу дошёл один-единственный пост вместо трёх-четырёх.

### Почему автоматики нет вообще

Проверено вдоль и поперёк:

- в `~/.hermes/scripts/agent-flow-*.sh` (merge-gate, e2e-process) нет ни `git pull`,
  ни `git merge --ff-only`, ни `git update-ref` для живого клона студии;
- ни в кронах ни одного профиля (`agent-flow`, `devops`, `studio`, `architect`) нет задачи,
  которая это делает;
- `scripts/telegram/studio_session.sh` (ежедневная сессия) git-команд не содержит вовсе;
- в `docs/runbooks/channel-studio.md` описан только worktree `origin/develop` для
  **свежих материалов** — самого клона студии это не касается: шага «обновить клон» там нет;
- merge-gate работает с PR, а не с живыми клонами на хостах: он merges в `develop` и
  проверяет CI, но deploy-а на builder у него нет.

Итог: каждый merge в `develop` требовал ручного `git pull` + рестарта `studio-watch`.
13.11 это стоило одного неделевого провала.

## Решение

**Студия обновляет свой код сама, после мержа в `develop`.**

### 1. Скрипт синхронизации

Новый `scripts/telegram/studio_sync.sh` — единственное место, где живёт эта логика:

```
fetch origin develop → сравнить с HEAD → если отстал: fast-forward → перезапуск studio-watch
```

Ключевые свойства:

- **обновление одним шагом**: `git merge --ff-only origin/develop` — ровно то, что делает
  разработчик руками, но без интерактива;
- **без `git stash`**: `stash` прячет несохранённую работу и потом требует ручного
  `stash pop` — это ровно тот класс «решение есть, а код не доехал», который здесь и чинится;
- **без `reset --hard` поверх несохранённого**: если в клоне есть изменённые tracked-файлы,
  скрипт **не** трогает их и честно пишет в журнал, что не обновился и на сколько отстал.
  Чужую работу не затираем;
- **untracked-файлы студии не трогаются**: `docs/channel/queue/*.md` и
  `docs/channel/infographics/*.json` создаёт сама студия; fast-forward их не задевает,
  потому что в `develop` по этим путям файлов нет. Если вдруг появится конфликт
  (файл с тем же путём приехал в `develop`) — скрипт останавливается и пишет причину,
  а не удаляет чужое;
- **перезапуск `studio-watch` после обновления**: сервис загружает модули Python один
  раз на старте, поэтому без рестарта он продолжает работать на старом коде. Рестарт
  делается **только если код реально изменился** — иначе длиннополлер студии рвётся
  каждые несколько минут без причины;
- **честный журнал**: в журнал пишется, какой коммит запущен и на сколько клон отставал
  от `origin/develop` — до и после. Если обновиться не вышло — пишется причина.

### 2. Когда запускается

**Не кроном.** Крон в профиле студии — это `hermes --profile studio cron`, и он живёт
в другом профиле: синхронизация клона — операция самого хоста, а не студийного профиля.

**Systemd-таймером на хосте студии** — рядом с `studio-watch`, который уже живёт как
user-юнит (`~/.config/systemd/user/`). Юниты и таймер ставятся тем же
`studio_install.sh`, который уже ставит `studio-watch`, — из репозитория, с подстановкой
корня клона. Файл юнита — `docker/studio/studio-sync.service` + `.timer`, рядом с
существующим `docker/studio/studio-watch.service`.

Таймер срабатывает **раз в 5 минут**. Пять минут — компромисс: реже — фикс из `develop`
не доедет до боя до вечера (прошлая неделя — 48 часов молчания); чаще — сеть и git
дёргаются без нужды. Синхронизация идёт по сети в любом случае, но при отсутствии
изменений это один `git fetch` раз в пять минут.

Почему не «по событию мержа» (webhook в GitHub → хост): это требует входящего вебхука
на хост, секрета и публичного адреса — три новых сущности вместо одного таймера. Таймер
проще, не требует сети «входящей» и не ломается, когда GitHub недоступен.

### 3. Что не делаем

- **Не обновляем клон в начале сессии** (`studio_session.sh` перед сбором фактов).
  Сессия и так работает по расписанию, а синхронизация отдельным таймером уже приводит
  клон в актуальное состояние за 5 минут. Ещё одна точка обновления — ещё одно место,
  где можно забыть перезапустить сервис.
- **Не заводим обновление на merge-gate.** Merge-gate работает с PR и CI, у него нет
  доступа к живому клону студии и нет обязанности обслуживать хосты.
- **Не ставим `git pull` в cron профиля студии.** Профиль студии — это Telegram-бот,
  а не деплой бота.

## Что проверяем

### На живом хосте

1. Клон отстаёт от `origin/develop` → после запуска скрипта `git rev-parse HEAD` совпадает
   с `origin/develop`, в журнале — «было отставал на N, стало 0».
2. `studio-watch` после обновления — `active`, в журнале — новый `MainPID`.
3. В клоне изменён tracked-файл → скрипт **не** обновляет клон, не затирает файл,
   пишет в журнал причину и ненулевой код возврата.
4. Untracked-файлы студии (`docs/channel/queue/900-post.md`,
   `docs/channel/infographics/loc-drift.json`) после синхронизации на месте.
5. Клон актуален → скрипт ничего не делает, `studio-watch` **не** перезапускается.

### Автоматически (юнит-тесты)

- `tests/unit/scripts/test_telegram_studio_sync.py`: синхронизация в отдельном временном
  клоне — fast-forward срабатывает, изменённый tracked-файл не затирается, untracked
  переживает обновление, повторный запуск на актуальном клоне — no-op без рестарта сервиса.

## Последствия

- **Плюс:** фикс из `develop` доезжает до боевой студии сам, за 5 минут. Класс отказов
  «всё смержено, в бою старое» закрыт.
- **Плюс:** журнал отвечает на вопрос «какой коммит сейчас работает» прямо, без
  догадок по `reflog`.
- **Минус:** таймер тянет сеть каждые 5 минут (`git fetch`). Это дешёвый запрос к
  GitHub, но он не нулевой.
- **Минус:** на merge в `develop` придётся перезапускать `studio-watch` — до 5 минут
  «окна», когда клон новый, а процесс старый. Незаметно: кнопки Шифу в это окно
  обрабатываются старым кодом, но следующий тик уже новый.
- **Ограничение:** таймер ставится на хост **вручную** (`studio_install.sh`). Новый хост
  со студией требует прогона установки — как и сейчас с `studio-watch`.
