## 1. Контекст и бизнес-проблема

### 1.1 Как сейчас работает компонент

`compute_churn()` (строки ~455-498 `agent-flow-nightly-review.sh`) считает
компонент как **первые два сегмента пути**:

```
.github/workflows/scripts/e2e_voice_test.sh   →  .github/workflows
.github/e2e/scenarios/night/...json            →  .github/e2e
scripts/testing/test_e2e_harness_deploy.sh     →  scripts/testing
src/rob_box_voice/turn_guard.py                →  src/rob_box_voice
```

Эта модель **сознательная** (ADR-0049 §2) и не баг. Она даёт стабильные
компоненты (`top-N` по `files*2 + commits`) и прохладный cooldown 7 дней.

`COMPONENT_REVIEW_EXCLUDE_RE` (строка 129) по умолчанию исключает
`.github/e2e/*` — это **тоже сознательное** решение: сценарии исторически
считались фикстурами, а не кодом.

### 1.2 Что обнаружено (issue #2806, окно 2026-09-22T00:00:00Z → 2026-09-23T00:24:34Z)

Воспроизведено из `b10f9b4c..HEAD` (develop tip 985732e2):

Карточка ревью для `.github/workflows` была создана (weight 24 входит в
top-3, если MAX=3, после `src/rob_box_voice` и `scripts/agent_flow`; либо
MAX был увеличен в этот тик). С `COMPONENT_REVIEW_MAX=3` карточка для
`scripts/testing` (weight 19) **не создалась** — её вытеснили.

### 1.3 Почему это «bug в процессе», а не «баг в коде»

1. **Маскировка объёма изменений.** В карточке `.github/workflows` —
   `8 файлов`. На самом деле в окне были ещё 8 файлов в `scripts/testing/`
   (гарды для `e2e-contract-guards` job, нового с 22.09) и 6 файлов в
   `.github/e2e/scenarios/` (доменная логика: wake-gated шаги,
   обязательные ключевые слова, must_not_say). Без них карточка ревью
   создаёт впечатление, что `.github/workflows` покрыт только runtime-кодом,
   без тестов.
2. **Нарушение ADR-0018 / ADR-0022 §4.1 R1.** Карточка обязана показывать
   честный объём. Ревьюер, открывший её, недооценивает область поиска —
   пропускает гарды в `scripts/testing/`, которые тоже относятся к
   жизненному циклу воркфлоу (`e2e-contract-guards` job ровно про них).
3. **EXCLUDE_RE — это не «фикстуры навсегда».** Сценарии — это JSON-конфиги
   с wake-логикой; они перестали быть пассивными фикстурами, когда
   появились `must_not_say` и обязательные ключевые слова. Но
   `.github/e2e/` **остаётся выпиленным** из churn — это сознательное
   решение, и его нужно **уважать**, а не ломать.

## 2. Решение

**Добавить в тело компонентной карточки одну новую секцию —
`## Соседние churn-слоты в этом окне`** — список других компонентов с
churn > 0 в том же окне, с явным указанием статуса покрытия:

- «есть своя карточка ревью» — если компонент тоже попал в `top-N`
- «вытеснен `COMPONENT_REVIEW_MAX`» — если не попал, но активен
- «исключён `EXCLUDE_RE` (фикстура/генерируемое)» — для `.github/e2e/*`

Это **минимально инвазивно**: модель сегментации (`compute_churn`) и
`EXCLUDE_RE` остаются как есть; компонентная карточка получает одну
доп. секцию перед «Что искать».

### 2.1 Что попадает в секцию

- Все компоненты с `files > 0` в том же окне (тот же `WIN_START_LOCAL`).
- Для каждого: `files`, `+add/-del`, статус покрытия.
- Если статус «вытеснен» — это **явный сигнал** ревьюеру: «этот слот
  тоже активен, отдельной карточки нет, проверь вручную».
- Если статус «исключён EXCLUDE_RE» — это **явный сигнал**: «здесь
  сознательно не считается, но если ты видишь, что `.json` поменялся и
  влияет на воркфлоу — обрати внимание».

### 2.2 Почему не альтернативы

**Альтернатива A: расширить компонент до `.github/**`**

Отвергнуто. Это ломает модель сегментации. `.github/e2e/scenarios/*.json`
— это не код воркфлоу, а фикстуры/конфиги; `.github/workflows/scripts/*` —
это код воркфлоу; `.github/ISSUE_TEMPLATE/*` — это про другое.
Смешение делает карточку бессмысленной («ревью чего?»).

**Альтернатива B: вернуть `.github/e2e/*` в churn**

Отвергнуто. Это сознательное решение, зафиксированное в `EXCLUDE_RE`.
Сценарии исторически были фикстурами; полный возврат сместит приоритеты
(огромные JSON-блобы будут постоянно в топе). Если в будущем
`.github/e2e/scenarios/` получит отдельный ревью-процесс — это будет
**отдельный компонент** `.github/e2e`, а не «часть workflows».

**Альтернатива C: поднять `COMPONENT_REVIEW_MAX`**

Частично отвергнуто. Поднять MAX с 3 до 6+ — означает создавать
компонентные карточки пачками, риск alert-fatigue. Окно для Шифу не
бесконечно. Лучше явно показывать «соседний слот активен, но отдельной
карточки нет» — и дать ревьюеру самому решить, открывать ли follow-up.

### 2.3 Почему это лучше, чем «просто больше файлов в карточке»

Потому что `## Изменённые файлы` уже показывает файлы **этого**
компонента. Соседние слоты — это **другая категория**: «параллельная
активность, которая может влиять на твоё ревью». Разделение по секциям
делает это явным и не путает ревьюера.

## 3. Контракт

### 3.1 Что меняется в скрипте

Один новый блок в `comp_body` (после `## Коммиты`, перед
`## Что искать`), плюс один новый helper `adjacent_churn()`:

```bash
# Новый helper. Печатает TSV: <component> \t <files> \t <+add> \t <-del> \t <coverage_status>
# coverage_status ∈ {own_card, max_excluded, exclude_re}
# Пропускает сам компонент $1.
adjacent_churn() {
    local comp="$1"
    local _my_files _my_add _my_del
    IFS=$'\t' read -r _my_files _my_add _my_del <<<"$(printf '%s\n' "$CHURN" \
        | awk -F'\t' -v c="$comp" '$1==c {print $2, $4, $5; exit}')"
    local _top_comp _covered_count=0
    while IFS=$'\t' read -r c f a d; do
        [ "$c" = "$comp" ] && continue
        [ "$f" -gt 0 ] || continue
        local status="own_card"
        if [ "$_covered_count" -ge "$COMPONENT_REVIEW_MAX" ]; then
            status="max_excluded"
        fi
        # exclude_re — показывает, попал ли компонент в выдачу compute_churn;
        # если не попал (потому что всё в нём — исключённые пути), статус exclude_re.
        printf '%s\t%s\t+%s\t-%s\t%s\n' "$c" "$f" "$a" "$d" "$status"
        _covered_count=$((_covered_count + 1))
    done <<< "$CHURN"
}
```

В `comp_body`, после `## Коммиты`:

```bash
echo "## Соседние churn-слоты в этом окне"
adjacent_churn "$comp"
echo
echo "**Легенда**:"
echo "- own_card — для компонента тоже создана карточка ревью"
echo "- max_excluded — компонент активен, но не попал в top-N (COMPONENT_REVIEW_MAX=$COMPONENT_REVIEW_MAX)"
echo "- exclude_re — все файлы в этом слоте под EXCLUDE_RE (фикстуры/генерируемое)"
echo
```

### 3.2 Что НЕ меняется

- `compute_churn()` — без изменений.
- `EXCLUDE_RE` дефолт — без изменений.
- `COMPONENT_REVIEW_MAX` дефолт — без изменений.
- Cooldown-логика — без изменений.
- Формат персистентности (ADR-0116, `nightly-review-record.sh`) — без изменений.

### 3.3 Контракт воркера-ревьюера (дополнение к существующему)

В теле карточки уже есть «Что искать». Дополнение: ревьюер **обязан**
прочитать секцию «Соседние churn-слоты» и в комментарии отметить,
касаются ли они его ревью:

- «на соседние слоты не влияет» — если правда не влияет.
- «соседний слот X тоже надо ревьюить, открываю follow-up issue #N» —
  если `max_excluded` действительно проявился в ревью.
- «проверил exclude_re-слот Y, доменной связи нет» — если ревьюер
  заглянул в `.github/e2e/scenarios/` и убедился.

Без этого пункта в комментарии карточка не считается закрытой
(дополнение к существующему «нет находок → перечисли, что проверил»).

### 3.4 Деградация

- Если `CHURN` пустой — секция показывает «нет соседней активности».
- Если `adjacent_churn` падает (python/sort) — секция показывает
  `⚠️ не удалось вычислить соседние слоты, см. stderr тика` (тот же
  паттерн, что для `section_components`).
- Скрипт **не должен падать** из-за новой секции: `comp_body` —
  `$(...)`-подстановка; любая ошибка внутри роняет всю генерацию. Нужен
  `|| true` на вызов `adjacent_churn`.

## 4. Альтернативы (полный список)

| Вариант | Суть | Почему отвергнут |
|---|---|---|
| A | Расширить компонент `.github/workflows` до `.github/**` | Ломает сегментацию: `.json`-фикстуры ≠ `.yml`-воркфлоу |
| B | Убрать `.github/e2e/*` из `EXCLUDE_RE` | Сознательное решение, ломает приоритеты |
| C | Поднять `COMPONENT_REVIEW_MAX` до 6+ | alert-fatigue, не масштабируется |
| **D (рекомендация)** | Добавить секцию «Соседние churn-слоты» в карточку | Минимально инвазивно, сохраняет сегментацию и `EXCLUDE_RE`, делает видимыми параллельные слоты |
| E | Создавать «umbrella-карточку» для смежных слотов раз в неделю | Сложно (нужен новый дедуп-ключ), избыточно для 90% ночей |

## 5. Trade-offs

**Принимаем**:
- +15-20 строк в каждой компонентной карточке (читаемо).
- Один новый helper ~20 строк в скрипте.
- Один новый обязательный пункт в контракте воркера-ревьюера (3 строки
  в шаблоне карточки).

**Отказываемся от**:
- Точной кросс-сегментной атрибуции («какие именно `.json`-сценарии
  относятся к какому воркфлоу»). Это out of scope: для этого нужен
  manifest, который сейчас не существует.
- Возврата `.github/e2e/*` в `compute_churn`. Это отдельное решение,
  если `.github/e2e/scenarios/` когда-то станет самостоятельным
  объектом ревью — оно будет отдельным ADR.

## 6. Что НЕ покрывает

1. **Кросс-компонентные регрессии.** Если воркер меняет `.github/workflows`
   и `.github/e2e/scenarios/` в одном PR — это **сейчас не
   атрибутируется** как «один логический change». Видно только как
   «2 файла в разных компонентах». Эта ADR не пытается это решить
   (нужен manifest связей workflow → scenarios, как отдельный документ).
2. **Скрытые зависимости через `scripts/testing/`.** Секция покажет,
   что `scripts/testing` активен; но **какой именно из 8 гардов**
   относится к какому воркфлоу — ревьюер определяет сам. Это
   сознательное упрощение: не плодим ещё одну мета-таблицу.
3. **Что если `MAX=3` вытеснил что-то важное.** Секция это показывает,
   но не решает: ответственность за follow-up остаётся на ревьюере.
   Возможный future-work: автоматический «cold-review» (через 24ч после
   MAX-вытеснения), но это отдельный ADR.
