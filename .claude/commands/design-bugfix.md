# Design Bug Fix

Ты — Senior Engineer для проекта **Rob Box** (автономный ровер, ROS 2 Humble + Zenoh).

## Твоя роль
Создать детальный дизайн исправления бага на основе research документа.

## Аргументы
Формат: `<bug-id-или-название> <путь-к-research-файлу>`

$ARGUMENTS

## Перед началом работы: прочитай обязательно
1. Указанный research файл (ПОЛНОСТЬЮ)
2. `docs/development/PYTHON_STYLE_GUIDE.md`
3. Если баг в voice/LLM: `docs/VOICE_AGENT_BEST_PRACTICES.md`
4. Если баг в Docker: `docs/development/DOCKER_STANDARDS.md`

## Стек и ограничения
- Python / ROS 2 Humble / Docker Compose / Zenoh DDS
- Принцип минимального исправления: меняем только то, что сломано
- Не рефакторить ничего "заодно"
- Сохранять обратную совместимость топиков/сервисов/API

## Процесс анализа бага

### Шаг 1: Root Cause Analysis (сам, не субагент)
Детально изучи файлы из research документа.
Найди ТОЧНУЮ root cause — не симптом, а причину.

### Шаг 2: Запусти субагентов

**Субагент 1: Impact Analyzer**
Определяет:
- Какой код затронет исправление (список файлов и строк)
- Есть ли риск регрессий (что ещё может сломаться)
- Зависимые компоненты (ноды, топики, конфиги)

**Субагент 2: Fix Strategist**
Предлагает:
- Минимальное исправление (Minimal Viable Fix)
- Альтернативные подходы (если есть)
- Риски каждого подхода

**Субагент 3: Test Designer**
Разрабатывает:
- Тест для воспроизведения бага (regression test)
- Тест-кейсы для верификации исправления
- Smoke тест если нужен

## Выходные документы

Создай директорию `docs/design/bugfix-<bug-id>/` и в ней:

### `root-cause.md`
```markdown
# Bug: <название>

## Симптомы
(что происходит с точки зрения пользователя)

## Root Cause
(точная причина: файл, строка, объяснение)

```python
# Проблемный код (файл:строка):
...
```

## Воспроизведение
(минимальные шаги для воспроизведения)

## Затронутые компоненты
| Компонент | Файл | Строки | Как затронут |
|-----------|------|--------|-------------|
```

### `fix-design.md`
```markdown
# Fix Design: <название>

## Выбранный подход
(почему именно этот)

## Изменения
| Файл | Строки | Что меняем | До | После |
|------|--------|-----------|-----|-------|

## Псевдокод / diff концепция
```python
# БЫЛО:
...
# СТАЛО:
...
```

## Риски исправления
(что может сломаться, как проверим)

## Альтернативные подходы
(почему отклонили)
```

### `test-plan.md`
```markdown
# Test Plan: <bug-id>

## Regression Test
(тест который воспроизводит баг ДО исправления)

## Verification Tests
| ID | Описание | Ожидаемый результат |
|----|----------|-------------------|

## Smoke Tests
(если нужны)
```

## Sequence диаграмма (если баг в взаимодействии компонентов)
Если баг связан с взаимодействием нескольких компонентов, добавь в `root-cause.md` sequence диаграмму в Mermaid:
- Как это СЕЙЧАС работает (с багом)
- Как должно работать ПОСЛЕ исправления

**ВАЖНО:** Не меняй код. Только создай документы дизайна.
После создания сообщи: root cause в одном предложении + список файлов для изменения.
