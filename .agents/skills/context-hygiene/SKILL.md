# Context Hygiene — Rob Box

Правила, которые экономят контекст и не дают ему «отравиться». Действуют в каждой сессии,
независимо от того, идёт ли работа по методологии context-engineering или это простой вопрос.

---

## 1. Контекст — рабочий стол, а не архив

Модель не помнит ничего между запросами. На каждый ход агента ей отправляется **вся история
сессии целиком**: системный промпт, AGENTS.md, описания инструментов, все сообщения, все
прочитанные файлы, весь вывод команд.

Следствия:

- Всё, что лежит в контексте, модель видит **одновременно** и пытается учесть.
- Каждый прочитанный файл и каждый вывод команды — это плата на **каждом** следующем ходу.

**Правило:** читай только то, что нужно текущему шагу. Артефакт фазы (research/design/plan)
существует, чтобы следующая фаза читала его, а исходники и большие документы открывала точечно.

---

## 2. Контекст жрут не сообщения, а выводы инструментов

Распределение типичной сессии: чтение файлов целиком и поиск по репозиторию — много; вывод
тестов/сборок/логов — много; диффы — заметно; сообщения пользователя — единицы процентов.

| Что делать | Как |
|-----------|-----|
| Не давать агенту бродить по проекту | Указывай файлы через `@`, а не «поищи сам» |
| Разведку отдавать сабагенту | «Найди, где обрабатывается X» → сабагент, в основную сессию только вывод «вот здесь, файл:строка» |
| Не вываливать весь лог | Давай релевантный кусок (последние 30–50 строк, конкретный FAILED-блок) |
| Стек/конвенции/команды/запреты | В `AGENTS.md` / `copilot-instructions.md` — грузится один раз и живёт в кэше, а не в переписке |

**Совместимость с культурой честности (`AGENTS.md`):** raw-вывод обязателен, но прикладывай его
**релевантными кусками**, а не целиком. «Тесты прошли» → `pytest -v` по затронутым тестам, не весь
дамп на 2000 строк. Честность ≠ вываливание всего в контекст.

---

## 3. Качество падает раньше, чем кончается окно (отравление контекста)

Даже при заполнении окна на 40%, но с тремя неудачными попытками внутри, модель начинает ходить
по кругу.

**Симптомы отравления:**

- второй раз ломает то, что сама только что починила;
- предлагает решение, которое уже отвергнуто;
- начинает «чинить» файлы, которых задача не касается;
- ответы становятся общими и осторожными.

**Лечение — только новая сессия.** Сжатие не помогает (см. п. 5). При появлении двух и более
симптомов: зафиксируй состояние в handoff-файле и начни новую сессию с него.

---

## 4. Сессия = единица работы

**Одна сессия — один осмысленный кусок работы, размером примерно с коммит или небольшой PR.**

Новая сессия обязательна, когда:

- **сменился слой** — дописали бэкенд, переходите к фронтенду (фронтенду нужен контракт API, а не реализация БД);
- **сменился тип задачи** — писали фичу, попутно нашли баг в другом модуле;
- **контекст отравлен** (п. 3).

Не дробите сессии ради дробления: пять коротких сессий, в каждой из которых агент заново читает
одни и те же пять файлов, дороже и хуже одной нормальной.

---

## 5. Сжатие контекста: чего от него ждать

- **Не экономит токены** — тратит их на отдельный вызов, который читает всё окно.
- **С потерями и неуправляемо** — что выбросить решает модель, может выкинуть архитектурное решение и оставить тупик.
- **Не стирает неудачные ветки** — summary честно запишет «пробовали X, не сработало», и это продолжит травить контекст.

**Правила:**
- Ручное сжатие оправдано **только на чистой границе**: тесты зелёные, изменения закоммичены, нужно продолжить именно эту цепочку рассуждений.
- Не жми контекст «для профилактики».
- Неудачная итерация → `/undo` и переформулировка задачи, а не наслаивание новых попыток поверх.

---

## 6. Handoff-файл — лучше сжатия

Перед закрытием сессии допиши в файл (например `docs/handoff/YYYY-MM-DD-<задача>.md` или
`docs/plan/<имя>/HANDOFF.md`):

```
# Handoff: <задача>

## Сделано
<что готово, с commit-ами и файл:строками>

## Осталось
<что не доделано и почему>

## Решения
<что решили и почему>

## Отвергнуто
<какие подходы пробовали и почему отвергли>

## Как проверить
<команды и ожидаемый вывод>
```

Дальше — новая сессия, и этот файл на вход. Это ручная компакция, но качественная: она видна,
её можно поправить, она переживает перезапуск терминала и не тянет мусорный хвост.

В методологии context-engineering handoff-файл пишется **в конце каждой фазы** (Research → Design
→ Plan → каждая фаза Implement) — см. `context-engineering/SKILL.md`.

## 7. Экономика: подписка vs токены

**Подписка (Copilot, Claude Max):** токены не тарифицируются поштучно, есть лимиты по запросам.
Оптимизируй под качество и число ходов: сессии короче, границы чётче, сжимать можно смелее.
Одна лишняя итерация из-за размытого промпта дороже лишней сессии.

**Оплата по токенам (API-ключ, DeepSeek):** главный герой — кэш промпта. Пока начало сессии
не меняется, повторная отправка тех же токенов ≈ 1/10 цены. Кэш обнуляют: новая сессия, сжатие,
смена модели, правка `AGENTS.md`.

- не дроби работу на микросессии без нужды;
- не жми контекст «для профилактики» — платишь дважды;
- дешёвая модель на разведку/планирование, дорогая — на сложную правку;
- следи за тем, **сколько файлов читается**, а не сколько сообщений написано.

Подробно про кэш DeepSeek: `docs/guides/DEEPSEEK_CONTEXT_CACHING.md`.

## Применение в Hermes ADD-процессе (agent-flow)

Живой процесс Rob Box: issue → `agent-flow-triage` → kanban-карточка `t_xxx` → worker
(sub-agent) → PR → `merge-gate` → `e2e-process` → `L-E2E Voice Test` → ручной merge → close.

| Правило | Как выглядит в agent-flow |
|---|---|
| Сессия = единица работы | **1 kanban-карточка = 1 воркер-сессия.** Новая итерация той же карточки — новая сессия с handoff-комментом в issue, не «отравленная» старая. |
| Не бродить по проекту | Карточка несёт блок `Context` (`sources_of_truth`, `local_clone`, `base_branch`) — начинай с этих файлов, остальное открывай точечно. |
| Разведка — сабагентом | «Где обрабатывается X» → sub-agent, в сессию воркера только вывод «файл:строка». |
| Handoff = комменты в issue + карточка | Воркер комментит содержательно (Q23): причина / решение / препятствие. Карточка + issue-комменты = handoff между итерациями и к Шифу. |
| Не вываливать логи | e2e-доклад в issue — релевантные куски (verdict, run, RMS, ASR, diff summary), не полный дамп docker logs. Raw обязателен (ADR-0018), но точечно. |
| Отравление контекста | 2+ FAIL-итераций по одной карточке → новая сессия с handoff-комментом, не та же сессия. |

Воркер-контракт уже несёт эти правила:
`scripts/agent_flow/agent-flow-triage.sh::worker_contract_block()`.

## Чеклист перед стартом сессии

- [ ] Знаю, что это за единица работы (один коммит/PR, один слой, один тип задачи).
- [ ] Файлы, которые буду менять, известны точечно (через `@` или вывод сабагента), а не «поищу по проекту».
- [ ] Разведку «где это обрабатывается» отдал сабагенту.
- [ ] Логи/вывод тестов буду давать релевантными кусками.
- [ ] Знаю, куда запишу handoff-файл в конце.
